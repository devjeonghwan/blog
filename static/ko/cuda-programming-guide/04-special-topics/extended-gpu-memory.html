4.17. 확장 GPU 메모리

고대역폭 NVLink-C2C를 활용하는 확장 GPU 메모리(EGM) 기능은 단일 노드 및 다중 노드 시스템 모두에서 GPU가 모든 시스템 메모리에 효율적으로 접근할 수 있도록 합니다. EGM은 설정 내 어느 GPU 스레드에서나 접근할 수 있는 물리 메모리 할당을 가능하게 함으로써 통합 CPU-GPU NVIDIA 시스템에 적용됩니다. EGM은 모든 GPU가 GPU-GPU NVLink 또는 NVLink-C2C의 속도로 해당 리소스에 접근할 수 있도록 보장합니다.

이 설정에서는 로컬 고대역폭 NVLink-C2C를 통해 메모리 접근이 이루어집니다. 원격 메모리 접근에는 GPU NVLink가 사용되며, 일부 경우에는 NVLink-C2C도 사용됩니다. EGM을 사용하면 GPU 스레드는 NVSwitch 패브릭을 통해 CPU 연결 메모리와 HBM3를 포함한 사용 가능한 모든 메모리 리소스에 접근할 수 있는 기능을 갖게 됩니다.

4.17.1. 사전 준비#

EGM 기능을 위한 API 변경 사항을 살펴보기 전에, 현재 지원되는 토폴로지, 식별자 할당, 가상 메모리 관리의 전제 조건, 그리고 EGM을 위한 CUDA 타입을 다룹니다.

4.17.1.1. EGM 플랫폼: 시스템 토폴로지#

현재 EGM은 여러 플랫폼에서 활성화할 수 있습니다: (1) 단일 노드, 단일 GPU: Arm 기반 CPU, CPU에 연결된 메모리, 그리고 GPU로 구성됩니다. CPU와 GPU 사이에는 고대역폭 C2C(Chip-to-Chip) 인터커넥트가 있습니다. (2) 단일 노드, 다중 GPU: 각각 연결된 메모리를 가진 ARM 기반 CPU들과, NVLink 기반 네트워크를 통해 연결된 여러 GPU로 구성됩니다. (3) 다중 노드, 다중 GPU: 위 (1) 또는 (2)와 같은 단일 노드 시스템이 둘 이상이며, NVLink 기반 네트워크를 통해 연결됩니다.

참고

사용 가능한 디바이스를 제한하기 위해 cgroups를 사용하면 EGM을 통한 라우팅이 차단되고 성능 문제가 발생합니다. 대신 CUDA_VISIBLE_DEVICES를 사용하세요.

4.17.1.2. 소켓 식별자: 무엇인가요? 어떻게 접근하나요?#

NUMA(Non-Uniform Memory Access)는 멀티프로세서 컴퓨터 시스템에서 사용되는 메모리 아키텍처로, 메모리가 여러 노드로 나뉩니다. 각 노드는 자체 프로세서와 메모리를 가집니다. 이러한 시스템에서 NUMA는 시스템을 노드로 분할하고 고유한 식별자( 를 할당합니다.numaID)를 모든 노드에 할당합니다.

EGM은 운영 체제가 할당하는 NUMA 노드 식별자를 사용합니다. 이 식별자는 디바이스의 순서 번호(ordinal)와는 다르며, 가장 가까운 호스트 노드와 연관되어 있습니다. 또한 기존 방법에 더해, 사용자는 호스트 노드의 식별자를 얻을 수 있습니다 (numaID)를 호출하여 cuDeviceGetAttribute 와 함께 CU_DEVICE_ATTRIBUTE_HOST_NUMA_ID 다음과 같이 속성 유형을 사용합니다:

int numaId;
cuDeviceGetAttribute(&numaId, CU_DEVICE_ATTRIBUTE_HOST_NUMA_ID, deviceOrdinal);

4.17.1.3. 할당자 및 EGM 지원#

시스템 메모리를 EGM으로 매핑하는 것은 어떤 성능 문제도 일으키지 않습니다. 사실, EGM으로 매핑된 원격 소켓의 시스템 메모리에 접근하는 것은 더 빠를 것입니다. 이는 EGM 트래픽이 NVLinks를 통해 라우팅되도록 보장되기 때문입니다. 현재, cuMemCreate 및 cudaMemPoolCreate 할당자는 적절한 위치 유형과 NUMA 식별자와 함께 지원됩니다.

4.17.1.4. 현재 API에 대한 메모리 관리 확장#

현재 EGM 메모리는 Virtual Memory (cuMemCreate) 또는 Stream Ordered Memory (cudaMemPoolCreate) 할당자를 통해 매핑할 수 있습니다. 사용자는 물리 메모리를 할당하고 모든 소켓에서 이를 가상 메모리 주소 공간에 매핑할 책임이 있습니다.

참고

멀티 노드, 멀티 GPU 플랫폼에는 프로세스 간 통신이 필요합니다. 따라서 독자께서는 Chapter 4.15를 참고하시기를 권장합니다.

참고

더 잘 이해하기 위해 CUDA Programming Guide의 Chapter 4.16 및 Chapter 4.3을 읽어보시기를 권장합니다.

NUMA와 유사한 노드 식별자를 사용하여 이러한 접근 방식이 할당 위치를 이해할 수 있도록, 새로운 CUDA 속성 유형이 API에 추가되었습니다:

CUDA 유형

사용 대상

CU_MEM_LOCATION_TYPE_HOST_NUMA

CUmemAllocationProp for cuMemCreate

cudaMemLocationTypeHostNuma

cudaMemPoolProps for cudaMemPoolCreate

참고

NUMA 전용 CUDA 타입에 대해 더 알아보려면 CUDA Driver API 및 CUDA Runtime Data Types를 참조하십시오.

4.17.2. EGM 인터페이스 사용#

4.17.2.1. 단일 노드, 단일 GPU#

기존 CUDA 호스트 할당자 중 어느 것이든, 그리고 시스템에서 할당된 메모리 또한 고대역폭 C2C의 이점을 얻는 데 사용할 수 있습니다. 사용자에게는 로컬 액세스가 오늘날의 호스트 할당이 의미하는 바입니다.

참고

메모리 할당자와 페이지 크기에 대한 자세한 내용은 튜닝 가이드를 참조하십시오.

4.17.2.2. 단일 노드, 멀티 GPU#

멀티 GPU 시스템에서는 사용자가 배치를 위한 호스트 정보를 제공해야 합니다. 앞서 언급했듯이, 해당 정보를 표현하는 자연스러운 방법은 NUMA 노드 ID를 사용하는 것이며 EGM은 이 접근 방식을 따릅니다. 따라서 cuDeviceGetAttribute 함수를 사용하면 사용자는 가장 가까운 NUMA 노드 id를 알아낼 수 있어야 합니다. (참조: Socket Identifiers: What are they? How to access them?). 그다음 사용자는 VMM(가상 메모리 관리) API 또는 CUDA 메모리 풀을 사용하여 EGM 메모리를 할당하고 관리할 수 있습니다.

4.17.2.2.1. VMM API 사용#

가상 메모리 관리 API를 사용한 메모리 할당의 첫 단계는 할당을 뒷받침할 물리 메모리 청크를 생성하는 것입니다. 자세한 내용은 CUDA Programming Guide의 가상 메모리 관리 섹션을 참조하십시오. EGM 할당에서는 사용자가 위치 유형으로 CU_MEM_LOCATION_TYPE_HOST_NUMA  을, 위치 식별자로는 numaID를 명시적으로 제공해야 합니다. 또한 EGM에서는 할당이 플랫폼의 적절한 단위(granularity)에 맞게 정렬되어야 합니다. 다음 코드 스니펫은 cuMemCreate를 사용하여 물리 메모리를 할당하는 예를 보여줍니다:

CUmemAllocationProp prop{};
prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
prop.location.type = CU_MEM_LOCATION_TYPE_HOST_NUMA;
prop.location.id = numaId;
size_t granularity = 0;
cuMemGetAllocationGranularity(&granularity, &prop, MEM_ALLOC_GRANULARITY_MINIMUM);
size_t padded_size = ROUND_UP(size, granularity);
CUmemGenericAllocationHandle allocHandle;
cuMemCreate(&allocHandle, padded_size, &prop, 0);

물리 메모리 할당 후에는 주소 공간을 예약하고 이를 포인터에 매핑해야 합니다. 이러한 절차에는 EGM 관련 변경 사항이 없습니다:

CUdeviceptr dptr;
cuMemAddressReserve(&dptr, padded_size, 0, 0, 0);
cuMemMap(dptr, padded_size, 0, allocHandle, 0);

마지막으로 사용자는 매핑된 가상 주소 범위를 명시적으로 보호해야 합니다. 그렇지 않으면 매핑된 공간에 대한 접근이 크래시로 이어집니다. 메모리 할당과 마찬가지로 사용자는 위치 유형으로 CU_MEM_LOCATION_TYPE_HOST_NUMA을 제공해야 하며, 위치 식별자로는 numaId를 제공해야 합니다. 다음 코드 스니펫은 호스트 노드와 GPU에 대한 액세스 디스크립터를 생성하여, 매핑된 메모리에 대해 양쪽 모두에 읽기 및 쓰기 액세스를 부여합니다:

CUmemAccessDesc accessDesc[2]{{}};
accessDesc[0].location.type = CU_MEM_LOCATION_TYPE_HOST_NUMA;
accessDesc[0].location.id = numaId;
accessDesc[0].flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;
accessDesc[1].location.type = CU_MEM_LOCATION_TYPE_DEVICE;
accessDesc[1].location.id = currentDev;
accessDesc[1].flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;
cuMemSetAccess(dptr, size, accessDesc, 2);

4.17.2.2.2. CUDA 메모리 풀 사용#

EGM을 정의하기 위해 사용자는 노드에 메모리 풀을 생성하고 피어에 대한 액세스를 부여할 수 있습니다. 이 경우 사용자는 위치 유형으로 cudaMemLocationTypeHostNuma을, 위치 식별자로는 numaId를 명시적으로 정의해야 합니다. 다음 코드 스니펫은 메모리 풀 cudaMemPoolCreate을 생성하는 예를 보여줍니다:

cudaSetDevice(homeDevice);
cudaMemPoolProps props{};
props.allocType = cudaMemAllocationTypePinned;
props.location.type = cudaMemLocationTypeHostNuma;
props.location.id = numaId;
cudaMemPoolCreate(&memPool, &props);

또한 직접 연결 피어 액세스의 경우, 기존 피어 액세스 API인 cudaMemPoolSetAccess를 사용하는 것도 가능합니다. accessingDevice에 대한 예는 다음 코드 스니펫에 나와 있습니다:

cudaMemAccessDesc desc{};
desc.flags = cudaMemAccessFlagsProtReadWrite;
desc.location.type = cudaMemLocationTypeDevice;
desc.location.id = accessingDevice;
cudaMemPoolSetAccess(memPool, &desc, 1);

메모리 풀이 생성되고 액세스가 부여되면, 사용자는 생성된 메모리 풀을 residentDevice로 설정하고 cudaMallocAsync를 사용하여 메모리 할당을 시작할 수 있습니다:

cudaDeviceSetMemPool(residentDevice, memPool);
cudaMallocAsync(&ptr, size, memPool, stream);

참고

EGM은 2MB 페이지로 매핑됩니다. 따라서 매우 큰 할당에 접근할 때 사용자는 TLB 미스를 더 많이 겪을 수 있습니다.

4.17.2.3. 멀티 노드, 멀티 GPU#

메모리 할당을 넘어, 원격 피어 액세스에는 EGM 전용 수정 사항이 없으며 CUDA 프로세스 간(IPC) 프로토콜을 따릅니다. IPC에 대한 자세한 내용은 CUDA Programming Guide를 참조하십시오.

사용자는 cuMemCreate를 사용하여 메모리를 할당해야 하며, 또한 위치 유형으로 CU_MEM_LOCATION_TYPE_HOST_NUMA를, 위치 식별자로 numaID를 다시 명시적으로 제공해야 합니다. 또한 요청된 핸들 유형으로 CU_MEM_HANDLE_TYPE_FABRIC를 정의해야 합니다. 다음 코드 스니펫은 노드 A에서 물리 메모리를 할당하는 예를 보여줍니다:

CUmemAllocationProp prop{};
prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
prop.requestedHandleTypes = CU_MEM_HANDLE_TYPE_FABRIC;
prop.location.type = CU_MEM_LOCATION_TYPE_HOST_NUMA;
prop.location.id = numaId;
size_t granularity = 0;
cuMemGetAllocationGranularity(&granularity, &prop,
                              MEM_ALLOC_GRANULARITY_MINIMUM);
size_t padded_size = ROUND_UP(size, granularity);
size_t page_size = ...;
assert(padded_size % page_size == 0);
CUmemGenericAllocationHandle allocHandle;
cuMemCreate(&allocHandle, padded_size, &prop, 0);

cuMemCreate를 사용하여 할당 핸들을 생성한 후, 사용자는 cuMemExportToShareableHandle를 호출하여 해당 핸들을 다른 노드인 노드 B로 내보낼 수 있습니다:

cuMemExportToShareableHandle(&fabricHandle, allocHandle,
                             CU_MEM_HANDLE_TYPE_FABRIC, 0);
// At this point, fabricHandle should be sent to Node B via TCP/IP.

노드 B에서는 cuMemImportFromShareableHandle를 사용하여 핸들을 가져올 수 있으며, 다른 패브릭 핸들과 동일하게 취급할 수 있습니다

// At this point, fabricHandle should be received from Node A via TCP/IP.
CUmemGenericAllocationHandle allocHandle;
cuMemImportFromShareableHandle(&allocHandle, &fabricHandle,
                               CU_MEM_HANDLE_TYPE_FABRIC);

노드 B에서 핸들이 가져와지면, 사용자는 주소 공간을 예약하고 이를 일반적인 방식으로 로컬에 매핑할 수 있습니다:

size_t granularity = 0;
cuMemGetAllocationGranularity(&granularity, &prop,
                              MEM_ALLOC_GRANULARITY_MINIMUM);
size_t padded_size = ROUND_UP(size, granularity);
size_t page_size = ...;
assert(padded_size % page_size == 0);
CUdeviceptr dptr;
cuMemAddressReserve(&dptr, padded_size, 0, 0, 0);
cuMemMap(dptr, padded_size, 0, allocHandle, 0);

마지막 단계로, 사용자는 노드 B의 각 로컬 GPU에 적절한 액세스를 부여해야 합니다. 여덟 개의 로컬 GPU에 읽기 및 쓰기 액세스를 부여하는 예제 코드 스니펫은 다음과 같습니다:

// Give all 8 local  GPUS access to exported EGM memory located on Node A.                                                               |
CUmemAccessDesc accessDesc[8];
for (int i = 0; i < 8; i++) {
   accessDesc[i].location.type = CU_MEM_LOCATION_TYPE_DEVICE;
   accessDesc[i].location.id = i;
   accessDesc[i].flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;
}
cuMemSetAccess(dptr, size, accessDesc, 8);
