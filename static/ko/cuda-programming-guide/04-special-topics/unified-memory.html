4.1. 통합 메모리

이 섹션에서는 사용 가능한 서로 다른 통합 메모리 패러다임 각각의 자세한 동작과 사용 방법을 설명합니다. 이전의 통합 메모리 섹션에서는 어떤 통합 메모리 패러다임이 적용되는지 판단하는 방법을 보여주고 각 패러다임을 간략히 소개했습니다.

앞서 논의했듯이 통합 메모리 프로그래밍에는 네 가지 패러다임이 있습니다:

  • 명시적 관리 메모리 할당에 대한 완전한 지원

  • 소프트웨어 코히어런스를 통한 모든 할당에 대한 완전한 지원

  • 하드웨어 코히어런스를 통한 모든 할당에 대한 완전한 지원

  • 제한된 통합 메모리 지원

완전한 통합 메모리 지원을 포함하는 처음 세 가지 패러다임은 동작과 프로그래밍 모델이 매우 유사하며, 차이점이 있는 경우 이를 강조하여 완전한 CUDA 통합 메모리 지원이 있는 디바이스에서의 통합 메모리에서 다룹니다.

통합 메모리 지원이 제한되는 마지막 패러다임은 Windows, WSL 및 Tegra에서의 통합 메모리에서 자세히 설명합니다.

4.1.1. 완전한 CUDA 통합 메모리 지원이 있는 디바이스에서의 통합 메모리#

이러한 시스템에는 NVIDIA Grace Hopper와 같이 하드웨어 코히어런트 메모리 시스템, 그리고 Heterogeneous Memory Management(HMM)가 활성화된 최신 Linux 시스템이 포함됩니다. HMM은 소프트웨어 기반 메모리 관리 시스템으로, 하드웨어 코히어런트 메모리 시스템과 동일한 프로그래밍 모델을 제공합니다.

Linux HMM을 사용하려면 Linux 커널 버전 6.1.24+, 6.2.11+ 또는 6.3+, 컴퓨트 기능 7.5 이상의 디바이스, 그리고 Open Kernel Modules와 함께 설치된 CUDA 드라이버 버전 535+가 필요합니다.

참고

CPU와 GPU 모두에 대해 결합된 페이지 테이블을 사용하는 시스템을 하드웨어 코히어런트 시스템이라고 부릅니다. CPU와 GPU에 대해 별도의 페이지 테이블을 사용하는 시스템은 소프트웨어 코히어런트라고 부릅니다.

NVIDIA Grace Hopper와 같은 하드웨어 코히어런트 시스템은 CPU와 GPU 모두에 대해 논리적으로 결합된 페이지 테이블을 제공합니다. 자세한 내용은 CPU 및 GPU 페이지 테이블: 하드웨어 코히어런시 vs. 소프트웨어 코히어런시를 참조하세요. 다음 섹션은 하드웨어 코히어런트 시스템에만 적용됩니다:

4.1.1.1. 통합 메모리: 심층 예제#

전체 CUDA 통합 메모리 지원을 제공하는 시스템(표 통합 메모리 패러다임 개요 참조)은 디바이스가 디바이스와 상호작용하는 호스트 프로세스가 소유한 어떤 메모리에도 액세스할 수 있도록 합니다.

이 섹션에서는 표준 출력 스트림에 입력 문자 배열의 첫 8자를 단순히 출력하는 커널을 사용하여 몇 가지 고급 사용 사례를 보여줍니다:

__global__ void kernel(const char* type, const char* data) {
  static const int n_char = 8;
  printf("%s - first %d characters: '", type, n_char);
  for (int i = 0; i < n_char; ++i) printf("%c", data[i]);
  printf("'\n");
}

다음 탭에서는 이 커널을 시스템 할당 메모리로 호출할 수 있는 다양한 방법을 보여줍니다:

void test_malloc() {
  const char test_string[] = "Hello World";
  char* heap_data = (char*)malloc(sizeof(test_string));
  strncpy(heap_data, test_string, sizeof(test_string));
  kernel<<<1, 1>>>("malloc", heap_data);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  free(heap_data);
}

void test_managed() {
  const char test_string[] = "Hello World";
  char* data;
  cudaMallocManaged(&data, sizeof(test_string));
  strncpy(data, test_string, sizeof(test_string));
  kernel<<<1, 1>>>("managed", data);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  cudaFree(data);
}

void test_stack() {
  const char test_string[] = "Hello World";
  kernel<<<1, 1>>>("stack", test_string);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}

void test_static() {
  static const char test_string[] = "Hello World";
  kernel<<<1, 1>>>("static", test_string);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}

const char global_string[] = "Hello World";

void test_global() {
  kernel<<<1, 1>>>("global", global_string);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}

// declared in separate file, see below
extern char* ext_data;

void test_extern() {
  kernel<<<1, 1>>>("extern", ext_data);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}

/** This may be a non-CUDA file */
char* ext_data;
static const char global_string[] = "Hello World";

void __attribute__ ((constructor)) setup(void) {
  ext_data = (char*)malloc(sizeof(global_string));
  strncpy(ext_data, global_string, sizeof(global_string));
}

void __attribute__ ((destructor)) tear_down(void) {
  free(ext_data);
}

extern 변수의 경우, CUDA와 전혀 상호작용하지 않는 서드파티 라이브러리에 의해 선언되며 그 메모리가 소유 및 관리될 수도 있다는 점에 유의하십시오.

또한 스택 변수뿐 아니라 파일 스코프 및 전역 스코프 변수는 GPU가 포인터를 통해서만 액세스할 수 있다는 점에도 유의하십시오. 이 특정 예제에서는 문자 배열이 이미 포인터로 선언되어 있으므로 이는 편리합니다: const char*. 그러나 전역 스코프 정수를 사용한 다음 예제를 고려하십시오:

// this variable is declared at global scope
int global_variable;

__global__ void kernel_uncompilable() {
  // this causes a compilation error: global (__host__) variables must not
  // be accessed from __device__ / __global__ code
  printf("%d\n", global_variable);
}

// On systems with pageableMemoryAccess set to 1, we can access the address
// of a global variable. The below kernel takes that address as an argument
__global__ void kernel(int* global_variable_addr) {
  printf("%d\n", *global_variable_addr);
}
int main() {
  kernel<<<1, 1>>>(&global_variable);
  ...
  return 0;
}

위의 예제에서는 커널에서 전역 변수를 직접 액세스하는 대신, 전역 변수에 대한 포인터를 커널에 전달하도록 보장해야 합니다. 이는 __managed__ 지정자가 없는 전역 변수는 기본적으로 __host__-전용으로 선언되므로, 현재로서는 대부분의 컴파일러가 디바이스 코드에서 이러한 변수를 직접 사용하는 것을 허용하지 않기 때문입니다.

4.1.1.1.1. 파일 백드 통합 메모리#

전체 CUDA 통합 메모리 지원을 제공하는 시스템은 디바이스가 호스트 프로세스가 소유한 어떤 메모리에도 액세스할 수 있도록 하므로, 파일 백드 메모리에도 직접 액세스할 수 있습니다.

여기서는 GPU에서 문자열을 출력하기 위해 입력 파일에서 직접 읽은 문자열을 사용하도록, 이전 섹션에 나온 초기 예제를 수정한 버전을 보여줍니다. 다음 예제에서 메모리는 물리적 파일에 의해 백업되지만, 이 예제는 메모리-백드 파일에도 적용됩니다.

__global__ void kernel(const char* type, const char* data) {
  static const int n_char = 8;
  printf("%s - first %d characters: '", type, n_char);
  for (int i = 0; i < n_char; ++i) printf("%c", data[i]);
  printf("'\n");
}

void test_file_backed() {
  int fd = open(INPUT_FILE_NAME, O_RDONLY);
  ASSERT(fd >= 0, "Invalid file handle");
  struct stat file_stat;
  int status = fstat(fd, &file_stat);
  ASSERT(status >= 0, "Invalid file stats");
  char* mapped = (char*)mmap(0, file_stat.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
  ASSERT(mapped != MAP_FAILED, "Cannot map file into memory");
  kernel<<<1, 1>>>("file-backed", mapped);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  ASSERT(munmap(mapped, file_stat.st_size) == 0, "Cannot unmap file");
  ASSERT(close(fd) == 0, "Cannot close file");
}

hostNativeAtomicSupported 속성이 없는 시스템(리눅스 HMM이 활성화된 시스템 포함)에서는 파일 백드 메모리에 대한 원자적 액세스가 지원되지 않는다는 점에 유의하십시오( Host Native Atomics 참조).

4.1.1.1.2. 통합 메모리를 사용한 프로세스 간 통신(IPC)#

참고

현재로서는 통합 메모리와 함께 IPC를 사용하는 경우 상당한 성능상의 영향이 있을 수 있습니다.

많은 애플리케이션은 프로세스당 하나의 GPU를 관리하는 것을 선호하지만, 예를 들어 오버서브스크립션을 위해 통합 메모리를 사용하고 여러 GPU에서 이를 액세스해야 하는 경우도 있습니다.

CUDA IPC ( Interprocess Communication 참조 )는 관리 메모리를 지원하지 않습니다. 이 유형의 메모리에 대한 핸들은 이 섹션에서 논의한 어떤 메커니즘을 통해서도 공유될 수 없습니다. 전체 CUDA 통합 메모리 지원을 제공하는 시스템에서는 시스템 할당 메모리가 IPC 가능(IPC capable)합니다. 시스템 할당 메모리에 대한 액세스가 다른 프로세스와 공유되고 나면, 파일 백드 통합 메모리와 유사하게 동일한 프로그래밍 모델이 적용됩니다.

Linux에서 IPC 가능한 시스템 할당 메모리를 생성하는 다양한 방법에 대한 자세한 내용은 다음 참고 자료를 참조하십시오:

  • MAP_SHARED를 사용한 mmap

  • POSIX IPC API

  • Linux memfd_create .

이 기법을 사용하여 서로 다른 호스트와 그 디바이스 간에 메모리를 공유하는 것은 불가능하다는 점에 유의하십시오.

4.1.1.2. 성능 튜닝#

통합 메모리로 좋은 성능을 달성하려면 다음이 중요합니다:

  • 시스템에서 페이징이 어떻게 동작하는지, 그리고 불필요한 페이지 폴트(page fault)를 어떻게 피할 수 있는지 이해하기

  • 데이터를 액세스하는 프로세서에 로컬로 유지할 수 있게 해주는 다양한 메커니즘을 이해하기

  • 시스템의 메모리 전송 단위(그래뉼러리티)에 맞게 애플리케이션 튜닝을 고려하기.

일반적인 조언으로, 성능 힌트( Performance Hints 참조)는 성능을 개선할 수 있지만, 이를 잘못 사용하면 기본 동작에 비해 성능이 저하될 수 있습니다. 또한 어떤 힌트든 호스트에서 그에 수반되는 성능 비용이 있으므로, 유용한 힌트는 최소한 이 비용을 상쇄할 수 있을 만큼 충분히 성능을 개선해야 합니다.

4.1.1.2.1. 메모리 페이징과 페이지 크기#

통합 메모리의 성능상 영향을 더 잘 이해하려면 가상 주소 지정, 메모리 페이지 및 페이지 크기를 이해하는 것이 중요합니다. 이 하위 섹션에서는 필요한 모든 용어를 정의하고, 페이징이 성능에 왜 중요한지 설명하고자 합니다.

통합 메모리에 대해 현재 지원되는 모든 시스템은 가상 주소 공간을 사용합니다. 이는 애플리케이션이 사용하는 메모리 주소가 가상 위치를 나타내며, 해당 메모리가 실제로 존재하는 물리적 위치에 매핑될 수 있음을 의미합니다.

현재 지원되는 모든 프로세서(CPU와 GPU 모두 포함)도 추가로 메모리 페이징을 사용합니다. 모든 시스템이 가상 주소 공간을 사용하므로, 메모리 페이지에는 두 가지 유형이 있습니다:

  • 가상 페이지: 이는 운영체제가 추적하는, 프로세스당 고정 크기의 연속적인 가상 메모리 청크를 나타내며 물리 메모리에 매핑될 수 있습니다. 가상 페이지는 매핑과 연결된다는 점에 유의하십시오. 예를 들어 단일 가상 주소가 서로 다른 페이지 크기를 사용하여 물리 메모리에 매핑될 수 있습니다.

  • 물리 페이지: 이는 프로세서의 주 메모리 관리 유닛(MMU)이 지원하는 고정 크기의 연속적인 메모리 청크를 나타내며, 가상 페이지가 여기에 매핑될 수 있습니다.

현재 모든 x86_64 CPU는 기본 물리 페이지 크기로 4KiB를 사용합니다. Arm CPU는 정확한 CPU에 따라 4KiB, 16KiB, 32KiB, 64KiB 등 여러 물리 페이지 크기를 지원합니다. 마지막으로 NVIDIA GPU는 여러 물리 페이지 크기를 지원하지만, 2MiB 물리 페이지 또는 그보다 큰 페이지를 선호합니다. 이러한 크기는 향후 하드웨어에서 변경될 수 있다는 점에 유의하십시오.

가상 페이지의 기본 페이지 크기는 보통 물리 페이지 크기와 대응되지만, 운영체제와 하드웨어에서 지원되는 한 애플리케이션은 서로 다른 페이지 크기를 사용할 수 있습니다. 일반적으로 지원되는 가상 페이지 크기는 2의 거듭제곱이어야 하며 물리 페이지 크기의 배수여야 합니다.

가상 페이지가 물리 페이지에 매핑되는 것을 추적하는 논리적 엔터티를 페이지 테이블(page table)이라고 부르며, 주어진 가상 페이지를 주어진 가상 크기로 물리 페이지에 매핑하는 각각의 매핑을 페이지 테이블 엔트리(Page Table Entry, PTE)라고 합니다. 지원되는 모든 프로세서는 가상 주소에서 물리 주소로의 변환을 가속하기 위해 페이지 테이블 전용 캐시를 제공합니다. 이러한 캐시는 TLB(Translation Lookaside Buffer)라고 합니다.

애플리케이션 성능 튜닝에는 두 가지 중요한 측면이 있습니다:

  • 가상 페이지 크기의 선택,

  • 시스템이 CPU와 GPU가 모두 사용하는 결합된(combined) 페이지 테이블을 제공하는지, 아니면 CPU와 GPU 각각에 대해 별도의 페이지 테이블을 제공하는지 여부.

4.1.1.2.1.1. 적절한 페이지 크기 선택#

일반적으로 작은 페이지 크기는 (가상) 메모리 단편화를 줄이는 대신 TLB 미스가 더 많고, 큰 페이지 크기는 메모리 단편화는 더 크지만 TLB 미스가 더 적습니다. 또한 일반적으로 메모리 마이그레이션은 작은 페이지 크기에 비해 큰 페이지 크기에서 더 비용이 많이 드는데, 보통 전체 메모리 페이지를 마이그레이션하기 때문입니다. 이로 인해 큰 페이지 크기를 사용하는 애플리케이션에서는 더 큰 지연 시간 스파이크가 발생할 수 있습니다. 페이지 폴트에 대한 자세한 내용은 다음 섹션도 참조하십시오.

성능 튜닝에서 중요한 한 가지 측면은 TLB 미스가 일반적으로 CPU에 비해 GPU에서 훨씬 더 비용이 크다는 점입니다. 이는 GPU 스레드가 작은 페이지 크기를 사용해 매핑된 통합 메모리의 임의 위치에 자주 액세스한다면, 충분히 큰 페이지 크기를 사용해 매핑된 통합 메모리에 대한 동일한 액세스에 비해 현저히 느려질 수 있음을 의미합니다. CPU 스레드가 작은 페이지 크기를 사용해 매핑된 큰 메모리 영역의 임의 위치에 액세스할 때도 유사한 효과가 발생할 수 있지만, 감속은 덜 두드러지므로, 애플리케이션은 이 감속과 메모리 단편화를 줄이는 것 사이에서 트레이드오프를 하고자 할 수 있습니다.

일반적으로 애플리케이션은 특정 프로세서의 물리 페이지 크기에 맞춰 성능을 튜닝해서는 안 된다는 점에 유의하십시오. 물리 페이지 크기는 하드웨어에 따라 변경될 수 있기 때문입니다. 위의 조언은 가상 페이지 크기에만 적용됩니다.

4.1.1.2.1.2. CPU 및 GPU 페이지 테이블: 하드웨어 코히어런트 vs. 소프트웨어 코히어런트#

NVIDIA Grace Hopper와 같은 하드웨어 코히어런트 시스템은 CPU와 GPU 모두를 위한 논리적으로 결합된 페이지 테이블을 제공합니다. 이는 GPU에서 시스템 할당 메모리에 액세스하기 위해, GPU가 요청된 메모리에 대해 CPU가 생성한 페이지 테이블 엔트리를 사용하기 때문에 중요합니다. 해당 페이지 테이블 엔트리가 기본 CPU 페이지 크기인 4KiB 또는 64KiB를 사용한다면, 큰 가상 메모리 영역에 대한 액세스는 상당한 TLB 미스를 유발하여, 결과적으로 상당한 성능 저하를 초래합니다.

반면, CPU와 GPU가 각각 자체 논리 페이지 테이블을 갖는 소프트웨어 코히어런트 시스템에서는 서로 다른 성능 튜닝 측면을 고려해야 합니다: 코히어런시를 보장하기 위해, 이러한 시스템은 보통 프로세서가 다른 프로세서의 물리 메모리에 매핑된 메모리 주소에 액세스하는 경우 페이지 폴트를 사용합니다. 이러한 페이지 폴트는 다음을 의미합니다:

  • 현재 소유한 프로세서(물리 페이지가 현재 상주하는 곳)가 이 페이지에 더 이상 액세스할 수 없도록, 페이지 테이블 엔트리를 삭제하거나 업데이트하여 보장해야 합니다.

  • 액세스를 요청하는 프로세서가 이 페이지에 액세스할 수 있도록, 새로운 페이지 테이블 엔트리를 생성하거나 기존 엔트리를 업데이트하여, 유효/활성 상태가 되도록 보장해야 합니다.

  • 이 가상 페이지를 뒷받침하는 물리 페이지는 액세스를 요청하는 프로세서로 이동/마이그레이션되어야 합니다: 이는 비용이 큰 작업일 수 있으며, 작업량은 페이지 크기에 비례합니다.

전반적으로 하드웨어 코히어런트 시스템은 CPU 및 GPU 스레드 모두가 동일한 메모리 페이지에 대해 빈번한 동시 액세스를 수행하는 경우에, 소프트웨어 코히어런트 시스템에 비해 상당한 성능 이점을 제공합니다:

  • 페이지 폴트가 더 적음: 이러한 시스템은 코히어런시를 에뮬레이션하거나 메모리를 마이그레이션하기 위해 페이지 폴트를 사용할 필요가 없습니다.

  • 경합이 더 적음: 이러한 시스템은 페이지 크기 단위가 아니라 캐시 라인 단위의 세분성에서 코히어런트를 제공합니다. 즉, 캐시 라인 내에서 여러 프로세서로부터 경합이 발생할 때는 가장 작은 페이지 크기보다 훨씬 작은 캐시 라인만 교환되며, 서로 다른 프로세서가 한 페이지 내의 서로 다른 캐시 라인에 액세스하는 경우에는 경합이 발생하지 않습니다.

이는 다음 시나리오의 성능에 영향을 미칩니다:

  • CPU와 GPU 모두에서 동일한 주소에 대해 동시에 수행되는 atomic 업데이트

  • CPU 스레드에서 GPU 스레드로 또는 그 반대로 신호를 보내는 경우.

4.1.1.2.2. 호스트에서의 통합 메모리 직접 액세스#

일부 디바이스는 GPU 상주 통합 메모리에 대해 호스트에서 수행되는 코히어런트 읽기, 저장(store) 및 atomic 액세스를 위한 하드웨어 지원을 갖추고 있습니다. 이러한 디바이스에는 다음 속성이 있습니다. cudaDevAttrDirectManagedMemAccessFromHost 1로 설정됩니다. 모든 하드웨어 코히어런트 시스템은 NVLink로 연결된 디바이스에 대해 이 속성이 설정되어 있다는 점에 유의하십시오. 이러한 시스템에서는 호스트가 페이지 폴트 및 데이터 마이그레이션 없이 GPU 상주 메모리에 직접 액세스할 수 있습니다. CUDA managed memory를 사용하는 경우, cudaMemAdviseSetAccessedBy 위치 유형(location type) 힌트 cudaMemLocationTypeHost 페이지 폴트 없이 이러한 직접 액세스를 활성화하려면 필요합니다. 아래 예제를 참조하십시오.

__global__ void write(int *ret, int a, int b) {
  ret[threadIdx.x] = a + b + threadIdx.x;
}

__global__ void append(int *ret, int a, int b) {
  ret[threadIdx.x] += a + b + threadIdx.x;
}

void test_malloc() {
  int *ret = (int*)malloc(1000 * sizeof(int));
  // for shared page table systems, the following hint is not necesary
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(ret, 1000 * sizeof(int), cudaMemAdviseSetAccessedBy, location);

  write<<< 1, 1000 >>>(ret, 10, 100);            // pages populated in GPU memory
  cudaDeviceSynchronize();
  for(int i = 0; i < 1000; i++)
      printf("%d: A+B = %d\n", i, ret[i]);        // directManagedMemAccessFromHost=1: CPU accesses GPU memory directly without migrations
                                                  // directManagedMemAccessFromHost=0: CPU faults and triggers device-to-host migrations
  append<<< 1, 1000 >>>(ret, 10, 100);            // directManagedMemAccessFromHost=1: GPU accesses GPU memory without migrations
  cudaDeviceSynchronize();                        // directManagedMemAccessFromHost=0: GPU faults and triggers host-to-device migrations
  free(ret);
}

__global__ void write(int *ret, int a, int b) {
  ret[threadIdx.x] = a + b + threadIdx.x;
}

__global__ void append(int *ret, int a, int b) {
  ret[threadIdx.x] += a + b + threadIdx.x;
}

void test_managed() {
  int *ret;
  cudaMallocManaged(&ret, 1000 * sizeof(int));
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(ret, 1000 * sizeof(int), cudaMemAdviseSetAccessedBy, location);  // set direct access hint

  write<<< 1, 1000 >>>(ret, 10, 100);            // pages populated in GPU memory
  cudaDeviceSynchronize();
  for(int i = 0; i < 1000; i++)
      printf("%d: A+B = %d\n", i, ret[i]);        // directManagedMemAccessFromHost=1: CPU accesses GPU memory directly without migrations
                                                  // directManagedMemAccessFromHost=0: CPU faults and triggers device-to-host migrations
  append<<< 1, 1000 >>>(ret, 10, 100);            // directManagedMemAccessFromHost=1: GPU accesses GPU memory without migrations
  cudaDeviceSynchronize();                        // directManagedMemAccessFromHost=0: GPU faults and triggers host-to-device migrations
  cudaFree(ret);

이후 write 커널이 완료되면, ret GPU 메모리에 생성되고 초기화됩니다. 다음으로, CPU가 액세스합니다 ret 그다음에 append 동일한 것을 사용하는 커널 ret 메모리를 다시. 이 코드는 시스템 아키텍처와 하드웨어 코히어런시 지원 여부에 따라 서로 다른 동작을 보일 것입니다:

  • 다음과 같은 시스템에서 directManagedMemAccessFromHost=1: CPU가 managed 버퍼에 액세스하더라도 어떤 마이그레이션도 트리거되지 않습니다. 데이터는 GPU 메모리에 계속 상주하며, 이후의 어떤 GPU 커널도 폴트나 마이그레이션을 유발하지 않고 이를 직접 계속 액세스할 수 있습니다.

  • 다음과 같은 시스템에서 directManagedMemAccessFromHost=0: CPU가 managed 버퍼에 액세스하면 페이지 폴트가 발생하고 데이터 마이그레이션을 시작합니다; GPU 커널이 동일한 데이터에 처음 액세스하려고 하면 페이지 폴트가 발생하고 페이지를 다시 GPU 메모리로 마이그레이션합니다.

4.1.1.2.3. 호스트 네이티브 atomic#

하드웨어 코히어런트 시스템에서 NVLink로 연결된 디바이스를 포함한 일부 디바이스는 CPU에 상주하는 메모리에 대한 하드웨어 가속 atomic 액세스를 지원합니다. 이는 호스트 메모리에 대한 atomic 액세스가 페이지 폴트로 에뮬레이션될 필요가 없음을 의미합니다. 이러한 디바이스에서는 속성 cudaDevAttrHostNativeAtomicSupported 이(가) 1로 설정됩니다.

4.1.1.2.4. Atomic 액세스 및 동기화 프리미티브#

CUDA 통합 메모리는 호스트 및 디바이스 스레드에서 사용 가능한 모든 atomic 연산을 지원하여, 모든 스레드가 동일한 공유 메모리 위치에 동시에 액세스함으로써 협력할 수 있도록 합니다. libcu++ 라이브러리는 cuda::atomic, cuda::atomic_ref, cuda::barrier, cuda::semaphore 등을 포함하여(그 밖에도 매우 많음), 호스트와 디바이스 스레드 간의 동시 사용에 맞게 튜닝된 다양한 이기종 동기화 프리미티브를 제공합니다.

소프트웨어 코히어런트 시스템에서는 디바이스에서 파일 백드 호스트 메모리로의 atomic 액세스가 지원되지 않습니다. 다음 예제 코드는 하드웨어 코히어런트 시스템에서는 유효하지만, 다른 시스템에서는 정의되지 않은 동작을 보입니다:

#include <cuda/atomic>

#include <cstdio>
#include <fcntl.h>
#include <sys/mman.h>

#define ERR(msg, ...) { fprintf(stderr, msg, ##__VA_ARGS__); return EXIT_FAILURE; }

__global__ void kernel(int* ptr) {
  cuda::atomic_ref{*ptr}.store(2);
}

int main() {
  // this will be closed/deleted by default on exit
  FILE* tmp_file = tmpfile64();
  // need to allocate space in the file, we do this with posix_fallocate here
  int status = posix_fallocate(fileno(tmp_file), 0, 4096);
  if (status != 0) ERR("Failed to allocate space in temp file\n");
  int* ptr = (int*)mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_PRIVATE, fileno(tmp_file), 0);
  if (ptr == MAP_FAILED) ERR("Failed to map temp file\n");

  // initialize the value in our file-backed memory
  *ptr = 1;
  printf("Atom value: %d\n", *ptr);

  // device and host thread access ptr concurrently, using cuda::atomic_ref
  kernel<<<1, 1>>>(ptr);
  while (cuda::atomic_ref{*ptr}.load() != 2);
  // this will always be 2
  printf("Atom value: %d\n", *ptr);

  return EXIT_SUCCESS;
}

소프트웨어 코히어런트 시스템에서는 통합 메모리에 대한 atomic 액세스가 페이지 폴트를 유발할 수 있으며, 이는 상당한 지연 시간으로 이어질 수 있습니다. 다만 이러한 시스템에서 CPU 메모리에 대한 모든 GPU atomic에 해당하는 것은 아닙니다. nvidia-smi -q | grep "Atomic Caps Outbound"에 의해 나열된 연산은 페이지 폴트를 피할 수 있습니다.

하드웨어 코히어런트 시스템에서는 호스트와 디바이스 간 atomic에 페이지 폴트가 필요하지 않지만, 메모리 액세스가 폴트가 나게 할 수 있는 다른 이유로 인해 여전히 폴트가 발생할 수 있습니다.

4.1.1.2.5. 통합 메모리에서의 Memcpy()/Memset() 동작#

cudaMemcpy*() 및 cudaMemset*()는 어떤 통합 메모리 포인터든 인자로 받을 수 있습니다.

cudaMemcpy*()의 경우, cudaMemcpyKind로 지정된 방향은 성능 힌트이며, 인자 중 하나라도 통합 메모리 포인터인 경우 성능에 더 큰 영향을 미칠 수 있습니다.

따라서 다음의 성능 조언을 따를 것을 권장합니다:

  • 통합 메모리의 물리적 위치를 알고 있는 경우, 정확한 cudaMemcpyKind 힌트를 사용하십시오.

  • 선호하십시오 cudaMemcpyDefault 부정확한 것보다 cudaMemcpyKind 힌트.

  • 항상 채워진(초기화된) 버퍼를 사용하십시오: 이 API들을 메모리 초기화에 사용하는 것은 피하십시오.

  • 사용을 피하십시오 cudaMemcpy*() 두 포인터가 모두 시스템 할당 메모리를 가리키는 경우: 커널을 실행하거나 다음과 같은 CPU 메모리 복사 알고리즘을 사용하십시오 std::memcpy 대신.

다음은 공유되는 메모리의 할당자에 적용됩니다:

  • mmap와 같은 시스템 할당자는 MAP_SHARED 플래그를 사용해 프로세스 간에 메모리를 공유할 수 있게 합니다. 이는 CUDA에서 지원되며, 동일한 호스트에 연결된 서로 다른 디바이스 간에 메모리를 공유하는 데 사용할 수 있습니다. 그러나 현재 이는 여러 호스트 간뿐만 아니라 여러 디바이스 간 메모리 공유는 지원되지 않습니다. 자세한 내용은 통합 메모리에서의 프로세스 간 통신(IPC)을 참조하십시오.

  • 여러 호스트에서 네트워크를 통해 통합 메모리 또는 기타 CUDA 메모리에 액세스하려면, 사용 중인 통신 라이브러리의 문서를 참조하십시오. 예를 들어 NCCL, NVSHMEM, OpenMPI, UCX 등이 있습니다.

4.1.1.2.7. 액세스 카운터 마이그레이션#

하드웨어 코히어런트 시스템에서 액세스 카운터 기능은 GPU가 다른 프로세서에 위치한 메모리에 액세스하는 빈도를 추적합니다. 이는 메모리 페이지가 해당 페이지에 가장 자주 액세스하는 프로세서의 물리 메모리로 이동되도록 보장하기 위해 필요합니다. 이는 CPU와 GPU 간, 그리고 피어 GPU 간의 마이그레이션을 유도할 수 있으며, 이 과정을 액세스 카운터 마이그레이션이라고 합니다.

CUDA 12.4부터 액세스 카운터는 시스템 할당 메모리에서 지원됩니다. 파일 백드 메모리는 액세스에 따라 마이그레이션되지 않는다는 점에 유의하십시오. 시스템 할당 메모리의 경우, 해당 디바이스 id를 가진 디바이스에 대해 cudaMemAdviseSetAccessedBy 힌트를 사용하면 액세스 카운터 마이그레이션을 켤 수 있습니다. 액세스 카운터가 켜져 있다면, 마이그레이션을 방지하기 위해 호스트로 설정된 cudaMemAdviseSetPreferredLocation를 사용할 수 있습니다. 기본적으로 cudaMallocManaged는 fault-and-migrate 메커니즘에 기반해 마이그레이션합니다. [7]

드라이버는 더 효율적인 스래싱(thrashing) 완화 또는 메모리 오버서브스크립션(oversubscription) 시나리오를 위해 액세스 카운터를 사용할 수도 있습니다.

[7]

현재 시스템에서는 accessed-by 디바이스 힌트가 설정되어 있을 때 managed 메모리에서 액세스 카운터 마이그레이션을 사용할 수 있습니다. 이는 구현 세부 사항이며, 향후 호환성을 위해 의존해서는 안 됩니다.

4.1.1.2.8. CPU에서 GPU 상주 메모리로의 잦은 쓰기 방지#

호스트가 통합 메모리에 액세스하면, 캐시 미스가 호스트와 디바이스 사이에서 예상보다 더 많은 트래픽을 유발할 수 있습니다. 많은 CPU 아키텍처는 쓰기를 포함한 모든 메모리 연산이 캐시 계층을 거치도록 요구합니다. 시스템 메모리가 GPU에 상주한다면, CPU가 이 메모리에 자주 쓰기(write)를 수행할 때 캐시 미스가 발생할 수 있으며, 그 결과 요청된 메모리 범위에 실제 값을 쓰기 전에 먼저 데이터를 GPU에서 CPU로 전송하게 됩니다. 소프트웨어 코히어런트 시스템에서는 추가 페이지 폴트를 유발할 수 있고, 하드웨어 코히어런트 시스템에서는 CPU 연산 간 더 높은 지연 시간을 초래할 수 있습니다. 따라서 호스트가 생성한 데이터를 디바이스와 공유하려면, CPU 상주 메모리에 쓰고 디바이스에서 해당 값을 직접 읽는 것을 고려하십시오. 아래 코드는 통합 메모리로 이를 달성하는 방법을 보여줍니다.

  size_t data_size = sizeof(int);
  int* data = (int*)malloc(data_size);
  // ensure that data stays local to the host and avoid faults
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, data_size, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, data_size, cudaMemAdviseSetAccessedBy, location);

  // frequent exchanges of small data: if the CPU writes to CPU-resident memory,
  // and GPU directly accesses that data, we can avoid the CPU caches re-loading
  // data if it was evicted in between writes
  for (int i = 0; i < 10; ++i) {
    *data = 42 + i;
    kernel<<<1, 1>>>(data);
    cudaDeviceSynchronize();
    // CPU cache potentially evicted data here
  }
  free(data);

  int* data;
  size_t data_size = sizeof(int);
  cudaMallocManaged(&data, data_size);
  // ensure that data stays local to the host and avoid faults
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, data_size, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, data_size, cudaMemAdviseSetAccessedBy, location);

  // frequent exchanges of small data: if the CPU writes to CPU-resident memory,
  // and GPU directly accesses that data, we can avoid the CPU caches re-loading
  // data if it was evicted in between writes

    kernel<<<1, 1>>>(data);
    cudaDeviceSynchronize();
    // CPU cache potentially evicted data here

  cudaFree(data);

4.1.1.2.9. 시스템 메모리에 대한 비동기 액세스 활용#

애플리케이션이 디바이스에서 수행한 작업의 결과를 호스트와 공유해야 한다면, 몇 가지 가능한 옵션이 있습니다:

  1. 디바이스가 결과를 GPU 상주 메모리에 기록하고, cudaMemcpy*을 사용해 결과를 전송한 뒤, 호스트가 전송된 데이터를 읽습니다.

  2. 디바이스가 결과를 CPU 상주 메모리에 직접 기록하고, 호스트가 그 데이터를 읽습니다.

  3. 디바이스가 GPU 상주 메모리에 기록하고, 호스트가 그 데이터에 직접 액세스합니다.

결과가 전송/액세스되는 동안 디바이스에서 독립적인 작업을 스케줄링할 수 있다면, 옵션 1 또는 3이 선호됩니다. 호스트가 결과에 액세스할 때까지 디바이스가 놀게(starved) 된다면, 옵션 2가 선호될 수 있습니다. 이는 일반적으로 많은 호스트 스레드를 사용해 데이터를 읽지 않는 한, 디바이스가 호스트가 읽을 수 있는 것보다 더 높은 대역폭으로 쓸 수 있기 때문입니다.

void exchange_explicit_copy(cudaStream_t stream) {
  int* data, *host_data;
  size_t n_bytes = sizeof(int) * 16;
  // allocate receiving buffer
  host_data = (int*)malloc(n_bytes);
  // allocate, since we touch on the device first, will be GPU-resident
  cudaMallocManaged(&data, n_bytes);
  kernel<<<1, 16, 0, stream>>>(data);
  // launch independent work on the device
  // other_kernel<<<1024, 256, 0, stream>>>(other_data, ...);
  // transfer to host
  cudaMemcpyAsync(host_data, data, n_bytes, cudaMemcpyDeviceToHost, stream);
  // sync stream to ensure data has been transferred
  cudaStreamSynchronize(stream);
  // read transferred data
  printf("Got values %d - %d from GPU\n", host_data[0], host_data[15]);
  cudaFree(data);
  free(host_data);
}

void exchange_device_direct_write(cudaStream_t stream) {
  int* data;
  size_t n_bytes = sizeof(int) * 16;
  // allocate receiving buffer
  cudaMallocManaged(&data, n_bytes);
  // ensure that data is mapped and resident on the host
  cudaMemLocation location = {.type = cudaMemLocationTypeHost};
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetPreferredLocation, location);
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetAccessedBy, location);
  kernel<<<1, 16, 0, stream>>>(data);
  // sync stream to ensure data has been transferred
  cudaStreamSynchronize(stream);
  // read transferred data
  printf("Got values %d - %d from GPU\n", data[0], data[15]);
  cudaFree(data);
}

void exchange_host_direct_read(cudaStream_t stream) {
  int* data;
  size_t n_bytes = sizeof(int) * 16;
  // allocate receiving buffer
  cudaMallocManaged(&data, n_bytes);
  // ensure that data is mapped and resident on the device
  cudaMemLocation device_loc = {};
  cudaGetDevice(&device_loc.id);
  device_loc.type = cudaMemLocationTypeDevice;
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetPreferredLocation, device_loc);
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetAccessedBy, device_loc);
  kernel<<<1, 16, 0, stream>>>(data);
  // launch independent work on the GPU
  // other_kernel<<<1024, 256, 0, stream>>>(other_data, ...);
  // sync stream to ensure data may be accessed (has been written by device)
  cudaStreamSynchronize(stream);
  // read data directly from host
  printf("Got values %d - %d from GPU\n", data[0], data[15]);
  cudaFree(data);

마지막으로, 위의 명시적 복사 예제에서 데이터 전송을 위해 cudaMemcpy*를 사용하는 대신, 호스트 또는 디바이스 커널을 사용하여 이 전송을 명시적으로 수행할 수 있습니다. 연속적인 데이터의 경우, copy-engine으로 수행되는 작업은 호스트와 디바이스 양쪽의 작업과 오버랩될 수 있으므로 CUDA copy-engine을 사용하는 것이 바람직합니다. copy-engine은 cudaMemcpy* 및 cudaMemPrefetchAsync API에서 사용될 수도 있지만, 보장되지는 않습니다. cudaMemcpy* API 호출에서 copy-engine이 사용된다는 보장은 없습니다. 같은 이유로, 충분히 큰 데이터에 대해서는 호스트 직접 읽기보다 명시적 복사가 선호됩니다. 호스트와 디바이스 모두 각자의 메모리 시스템을 포화시키지 않는 작업을 수행한다면, 전송은 copy-engine에 의해 호스트와 디바이스 양쪽에서 수행되는 작업과 동시에 수행될 수 있습니다.

copy-engine은 일반적으로 호스트와 디바이스 간 전송뿐 아니라 NVLink로 연결된 시스템 내 피어 디바이스 간 전송에도 사용됩니다. copy-engine의 총 개수가 제한되어 있기 때문에, 일부 시스템에서는 디바이스를 사용해 전송을 명시적으로 수행하는 것에 비해 cudaMemcpy*의 대역폭이 더 낮을 수 있습니다. 이러한 경우 전송이 애플리케이션의 크리티컬 패스에 있다면, 디바이스 기반의 명시적 전송을 사용하는 것이 더 바람직할 수 있습니다.

4.1.2. CUDA managed memory 지원만 있는 디바이스에서의 통합 메모리#

페이지형(pageable) 메모리 액세스는 없지만 compute capability 6.x 이상인 디바이스의 경우, 표 통합 메모리 패러다임 개요를 참조하십시오. CUDA managed memory는 완전히 지원되며 코히어런트하지만, GPU는 시스템 할당 메모리에 액세스할 수 없습니다. 통합 메모리의 프로그래밍 모델과 성능 튜닝은 전체 CUDA 통합 메모리 지원 디바이스에서의 통합 메모리 섹션에 설명된 모델과 대체로 유사하지만, 시스템 할당자를 사용해 메모리를 할당할 수 없다는 중요한 예외가 있습니다. 따라서 다음 하위 섹션 목록은 적용되지 않습니다:

  • 통합 메모리: 심층 예제

  • Atomic 액세스 및 동기화 프리미티브

  • 액세스 카운터 마이그레이션

  • CPU에서 GPU 상주 메모리로의 잦은 쓰기 피하기

  • 시스템 메모리에 대한 비동기 액세스 활용

4.1.3. Windows, WSL 및 Tegra에서의 통합 메모리#

참고

이 섹션은 compute capability가 6.0 미만인 디바이스 또는 Windows 플랫폼, 즉 concurrentManagedAccess 속성이 0으로 설정된 디바이스만을 다룹니다.

compute capability가 6.0 미만인 디바이스 또는 Windows 플랫폼, 즉 concurrentManagedAccess 속성이 0으로 설정된 디바이스는 통합 메모리 패러다임 개요를 참조하십시오. 이러한 디바이스는 다음과 같은 제한과 함께 CUDA managed memory를 지원합니다:

  • 데이터 마이그레이션 및 코히어런시: 필요 시(on-demand) 관리되는 데이터를 GPU로 세밀하게 이동시키는 기능은 지원되지 않습니다. GPU 커널이 런치될 때마다, 메모리 액세스에서 폴트가 발생하는 것을 피하기 위해 일반적으로 모든 managed memory를 GPU 메모리로 전송해야 합니다. 페이지 폴트는 CPU 측에서만 지원됩니다.

  • GPU 메모리 오버서브스크립션: 물리적인 GPU 메모리 크기보다 더 많은 managed memory를 할당할 수 없습니다.

  • 코히어런시 및 동시성: GPU 페이지 폴트 메커니즘이 없기 때문에 GPU 커널이 활성 상태인 동안 CPU가 통합 메모리 할당에 액세스하면 코히어런시를 보장할 수 없어, managed memory에 대한 동시 액세스는 불가능합니다.

4.1.3.1. 멀티-GPU#

compute capability가 6.0 미만인 디바이스 또는 Windows 플랫폼의 시스템에서는, managed 할당이 GPU의 피어-투-피어 기능을 통해 시스템의 모든 GPU에 자동으로 표시됩니다. Managed memory 할당은 cudaMalloc()를 사용해 할당한 비관리(unmanaged) 메모리와 유사하게 동작합니다. 현재 활성 디바이스가 물리적 할당의 홈(home)이지만, 시스템의 다른 GPU들은 PCIe 버스를 통해 감소된 대역폭으로 해당 메모리에 액세스합니다.

Linux에서는, 프로그램이 적극적으로 사용 중인 모든 GPU가 피어-투-피어를 지원하는 한 managed memory는 GPU 메모리에 할당됩니다. 애플리케이션이 어느 시점에 managed 할당이 있는 다른 GPU 중 어떤 것과도 피어-투-피어를 지원하지 않는 GPU를 사용하기 시작하면, 드라이버는 모든 managed 할당을 시스템 메모리로 마이그레이션합니다. 이 경우 모든 GPU가 PCIe 대역폭 제약을 겪게 됩니다.

Windows에서는 피어 매핑을 사용할 수 없는 경우(예: 서로 다른 아키텍처의 GPU 간), 두 GPU가 실제로 프로그램에서 사용되는지 여부와 관계없이 시스템은 자동으로 매핑된 메모리를 사용하도록 폴백(fallback)합니다. 실제로 하나의 GPU만 사용될 예정이라면, 프로그램을 실행하기 전에 CUDA_VISIBLE_DEVICES 환경 변수를 설정해야 합니다. 이는 어떤 GPU가 보이는지를 제한하여 managed memory가 GPU 메모리에 할당될 수 있게 합니다.

또는 Windows에서 사용자는 드라이버가 물리적 저장소로 항상 디바이스 메모리를 사용하도록 강제하기 위해 CUDA_MANAGED_FORCE_DEVICE_ALLOC를 0이 아닌 값으로 설정할 수도 있습니다. 이 환경 변수가 0이 아닌 값으로 설정되면, 해당 프로세스에서 사용되는 모든 디바이스(그중 managed memory를 지원하는 디바이스)는 서로 피어-투-피어 호환이어야 합니다. 오류 ::cudaErrorInvalidDevice는 managed memory를 지원하는 디바이스가 사용되었는데, 그 디바이스가 해당 프로세스에서 이전에 사용된 다른 어떤 managed memory 지원 디바이스와도 피어-투-피어 호환이 아닐 경우 반환됩니다. 이는 해당 디바이스들에서 ::cudaDeviceReset가 호출되었더라도 마찬가지입니다. 이러한 환경 변수는 CUDA 환경 변수에 설명되어 있습니다.

4.1.3.2. 코히어런시 및 동시성#

코히어런시를 보장하기 위해 통합 메모리 프로그래밍 모델은 CPU와 GPU가 동시에 실행되는 동안의 데이터 액세스에 제약을 둡니다. 사실상 GPU는 모든 managed 데이터에 대해 독점적 액세스를 가지며, 특정 커널이 해당 데이터를 적극적으로 사용하고 있는지 여부와 관계없이 어떤 커널 작업이 실행되는 동안에는 CPU가 이에 액세스하는 것이 허용되지 않습니다. 서로 다른 managed memory 할당에 대한 것이라도 CPU/GPU 동시 액세스는 페이지가 CPU에서 액세스 불가로 간주되기 때문에 세그멘테이션 폴트를 유발합니다.

예를 들어, 다음 코드는 GPU 페이지 폴트 기능이 있어 동시 액세스에 대한 모든 제한이 해제되는 compute capability 6.x 디바이스에서는 성공적으로 실행되지만, GPU 프로그램 커널이 여전히 활성 상태인 동안 CPU가 y를 건드리기 때문에 6.x 이전 아키텍처 및 Windows 플랫폼에서는 실패합니다:

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    kernel<<< 1, 1 >>>();
    y = 20;            // Error on GPUs not supporting concurrent access

    cudaDeviceSynchronize();
    return  0;
}

프로그램은 CPU가 y에 액세스하기 전에 GPU와 명시적으로 동기화해야 합니다(해당 GPU 커널이 실제로 y (또는 어떤 managed 데이터도) 건드리는지 여부와 무관):

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    kernel<<< 1, 1 >>>();
    cudaDeviceSynchronize();
    y = 20;            //  Success on GPUs not supporting concurrent access
    return  0;
}

GPU가 작업을 완료함을 논리적으로 보장하는 어떤 함수 호출도 GPU 작업의 완료를 논리적으로 보장하는 데 유효하다는 점에 유의하십시오. 명시적 동기화 섹션을 참조하십시오.

또한 GPU가 활성 상태일 때 cudaMallocManaged() 또는 cuMemAllocManaged()로 메모리를 동적으로 할당하면, 추가 작업이 런치되거나 GPU가 동기화될 때까지 해당 메모리의 동작은 정의되지 않는다는 점에 유의하십시오. 이 시간 동안 CPU에서 메모리에 액세스하려고 하면 세그멘테이션 폴트를 유발할 수도 있고 유발하지 않을 수도 있습니다. 이는 플래그 cudaMemAttachHost 또는 CU_MEM_ATTACH_HOST를 사용해 할당한 메모리에는 적용되지 않습니다.

4.1.3.3. 스트림 연관 통합 메모리#

CUDA 프로그래밍 모델은 프로그램이 커널 런치 간의 의존성과 독립성을 나타내는 메커니즘으로 스트림을 제공합니다. 같은 스트림에 런치된 커널은 연속적으로 실행됨이 보장되며, 서로 다른 스트림에 런치된 커널은 동시에 실행될 수 있습니다. CUDA 스트림 섹션을 참조하십시오.

4.1.3.3.1. 스트림 콜백#

GPU에서 managed 데이터에 액세스하고 있을 가능성이 있는 다른 어떤 스트림도 활성 상태가 아니라면, 스트림 콜백 내에서 CPU가 managed 데이터에 액세스하는 것은 합법입니다. 또한, 어떤 디바이스 작업도 뒤따르지 않는 콜백은 동기화에 사용될 수 있습니다. 예를 들어 콜백 내부에서 조건 변수를 시그널링하는 방식입니다. 그렇지 않으면, CPU 액세스는 콜백(들)의 지속 시간 동안에만 유효합니다. 몇 가지 중요한 유의 사항이 있습니다:

  1. GPU가 활성 상태인 동안에도 CPU가 비-managed 매핑 메모리 데이터에 액세스하는 것은 항상 허용됩니다.

  2. GPU는 managed 데이터를 사용하지 않는 커널이라도 어떤 커널이든 실행 중이면 활성 상태로 간주됩니다. 커널이 데이터를 사용할 수도 있다면, 액세스는 금지됩니다.

  3. managed 메모리에 대한 GPU 간 동시 액세스에는, 비-managed 메모리의 멀티-GPU 액세스에 적용되는 제약 외에는 어떠한 제약도 없습니다.

  4. managed 데이터에 액세스하는 동시 GPU 커널에 대해서는 어떠한 제약도 없습니다.

마지막 항목이 현재 비-managed GPU 메모리의 경우와 마찬가지로 GPU 커널 간 레이스를 허용한다는 점에 유의하십시오. GPU의 관점에서, managed 메모리 함수는 비-managed 메모리와 동일합니다. 다음 코드 예제는 이러한 점들을 설명합니다:

int main() {
    cudaStream_t stream1, stream2;
    cudaStreamCreate(&stream1);
    cudaStreamCreate(&stream2);
    int *non_managed, *managed, *also_managed;
    cudaMallocHost(&non_managed, 4);    // Non-managed, CPU-accessible memory
    cudaMallocManaged(&managed, 4);
    cudaMallocManaged(&also_managed, 4);
    // Point 1: CPU can access non-managed data.
    kernel<<< 1, 1, 0, stream1 >>>(managed);
    *non_managed = 1;
    // Point 2: CPU cannot access any managed data while GPU is busy,
    //          unless concurrentManagedAccess = 1
    // Note we have not yet synchronized, so "kernel" is still active.
    *also_managed = 2;      // Will issue segmentation fault
    // Point 3: Concurrent GPU kernels can access the same data.
    kernel<<< 1, 1, 0, stream2 >>>(managed);
    // Point 4: Multi-GPU concurrent access is also permitted.
    cudaSetDevice(1);
    kernel<<< 1, 1 >>>(managed);
    return  0;
}

4.1.3.3.2. 스트림과 연관된 Managed 메모리는 더 미세한 제어를 가능하게 합니다#

통합 메모리는 CUDA 프로그램이 managed 할당을 CUDA 스트림과 명시적으로 연관시킬 수 있도록 함으로써 스트림 독립성 모델을 기반으로 합니다. 이렇게 하면 프로그래머는 지정된 스트림에 런치되는지 여부에 따라 커널의 데이터 사용을 나타냅니다. 이는 프로그램별 데이터 액세스 패턴에 기반한 동시성 기회를 가능하게 합니다. 이 동작을 제어하는 함수는 다음과 같습니다:

cudaError_t cudaStreamAttachMemAsync(cudaStream_t stream,
                                     void *ptr,
                                     size_t length=0,
                                     unsigned int flags=0);

cudaStreamAttachMemAsync() 함수는 ptr에서 시작하는 길이 length 바이트의 메모리를 지정된 스트림과 연관시킵니다. 이를 통해 다른 스트림이 활성 상태인지와 무관하게, 해당 스트림 내의 모든 작업이 완료된 한 해당 메모리 영역에 대한 CPU 액세스가 가능합니다. 사실상 이는 활성 GPU에 의한 managed 메모리 영역의 독점 소유를 전체 GPU 활동이 아니라 스트림별 활동으로 제한합니다. 가장 중요한 점은, 할당이 특정 스트림과 연관되어 있지 않으면 스트림과 관계없이 실행 중인 모든 커널에 보인다는 것입니다. 이는 cudaMallocManaged() 할당 또는 __managed__ 변수의 기본 가시성이므로, 어떤 커널이든 실행 중일 때 CPU가 데이터를 건드리면 안 된다는 단순 케이스 규칙이 성립합니다.

Note

할당을 특정 스트림과 연관시킴으로써, 프로그램은 해당 스트림에 런치된 커널만 그 데이터를 건드릴 것이라는 보장을 합니다. 통합 메모리 시스템은 오류 검사를 수행하지 않습니다.

Note

더 큰 동시성을 허용하는 것에 더해, cudaStreamAttachMemAsync()의 사용은 통합 메모리 시스템 내에서 지연 시간과 기타 오버헤드에 영향을 줄 수 있는 데이터 전송 최적화를 가능하게 할 수 있습니다.

다음 예제는 y를 호스트 접근성과 명시적으로 연관시켜 CPU에서 항상 액세스할 수 있도록 하는 방법을 보여줍니다. (커널 호출 뒤에 cudaDeviceSynchronize()가 없다는 점에 유의하십시오.) 이제 커널을 실행 중인 GPU의 y에 대한 액세스는 정의되지 않은 결과를 생성합니다.

__device__ __managed__ int x, y=2;
__global__  void  kernel() {
    x = 10;
}
int main() {
    cudaStream_t stream1;
    cudaStreamCreate(&stream1);
    cudaStreamAttachMemAsync(stream1, &y, 0, cudaMemAttachHost);
    cudaDeviceSynchronize();          // Wait for Host attachment to occur.
    kernel<<< 1, 1, 0, stream1 >>>(); // Note: Launches into stream1.
    y = 20;                           // Success – a kernel is running but “y”
                                      // has been associated with no stream.
    return  0;
}

4.1.3.3.3. 멀티스레드 호스트 프로그램에 대한 더 정교한 예제#

cudaStreamAttachMemAsync()의 주요 용도는 CPU 스레드를 사용한 독립적인 태스크 병렬성을 가능하게 하는 것입니다. 일반적으로 이러한 프로그램에서는 CUDA의 NULL 스트림을 사용하면 스레드 간 의존성이 생기므로, CPU 스레드는 자신이 생성하는 모든 작업을 위해 자신의 스트림을 생성합니다. 어떤 GPU 스트림에서든 managed 데이터가 기본적으로 전역 가시성을 갖는다는 점은 멀티스레드 프로그램에서 CPU 스레드 간 상호작용을 피하기 어렵게 만들 수 있습니다. 따라서 함수 cudaStreamAttachMemAsync()를 사용하여 스레드의 managed 할당을 해당 스레드의 고유 스트림과 연관시키며, 이러한 연관은 보통 스레드 수명 동안 변경되지 않습니다. 그러한 프로그램은 데이터 액세스에 통합 메모리를 사용하기 위해 cudaStreamAttachMemAsync() 호출을 한 번만 추가하면 됩니다:

// This function performs some task, in its own , in its own private stream and can be run in parallel
void run_task(int *in, int *out, int length) {
    // Create a stream for us to use.
    cudaStream_t stream;
    cudaStreamCreate(&stream);
    // Allocate some managed data and associate with our stream.
    // Note the use of the host-attach flag to cudaMallocManaged();
    // we then associate the allocation with our stream so that
    // our GPU kernel launches can access it.
    int *data;
    cudaMallocManaged((void **)&data, length, cudaMemAttachHost);
    cudaStreamAttachMemAsync(stream, data);
    cudaStreamSynchronize(stream);
    // Iterate on the data in some way, using both Host & Device.
    for(int i=0; i<N; i++) {
        transform<<< 100, 256, 0, stream >>>(in, data, length);
        cudaStreamSynchronize(stream);
        host_process(data, length);    // CPU uses managed data.
        convert<<< 100, 256, 0, stream >>>(out, data, length);
    }
    cudaStreamSynchronize(stream);
    cudaStreamDestroy(stream);
    cudaFree(data);
}

이 예제에서는 할당-스트림 연관이 한 번만 설정되고, 이후 호스트와 디바이스 모두에서 데이터를 반복적으로 사용합니다. 그 결과, 호스트와 디바이스 사이에서 데이터를 명시적으로 복사하는 경우에 비해 훨씬 더 단순한 코드가 되며, 결과는 동일합니다.

함수 cudaMallocManaged()는 cudaMemAttachHost 플래그를 지정하며, 이는 처음에는 디바이스 측 실행에서 보이지 않는 할당을 생성합니다. (기본 할당은 모든 스트림의 모든 GPU 커널에서 보입니다.) 이는 데이터 할당과, 특정 스트림을 위해 데이터를 획득하는 시점 사이의 구간에서 다른 스레드의 실행과의 우발적 상호작용이 없도록 보장합니다.

이 플래그가 없으면, 다른 스레드가 런치한 커널이 우연히 실행 중인 경우 새 할당은 GPU에서 사용 중인 것으로 간주됩니다. 이는 새로 할당된 데이터를 CPU에서, 개인 스트림에 명시적으로 attach할 수 있게 되기 전까지 액세스하는 스레드의 능력에 영향을 줄 수 있습니다. 따라서 스레드 간 안전한 독립성을 가능하게 하려면, 할당은 이 플래그를 지정하여 만들어야 합니다.

대안으로는 할당이 스트림에 attach된 후 모든 스레드에 걸쳐 프로세스 전체 배리어를 두는 방법이 있습니다. 이는 어떤 커널이든 런치되기 전에 모든 스레드가 데이터/스트림 연관을 완료하도록 보장하여, 위험을 피합니다. 스트림 파괴는 할당이 기본 가시성으로 되돌아가게 하므로, 스트림이 파괴되기 전에도 두 번째 배리어가 필요합니다. cudaMemAttachHost 플래그는 이 과정을 단순화하기 위해서도 존재하며, 또한 필요한 곳에 전역 배리어를 삽입하는 것이 항상 가능한 것은 아니기 때문에 존재합니다.

4.1.3.3.4. 스트림 연관 통합 메모리의 데이터 이동#

스트림 연관 통합 메모리에서의 Memcpy()/Memset()은 concurrentManagedAccess가 설정되어 있지 않은 디바이스에서 다르게 동작하며, 다음 규칙이 적용됩니다:

cudaMemcpyHostTo*가 지정되고 소스 데이터가 통합 메모리이면, 복사 스트림에서 호스트로부터 코히어런트하게 액세스 가능하다면 (1) 호스트에서 액세스됩니다. 그렇지 않으면 디바이스에서 액세스됩니다. 목적지에 대해서도 cudaMemcpy*ToHost가 지정되고 목적지가 통합 메모리인 경우 유사한 규칙이 적용됩니다.

cudaMemcpyDeviceTo*가 지정되고 소스 데이터가 통합 메모리이면, 디바이스에서 액세스됩니다. 소스는 복사 스트림에서 디바이스로부터 코히어런트하게 액세스 가능해야 합니다 (2). 그렇지 않으면 오류가 반환됩니다. 목적지에 대해서도 cudaMemcpy*ToDevice가 지정되고 목적지가 통합 메모리인 경우 유사한 규칙이 적용됩니다.

cudaMemcpyDefault가 지정되면, 통합 메모리는 복사 스트림에서 디바이스로부터 코히어런트하게 액세스할 수 없거나 (2), 또는 데이터의 선호 위치가 cudaCpuDeviceId이고 복사 스트림에서 호스트로부터 코히어런트하게 액세스 가능하다면 (1) 호스트에서 액세스됩니다. 그렇지 않으면 디바이스에서 액세스됩니다.

통합 메모리에서 cudaMemset*()를 사용하는 경우, 데이터는 cudaMemset() 작업에 사용되는 스트림에서 디바이스로부터 코히어런트하게 액세스 가능해야 합니다 (2). 그렇지 않으면 오류가 반환됩니다.

데이터가 cudaMemcpy* 또는 cudaMemset*에 의해 디바이스에서 액세스될 때, 해당 작업의 스트림은 GPU에서 활성 상태로 간주됩니다. 이 시간 동안, 해당 스트림과 연관된 데이터 또는 전역 가시성을 가진 데이터에 대한 모든 CPU 액세스는, GPU가 디바이스 속성 concurrentManagedAccess에 대해 0 값을 가진 경우 세그멘테이션 폴트를 초래합니다. 프로그램은 CPU에서 연관된 데이터를 액세스하기 전에 작업이 완료되었음을 보장하도록 적절히 동기화해야 합니다.

  1. 주어진 스트림에서 호스트로부터 코히어런트하게 액세스 가능하다는 것은, 메모리가 전역 가시성을 갖지 않으며 주어진 스트림과도 연관되어 있지 않다는 것을 의미합니다.

  1. 주어진 스트림에서 디바이스로부터 코히어런트하게 액세스 가능하다는 것은, 메모리가 전역 가시성을 가지거나 주어진 스트림과 연관되어 있다는 것을 의미합니다.

4.1.4. 성능 힌트#

성능 힌트는 프로그래머가 통합 메모리 사용에 대해 CUDA에 더 많은 정보를 제공할 수 있게 합니다. CUDA는 성능 힌트를 사용하여 managed 메모리를 더 효율적으로 관리하고 애플리케이션 성능을 개선합니다. 성능 힌트는 애플리케이션의 정확성에 영향을 주지 않습니다. 성능 힌트는 성능에만 영향을 줍니다.

Note

애플리케이션은 성능을 개선하는 경우에만 통합 메모리 성능 힌트를 사용해야 합니다.

성능 힌트는 CUDA managed 메모리를 포함하여, 어떤 통합 메모리 할당에도 사용할 수 있습니다. CUDA 통합 메모리를 완전히 지원하는 시스템에서는 성능 힌트를 모든 시스템 할당 메모리에 적용할 수 있습니다.

4.1.4.1. 데이터 프리페칭#

cudaMemPrefetchAsync API는 지정된 프로세서에 더 가까이 상주하도록 데이터를 마이그레이션할 수 있는 비동기 스트림-순서(ordered) API입니다. 데이터는 프리페칭되는 동안에도 액세스될 수 있습니다. 마이그레이션은 스트림 내의 이전 모든 작업이 완료될 때까지 시작되지 않으며, 스트림 내의 이후 어떤 작업보다도 먼저 완료됩니다.

cudaError_t cudaMemPrefetchAsync(const void *devPtr,
                                 size_t count,
                                 struct cudaMemLocation location,
                                 unsigned int flags,
                                 cudaStream_t stream=0);

…을 포함하는 메모리 영역 [devPtr, devPtr + count) 대상 디바이스로 마이그레이션될 수 있음 location.id 만약 location.type 인 경우 cudaMemLocationTypeDevice, 또는 CPU인 경우 location.type 인 경우 cudaMemLocationTypeHost, 주어진 환경에서 프리페치 작업이 실행될 때 stream. 자세한 내용은 flags, 현재 CUDA Runtime API 문서.

아래의 간단한 코드 예제를 살펴보십시오:

void test_prefetch_sam(const cudaStream_t& s) {
  // initialize data on CPU
  char *data = (char*)malloc(dataSizeBytes);
  init_data(data, dataSizeBytes);                                     
  cudaMemLocation location = {.type = cudaMemLocationTypeDevice, .id = myGpuId};

  // encourage data to move to GPU before use
  const unsigned int flags = 0;
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);      

  // use data on GPU
  const unsigned num_blocks = (dataSizeBytes + threadsPerBlock - 1) / threadsPerBlock;
  mykernel<<<num_blocks, threadsPerBlock, 0, s>>>(data, dataSizeBytes);  

  // encourage data to move back to CPU
  location = {.type = cudaMemLocationTypeHost};
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);      
  
  cudaStreamSynchronize(s);

  // use data on CPU
  use_data(data, dataSizeBytes);                                      
  free(data);
}

void test_prefetch_managed(const cudaStream_t& s) {
  // initialize data on CPU
  char *data;
  cudaMallocManaged(&data, dataSizeBytes);
  init_data(data, dataSizeBytes);                                     
  cudaMemLocation location = {.type = cudaMemLocationTypeDevice, .id = myGpuId};

  // encourage data to move to GPU before use
  const unsigned int flags = 0;
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);

  // use data on GPU
  const uinsigned num_blocks = (dataSizeBytes + threadsPerBlock - 1) / threadsPerBlock;
  mykernel<<<num_blocks, threadsPerBlock, 0, s>>>(data, dataSizeBytes); 

  // encourage data to move back to CPU
  location = {.type = cudaMemLocationTypeHost};
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s); 

  cudaStreamSynchronize(s);

  // use data on CPU
  use_data(data, dataSizeBytes);
  cudaFree(data);
}

  • cudaMemAdviseSetReadMostly:

    이는 데이터가 대부분 읽히고, 가끔만 쓰일 것임을 의미합니다. 일반적으로, 이 영역에서는 읽기 대역폭과 쓰기 대역폭 간의 트레이드오프가 가능하도록 합니다.

  • cudaMemAdviseSetPreferredLocation:

    이 힌트는 데이터의 선호 위치를 지정된 디바이스의 물리 메모리로 설정합니다. 이 힌트는 시스템이 데이터를 선호 위치에 유지하도록 장려하지만, 이를 보장하지는 않습니다. location.type에 대해 cudaMemLocationTypeHost 값을 전달하면 선호 위치가 CPU 메모리로 설정됩니다. cudaMemPrefetchAsync와 같은 다른 힌트는 이 힌트를 오버라이드하고, 메모리가 선호 위치에서 벗어나 마이그레이션될 수 있도록 허용할 수 있습니다.

void test_advise_sam(cudaStream_t stream) {
  char *dataPtr;
  size_t dataSize = 64 * threadsPerBlock;  // 16 KiB
  
  // Allocate memory using malloc or cudaMallocManaged
  dataPtr = (char*)malloc(dataSize);

  // Set the advice on the memory region
  cudaMemLocation loc = {.type = cudaMemLocationTypeDevice, .id = myGpuId};
  cudaMemAdvise(dataPtr, dataSize, cudaMemAdviseSetReadMostly, loc);

  int outerLoopIter = 0;
  while (outerLoopIter < maxOuterLoopIter) {
    // The data is written by the CPU each outer loop iteration
    init_data(dataPtr, dataSize);

    // The data is made available to all GPUs by prefetching.
    // Prefetching here causes read duplication of data instead
    // of data migration
    cudaMemLocation location;
    location.type = cudaMemLocationTypeDevice;
    for (int device = 0; device < maxDevices; device++) {
      location.id = device;
      const unsigned int flags = 0;
      cudaMemPrefetchAsync(dataPtr, dataSize, location, flags, stream);
    }

    // The kernel only reads this data in the inner loop
    int innerLoopIter = 0;
    while (innerLoopIter < maxInnerLoopIter) {
      mykernel<<<32, threadsPerBlock, 0, stream>>>((const char *)dataPtr, dataSize);
      innerLoopIter++;
    }
    outerLoopIter++;
  }

  free(dataPtr);
}

4.1.4.3. 메모리 폐기#

cudaMemDiscardBatchAsync API는 애플리케이션이 지정된 메모리 범위의 내용이 더 이상 유용하지 않음을 CUDA 런타임에 알릴 수 있게 해줍니다. 통합 메모리 드라이버는 디바이스 메모리 오버서브스크립션을 지원하기 위해 fault-based 마이그레이션 또는 메모리 퇴거로 인해 자동 메모리 전송을 수행합니다. 이러한 자동 메모리 전송은 때때로 중복될 수 있으며, 이는 성능을 심각하게 저하시킵니다. 주소 범위를 ‘discard’로 표시하면 통합 메모리 드라이버에 애플리케이션이 해당 범위의 내용을 소비했으며 다른 할당을 위한 공간을 만들기 위해 프리페치 또는 페이지 퇴거 시 이 데이터를 마이그레이션할 필요가 없음을 알려줍니다. 이후 쓰기 액세스 또는 프리페치 없이 폐기된 페이지를 읽으면 불확정 값이 반환됩니다. 반면, discard 작업 이후의 어떤 새로운 쓰기든 후속 읽기 액세스에서 보이는 것이 보장됩니다. 폐기 중인 주소 범위에 대한 동시 액세스 또는 프리페치는 정의되지 않은 동작을 초래합니다.

cudaError_t cudaMemDiscardBatchAsync(void **dptrs,
                                    size_t *sizes,
                                    size_t count,
                                    unsigned long long flags,
                                    cudaStream_t stream);

이 함수는 dptrs 및 sizes 배열에 지정된 주소 범위들에 대해 메모리 폐기를 배치로 수행합니다. 두 배열은 count로 지정된 것과 동일한 길이여야 합니다. 각 메모리 범위는 cudaMallocManaged를 통해 할당된 managed 메모리를 참조하거나 __managed__ 변수로 선언된 것이어야 합니다.

cudaMemDiscardAndPrefetchBatchAsync API는 폐기와 프리페치 연산을 모두 결합합니다. cudaMemDiscardAndPrefetchBatchAsync를 호출하는 것은 의미적으로 cudaMemDiscardBatchAsync를 호출한 다음 cudaMemPrefetchBatchAsync를 호출하는 것과 동일하지만, 더 최적입니다. 이는 애플리케이션이 메모리가 대상 위치에 있어야 하지만 메모리의 내용은 필요하지 않을 때 유용합니다.

cudaError_t cudaMemDiscardAndPrefetchBatchAsync(void **dptrs,
                                               size_t *sizes,
                                               size_t count,
                                               struct cudaMemLocation *prefetchLocs,
                                               size_t *prefetchLocIdxs,
                                               size_t numPrefetchLocs,
                                               unsigned long long flags,
                                               cudaStream_t stream);

prefetchLocs 배열은 프리페칭의 목적지를 지정하며, prefetchLocIdxs는 각 프리페치 위치가 어떤 연산에 적용되는지를 나타냅니다. 예를 들어 배치에 10개의 연산이 있고, 처음 6개는 한 위치로 프리페치되어야 하며 나머지 4개는 다른 위치로 프리페치되어야 한다면, numPrefetchLocs는 2가 되고, prefetchLocIdxs는 {0, 6}이 되며, prefetchLocs에는 두 목적지 위치가 포함됩니다.

중요 고려 사항:

  • 폐기된 범위를, 이후의 쓰기 또는 프리페치 없이 읽으면 불확정 값이 반환됩니다.

  • 폐기 연산은 해당 범위에 쓰기를 수행하거나 cudaMemPrefetchAsync를 통해 프리페치함으로써 되돌릴 수 있습니다.

  • 폐기 연산과 동시에 발생하는 모든 읽기, 쓰기 또는 프리페치는 정의되지 않은 동작을 초래합니다.

  • 모든 디바이스는 cudaDevAttrConcurrentManagedAccess에 대해 0이 아닌 값을 가져야 합니다.

4.1.4.4. managed 메모리에서 데이터 사용 속성 쿼리#

프로그램은 다음 API를 사용하여 CUDA managed 메모리에서 cudaMemAdvise 또는 cudaMemPrefetchAsync을 통해 할당된 메모리 범위 속성을 쿼리할 수 있습니다:

cudaMemRangeGetAttribute(void *data,
                         size_t dataSize,
                         enum cudaMemRangeAttribute attribute,
                         const void *devPtr,
                         size_t count);

이 함수는 devPtr에서 시작하고 크기가 count바이트인 메모리 범위의 속성을 쿼리합니다. 메모리 범위는 cudaMallocManaged를 통해 할당된 managed 메모리를 참조하거나 __managed__ 변수로 선언된 것이어야 합니다. 다음 속성들을 쿼리할 수 있습니다:

  • cudaMemRangeAttributeReadMostly: 전체 메모리 범위에 cudaMemAdviseSetReadMostly 속성이 설정되어 있으면 1을, 그렇지 않으면 0을 반환합니다.

  • cudaMemRangeAttributePreferredLocation: 전체 메모리 범위에 대해 해당 프로세서가 선호 위치로 설정되어 있으면 반환 결과는 GPU 디바이스 id 또는 cudaCpuDeviceId가 되며, 그렇지 않으면 cudaInvalidDeviceId가 반환됩니다. 애플리케이션은 이 쿼리 API를 사용하여 managed 포인터의 선호 위치 속성에 따라 CPU 또는 GPU를 통한 스테이징 데이터에 대한 결정을 내릴 수 있습니다. 쿼리 시점의 메모리 범위의 실제 위치는 선호 위치와 다를 수 있다는 점에 유의하십시오.

  • cudaMemRangeAttributeAccessedBy: 해당 메모리 범위에 대해 그 advise가 설정된 디바이스 목록을 반환합니다.

  • cudaMemRangeAttributeLastPrefetchLocation: cudaMemPrefetchAsync를 사용하여 메모리 범위를 명시적으로 프리페치한 마지막 위치를 반환합니다. 이는 단순히 애플리케이션이 메모리 범위를 프리페치하도록 요청한 마지막 위치를 반환할 뿐임에 유의하십시오. 해당 위치로의 프리페치 작업이 완료되었는지, 또는 시작되었는지에 대한 어떤 표시도 제공하지 않습니다.

  • cudaMemRangeAttributePreferredLocationType: 다음 값들로 선호 위치의 위치 타입을 반환합니다:

    • cudaMemLocationTypeDevice: 메모리 범위의 모든 페이지가 선호 위치로 동일한 GPU를 갖는 경우,

    • cudaMemLocationTypeHost: 메모리 범위의 모든 페이지가 선호 위치로 CPU를 갖는 경우,

    • cudaMemLocationTypeHostNuma: 메모리 범위의 모든 페이지가 선호 위치로 동일한 호스트 NUMA 노드 ID를 갖는 경우,

    • cudaMemLocationTypeInvalid: 모든 페이지가 동일한 선호 위치를 갖지 않거나, 일부 페이지는 선호 위치를 전혀 갖지 않는 경우.

  • cudaMemRangeAttributePreferredLocationId: 동일한 주소 범위에 대한 cudaMemRangeAttributePreferredLocationType 쿼리가 cudaMemLocationTypeDevice을 반환하는 경우, 디바이스 ordinal을 반환합니다. 선호 위치 타입이 호스트 NUMA 노드인 경우, 호스트 NUMA 노드 ID를 반환합니다. 그렇지 않으면, id는 무시해야 합니다.

  • cudaMemRangeAttributeLastPrefetchLocationType: 메모리 범위의 모든 페이지가 cudaMemPrefetchAsync을 통해 명시적으로 마지막으로 프리페치된 위치 타입을 반환합니다. 다음 값들이 반환됩니다:

    • cudaMemLocationTypeDevice: 메모리 범위의 모든 페이지가 동일한 GPU로 프리페치된 경우,

    • cudaMemLocationTypeHost: 메모리 범위의 모든 페이지가 CPU로 프리페치된 경우,

    • cudaMemLocationTypeHostNuma: 메모리 범위의 모든 페이지가 동일한 호스트 NUMA 노드 ID로 프리페치된 경우,

    • cudaMemLocationTypeInvalid: 모든 페이지가 동일한 위치로 프리페치되지 않았거나 일부 페이지가 아예 프리페치된 적이 없는 경우.

  • cudaMemRangeAttributeLastPrefetchLocationId: 동일한 주소 범위에 대한 cudaMemRangeAttributeLastPrefetchLocationType 쿼리가 cudaMemLocationTypeDevice을 반환하는 경우, 유효한 디바이스 ordinal이 되며, cudaMemLocationTypeHostNuma을 반환하는 경우 유효한 호스트 NUMA 노드 ID가 됩니다. 그렇지 않으면, id는 무시해야 합니다.

또한 해당하는 cudaMemRangeGetAttributes 함수를 사용하여 여러 속성을 쿼리할 수 있습니다.

4.1.4.5. GPU 메모리 오버서브스크립션#

Unified memory는 애플리케이션이 어떤 개별 프로세서의 메모리든 오버서브스크라이브할 수 있게 합니다: 즉, 시스템의 어떤 개별 프로세서의 메모리 용량보다 더 큰 배열을 할당하고 공유할 수 있으며, 프로그래밍 모델에 큰 복잡성을 추가하지 않으면서도 단일 GPU에 맞지 않는 데이터셋의 아웃-오브-코어 처리 등을 가능하게 합니다.

또한 해당하는 cudaMemRangeGetAttributes 함수를 사용하여 여러 속성을 쿼리할 수 있습니다.
