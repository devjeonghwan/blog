4.20. 드라이버 엔트리 포인트 액세스

4.20.1. 소개#

Driver Entry Point Access APIs는 CUDA 드라이버 함수의 주소를 가져오는 방법을 제공합니다. CUDA 11.3부터 사용자는 이들 API에서 얻은 함수 포인터를 사용하여 사용 가능한 CUDA 드라이버 API를 호출할 수 있습니다.

이들 API는 POSIX 플랫폼의 dlsym 및 Windows의 GetProcAddress와 유사한 기능을 제공합니다. 제공되는 API를 통해 사용자는 다음을 할 수 있습니다:

  • CUDA Driver API.을 사용하여 드라이버 함수의 주소를 가져옵니다.

  • CUDA Runtime API.를 사용하여 드라이버 함수의 주소를 가져옵니다.

  • CUDA 드라이버 함수의 스레드별 기본 스트림(per-thread default stream) 버전을 요청합니다. 자세한 내용은 스레드별 기본 스트림 버전 가져오기를 참조하세요.

  • 오래된 툴킷에서도 더 최신 드라이버를 사용하여 새로운 CUDA 기능에 접근합니다.

4.20.2. 드라이버 함수 typedef#

CUDA Driver API 엔트리 포인트를 가져오는 데 도움이 되도록, CUDA Toolkit은 모든 CUDA 드라이버 API에 대한 함수 포인터 정의를 포함하는 헤더에 대한 액세스를 제공합니다. 이러한 헤더는 CUDA Toolkit과 함께 설치되며, 툴킷의 include/ 디렉터리에서 사용할 수 있습니다. 아래 표는 각 CUDA API 헤더 파일에 대해 typedefs를 포함하는 헤더 파일을 요약합니다.

위 헤더는 실제 함수 포인터 자체를 정의하지 않으며, 함수 포인터에 대한 typedef를 정의합니다. 예를 들어, cudaTypedefs.h에는 드라이버 API cuMemAlloc에 대해 아래 typedef가 있습니다:

typedef CUresult (CUDAAPI *PFN_cuMemAlloc_v3020)(CUdeviceptr_v2 *dptr, size_t bytesize);
typedef CUresult (CUDAAPI *PFN_cuMemAlloc_v2000)(CUdeviceptr_v1 *dptr, unsigned int bytesize);

CUDA 드라이버 심볼은 첫 번째 버전을 제외하고 이름에 _v* 확장자가 포함되는 버전 기반 명명 체계를 갖습니다. 특정 CUDA 드라이버 API의 시그니처 또는 의미(semantics)가 변경되면, 해당 드라이버 심볼의 버전 번호를 증가시킵니다. cuMemAlloc 드라이버 API의 경우, 첫 번째 드라이버 심볼 이름은 cuMemAlloc이고 다음 심볼 이름은 cuMemAlloc_v2입니다. CUDA 2.0 (2000)에서 도입된 첫 번째 버전에 대한 typedef는 PFN_cuMemAlloc_v2000입니다. CUDA 3.2 (3020)에서 도입된 다음 버전에 대한 typedef는 PFN_cuMemAlloc_v3020입니다.

코드에서 적절한 타입의 함수 포인터를 더 쉽게 정의하기 위해 typedefs를 사용할 수 있습니다:

PFN_cuMemAlloc_v3020 pfn_cuMemAlloc_v2;
PFN_cuMemAlloc_v2000 pfn_cuMemAlloc_v1;

위 방법은 사용자가 특정 버전의 API에 관심이 있는 경우에 더 바람직합니다. 또한 헤더에는 설치된 CUDA 툴킷이 릴리스되었을 때 사용 가능했던 모든 드라이버 심볼의 최신 버전에 대해 미리 정의된 매크로가 있으며, 이러한 typedef에는 _v* 접미사가 없습니다. CUDA 11.3 툴킷의 경우 cuMemAlloc_v2이 최신 버전이었으므로, 아래와 같이 해당 함수 포인터를 정의할 수도 있습니다:

PFN_cuMemAlloc pfn_cuMemAlloc;

4.20.3. 드라이버 함수 가져오기#

드라이버 엔트리 포인트 액세스 API와 적절한 typedef를 사용하면, 어떤 CUDA 드라이버 API에 대해서도 함수 포인터를 얻을 수 있습니다.

4.20.3.1. 드라이버 API 사용#

드라이버 API는 요청된 드라이버 심볼에 대해 ABI 호환 버전을 얻기 위해 인자로 CUDA 버전을 요구합니다. CUDA 드라이버 API는 함수별 ABI를 가지며, 이는 다음으로 표시됩니다. _v* 확장자입니다. 예를 들어, 다음의 버전들을 고려해 보겠습니다. cuStreamBeginCapture 및 이에 대응하는 typedefs 에서 cudaTypedefs.h:

// cuda.h
CUresult CUDAAPI cuStreamBeginCapture(CUstream hStream);
CUresult CUDAAPI cuStreamBeginCapture_v2(CUstream hStream, CUstreamCaptureMode mode);

// cudaTypedefs.h
typedef CUresult (CUDAAPI *PFN_cuStreamBeginCapture_v10000)(CUstream hStream);
typedef CUresult (CUDAAPI *PFN_cuStreamBeginCapture_v10010)(CUstream hStream, CUstreamCaptureMode mode);

위 내용에서 typedefs 코드 스니펫에서, 버전 접미사 _v10000 그리고 _v10010 위 API는 각각 CUDA 10.0과 CUDA 10.1에서 도입되었음을 나타냅니다.

#include <cudaTypedefs.h>

// Declare the entry points for cuStreamBeginCapture
PFN_cuStreamBeginCapture_v10000 pfn_cuStreamBeginCapture_v1;
PFN_cuStreamBeginCapture_v10010 pfn_cuStreamBeginCapture_v2;

// Get the function pointer to the cuStreamBeginCapture driver symbol
cuGetProcAddress("cuStreamBeginCapture", &pfn_cuStreamBeginCapture_v1, 10000, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
// Get the function pointer to the cuStreamBeginCapture_v2 driver symbol
cuGetProcAddress("cuStreamBeginCapture", &pfn_cuStreamBeginCapture_v2, 10010, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);

위 코드 스니펫을 참조하면, 다음에 대한 주소를 가져오기 위해 _v1 드라이버 API의 버전 cuStreamBeginCapture, CUDA 버전 인자는 정확히 10.0(10000)이어야 합니다. 마찬가지로, 다음에 대한 주소를 가져오기 위한 CUDA 버전은 _v2 API의 버전은 10.1(10010)이어야 합니다. 드라이버 API의 특정 버전을 가져오기 위해 더 높은 CUDA 버전을 지정하는 것은 항상 이식 가능하지 않을 수 있습니다. 예를 들어, 여기에서 11030을 사용하더라도 여전히 _v2 심볼이지만, 만약 가상의 _v3 버전이 CUDA 11.3에서 릴리스되면, cuGetProcAddress API는 더 새로운 것을 반환하기 시작할 것입니다. _v3 CUDA 11.3 드라이버와 함께 페어링되면 대신 더 새로운 심볼을 반환합니다. ABI 및 함수 시그니처가 _v2 그리고 _v3 심볼이 서로 다를 수 있으므로, 이를 호출하면 _v3 다음을 사용하는 함수 _v10010 다음을 위한 typedef _v2 해당 심볼은 정의되지 않은 동작을 보일 것입니다.

주어진 CUDA Toolkit에 대해 드라이버 API의 최신 버전을 가져오려면, version 인자로 CUDA_VERSION을 지정하고 버전이 없는 typedef를 사용해 함수 포인터를 정의할 수도 있습니다. _v2는 CUDA 11.3에서 드라이버 API cuStreamBeginCapture의 최신 버전이므로, 아래 코드 스니펫은 이를 가져오는 다른 방법을 보여줍니다.

// Assuming we are using CUDA 11.3 Toolkit

#include <cudaTypedefs.h>

// Declare the entry point
PFN_cuStreamBeginCapture pfn_cuStreamBeginCapture_latest;

// Initialize the entry point. Specifying CUDA_VERSION will give the function pointer to the
// cuStreamBeginCapture_v2 symbol since it is latest version on CUDA 11.3.
cuGetProcAddress("cuStreamBeginCapture", &pfn_cuStreamBeginCapture_latest, CUDA_VERSION, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);

유효하지 않은 CUDA 버전으로 드라이버 API를 요청하면 오류 CUDA_ERROR_NOT_FOUND가 반환된다는 점에 유의하십시오. 위 코드 예제에서 10000(CUDA 10.0) 미만의 버전을 전달하는 것은 유효하지 않습니다.

4.20.3.2. 런타임 API 사용#

런타임 API cudaGetDriverEntryPoint는 CUDA 런타임 버전을 사용하여 요청된 드라이버 심볼에 대해 ABI 호환 버전을 가져옵니다. 아래 코드 스니펫에서 필요한 최소 CUDA 런타임 버전은, cuMemAllocAsync가 그때 도입되었으므로 CUDA 11.2입니다.

#include <cudaTypedefs.h>

// Declare the entry point
PFN_cuMemAllocAsync pfn_cuMemAllocAsync;

// Initialize the entry point. Assuming CUDA runtime version >= 11.2
cudaGetDriverEntryPoint("cuMemAllocAsync", &pfn_cuMemAllocAsync, cudaEnableDefault, &driverStatus);

// Call the entry point
if(driverStatus == cudaDriverEntryPointSuccess && pfn_cuMemAllocAsync) {
    pfn_cuMemAllocAsync(...);
}

런타임 API cudaGetDriverEntryPointByVersion는 사용자가 제공한 CUDA 버전을 사용하여 요청된 드라이버 심볼에 대해 ABI 호환 버전을 가져옵니다. 이를 통해 요청된 ABI 버전에 대해 더 구체적으로 제어할 수 있습니다.

4.20.3.3. 스레드별 기본 스트림(per-thread default stream) 버전 가져오기#

일부 CUDA 드라이버 API는 기본 스트림 시맨틱이나 스레드별 기본 스트림(per-thread default stream) 시맨틱으로 구성할 수 있습니다. 스레드별 기본 스트림 시맨틱을 따르는 드라이버 API는 이름에 _ptsz 또는 _ptds 접미사가 붙습니다. 예를 들어 cuLaunchKernel에는 cuLaunchKernel_ptsz라는 스레드별 기본 스트림 변형이 있습니다. 드라이버 엔트리 포인트 액세스 API를 사용하면 사용자는 cuLaunchKernel의 기본 스트림 버전 대신 스레드별 기본 스트림 버전을 요청할 수 있습니다. CUDA 드라이버 API를 기본 스트림 또는 스레드별 기본 스트림 시맨틱으로 구성하면 동기화 동작에 차이가 생깁니다. 자세한 내용은 스트림 동기화 동작 문서를 참조하십시오.

드라이버 API의 기본 스트림 버전이나 스레드별 기본 스트림(per-thread default stream) 버전은 다음 방법 중 하나로 얻을 수 있습니다:

  • 컴파일 플래그 --default-stream per-thread를 사용하거나 매크로 CUDA_API_PER_THREAD_DEFAULT_STREAM를 정의해 스레드별 기본 스트림 동작을 선택합니다.

  • CU_GET_PROC_ADDRESS_LEGACY_STREAM/cudaEnableLegacyStream 또는 CU_GET_PROC_ADDRESS_PER_THREAD_DEFAULT_STREAM/cudaEnablePerThreadDefaultStream 플래그를 사용해 각각 기본 스트림 또는 스레드별 기본 스트림 동작을 강제합니다.

4.20.3.4. 새로운 CUDA 기능에 액세스#

새로운 CUDA 드라이버 기능에 액세스하려면 항상 최신 CUDA 툴킷을 설치하는 것이 권장되지만, 어떤 이유로 사용자가 업데이트를 원하지 않거나 최신 툴킷에 액세스할 수 없는 경우에도, API를 사용하면 업데이트된 CUDA 드라이버만으로 새로운 CUDA 기능에 액세스할 수 있습니다. 논의를 위해, 사용자가 CUDA 11.3을 사용 중이며 CUDA 12.0 드라이버에서 사용 가능한 새로운 드라이버 API cuFoo를 사용하고자 한다고 가정하겠습니다. 아래 코드 스니펫은 이 사용 사례를 보여줍니다:

int main()
{
    // Assuming we have CUDA 12.0 driver installed.

    // Manually define the prototype as cudaTypedefs.h in CUDA 11.3 does not have the cuFoo typedef
    typedef CUresult (CUDAAPI *PFN_cuFoo)(...);
    PFN_cuFoo pfn_cuFoo = NULL;
    CUdriverProcAddressQueryResult driverStatus;

    // Get the address for cuFoo API using cuGetProcAddress. Specify CUDA version as
    // 12000 since cuFoo was introduced then or get the driver version dynamically
    // using cuDriverGetVersion
    int driverVersion;
    cuDriverGetVersion(&driverVersion);
    CUresult status = cuGetProcAddress("cuFoo", &pfn_cuFoo, driverVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);

    if (status == CUDA_SUCCESS && pfn_cuFoo) {
        pfn_cuFoo(...);
    }
    else {
        printf("Cannot retrieve the address to cuFoo - driverStatus = %d. Check if the latest driver for CUDA 12.0 is installed.\n", driverStatus);
        assert(0);
    }

    // rest of code here

}

4.20.4. cuGetProcAddress 사용 시 잠재적 영향#

아래는 cuGetProcAddress 및 cudaGetDriverEntryPoint에서 발생할 수 있는 잠재적 문제에 대한 구체적 및 이론적 예시 모음입니다.

4.20.4.1. cuGetProcAddress와 암시적 링킹(implicit linking)의 영향 비교#

cuDeviceGetUuid CUDA 9.2에서 도입되었습니다. 이 API에는 더 새로운 개정판이 있습니다 (cuDeviceGetUuid_v2) CUDA 11.4에서 도입되었습니다. 마이너 버전 호환성을 유지하기 위해, cuDeviceGetUuid 버전이 상향 조정되지 않습니다: cuDeviceGetUuid_v2 CUDA 12.0까지는 cuda.h에서 그렇지 않습니다. 이는 이를 통해 함수 포인터를 얻어 호출하는 것은 cuGetProcAddress 다른 동작을 할 수도 있습니다. API를 직접 사용하는 예:

#include <cuda.h>

CUuuid uuid;
CUdevice dev;
CUresult status;

status = cuDeviceGet(&dev, 0); // Get device 0
// handle status

status = cuDeviceGetUuid(&uuid, dev) // Get uuid of device 0

이 예에서는 사용자가 CUDA 11.4로 컴파일하고 있다고 가정합니다. 이는 다음의 동작을 수행한다는 점에 유의하십시오. cuDeviceGetUuid, _v2 버전이 아닙니다. 이제 다음을 사용하는 예시를 살펴보겠습니다. cuGetProcAddress:

#include <cudaTypedefs.h>

CUuuid uuid;
CUdevice dev;
CUresult status;
CUdriverProcAddressQueryResult driverStatus;

status = cuDeviceGet(&dev, 0); // Get device 0
// handle status

PFN_cuDeviceGetUuid pfn_cuDeviceGetUuid;
status = cuGetProcAddress("cuDeviceGetUuid", &pfn_cuDeviceGetUuid, CUDA_VERSION, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && pfn_cuDeviceGetUuid) {
    // pfn_cuDeviceGetUuid points to ???
}

이 예에서는 사용자가 CUDA 11.4로 컴파일하고 있다고 가정합니다. 그러면 cuDeviceGetUuid_v2의 함수 포인터를 가져옵니다. 그런 다음 해당 함수 포인터를 호출하면 이전 예에서 보여준 것과 동일한 cuDeviceGetUuid가 아니라, 새로운 _v2 함수가 호출됩니다.

4.20.4.2. cuGetProcAddress에서의 컴파일 타임 vs 런타임 버전 사용#

동일한 문제를 살펴보되, 작은 조정을 하나 해보겠습니다. 마지막 예제는 어떤 함수 포인터를 얻을지 결정하기 위해 CUDA_VERSION의 컴파일 타임 상수를 사용했습니다. 사용자가 cuDriverGetVersion 또는 cudaDriverGetVersion를 사용해 드라이버 버전을 동적으로 질의하고, 이를 cuGetProcAddress에 전달하는 경우에는 더 많은 복잡성이 발생합니다. 예:

#include <cudaTypedefs.h>

CUuuid uuid;
CUdevice dev;
CUresult status;
int cudaVersion;
CUdriverProcAddressQueryResult driverStatus;

status = cuDeviceGet(&dev, 0); // Get device 0
// handle status

status = cuDriverGetVersion(&cudaVersion);
// handle status

PFN_cuDeviceGetUuid pfn_cuDeviceGetUuid;
status = cuGetProcAddress("cuDeviceGetUuid", &pfn_cuDeviceGetUuid, cudaVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && pfn_cuDeviceGetUuid) {
    // pfn_cuDeviceGetUuid points to ???
}

이 예제에서는 사용자가 CUDA 11.3으로 컴파일한다고 가정합니다. 사용자는 cuDeviceGetUuid(_v2 버전이 아님)를 얻는다는 알려진 동작을 바탕으로 이 애플리케이션을 디버그, 테스트 및 배포할 것입니다. CUDA는 마이너 버전 간 ABI 호환성을 보장하므로, 동일한 애플리케이션은 재컴파일 없이 드라이버가 CUDA 11.4로 업그레이드된 후에도(툴킷과 런타임을 업데이트하지 않고도) 실행될 것으로 예상됩니다. 그러나 이는 정의되지 않은 동작(undefined behavior)을 야기할 수 있는데, 이제 PFN_cuDeviceGetUuid에 대한 typedef는 여전히 원래 버전의 시그니처를 갖게 되지만, cudaVersion가 이제 11040(CUDA 11.4)이므로, cuGetProcAddress는 _v2 버전에 대한 함수 포인터를 반환하게 되어, 이를 호출하면 정의되지 않은 동작이 발생할 수 있다는 뜻입니다.

이 경우 원래(_v2 버전이 아님) typedef는 다음과 같습니다:

typedef CUresult (CUDAAPI *PFN_cuDeviceGetUuid_v9020)(CUuuid *uuid, CUdevice_v1 dev);

하지만 _v2 버전 typedef는 다음과 같습니다:

typedef CUresult (CUDAAPI *PFN_cuDeviceGetUuid_v11040)(CUuuid *uuid, CUdevice_v1 dev);

따라서 이 경우 API/ABI는 동일할 것이며 런타임 API 호출은 아마도 문제를 일으키지 않을 것입니다–알 수 없는 uuid 반환 가능성만 존재합니다. API/ABI에 대한 시사점에서 API/ABI 호환성의 더 문제가 되는 사례를 논의합니다.

4.20.4.3. 명시적 버전 확인을 통한 API 버전 증가#

위에서는 구체적인 특정 예를 보였습니다. 이제 예를 들어 드라이버 버전 전반에 걸친 호환성과 관련해 여전히 문제가 있는 이론적인 예를 사용해 보겠습니다. 예:

CUresult cuFoo(int bar); // Introduced in CUDA 11.4
CUresult cuFoo_v2(int bar); // Introduced in CUDA 11.5
CUresult cuFoo_v3(int bar, void* jazz); // Introduced in CUDA 11.6

typedef CUresult (CUDAAPI *PFN_cuFoo_v11040)(int bar);
typedef CUresult (CUDAAPI *PFN_cuFoo_v11050)(int bar);
typedef CUresult (CUDAAPI *PFN_cuFoo_v11060)(int bar, void* jazz);

이 API는 CUDA 11.4에서 처음 만들어진 이후 두 번 수정되었으며, 최신인 CUDA 11.6에서는 함수에 대한 API/ABI 인터페이스도 수정했습니다. CUDA 11.5에 대해 컴파일된 사용자 코드에서의 사용은 다음과 같습니다:

#include <cuda.h>
#include <cudaTypedefs.h>

CUresult status;
int cudaVersion;
CUdriverProcAddressQueryResult driverStatus;

status = cuDriverGetVersion(&cudaVersion);
// handle status

PFN_cuFoo_v11040 pfn_cuFoo_v11040;
PFN_cuFoo_v11050 pfn_cuFoo_v11050;
if(cudaVersion < 11050 ) {
    // We know to get the CUDA 11.4 version
    status = cuGetProcAddress("cuFoo", &pfn_cuFoo_v11040, cudaVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
    // Handle status and validating pfn_cuFoo_v11040
}
else {
    // Assume >= CUDA 11.5 version we can use the second version
    status = cuGetProcAddress("cuFoo", &pfn_cuFoo_v11050, cudaVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
    // Handle status and validating pfn_cuFoo_v11050
}

이 예에서는 CUDA 11.6의 새로운 typedef에 대한 업데이트와, 해당 새로운 typedef 및 case 처리로 애플리케이션을 재컴파일하는 작업이 없으면, 애플리케이션은 cuFoo_v3 함수 포인터를 반환받게 되며 그 함수를 어떤 방식으로든 사용하면 정의되지 않은 동작(undefined behavior)을 초래하게 됩니다. 이 예제의 요점은 cuGetProcAddress에 대한 명시적 버전 검사조차도 CUDA 메이저 릴리스 내의 마이너 버전 증가를 안전하게 포괄하지 못할 수 있음을 설명하는 것이었습니다.

4.20.4.4. 런타임 API 사용 시의 문제#

위 예제들은 드라이버 API에 대한 함수 포인터를 얻기 위한 Driver API 사용의 문제에 초점을 맞췄습니다. 이제 cudaApiGetDriverEntryPoint에 대한 런타임 API 사용 시 잠재적인 문제를 논의하겠습니다.

위와 유사하게 런타임 API를 사용하는 것부터 시작하겠습니다.

#include <cuda.h>
#include <cudaTypedefs.h>
#include <cuda_runtime.h>

CUresult status;
cudaError_t error;
int driverVersion, runtimeVersion;
CUdriverProcAddressQueryResult driverStatus;

// Ask the runtime for the function
PFN_cuDeviceGetUuid pfn_cuDeviceGetUuidRuntime;
error = cudaGetDriverEntryPoint ("cuDeviceGetUuid", &pfn_cuDeviceGetUuidRuntime, cudaEnableDefault, &driverStatus);
if(cudaSuccess == error && pfn_cuDeviceGetUuidRuntime) {
    // pfn_cuDeviceGetUuid points to ???
}

이 예제의 함수 포인터는 어떤 버전의 함수를 얻을지에 대한 제어가 없기 때문에, 위의 드라이버 전용 예제들보다 더 복잡합니다. 항상 현재 CUDA Runtime 버전에 대한 API를 얻게 됩니다. 자세한 내용은 다음 표를 참조하십시오:

위 표에서의 문제는 더 새로운 CUDA 11.4 런타임 및 툴킷과 더 오래된 드라이버(CUDA 11.3) 조합에서 발생하며, 위에서는 v1x로 표시되어 있습니다. 이 조합에서는 드라이버가 이전 함수( _v2가 아닌)에 대한 포인터를 반환하지만, 애플리케이션에서 사용되는 typedef는 새 함수 포인터에 대한 것이 됩니다.

4.20.4.5. 런타임 API 및 동적 버전 관리의 문제#

애플리케이션이 컴파일되는 CUDA 버전, CUDA 런타임 버전, 그리고 애플리케이션이 동적으로 링크하는 CUDA 드라이버 버전의 서로 다른 조합을 고려하면 더 많은 복잡성이 발생합니다.

#include <cuda.h>
#include <cudaTypedefs.h>
#include <cuda_runtime.h>

CUresult status;
cudaError_t error;
int driverVersion, runtimeVersion;
CUdriverProcAddressQueryResult driverStatus;
enum cudaDriverEntryPointQueryResult runtimeStatus;

PFN_cuDeviceGetUuid pfn_cuDeviceGetUuidDriver;
status = cuGetProcAddress("cuDeviceGetUuid", &pfn_cuDeviceGetUuidDriver, CUDA_VERSION, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && pfn_cuDeviceGetUuidDriver) {
    // pfn_cuDeviceGetUuidDriver points to ???
}

// Ask the runtime for the function
PFN_cuDeviceGetUuid pfn_cuDeviceGetUuidRuntime;
error = cudaGetDriverEntryPoint ("cuDeviceGetUuid", &pfn_cuDeviceGetUuidRuntime, cudaEnableDefault, &runtimeStatus);
if(cudaSuccess == error && pfn_cuDeviceGetUuidRuntime) {
    // pfn_cuDeviceGetUuidRuntime points to ???
}

// Ask the driver for the function based on the driver version (obtained via runtime)
error = cudaDriverGetVersion(&driverVersion);
PFN_cuDeviceGetUuid pfn_cuDeviceGetUuidDriverDriverVer;
status = cuGetProcAddress ("cuDeviceGetUuid", &pfn_cuDeviceGetUuidDriverDriverVer, driverVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && pfn_cuDeviceGetUuidDriverDriverVer) {
    // pfn_cuDeviceGetUuidDriverDriverVer points to ???
}

4.20.4.6. CUDA 버전을 허용하는 런타임 API의 문제#

별도로 지정하지 않는 한, CUDA 런타임 API cudaGetDriverEntryPointByVersion는 사용자가 특정 CUDA 드라이버 버전을 요청할 수 있도록 허용하므로 드라이버 엔트리 포인트 cuGetProcAddress와 유사한 함의를 갖습니다.

4.20.4.7. API/ABI에 대한 함의#

위의 cuDeviceGetUuid를 사용하는 예제에서, API 불일치의 함의는 미미하며, _v2가 멀티 인스턴스 GPU(MIG) 모드를 지원하기 위해 추가되었기 때문에 많은 사용자가 이를 완전히 알아차리지 못할 수도 있습니다. 따라서 MIG가 없는 시스템에서는, 사용자가 다른 API를 받고 있다는 사실조차 인지하지 못할 수 있습니다.

더 문제가 되는 것은 다음과 같이 애플리케이션 시그니처(따라서 ABI)가 변경되는 API입니다. cuCtxCreate. CUDA 3.2에서 도입된 _v2 버전은 현재 기본값으로 사용됩니다 cuCtxCreate 사용 시 cuda.h 하지만 이제 CUDA 11.4에서 도입된 더 새로운 버전이 있으며 (cuCtxCreate_v3). API 시그니처도 수정되었으며, 이제 추가 인자를 받습니다. 따라서 위의 일부 경우에서 함수 포인터에 대한 typedef가 반환된 함수 포인터와 일치하지 않으면, 눈에 띄지 않는 ABI 비호환성이 발생하여 정의되지 않은 동작으로 이어질 가능성이 있습니다.

예를 들어, CUDA 11.4 드라이버가 설치된 상태에서 CUDA 11.3 툴킷을 대상으로 컴파일된 다음 코드를 가정해 보겠습니다:

PFN_cuCtxCreate cuUnknown;
CUdriverProcAddressQueryResult driverStatus;

status = cuGetProcAddress("cuCtxCreate", (void**)&cuUnknown, cudaVersion, CU_GET_PROC_ADDRESS_DEFAULT, &driverStatus);
if(CUDA_SUCCESS == status && cuUnknown) {
    status = cuUnknown(&ctx, 0, dev);
}

이 코드를 실행할 때 cudaVersion이 11040 이상(즉, CUDA 11.4를 나타냄)으로 설정되어 있으면, cuCtxCreate_v3 API의 _v3 버전에 필요한 모든 매개변수를 충분히 제공하지 않았기 때문에 정의되지 않은 동작이 발생할 수 있습니다.

4.20.5. cuGetProcAddress 실패 원인 판단#

cuGetProcAddress에는 두 가지 유형의 오류가 있습니다. (1) API/사용 오류와 (2) 요청된 드라이버 API를 찾을 수 없음입니다. 첫 번째 오류 유형은 CUresult 반환 값을 통해 API에서 오류 코드를 반환합니다. 예를 들어, pfn 변수에 NULL을 전달하거나 유효하지 않은 flags를 전달하는 경우가 있습니다.

두 번째 오류 유형은 CUdriverProcAddressQueryResult *symbolStatus에 인코딩되며, 드라이버가 요청된 심볼을 찾을 수 없는 잠재적 문제를 구분하는 데 도움이 될 수 있습니다. 다음 예를 살펴보십시오:

// cuDeviceGetExecAffinitySupport was introduced in release CUDA 11.4
#include <cuda.h>
CUdriverProcAddressQueryResult driverStatus;
cudaVersion = ...;
status = cuGetProcAddress("cuDeviceGetExecAffinitySupport", &pfn, cudaVersion, 0, &driverStatus);
if (CUDA_SUCCESS == status) {
    if (CU_GET_PROC_ADDRESS_VERSION_NOT_SUFFICIENT == driverStatus) {
        printf("We can use the new feature when you upgrade cudaVersion to 11.4, but CUDA driver is good to go!\n");
        // Indicating cudaVersion was < 11.4 but run against a CUDA driver >= 11.4
    }
    else if (CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND == driverStatus) {
        printf("Please update both CUDA driver and cudaVersion to at least 11.4 to use the new feature!\n");
        // Indicating driver is < 11.4 since string not found, doesn't matter what cudaVersion was
    }
    else if (CU_GET_PROC_ADDRESS_SUCCESS == driverStatus && pfn) {
        printf("You're using cudaVersion and CUDA driver >= 11.4, using new feature!\n");
        pfn();
    }
}

첫 번째 경우에서 반환 코드가 CU_GET_PROC_ADDRESS_VERSION_NOT_SUFFICIENT라면, CUDA 드라이버에서 symbol 자체는 찾았지만 제공한 cudaVersion보다 나중 버전에서 추가된 API임을 뜻합니다. 예제에서 cudaVersion를 11030 이하로 지정한 뒤 CUDA 11.4 이상 드라이버에서 실행하면 이 반환 코드가 나옵니다. 이는 cuDeviceGetExecAffinitySupport가 CUDA 11.4(11040)에서 추가되었기 때문입니다.

두 번째 경우에서 반환 코드가 CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND라면, CUDA 드라이버에서 해당 symbol을 찾지 못했다는 뜻입니다. 이는 오래된 드라이버 때문에 해당 CUDA 함수가 아직 지원되지 않는 경우에도 발생할 수 있고, 단순한 오타 때문에도 발생할 수 있습니다. 예를 들어 마지막 예제와 비슷하게 사용자가 symbol에 CUDeviceGetExecAffinitySupport를 넣었다면(문자열이 대문자 CU로 시작함), cuGetProcAddress가 기대하는 문자열과 일치하지 않으므로 API를 찾을 수 없습니다. 또 다른 예로, 개발자는 새 API를 지원하는 CUDA 드라이버를 기준으로 애플리케이션을 개발했지만 실제 배포 대상은 더 오래된 CUDA 드라이버일 수 있습니다. 마지막 예제 기준으로 개발을 CUDA 11.4 이상에서 했더라도, CUDA 11.3 드라이버에서 실행하면 개발 중에는 성공하던 cuGetProcAddress 호출이 더 이상 성공하지 않고 driverStatus에 CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND가 반환됩니다.
