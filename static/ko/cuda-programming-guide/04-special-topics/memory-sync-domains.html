4.14. 메모리 동기화 도메인

4.14.1. 메모리 펜스 간섭#

일부 CUDA 애플리케이션은 CUDA 메모리 일관성 모델에 의해 필요한 것보다 더 많은 트랜잭션을 기다리게 되면서, 메모리 펜스/플러시 작업으로 인해 성능이 저하될 수 있습니다.

__managed__ int x = 0;
__device__  cuda::atomic<int, cuda::thread_scope_device> a(0);
__managed__ cuda::atomic<int, cuda::thread_scope_system> b(0);

스레드 1 (SM)

x = 1;
a = 1;

스레드 2 (SM)

while (a != 1) ;
assert(x == 1);
b = 1;

스레드 3 (CPU)

while (b != 1) ;
assert(x == 1);

위의 예를 고려해 보십시오. CUDA 메모리 일관성 모델은 assert된 조건이 참이 되도록 보장하므로, 스레드 1에서 x에 대한 쓰기는 스레드 2에서 b에 대한 쓰기보다 먼저 스레드 3에 보이는(visible) 상태여야 합니다.

a의 release 및 acquire가 제공하는 메모리 순서는 디바이스 범위(device-scope) 작업이므로, x을 스레드 2에는 보이게 만들기에만 충분하고 스레드 3에는 충분하지 않습니다. 따라서 b의 release 및 acquire가 제공하는 시스템 범위(system-scope) 순서는 스레드 2 자체에서 발행된 쓰기만 스레드 3에 보이도록 보장하는 것이 아니라, 스레드 2에 보이는 다른 스레드들의 쓰기 또한 스레드 3에 보이도록 보장해야 합니다. 이를 누적성(cumulativity)이라고 합니다. GPU는 실행 시점에 어떤 쓰기가 소스 수준에서 보이도록 보장되었는지, 그리고 어떤 쓰기가 우연한 타이밍에 의해서만 보이는지 알 수 없으므로, 비행 중(in-flight) 메모리 작업에 대해 보수적으로 넓은 범위를 대상으로 해야 합니다.

이는 때때로 간섭으로 이어집니다. 즉, GPU가 소스 수준에서 요구되지 않는 메모리 작업까지 기다리기 때문에, 펜스/플러시가 필요 이상으로 오래 걸릴 수 있습니다.

펜스는 예시처럼 인트린식(intrinsics)이나 원자 연산(atomic)으로 코드에서 명시적으로 발생할 수도 있고, 작업 경계(task boundaries)에서 synchronizes-with 관계를 구현하기 위해 암묵적으로 발생할 수도 있습니다.

일반적인 예로, 한 커널이 로컬 GPU 메모리에서 계산을 수행하고, 병렬 커널(예: NCCL)이 피어와의 통신을 수행하는 경우가 있습니다. 완료 시점에 로컬 커널은 다운스트림 작업에 대한 어떤 synchronizes-with 관계라도 만족시키기 위해 자신의 쓰기를 암묵적으로 플러시합니다. 이 과정에서 통신 커널의 더 느린 nvlink 또는 PCIe 쓰기를 전체 또는 부분적으로 불필요하게 기다릴 수 있습니다.

4.14.2. 도메인으로 트래픽 격리#

컴퓨트 기능 9.0(Hopper 아키텍처) GPU 및 CUDA 12.0부터, 메모리 동기화 도메인 기능은 이러한 간섭을 완화하는 방법을 제공합니다. 코드가 명시적으로 보조하는 대가로, GPU는 펜스 작업이 대상으로 삼는 범위를 줄일 수 있습니다. 각 커널 실행에는 도메인 ID가 부여됩니다. 쓰기와 펜스는 이 ID로 태그되며, 펜스는 펜스의 도메인과 일치하는 쓰기만 순서화(order)합니다. 동시 계산 대 통신 예시에서는, 통신 커널을 다른 도메인에 배치할 수 있습니다.

도메인을 사용할 때 코드는 동일 GPU에서 서로 다른 도메인 간의 순서화 또는 동기화에는 시스템 범위(system-scope) 펜싱이 필요하다는 규칙을 준수해야 합니다. 도메인 내에서는 디바이스 범위(device-scope) 펜싱으로도 충분합니다. 이는 한 커널의 쓰기가 다른 도메인의 커널에서 발행된 펜스에 포함되지 않기 때문에, 누적성(cumulativity)을 위해 필요합니다. 본질적으로, 교차 도메인 트래픽이 미리 시스템 범위로 플러시되도록 보장함으로써 누적성이 충족됩니다.

이는 thread_scope_device의 정의를 수정한다는 점에 유의하십시오. 하지만 아래에서 설명하듯 커널은 기본적으로 도메인 0을 사용하므로, 하위 호환성은 유지됩니다.

4.14.3. CUDA에서 도메인 사용#

도메인은 새로운 런치 속성(launch attributes) cudaLaunchAttributeMemSyncDomain 및 cudaLaunchAttributeMemSyncDomainMap을 통해 접근할 수 있습니다. 전자는 논리 도메인(logical domains) cudaLaunchMemSyncDomainDefault 및 cudaLaunchMemSyncDomainRemote 사이에서 선택하며, 후자는 논리 도메인에서 물리 도메인(physical domains)으로의 매핑(mapping)을 제공합니다. 원격 도메인(remote domain)은 원격 메모리 접근을 수행하는 커널이 로컬 커널과 메모리 트래픽을 분리(isolate)할 수 있도록 의도된 것입니다. 다만, 특정 도메인을 선택하더라도 커널이 합법적으로 수행할 수 있는 메모리 접근에는 영향을 주지 않습니다.

도메인 개수는 디바이스 속성(device attribute) cudaDevAttrMemSyncDomainCount을 통해 조회할 수 있습니다. 컴퓨트 기능(Compute Capability) 9.0(Hopper) 디바이스에는 4개의 도메인이 있습니다. 이식 가능한 코드(portable code)를 용이하게 하기 위해, 도메인 기능은 모든 디바이스에서 사용할 수 있으며 CUDA는 컴퓨트 기능 9.0 이전 디바이스에서는 개수를 1로 보고합니다.

논리 도메인을 두면 애플리케이션 구성(composition)이 쉬워집니다. NCCL에서처럼 스택의 낮은 수준에서 이루어지는 개별 커널 런치는 주변 애플리케이션 아키텍처에 대한 고려 없이 의미론적(semantic) 논리 도메인을 선택할 수 있습니다. 더 높은 수준에서는 이 매핑을 사용해 논리 도메인을 조정(steer)할 수 있습니다. 논리 도메인을 설정하지 않은 경우의 기본값은 기본 도메인(default domain)이며, 기본 매핑은 기본 도메인을 0에, 원격 도메인을 1에 매핑하는 것입니다(도메인이 1개보다 많은 GPU에서). 특정 라이브러리는 CUDA 12.0 이상에서 런치에 원격 도메인 태그를 붙일 수 있는데, 예를 들어 NCCL 2.16이 그렇게 합니다. 이를 통해 다른 컴포넌트, 프레임워크 또는 애플리케이션 수준에서 코드 변경 없이도, 일반적인 애플리케이션에 유익한 사용 패턴을 기본 제공(out of the box)합니다. 대체 사용 패턴으로는, 예를 들어 NVSHMEM을 사용하는 애플리케이션이거나 커널 유형이 명확히 분리되지 않은 경우, 병렬 스트림을 분할(partition)하는 방법이 있을 수 있습니다. 스트림 A는 두 논리 도메인을 모두 물리 도메인 0에 매핑하고, 스트림 B는 1에 매핑하는 식으로 계속 이어갈 수 있습니다.

// Example of launching a kernel with the remote logical domain
cudaLaunchAttribute domainAttr;
domainAttr.id = cudaLaunchAttrMemSyncDomain;
domainAttr.val = cudaLaunchMemSyncDomainRemote;
cudaLaunchConfig_t config;
// Fill out other config fields
config.attrs = &domainAttr;
config.numAttrs = 1;
cudaLaunchKernelEx(&config, myKernel, kernelArg1, kernelArg2...);

// Example of setting a mapping for a stream
// (This mapping is the default for streams starting on compute capability 9.0 (Hopper) or later if not
// explicitly set, and provided for illustration)
cudaLaunchAttributeValue mapAttr;
mapAttr.memSyncDomainMap.default_ = 0;
mapAttr.memSyncDomainMap.remote = 1;
cudaStreamSetAttribute(stream, cudaLaunchAttributeMemSyncDomainMap, &mapAttr);

// Example of mapping different streams to different physical domains, ignoring
// logical domain settings
cudaLaunchAttributeValue mapAttr;
mapAttr.memSyncDomainMap.default_ = 0;
mapAttr.memSyncDomainMap.remote = 0;
cudaStreamSetAttribute(streamA, cudaLaunchAttributeMemSyncDomainMap, &mapAttr);
mapAttr.memSyncDomainMap.default_ = 1;
mapAttr.memSyncDomainMap.remote = 1;
cudaStreamSetAttribute(streamB, cudaLaunchAttributeMemSyncDomainMap, &mapAttr);

다른 런치 속성과 마찬가지로, 이는 CUDA 스트림에서, cudaLaunchKernelEx을 사용하는 개별 런치에서, 그리고 CUDA 그래프의 커널 노드(kernel nodes)에서 일관되게(uniformly) 노출됩니다. 일반적인 사용 방식은 앞서 설명한 바와 같이, 스트림 수준에서 매핑을 설정하고 런치 수준에서(또는 스트림 사용의 일부 구간을 감싸는 형태로) 논리 도메인을 설정하는 것입니다.

두 속성 모두 스트림 캡처(stream capture) 중에 그래프 노드로 복사됩니다. 그래프는 두 속성을 노드 자체로부터 가져오며, 이는 본질적으로 물리 도메인을 간접적으로 지정하는 방식입니다. 그래프가 런치되는 스트림에 설정된 도메인 관련 속성은 그래프 실행에서는 사용되지 않습니다.
