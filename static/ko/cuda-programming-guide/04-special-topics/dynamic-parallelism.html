4.18. CUDA 동적 병렬 처리

4.18.1. 소개#

4.18.1.1. 개요#

CUDA 동적 병렬 처리(CUDA Dynamic Parallelism) - 흔히 CDP로 약칭 - 는 GPU에서 실행 중인 코드가 새로운 GPU 작업을 생성할 수 있게 하는 CUDA 프로그래밍 모델의 기능입니다. 즉, GPU에서 이미 실행 중인 디바이스 코드로부터 추가 커널 런치를 통해 새로운 작업을 GPU에 추가할 수 있습니다. 이 기능은 디바이스에서 실행되는 스레드가 런타임에 실행 구성을 결정할 수 있게 해 주므로, 호스트와 디바이스 간 실행 제어 및 데이터 전송의 필요성을 줄일 수 있습니다.

데이터 종속 병렬 작업은 커널에 의해 런타임에 생성될 수 있습니다. CDP가 CUDA에 추가되기 전에는 일부 알고리즘과 프로그래밍 패턴에서 재귀, 불규칙한 루프 구조 또는 평평한 단일 수준의 병렬성에 맞지 않는 기타 구문을 제거하기 위한 수정이 필요했습니다. 이러한 프로그램 구조는 CUDA 동적 병렬 처리를 사용하면 더 자연스럽게 표현할 수 있습니다.

참고

이 섹션은 CUDA 12.0 이상에서 기본값인, 때때로 CDP2라고도 불리는 CUDA 동적 병렬 처리의 업데이트된 버전을 문서화합니다. CDP2는 CC 9.0 이상 디바이스에서 사용할 수 있는 유일한 CUDA 동적 병렬 처리 버전입니다. 개발자는 컴파일러 인수 -DCUDA_FORCE_CDP1_IF_SUPPORTED를 사용하여 CC 9.0 미만 디바이스에 대해 레거시 CUDA 동적 병렬 처리인 CDP1을 계속 선택(opt in)할 수 있습니다. CDP1 문서는 CUDA 프로그래밍 가이드의 레거시 버전에서 찾을 수 있습니다. CDP1은 향후 CUDA 버전에서 제거될 예정입니다.

4.18.2. 실행 환경#

CUDA 동적 병렬 처리는 GPU 스레드가 새 그리드를 구성, 실행, 그리고 암묵적으로 동기화할 수 있게 합니다. 그리드는 커널 실행의 인스턴스로, 스레드 블록의 구체적인 형태와 스레드 블록 그리드를 포함합니다. 커널 함수 자체와 그 커널의 구체적 호출, 즉 그리드 간의 구분은 다음 섹션에서 주목해야 할 중요한 사항입니다.

4.18.2.1. 부모 및 자식 그리드#

새 그리드를 구성하고 실행하는 디바이스 스레드는 부모 그리드에 속합니다. 해당 호출에 의해 생성되는 새 그리드를 자식 그리드라고 합니다.

자식 그리드의 호출과 완료는 올바르게 중첩됩니다. 즉, 부모 그리드는 자신의 스레드가 생성한 모든 자식 그리드가 완료될 때까지 완료된 것으로 간주되지 않으며, 런타임은 부모와 자식 사이의 암묵적 동기화를 보장합니다.

4.18.2.2. CUDA 프리미티브의 범위#

CUDA 동적 병렬 처리는 CUDA Device Runtime에 의존하며, 이는 CUDA 런타임 API와 구문적으로 유사하지만 디바이스 코드에서 사용 가능한 제한된 API 집합을 호출할 수 있게 합니다. 디바이스 런타임 API의 동작은 호스트 대응 항목과 유사하지만, 몇 가지 차이점이 있습니다. 이러한 차이점은 API Reference 섹션의 표에 정리되어 있습니다.

호스트와 디바이스 모두에서 CUDA 런타임은 커널을 실행(launch)하고 스트림과 이벤트를 통해 실행 간의 종속성을 추적하기 위한 API를 제공합니다. 디바이스에서는 실행된 커널과 CUDA 객체가 호출하는 그리드의 모든 스레드에 보입니다. 이는 예를 들어, 한 스레드에서 스트림을 생성하고 같은 그리드의 다른 어떤 스레드에서도 이를 사용할 수 있음을 의미합니다. 그러나 디바이스 API 호출로 생성된 스트림 및 이벤트와 같은 CUDA 객체는 생성된 그리드 내에서만 유효합니다.

4.18.2.3. 스트림과 이벤트#

CUDA 스트림과 이벤트는 커널 실행 간의 종속성을 제어할 수 있게 합니다. 동일한 스트림으로 실행된 커널은 순서대로 실행되며, 이벤트는 스트림 간 종속성을 생성하는 데 사용할 수 있습니다. 디바이스에서 생성된 스트림과 이벤트도 정확히 동일한 목적을 수행합니다.

그리드 내에서 생성된 스트림과 이벤트는 그리드 범위 내에 존재하지만, 생성된 그리드 밖에서 사용될 경우 동작이 정의되지 않습니다. 위에서 설명했듯이 그리드가 실행한 모든 작업은 그리드가 종료될 때 암시적으로 동기화됩니다. 스트림으로 실행된 작업도 여기에 포함되며, 모든 종속성이 적절히 해소됩니다. 그리드 범위 밖에서 수정된 스트림에 대한 연산의 동작은 정의되지 않습니다.

호스트에서 생성된 스트림과 이벤트는 어떤 커널 내에서 사용될 때 동작이 정의되지 않으며, 이는 부모 그리드에서 생성된 스트림과 이벤트가 자식 그리드 내에서 사용될 때 동작이 정의되지 않는 것과 같습니다.

4.18.2.4. 순서 및 동시성#

디바이스 런타임에서의 커널 실행 순서는 CUDA 스트림 순서 지정 의미론을 따릅니다. 하나의 그리드 내에서 동일한 스트림으로 실행된 모든 커널( The Fire-and-Forget Stream 제외)은 순서대로 실행됩니다. 동일한 그리드의 여러 스레드가 동일한 스트림으로 실행을 수행하는 경우, 스트림 내 순서는 그리드 내의 스레드 스케줄링에 따라 달라지며, 이는 __syncthreads()과 같은 동기화 프리미티브로 제어할 수 있습니다.

명명된 스트림은 그리드 내의 모든 스레드가 공유하지만, 암시적 NULL 스트림은 스레드 블록 내의 모든 스레드만 공유한다는 점에 유의하십시오. 스레드 블록 내 여러 스레드가 암시적 스트림으로 실행을 수행하면, 이러한 실행은 순서대로 실행됩니다. 서로 다른 스레드 블록의 스레드가 암시적 스트림으로 실행을 수행하면, 이러한 실행은 동시에 실행될 수 있습니다. 스레드 블록 내 여러 스레드에서의 실행에 대해 동시성이 필요하다면, 명시적인 명명 스트림을 사용해야 합니다.

디바이스 런타임은 CUDA 실행 모델 내에서 새로운 동시성 보장을 도입하지 않습니다. 즉, 디바이스에서 서로 다른 어떤 수의 스레드 블록 사이에도 동시 실행이 보장되지 않습니다.

동시성 보장 부재는 부모 그리드와 그 자식 그리드에도 확장됩니다. 부모 그리드가 자식 그리드를 실행하면, 스트림 종속성이 만족되고 하드웨어 자원을 사용할 수 있으면 자식은 실행을 시작할 수 있지만, 부모 그리드가 암시적 동기화 지점에 도달할 때까지 실행 시작이 보장되지는 않습니다.

동시성은 디바이스 구성, 애플리케이션 작업 부하, 런타임 스케줄링에 따라 달라질 수 있습니다. 따라서 서로 다른 스레드 블록 간의 어떤 동시성에도 의존하는 것은 안전하지 않습니다.

4.18.3. 메모리 일관성(Coherence) 및 정합성(Consistency)#

부모 및 자식 그리드는 동일한 전역 및 상수 메모리 저장소를 공유하지만, 로컬 및 공유 메모리는 서로 구분됩니다. 다음 표는 어떤 메모리 공간이 동일한 포인터를 통해 부모와 자식이 접근할 수 있는지를 보여줍니다. 자식 그리드는 부모 그리드의 로컬 또는 공유 메모리에 절대로 접근할 수 없으며, 부모 그리드도 자식 그리드의 로컬 또는 공유 메모리에 접근할 수 없습니다.

4.18.3.1. 전역 메모리#

부모 및 자식 그리드는 전역 메모리에 대해 일관된(coherent) 접근을 가지며, 자식과 부모 사이에는 약한 정합성 보장이 있습니다. 자식 그리드의 메모리 관점이 부모 스레드와 완전히 정합적인 시점은 자식 그리드 실행이 부모에 의해 호출되는 시점 단 하나뿐입니다.

자식 그리드가 호출되기 전에 부모 스레드에서 수행된 모든 전역 메모리 연산은 자식 그리드에서 볼 수 있습니다. cudaDeviceSynchronize()가 제거됨에 따라, 이제 부모 그리드에서 자식 그리드의 스레드들이 수행한 수정 사항에 접근하는 것은 더 이상 불가능합니다. 부모 그리드가 종료되기 전에 자식 그리드 스레드가 수행한 수정에 접근할 수 있는 유일한 방법은 cudaStreamTailLaunch 스트림으로 실행된 커널을 통해서입니다.

다음 예에서, child_launch를 실행하는 자식 그리드는 자식 그리드 실행 이전에 수행된 data에 대한 수정만을 보는 것이 보장됩니다. 부모의 스레드 0이 실행을 수행하므로, 자식은 부모의 스레드 0이 본 메모리와 정합적입니다. 첫 번째 __syncthreads() 호출로 인해, 자식은 data[0]=0, data[1]=1, …, data[255]=255를 보게 됩니다(__syncthreads() 호출이 없었다면, 자식이 본다는 것이 보장되는 것은 data[0]=0뿐입니다). 자식 그리드는 암시적 동기화에서만 반환되는 것이 보장됩니다. 이는 자식 그리드 스레드가 수행한 수정이 부모 그리드에서 사용 가능해진다는 보장이 전혀 없음을 의미합니다. child_launch가 수행한 수정에 접근하기 위해, tail_launch 커널이 cudaStreamTailLaunch 스트림으로 실행됩니다.

__global__ void tail_launch(int *data) {
   data[threadIdx.x] = data[threadIdx.x]+1;
}

__global__ void child_launch(int *data) {
   data[threadIdx.x] = data[threadIdx.x]+1;
}

__global__ void parent_launch(int *data) {
   data[threadIdx.x] = threadIdx.x;

   __syncthreads();

   if (threadIdx.x == 0) {
       child_launch<<< 1, 256 >>>(data);
       tail_launch<<< 1, 256, 0, cudaStreamTailLaunch >>>(data);
   }
}

void host_launch(int *data) {
    parent_launch<<< 1, 256 >>>(data);
}

4.18.3.2. 매핑된 메모리#

매핑된 시스템 메모리는 전역 메모리와 동일한 일관성 및 정합성 보장을 가지며, 위에서 상세히 설명한 의미론을 따릅니다. 커널은 매핑된 메모리를 할당하거나 해제할 수 없지만, 호스트 프로그램에서 전달된 매핑된 메모리에 대한 포인터는 사용할 수 있습니다.

4.18.3.3. 공유 및 로컬 메모리#

공유 메모리와 로컬 메모리는 각각 스레드 블록 또는 스레드에 전용이며, 부모와 자식 사이에서 보이거나 일관되지 않습니다. 이러한 위치 중 하나에 있는 객체가 자신이 속한 범위 밖에서 참조될 때 동작은 정의되지 않으며, 오류를 유발할 수 있습니다.

NVIDIA 컴파일러는 로컬 또는 공유 메모리에 대한 포인터가 커널 실행 인수로 전달되고 있음을 감지할 수 있다면 경고를 시도합니다. 런타임에서 프로그래머는 __isGlobal() 내장(intrinsic)을 사용하여 포인터가 전역 메모리를 참조하는지 여부를 판단하고, 따라서 자식 실행에 안전하게 전달할 수 있는지 확인할 수 있습니다.

cudaMemcpy*Async() 또는 cudaMemset*Async() 호출은 스트림 의미론을 보존하기 위해 디바이스에서 새로운 자식 커널을 호출할 수 있습니다. 따라서 이러한 API에 공유 또는 로컬 메모리 포인터를 전달하는 것은 불법이며 오류를 반환합니다.

4.18.3.4. 로컬 메모리#

로컬 메모리는 실행 중인 스레드를 위한 전용 저장소이며, 해당 스레드 밖에서는 보이지 않습니다. 자식 커널을 실행할 때 로컬 메모리에 대한 포인터를 실행 인수로 전달하는 것은 불법입니다. 자식 그리드에서 이러한 로컬 메모리 포인터를 역참조한 결과는 정의되지 않습니다.

예를 들어, 다음은 불법이며, x_array이(가) child_launch에 의해 접근될 경우 동작이 정의되지 않습니다:

int x_array[10];       // Creates x_array in parent's local memory
child_launch<<< 1, 1 >>>(x_array);

프로그래머가 컴파일러에 의해 변수가 로컬 메모리에 배치되는 시점을 인지하기는 때때로 어렵습니다. 일반적인 규칙으로, 자식 커널에 전달되는 모든 저장소는 전역 메모리 힙에서 명시적으로 할당되어야 하며, cudaMalloc(), new()을 사용하거나 전역 범위에서 __device__ 저장소를 선언하여야 합니다. 예를 들어:

// Correct - "value" is global storage
__device__ int value;
__device__ void x() {
    value = 5;
    child<<< 1, 1 >>>(&value);
}

// Invalid - "value" is local storage
__device__ void y() {
    int value = 5;
    child<<< 1, 1 >>>(&value);
}

4.18.3.4.1. 텍스처 메모리#

텍스처가 매핑되는 전역 메모리 영역에 대한 쓰기 작업은 텍스처 액세스에 대해 비일관적(incoherent)입니다. 텍스처 메모리에 대한 일관성(Coherence)은 자식 그리드 호출 시점과 자식 그리드가 완료될 때 강제됩니다. 이는 자식 커널 실행(launch) 이전의 메모리 쓰기 작업이 자식의 텍스처 메모리 액세스에 반영된다는 것을 의미합니다. 위의 전역 메모리와 유사하게, 자식에 의한 메모리 쓰기 작업이 부모의 텍스처 메모리 액세스에 반영된다는 것은 결코 보장되지 않습니다. 부모 그리드가 종료되기 전에 자식 그리드의 스레드가 수행한 수정 사항에 접근하는 유일한 방법은 cudaStreamTailLaunch 스트림으로 실행된 커널을 통해서입니다. 부모와 자식의 동시 액세스는 일관되지 않은 데이터를 초래할 수 있습니다.

4.18.4. 프로그래밍 인터페이스#

4.18.4.1. 기본 사항#

다음 예제는 동적 병렬성을 포함하는 간단한 Hello World 프로그램을 보여줍니다:

#include <stdio.h>

__global__ void childKernel()
{
    printf("Hello ");
}

__global__ void tailKernel()
{
    printf("World!\n");
}

__global__ void parentKernel()
{
    // launch child
    childKernel<<<1,1>>>();
    if (cudaSuccess != cudaGetLastError()) {
        return;
    }

    // launch tail into cudaStreamTailLaunch stream
    // implicitly synchronizes: waits for child to complete
    tailKernel<<<1,1,0,cudaStreamTailLaunch>>>();

}

int main(int argc, char *argv[])
{
    // launch parent
    parentKernel<<<1,1>>>();
    if (cudaSuccess != cudaGetLastError()) {
        return 1;
    }

    // wait for parent to complete
    if (cudaSuccess != cudaDeviceSynchronize()) {
        return 2;
    }

    return 0;
}

이 프로그램은 다음과 같이 명령줄에서 단일 단계로 빌드할 수 있습니다:

$ nvcc -arch=sm_75 -rdc=true hello_world.cu -o hello -lcudadevrt

4.18.4.2. CDP를 위한 C++ 언어 인터페이스#

동적 병렬성을 위해 CUDA C++를 사용하는 CUDA 커널에서 사용할 수 있는 언어 인터페이스와 API는 CUDA Device Runtime이라고 합니다.

가능한 경우, 호스트 또는 디바이스 환경 중 어느 쪽에서든 실행될 수 있는 루틴에 대해 코드 재사용을 쉽게 하기 위해 CUDA Runtime API의 구문과 의미론(semantics)을 유지했습니다.

CUDA C++의 모든 코드와 마찬가지로, 여기에서 개요로 제시된 API와 코드는 스레드별(per-thread) 코드입니다. 이는 각 스레드가 다음에 어떤 커널 또는 연산을 실행할지에 대해 고유하고 동적인 결정을 내릴 수 있게 합니다. 제공된 디바이스 런타임 API를 실행하기 위해 블록 내 스레드 간에 동기화 요구 사항은 없으며, 이는 교착 상태(deadlock) 없이 임의로 발산(divergent)하는 커널 코드에서 디바이스 런타임 API 함수들을 호출할 수 있게 합니다.

4.18.4.2.1. 디바이스 측 커널 실행(launch)#

표준 CUDA <<< >>> 구문을 사용하여 디바이스에서 커널을 실행할 수 있습니다:

kernel_name<<< Dg, Db, Ns, S >>>([kernel arguments]);

  • Dg은(는) dim3 타입이며 그리드의 차원과 크기를 지정합니다

  • Db은(는) dim3 타입이며 각 스레드 블록의 차원과 크기를 지정합니다

  • Ns은(는) size_t 타입이며 정적으로 할당된 메모리에 더해, 이 호출에 대해 스레드 블록당 동적으로 할당되는 공유 메모리의 바이트 수를 지정합니다. Ns은(는) 기본값이 0인 선택적 인수입니다.

  • S은(는) cudaStream_t 타입이며 이 호출과 연관된 스트림을 지정합니다. 스트림은 호출이 수행되는 동일한 그리드에서 할당되어야 합니다. S은(는) 기본값이 NULL 스트림인 선택적 인수입니다.

4.18.4.2.1.1. 실행은 비동기입니다#

호스트 측 실행과 동일하게, 모든 디바이스 측 커널 실행은 실행을 수행하는 스레드에 대해 비동기입니다. 즉, <<<>>> 실행 명령은 즉시 반환되며, 실행 스레드는 암시적 실행-동기화 지점(예: cudaStreamTailLaunch 스트림(The Tail Launch Stream)으로 실행된 커널)까지 계속 실행됩니다. 자식 그리드는 실행 이후 어느 시점에서든 실행을 시작할 수 있지만, 실행 스레드가 암시적 실행-동기화 지점에 도달할 때까지 실행을 시작한다는 보장은 없습니다.

호스트 측 실행과 유사하게, 별도의 스트림으로 실행된 작업은 동시에 실행될 수 있지만 실제 동시성은 보장되지 않습니다. 자식 커널 간의 동시성에 의존하는 프로그램은 CUDA 프로그래밍 모델에서 지원되지 않으며 정의되지 않은 동작을 하게 됩니다.

4.18.4.2.1.2. 실행 환경 구성#

모든 전역 디바이스 구성 설정(예: cudaDeviceGetCacheConfig()에서 반환되는 공유 메모리 및 L1 캐시 크기, 그리고 cudaDeviceGetLimit()에서 반환되는 디바이스 제한)은 부모로부터 상속됩니다. 마찬가지로, 스택 크기와 같은 디바이스 제한은 구성된 상태 그대로 유지됩니다.

호스트에서 실행된 커널의 경우, 호스트에서 설정한 커널별(per-kernel) 구성이 전역 설정보다 우선합니다. 이러한 구성은 커널이 디바이스에서 실행될 때에도 사용됩니다. 디바이스에서 커널의 환경을 재구성하는 것은 불가능합니다.

4.18.4.2.2. 이벤트#

CUDA 이벤트의 스트림 간 동기화 기능만 지원됩니다. 이는 cudaStreamWaitEvent()은(는) 지원되지만, cudaEventSynchronize(), cudaEventElapsedTime(), 그리고 cudaEventQuery()은(는) 지원되지 않는다는 것을 의미합니다. cudaEventElapsedTime()이(가) 지원되지 않으므로, cudaEvents는 cudaEventCreateWithFlags()를 통해 생성해야 하며, 이때 cudaEventDisableTiming 플래그를 전달해야 합니다.

스트림과 마찬가지로, 이벤트 객체는 이를 생성한 그리드 내의 모든 스레드 간에 공유될 수 있지만 해당 그리드에 로컬이며 다른 커널로 전달될 수 없습니다. 이벤트 핸들은 그리드 간에 고유함이 보장되지 않으므로, 생성하지 않은 그리드에서 이벤트 핸들을 사용하면 정의되지 않은 동작이 발생합니다.

4.18.4.2.3. 동기화#

호출 스레드가 다른 스레드에서 호출된 자식 그리드와 동기화하도록 의도된 경우, 예를 들어 CUDA Event를 통해 충분한 스레드 간 동기화를 수행하는 것은 프로그램의 책임입니다.

부모 스레드에서 자식 작업을 명시적으로 동기화하는 것은 불가능하므로, 자식 그리드에서 발생하는 변경 사항이 부모 그리드 내 스레드에 보임을 보장할 방법은 없습니다.

4.18.4.2.4. 디바이스 관리#

커널이 실행 중인 디바이스만 해당 커널에서 제어할 수 있습니다. 이는 cudaSetDevice()와 같은 디바이스 API가 디바이스 런타임에서 지원되지 않음을 의미합니다. GPU에서 보이는 활성 디바이스(cudaGetDevice()에서 반환됨)는 호스트 시스템에서 보이는 것과 동일한 디바이스 번호를 갖습니다. cudaDeviceGetAttribute() 호출은 이 API가 호출의 매개변수로 디바이스 ID를 지정할 수 있게 하므로 다른 디바이스에 대한 정보를 요청할 수 있습니다. 범용(catch-all) cudaGetDeviceProperties() API는 디바이스 런타임에서 제공되지 않으며, 속성은 개별적으로 조회해야 합니다.

4.18.5. 프로그래밍 가이드라인#

4.18.5.1. 성능#

4.18.5.1.1. 동적 병렬성 활성 커널 오버헤드#

동적 실행을 제어할 때 활성화되는 시스템 소프트웨어는, 해당 커널이 자체적으로 커널 실행을 호출하는지 여부와 관계없이, 그 시점에 실행 중인 모든 커널에 오버헤드를 부과할 수 있습니다. 이 오버헤드는 디바이스 런타임의 실행 추적 및 관리 소프트웨어에서 발생하며 성능 저하를 초래할 수 있습니다. 이 오버헤드는 일반적으로 디바이스 런타임 라이브러리에 링크하는 애플리케이션에서 발생합니다.

4.18.5.2. 구현 제약 및 제한 사항#

동적 병렬성은 이 문서에 설명된 모든 의미론을 보장하지만, 특정 하드웨어 및 소프트웨어 리소스는 구현에 종속적이며 디바이스 런타임을 사용하는 프로그램의 규모, 성능 및 기타 속성을 제한합니다.

4.18.5.2.1. 런타임#

4.18.5.2.1.1. 메모리 풋프린트#

디바이스 런타임 시스템 소프트웨어는 다양한 관리 목적을 위해 메모리를 예약하며, 특히 대기 중인 그리드 실행을 추적하기 위한 예약이 있습니다. 특정 실행 제한과 맞바꾸는 대신 이 예약의 크기를 줄이기 위한 구성 제어가 제공됩니다. 자세한 내용은 아래의 Configuration Options를 참조하십시오.

4.18.5.2.1.2. 대기 중인 커널 실행#

커널이 실행(launch)되면, 연관된 모든 구성 및 파라미터 데이터가 커널이 완료될 때까지 추적됩니다. 이 데이터는 시스템에서 관리하는 실행(launch) 풀 내에 저장됩니다.

고정 크기 실행(launch) 풀의 크기는 호스트에서 cudaDeviceSetLimit()를 호출하고 cudaLimitDevRuntimePendingLaunchCount를 지정하여 구성할 수 있습니다.

4.18.5.3. 호환성 및 상호운용성#

CDP2가 기본값입니다. 함수는 compute capability 9.0 미만의 디바이스에서 CDP2 사용을 옵트아웃(opt-out)하기 위해 -DCUDA_FORCE_CDP1_IF_SUPPORTED로 컴파일할 수 있습니다.

CUDA 12.0 이상으로 컴파일된 함수(기본값)

CUDA 12.0 이전으로 컴파일된 함수 또는 CUDA 12.0 이상이지만 -DCUDA_FORCE_CDP1_IF_SUPPORTED가 지정된 상태로 컴파일된 함수

컴파일

디바이스 코드가 cudaDeviceSynchronize를 참조하면 컴파일 오류가 발생합니다.

코드가 cudaStreamTailLaunch 또는 cudaStreamFireAndForget를 참조하면 컴파일 오류가 발생합니다. 디바이스 코드가 cudaDeviceSynchronize를 참조하고 코드가 sm_90 또는 그 이후 대상으로 컴파일되면 컴파일 오류가 발생합니다.

Compute capability < 9.0

새 인터페이스가 사용됩니다.

레거시 인터페이스가 사용됩니다.

Compute capability 9.0 이상

새 인터페이스가 사용됩니다.

새 인터페이스가 사용됩니다. 함수가 디바이스 코드에서 cudaDeviceSynchronize를 참조하는 경우, 함수 로드는 cudaErrorSymbolNotFound를 반환합니다(이는 코드가 compute capability 9.0 미만 디바이스용으로 컴파일되었지만, JIT를 사용하여 compute capability 9.0 이상 디바이스에서 실행되는 경우 발생할 수 있습니다).

CDP1과 CDP2를 사용하는 함수는 동일한 컨텍스트에서 동시에 로드되어 실행될 수 있습니다. CDP1 함수는 CDP1 전용 기능(예: cudaDeviceSynchronize)을 사용할 수 있고, CDP2 함수는 CDP2 전용 기능(예: tail launch 및 fire-and-forget launch)을 사용할 수 있습니다.

CDP1을 사용하는 함수는 CDP2를 사용하는 함수를 실행(launch)할 수 없으며, 그 반대도 마찬가지입니다. CDP1을 사용할 함수가 호출 그래프에 CDP2를 사용할 함수가 포함되어 있거나(또는 그 반대의 경우), 함수 로드 중에 cudaErrorCdpVersionMismatch가 발생합니다.

레거시 CDP1의 동작은 이 문서에 포함되어 있지 않습니다. CDP1에 대한 정보는 CUDA Programming Guide의 레거시 버전을 참조하십시오.

4.18.6. PTX에서의 디바이스 측 실행(launch)#

이전 섹션에서는 동적 병렬성을 달성하기 위해 CUDA Device Runtime을 사용하는 방법을 논의했습니다. 동적 병렬성은 PTX에서도 수행할 수 있습니다. Parallel Thread Execution(PTX)을 대상으로 하고 자신의 언어에서 Dynamic Parallelism을 지원할 계획인 프로그래밍 언어 및 컴파일러 구현자를 위해, 이 섹션에서는 PTX 수준에서 커널 실행을 지원하는 것과 관련된 저수준 세부 사항을 제공합니다.

4.18.6.1. 커널 실행 API#

디바이스 측 커널 실행은 PTX에서 접근 가능한 다음 두 API를 사용하여 구현할 수 있습니다: cudaLaunchDevice() 및 cudaGetParameterBuffer(). cudaLaunchDevice()는 cudaGetParameterBuffer()를 호출하여 얻고 실행될 커널에 대한 파라미터로 채운 파라미터 버퍼와 함께 지정된 커널을 실행(launch)합니다. 실행될 커널이 어떤 파라미터도 받지 않는 경우 파라미터 버퍼는 NULL일 수 있으며, 즉 cudaGetParameterBuffer()를 호출할 필요가 없습니다.

4.18.6.1.1. cudaLaunchDevice#

PTX 수준에서, cudaLaunchDevice()는 사용되기 전에 아래에 표시된 두 가지 형태 중 하나로 선언되어야 합니다.

// PTX-level Declaration of cudaLaunchDevice() when .address_size is 64
.extern .func(.param .b32 func_retval0) cudaLaunchDevice
(
  .param .b64 func,
  .param .b64 parameterBuffer,
  .param .align 4 .b8 gridDimension[12],
  .param .align 4 .b8 blockDimension[12],
  .param .b32 sharedMemSize,
  .param .b64 stream
)
;

아래의 CUDA 수준 선언은 앞서 언급한 PTX 수준 선언 중 하나로 매핑되며, 시스템 헤더 파일 cuda_device_runtime_api.h에서 찾을 수 있습니다. 이 함수는 cudadevrt 시스템 라이브러리에 정의되어 있으며, 디바이스 측 커널 실행 기능을 사용하려면 프로그램과 링크되어야 합니다.

// CUDA-level declaration of cudaLaunchDevice()
extern "C" __device__
cudaError_t cudaLaunchDevice(void *func, void *parameterBuffer,
                             dim3 gridDimension, dim3 blockDimension,
                             unsigned int sharedMemSize,
                             cudaStream_t stream);

첫 번째 파라미터는 실행(launch)될 커널에 대한 포인터이고, 두 번째 파라미터는 실행될 커널에 대한 실제 파라미터를 담는 파라미터 버퍼입니다. 파라미터 버퍼의 레이아웃은 아래의 파라미터 버퍼 레이아웃에서 설명합니다. 다른 파라미터는 실행 구성, 즉 그리드 차원, 블록 차원, 공유 메모리 크기, 그리고 실행과 연관된 스트림을 지정합니다(실행 구성에 대한 자세한 설명은 Kernel Configuration을 참조하십시오.

4.18.6.1.2. cudaGetParameterBuffer#

cudaGetParameterBuffer()는 사용되기 전에 PTX 수준에서 선언되어야 합니다. PTX 수준 선언은 주소 크기에 따라 아래에 주어진 두 형태 중 하나여야 합니다:

// PTX-level Declaration of cudaGetParameterBuffer() when .address_size is 64
.extern .func(.param .b64 func_retval0) cudaGetParameterBuffer
(
  .param .b64 alignment,
  .param .b64 size
)
;

다음의 CUDA 수준 cudaGetParameterBuffer() 선언은 앞서 언급한 PTX 수준 선언으로 매핑됩니다:

// CUDA-level Declaration of cudaGetParameterBuffer()
extern "C" __device__
void *cudaGetParameterBuffer(size_t alignment, size_t size);

첫 번째 파라미터는 파라미터 버퍼의 정렬 요구 사항을 지정하고, 두 번째 파라미터는 바이트 단위의 크기 요구 사항을 지정합니다. 현재 구현에서는 cudaGetParameterBuffer()가 반환하는 파라미터 버퍼는 항상 64-바이트 정렬이 보장되며, 정렬 요구 사항 파라미터는 무시됩니다. 그러나 향후 이식성을 보장하기 위해, 파라미터 버퍼에 배치될 어떤 파라미터의 정렬 중 가장 큰 값인 올바른 정렬 요구 사항 값을 cudaGetParameterBuffer()에 전달하는 것이 권장됩니다.

4.18.6.2. 파라미터 버퍼 레이아웃#

파라미터 버퍼에서의 파라미터 재정렬은 금지되며, 파라미터 버퍼에 배치되는 각 개별 파라미터는 정렬되어야 합니다. 즉, 각 파라미터는 파라미터 버퍼의 nth 바이트에 배치되어야 하며, 여기서 n은 선행 파라미터가 차지하는 마지막 바이트의 오프셋보다 큰, 파라미터 크기의 가장 작은 배수입니다. 파라미터 버퍼의 최대 크기는 4KB입니다.

CUDA 컴파일러가 생성하는 PTX 코드에 대한 더 자세한 설명은 PTX-3.5 사양을 참조하십시오.
