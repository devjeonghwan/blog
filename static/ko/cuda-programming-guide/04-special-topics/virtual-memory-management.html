4.16. 가상 메모리 관리

CUDA 프로그래밍 모델에서 메모리 할당 호출(예: cudaMalloc())은 GPU 메모리의 메모리 주소를 반환합니다. 이 주소는 어떤 CUDA API와도 함께 사용하거나, 디바이스 커널 내부에서 사용할 수 있습니다. 개발자는 cudaEnablePeerAccess를 사용하여 해당 메모리 할당에 대해 피어 디바이스 액세스를 활성화할 수 있습니다. 이렇게 하면 서로 다른 디바이스의 커널이 동일한 데이터에 액세스할 수 있습니다. 하지만 과거 및 향후의 모든 사용자 할당도 대상 피어 디바이스에 매핑됩니다. 이로 인해 사용자가 의도치 않게 모든 cudaMalloc 할당을 피어 디바이스에 매핑하는 런타임 비용을 지불하게 될 수 있습니다. 대부분의 상황에서 애플리케이션은 다른 디바이스와 단 몇 개의 할당만 공유하여 통신합니다. 일반적으로 모든 할당을 모든 디바이스에 매핑할 필요는 없습니다. 또한 이 접근 방식을 멀티 노드 설정으로 확장하는 것은 본질적으로 어렵습니다.

CUDA는 개발자에게 이 프로세스에 대한 명시적이고 저수준의 제어를 제공하기 위해 가상 메모리 관리 (VMM) API를 제공합니다.

운영 체제와 메모리 관리 장치(MMU)가 관리하는 복잡한 프로세스인 가상 메모리 할당은 두 가지 핵심 단계로 작동합니다. 먼저 OS는 어떤 물리 메모리도 할당하지 않은 채 프로그램을 위해 연속된 범위의 가상 주소를 예약합니다. 그런 다음 프로그램이 해당 메모리를 처음 사용하려고 시도할 때, OS는 필요에 따라 가상 페이지에 물리 저장소를 할당하여 가상 주소를 커밋합니다.

CUDA의 VMM API는 개발자가 가상 주소 범위를 명시적으로 예약한 다음 나중에 이를 물리 GPU 메모리에 매핑할 수 있도록 함으로써 GPU 메모리 관리에 유사한 개념을 도입합니다. VMM을 사용하면 애플리케이션이 특정 할당을 다른 디바이스에서 액세스 가능하도록 구체적으로 선택할 수 있습니다.

VMM API를 사용하면 복잡한 애플리케이션이 여러 GPU(및 CPU 코어)에 걸쳐 메모리를 더 효율적으로 관리할 수 있습니다. 메모리 예약, 매핑, 액세스 권한에 대한 수동 제어를 가능하게 함으로써 VMM API는 세밀한 데이터 공유, 제로-카피 전송, 사용자 정의 메모리 할당자 같은 고급 기법을 지원합니다. CUDA VMM API는 애플리케이션에서 GPU 메모리를 관리하기 위한 세밀한 제어를 사용자에게 노출합니다.

개발자는 다음과 같은 몇 가지 핵심 방식으로 VMM API의 이점을 얻을 수 있습니다:

  • 가상 및 물리 메모리 관리에 대한 세밀한 제어로, 비연속적인 물리 메모리 청크를 연속적인 가상 주소 공간에 할당하고 매핑할 수 있습니다. 이는 GPU 메모리 단편화를 줄이고 메모리 활용도를 개선하는 데 도움이 되며, 특히 딥 뉴럴 네트워크 학습과 같은 대규모 워크로드에서 유용합니다.

  • 가상 주소 공간 예약을 물리 메모리 할당과 분리하여 효율적인 메모리 할당 및 할당 해제를 수행합니다. 개발자는 큰 가상 메모리 영역을 예약하고, 값비싼 메모리 복사나 재할당 없이 필요 시 물리 메모리를 온디맨드로 매핑할 수 있어, 동적 데이터 구조와 가변 크기 메모리 할당에서 성능이 향상됩니다.

  • CPU 메모리 관리에서 realloc 또는 std::vector가 동작하는 방식과 유사하게, 모든 데이터를 복사하고 재할당할 필요 없이 GPU 메모리 할당을 동적으로 확장할 수 있는 기능. 이는 더 유연하고 효율적인 GPU 메모리 사용 패턴을 지원합니다.

  • 정교한 메모리 할당자 및 캐시 관리 시스템(예: 대규모 언어 모델에서 키-값 캐시를 동적으로 관리하여 처리량과 지연 시간을 개선)을 구축할 수 있는 저수준 API를 제공함으로써 개발자 생산성과 애플리케이션 성능을 향상합니다.

  • CUDA VMM API는 여러 GPU 간의 효율적인 메모리 공유와 액세스를 가능하게 하므로, 분산 멀티 GPU 설정에서 매우 가치가 큽니다. 가상 주소를 물리 메모리에서 분리함으로써, 이 API는 데이터를 서로 다른 GPU에 동적으로 매핑할 수 있는 통합 가상 주소 공간을 개발자가 만들 수 있게 합니다. 이는 메모리 사용을 최적화하고 데이터 전송 오버헤드를 줄입니다. 예를 들어 NCCL 같은 NVIDIA 라이브러리와 NVShmem은 VMM을 적극적으로 사용합니다.

요약하면, CUDA VMM API는 기존의 malloc 유사 추상화를 넘어, 고성능 및 대용량 메모리 애플리케이션에 중요한, 미세 조정된 효율적이고 유연하며 확장 가능한 GPU 메모리 관리를 위한 고급 도구를 개발자에게 제공합니다

참고

이 섹션에서 설명하는 API 모음은 UVA를 지원하는 시스템이 필요합니다. Virtual Memory Management APIs를 참조하세요.

4.16.1. 사전 사항#

4.16.1.1. 정의#

패브릭 메모리: 패브릭 메모리는 NVIDIA의 NVLink 및 NVSwitch 같은 고속 인터커넥트 패브릭을 통해 접근 가능한 메모리를 의미합니다. 이 패브릭은 여러 GPU 또는 노드 사이에 메모리 코히어런스와 고대역폭 통신 계층을 제공하여, 개별 디바이스에 고립되어 붙어 있는 것이 아니라 통합 패브릭에 연결된 것처럼 메모리를 효율적으로 공유할 수 있게 합니다.

CUDA 12.4 이후에는 VMM 할당 핸들 타입 CU_MEM_HANDLE_TYPE_FABRIC이 있습니다. 지원되는 플랫폼에서 NVIDIA IMEX 데몬이 실행 중이면, 이 할당 핸들 타입은 MPI 같은 어떤 통신 메커니즘으로든 노드 내(intra-node) 공유뿐 아니라 노드 간(inter-node) 공유도 가능하게 합니다. 이를 통해 멀티 노드 NVLink 시스템의 GPU는 서로 다른 노드에 있더라도 같은 NVLink 패브릭의 일부인 다른 모든 GPU의 메모리를 매핑할 수 있습니다.

메모리 핸들: VMM에서 핸들은 물리 메모리 할당을 나타내는 불투명(opaque) 식별자입니다. 이 핸들은 저수준 CUDA VMM API에서 메모리를 관리하는 핵심 요소입니다. 핸들은 가상 주소 공간에 매핑할 수 있는 물리 메모리 객체에 대해 유연한 제어를 가능하게 합니다. 핸들은 물리 메모리 할당을 고유하게 식별합니다. 핸들은 직접 포인터를 노출하지 않으면서 메모리 리소스에 대한 추상 참조로 동작합니다. 핸들은 프로세스 또는 디바이스 간 메모리 내보내기(export) 및 가져오기(import) 같은 연산을 가능하게 하여 메모리 공유와 가상화를 촉진합니다.

IMEX 채널: IMEX라는 이름은 internode memory exchange를 뜻하며, 서로 다른 노드 간 GPU-대-GPU 통신을 위한 NVIDIA 솔루션의 일부입니다. IMEX 채널은 IMEX 도메인 내에서 멀티 사용자 또는 멀티 노드 환경에서 사용자 기반 메모리 격리를 제공하는 GPU 드라이버 기능입니다. IMEX 채널은 보안 및 격리 메커니즘으로 동작합니다.

IMEX 채널은 패브릭 핸들과 직접적으로 연관되어 있으며 멀티 노드 GPU 통신에서 활성화되어야 합니다. GPU가 메모리를 할당하고 다른 노드의 GPU가 이에 접근할 수 있게 하려면, 먼저 그 메모리에 대한 핸들을 export해야 합니다. IMEX 채널은 이 export 과정에서 올바른 채널 접근 권한을 가진 원격 프로세스만 import할 수 있는 보안 패브릭 핸들을 생성하는 데 사용됩니다.

유니캐스트 메모리 액세스: VMM API 문맥에서 유니캐스트 메모리 액세스는 특정 디바이스 또는 프로세스가 고유한 가상 주소 범위에 물리 메모리를 제어된 방식으로 직접 매핑하고 접근하는 것을 의미합니다. 여러 디바이스로 접근을 브로드캐스트하는 대신, 유니캐스트 메모리 액세스는 특정 GPU 디바이스에 물리 메모리 할당에 매핑되는 예약된 가상 주소 범위에 대한 명시적 읽기/쓰기 권한을 부여한다는 뜻입니다.

멀티캐스트 메모리 액세스: VMM API 문맥에서 멀티캐스트 메모리 액세스는 단일 물리 메모리 할당 또는 영역을 멀티캐스트 메커니즘을 사용해 여러 디바이스의 가상 주소 공간에 동시에 매핑할 수 있는 기능을 의미합니다. 이를 통해 여러 GPU에 걸쳐 1:N 방식으로 데이터를 효율적으로 공유할 수 있어 중복 데이터 전송을 줄이고 통신 효율을 향상합니다. NVIDIA의 CUDA VMM API는 여러 디바이스의 물리 메모리 할당을 함께 바인딩하는 멀티캐스트 객체 생성을 지원합니다.

4.16.1.2. 지원 여부 조회#

애플리케이션은 기능을 사용하기 전에 지원 여부를 조회해야 합니다. 가용성은 GPU 아키텍처, 드라이버 버전, 그리고 사용 중인 특정 소프트웨어 라이브러리에 따라 달라질 수 있기 때문입니다. 다음 섹션에서는 필요한 지원을 프로그래밍 방식으로 확인하는 방법을 자세히 설명합니다.

VMM 지원 VMM API를 사용하려고 시도하기 전에, 애플리케이션은 사용하려는 디바이스가 CUDA 가상 메모리 관리를 지원하는지 확인해야 합니다. 다음 코드 샘플은 VMM 지원을 조회하는 방법을 보여줍니다:

int deviceSupportsVmm;
CUresult result = cuDeviceGetAttribute(&deviceSupportsVmm, CU_DEVICE_ATTRIBUTE_VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED, device);
if (deviceSupportsVmm != 0) {
    // `device` supports Virtual Memory Management
}

패브릭 메모리 지원: 패브릭 메모리를 사용하려고 시도하기 전에, 애플리케이션은 사용하려는 디바이스가 패브릭 메모리를 지원하는지 확인해야 합니다. 다음 코드 샘플은 패브릭 메모리 지원을 조회하는 방법을 보여줍니다:

int deviceSupportsFabricMem;
CUresult result = cuDeviceGetAttribute(&deviceSupportsFabricMem, CU_DEVICE_ATTRIBUTE_HANDLE_TYPE_FABRIC_SUPPORTED, device);
if (deviceSupportsFabricMem != 0) {
    // `device` supports Fabric Memory
}

핸들 타입으로 CU_MEM_HANDLE_TYPE_FABRIC을 사용하고, 프로세스 간 통신을 위해 공유 가능한 핸들을 교환할 때 OS 네이티브 메커니즘을 요구하지 않는다는 점을 제외하면, 패브릭 메모리를 사용하는 것은 다른 할당 핸들 타입을 사용하는 것과 차이가 없습니다.

IMEX 채널 지원 IMEX 도메인 내에서 IMEX 채널은 멀티 사용자 환경에서 안전한 메모리 공유를 가능하게 합니다. NVIDIA 드라이버는 문자 디바이스 nvidia-caps-imex-channels를 생성함으로써 이를 구현합니다. 패브릭 핸들 기반 공유를 사용하려면 사용자는 두 가지를 확인해야 합니다:

  • 첫째, 애플리케이션은 이 디바이스가 /proc/devices 아래에 존재하는지 확인해야 합니다:

# cat /proc/devices | grep nvidia
195 nvidia
195 nvidiactl
234 nvidia-caps-imex-channels
509 nvidia-nvswitch

The nvidia-caps-imex-channels device should have a major number (e.g., 234).

4.16.2. API 개요#

VMM API는 개발자에게 가상 메모리 관리에 대한 세밀한 제어를 제공합니다. VMM은 매우 저수준 API이므로, CUDA Driver API를 직접 사용해야 합니다. 이 다목적 API는 단일 노드 및 멀티 노드 환경 모두에서 사용할 수 있습니다.

VMM을 효과적으로 사용하려면, 개발자는 메모리 관리의 몇 가지 핵심 개념을 확실히 이해해야 합니다: - 페이지와 주소 공간을 다루는 방식 등 운영체제의 가상 메모리 기본 원리에 대한 지식 - 메모리 계층 및 하드웨어 특성에 대한 이해 - 소켓 또는 메시지 패싱 같은 프로세스 간 통신(IPC) 방법에 대한 친숙함, - 메모리 접근 권한에 대한 보안의 기초 지식

VMM API 워크플로는 메모리 관리를 위한 일련의 단계로 구성되며, 서로 다른 디바이스 또는 프로세스 간 메모리 공유에 핵심 초점을 둡니다. 초기에 개발자는 소스 디바이스에서 물리 메모리를 할당해야 합니다. 공유를 용이하게 하기 위해 VMM API는 핸들을 사용해 필요한 정보를 대상 디바이스 또는 프로세스로 전달합니다. 사용자는 공유를 위해 핸들을 export해야 하며, 이는 OS별 핸들이거나 패브릭별 핸들일 수 있습니다. OS별 핸들은 단일 노드에서의 프로세스 간 통신으로 제한되는 반면, 패브릭별 핸들은 더 높은 범용성을 제공하며 단일 노드 및 멀티 노드 환경 모두에서 사용할 수 있습니다. 패브릭별 핸들을 사용하려면 IMEX 채널을 활성화해야 한다는 점이 중요합니다.

핸들을 export한 뒤에는, 개발자가 선택한 방법에 따라 프로세스 간 통신 프로토콜을 사용해 수신 프로세스(들)와 공유해야 합니다. 수신 프로세스는 이후 VMM API를 사용해 핸들을 import합니다. 핸들이 성공적으로 export되고, 공유되고, import된 후, 소스 및 대상 프로세스 모두는 할당된 물리 메모리가 매핑될 가상 주소 공간을 예약해야 합니다. 마지막 단계는 각 디바이스에 대한 메모리 접근 권한을 설정하여 올바른 권한이 구성되었는지 보장하는 것입니다. 핸들 접근 방식 두 가지를 포함한 이 전체 과정은 동반된 그림에서 더 자세히 설명합니다.

4.16.3. 유니캐스트 메모리 공유#

GPU 메모리 공유는 여러 GPU가 있는 한 대의 머신에서 발생할 수도 있고, 머신 네트워크 전반에 걸쳐 발생할 수도 있습니다. 이 과정은 다음 단계를 따릅니다:

  • 할당 및 내보내기: 한 GPU에서 실행되는 CUDA 프로그램이 메모리를 할당하고, 이에 대한 공유 가능한 핸들을 얻습니다.

  • 공유 및 가져오기: 그런 다음 IPC, MPI 또는 NCCL 등을 사용해 노드의 다른 프로그램으로 핸들을 전송합니다. 수신 GPU에서는 CUDA 드라이버가 핸들을 import하고 필요한 메모리 객체를 생성합니다

  • 예약 및 매핑: 드라이버가 프로그램의 가상 주소(VA)에서 GPU의 물리 주소(PA)를 거쳐 네트워크 패브릭 주소(FA)로의 매핑을 생성합니다.

  • 접근 권한: 할당에 대한 접근 권한을 설정합니다.

  • 메모리 해제: 프로그램 실행이 끝나면 모든 할당을 해제합니다.

4.16.3.1. 할당 및 내보내기#

물리 메모리 할당 가상 메모리 관리 API를 사용한 메모리 할당의 첫 번째 단계는 할당을 위한 백킹(backing)을 제공할 물리 메모리 청크를 생성하는 것입니다. 물리 메모리를 할당하려면 애플리케이션은 cuMemCreate API를 사용해야 합니다. 이 함수로 생성된 할당에는 어떤 디바이스 또는 호스트 매핑도 없습니다. 함수 인자 CUmemGenericAllocationHandle는 할당의 위치, 다른 프로세스(또는 그래픽 API)로 공유할지 여부, 또는 할당할 메모리의 물리 속성 같은, 할당할 메모리의 속성을 설명합니다. 사용자는 요청한 할당의 크기가 적절한 그래뉼러리티(granularity)에 정렬(aligned)되었는지 반드시 확인해야 합니다. 정보 할당의 그래뉼러리티 요구 사항에 관한 정보는 cuMemGetAllocationGranularity을 사용해 쿼리할 수 있습니다.

CUmemGenericAllocationHandle allocatePhysicalMemory(int device, size_t size) {
    CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;
    CUmemAllocationProp prop = {};
    prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
    prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    prop.location.id = device;
    prop.requestedHandleType = handleType;

    size_t granularity = 0;
    cuMemGetAllocationGranularity(&granularity, &prop, CU_MEM_ALLOC_GRANULARITY_MINIMUM);

    // Ensure size matches granularity requirements for the allocation
    size_t padded_size = ROUND_UP(size, granularity);

    // Allocate physical memory
    CUmemGenericAllocationHandle allocHandle;
    cuMemCreate(&allocHandle, padded_size, &prop, 0);

    return allocHandle;
}

CUmemGenericAllocationHandle allocatePhysicalMemory(int device, size_t size) {
    CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_FABRIC;
    CUmemAllocationProp prop = {};
    prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
    prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    prop.location.id = device;
    prop.requestedHandleType = handleType;

    size_t granularity = 0;
    cuMemGetAllocationGranularity(&granularity, &prop, CU_MEM_ALLOC_GRANULARITY_MINIMUM);

    // Ensure size matches granularity requirements for the allocation
    size_t padded_size = ROUND_UP(size, granularity);

    // Allocate physical memory
    CUmemGenericAllocationHandle allocHandle;
    cuMemCreate(&allocHandle, padded_size, &prop, 0);

    return allocHandle;
}

참고

참고

메모리 핸들 내보내기 CUDA 가상 메모리 관리 API는 핸들을 사용해 할당과 물리 주소 공간에 대한 필요한 정보를 교환하는, 프로세스 간 통신을 위한 새로운 메커니즘을 노출합니다. OS-특정 IPC 또는 패브릭-특정 IPC에 대한 핸들을 내보낼 수 있습니다. OS-특정 IPC 핸들은 단일 노드 설정에서만 사용할 수 있습니다. 패브릭-특정 핸들은 단일 또는 멀티 노드 설정에서 사용할 수 있습니다.

4.16.3.2. 공유 및 가져오기#

메모리 핸들 공유 핸들이 내보내진(exported) 후에는, 프로세스 간 통신 프로토콜을 사용해 수신 프로세스 또는 프로세스들과 공유되어야 합니다. 개발자는 핸들을 공유하는 어떤 방법이든 자유롭게 사용할 수 있습니다. 사용되는 구체적인 IPC 방법은 애플리케이션의 설계와 환경에 따라 달라집니다. 일반적인 방법으로는 OS-특정 프로세스 간 소켓과 분산 메시지 패싱이 있습니다. OS-특정 IPC를 사용하면 고성능 전송을 제공하지만, 동일한 머신의 프로세스로 제한되며 이식성이 없습니다. 패브릭-특정 IPC는 더 단순하고 더 이식성이 좋습니다. 하지만 패브릭-특정 IPC에는 시스템 수준의 지원이 필요합니다. 선택한 방법은 핸들 데이터를 대상 프로세스로 안전하고 신뢰성 있게 전송해야 하며, 대상 프로세스가 이를 사용해 메모리를 import하고 유효한 매핑을 설정할 수 있어야 합니다. IPC 방법을 선택할 수 있는 유연성은 VMM API가 단일 노드 애플리케이션부터 분산 멀티 노드 설정까지, 광범위한 시스템 아키텍처에 통합될 수 있게 합니다. 다음 코드 스니펫에서는 소켓 프로그래밍과 MPI를 모두 사용해 핸들을 공유하고 수신하는 예제를 제공하겠습니다.

int ipcSendShareableHandle(int socket, int fd, pid_t process) {
    struct msghdr msg;
    struct iovec iov[1];

    union {
        struct cmsghdr cm;
        char* control;
    } control_un;

    size_t sizeof_control = CMSG_SPACE(sizeof(int)) * sizeof(char);
    control_un.control = (char*) malloc(sizeof_control);

    struct cmsghdr *cmptr;
    ssize_t readResult;
    struct sockaddr_un cliaddr;
    socklen_t len = sizeof(cliaddr);

    // Construct client address to send this SHareable handle to
    memset(&cliaddr, 0, sizeof(cliaddr));
    cliaddr.sun_family = AF_UNIX;
    char temp[20];
    sprintf(temp, "%s%u", "/tmp/", process);
    strcpy(cliaddr.sun_path, temp);
    len = sizeof(cliaddr);

    // Send corresponding shareable handle to the client
    int sendfd = fd;

    msg.msg_control = control_un.control;
    msg.msg_controllen = sizeof_control;

    cmptr = CMSG_FIRSTHDR(&msg);
    cmptr->cmsg_len = CMSG_LEN(sizeof(int));
    cmptr->cmsg_level = SOL_SOCKET;
    cmptr->cmsg_type = SCM_RIGHTS;

    memmove(CMSG_DATA(cmptr), &sendfd, sizeof(sendfd));

    msg.msg_name = (void *)&cliaddr;
    msg.msg_namelen = sizeof(struct sockaddr_un);

    iov[0].iov_base = (void *)"";
    iov[0].iov_len = 1;
    msg.msg_iov = iov;
    msg.msg_iovlen = 1;

    ssize_t sendResult = sendmsg(socket, &msg, 0);
    if (sendResult <= 0) {
        perror("IPC failure: Sending data over socket failed");
        free(control_un.control);
        return -1;
    }

    free(control_un.control);
    return 0;
}

int ipcRecvShareableHandle(int socket, int* fd) {
    struct msghdr msg = {0};
    struct iovec iov[1];
    struct cmsghdr cm;

    // Union to guarantee alignment requirements for control array
    union {
        struct cmsghdr cm;
        // This will not work on QNX as QNX CMSG_SPACE calls __cmsg_alignbytes
        // And __cmsg_alignbytes is a runtime function instead of compile-time macros
        // char control[CMSG_SPACE(sizeof(int))]
        char* control;
    } control_un;

    size_t sizeof_control = CMSG_SPACE(sizeof(int)) * sizeof(char);
    control_un.control = (char*) malloc(sizeof_control);
    struct cmsghdr *cmptr;
    ssize_t n;
    int receivedfd;
    char dummy_buffer[1];
    ssize_t sendResult;
    msg.msg_control = control_un.control;
    msg.msg_controllen = sizeof_control;

    iov[0].iov_base = (void *)dummy_buffer;
    iov[0].iov_len = sizeof(dummy_buffer);

    msg.msg_iov = iov;
    msg.msg_iovlen = 1;
    if ((n = recvmsg(socket, &msg, 0)) <= 0) {
        perror("IPC failure: Receiving data over socket failed");
        free(control_un.control);
        return -1;
    }

    if (((cmptr = CMSG_FIRSTHDR(&msg)) != NULL) &&
        (cmptr->cmsg_len == CMSG_LEN(sizeof(int)))) {
        if ((cmptr->cmsg_level != SOL_SOCKET) || (cmptr->cmsg_type != SCM_RIGHTS)) {
        free(control_un.control);
        return -1;
        }

        memmove(&receivedfd, CMSG_DATA(cmptr), sizeof(receivedfd));
        *fd = receivedfd;
    } else {
        free(control_un.control);
        return -1;
    }

    free(control_un.control);
    return 0;
}

int ipcRecvShareableHandle(HANDLE &handle, HANDLE *shareableHandle) {
    DWORD cbRead;
    ReadFile(handle, shareableHandle, (DWORD)sizeof(*shareableHandles), &cbRead, NULL);
    return 0;
}

4.16.3.3. 예약 및 매핑#

가상 주소 범위 예약(reserving)

VMM에서 주소와 메모리의 개념이 구분되므로, 애플리케이션은 cuMemCreate로 수행된 메모리 할당을 담을 수 있는 주소 범위를 따로 확보해야 합니다. 예약되는 주소 범위는 사용자가 그 안에 배치할 계획인 모든 물리 메모리 할당 크기의 합만큼은 최소한 커야 합니다.

애플리케이션은 적절한 파라미터를 cuMemAddressReserve에 전달하여 가상 주소 범위를 예약할 수 있습니다. 얻어진 주소 범위에는 어떤 디바이스 또는 호스트 물리 메모리도 연관되어 있지 않습니다. 예약된 가상 주소 범위는 시스템 내 어떤 디바이스에 속한 메모리 청크로도 매핑될 수 있으며, 따라서 애플리케이션에 서로 다른 디바이스에 속한 메모리에 의해 백킹되고 매핑되는 연속적인 VA 범위를 제공합니다. 애플리케이션은 cuMemAddressFree을 사용해 가상 주소 범위를 CUDA로 반환해야 합니다. 사용자는 cuMemAddressFree을 호출하기 전에 전체 VA 범위가 언매핑되어 있는지 반드시 확인해야 합니다. 이 함수들은 개념적으로 Linux의 mmap 및 munmap 또는 Windows의 VirtualAlloc AND VirtualFree와 유사합니다. 다음 코드 스니펫은 해당 함수의 사용법을 보여줍니다:

CUdeviceptr ptr;
// `ptr` holds the returned start of virtual address range reserved.
CUresult result = cuMemAddressReserve(&ptr, size, 0, 0, 0); // alignment = 0 for default alignment

메모리 매핑(mapping)

할당된 물리 메모리와, 이전 두 섹션에서 잘라낸 가상 주소 공간은 VMM API가 도입한 메모리와 주소의 구분을 나타냅니다. 할당된 메모리를 사용 가능하게 만들려면, 사용자는 메모리를 주소 공간에 매핑해야 합니다. [cuMemAddressReserve]로 얻은 주소 범위와 cuMemCreate 또는 cuMemImportFromShareableHandle 로 얻은 물리 할당은 cuMemMap를 사용하여 서로 연관되어야 합니다.

사용자는 충분한 주소 공간을 잘라냈기만 하면, 여러 디바이스의 할당을 연속적인 가상 주소 범위에 상주하도록 연관시킬 수 있습니다. 물리 할당과 주소 범위를 분리(decouple)하려면, 사용자는 cuMemUnmap로 매핑의 주소를 언매핑해야 합니다. 사용자는 원한다면 같은 주소 범위에 메모리를 몇 번이든 매핑 및 언매핑할 수 있으며, VA 범위 예약이 이미 매핑된 상태에서 그 위에 매핑을 생성하려고 시도하지 않도록만 보장하면 됩니다. 다음 코드 스니펫은 해당 함수의 사용법을 보여줍니다:

CUdeviceptr ptr;
// `ptr`: address in the address range previously reserved by cuMemAddressReserve.
// `allocHandle`: CUmemGenericAllocationHandle obtained by a previous call to cuMemCreate.
CUresult result = cuMemMap(ptr, size, 0, allocHandle, 0);

4.16.3.4. 접근 권한#

CUDA의 가상 메모리 관리 API는 애플리케이션이 접근 제어 메커니즘으로 자신의 VA 범위를 명시적으로 보호할 수 있게 합니다. cuMemMap를 사용해 주소 범위의 한 영역에 할당을 매핑(mapping)하는 것만으로는 그 주소에 접근할 수 없으며, CUDA 커널이 접근하면 프로그램 크래시가 발생합니다. 사용자는 소스 디바이스와 접근 디바이스에서 cuMemSetAccess 함수를 사용해 접근 제어를 구체적으로 선택해야 합니다. 이를 통해 특정 디바이스의 매핑된 주소 범위에 대한 접근을 허용하거나 제한합니다. 다음 코드 스니펫은 해당 함수의 사용법을 보여줍니다:

void setAccessOnDevice(int device, CUdeviceptr ptr, size_t size) {
    CUmemAccessDesc accessDesc = {};
    accessDesc.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    accessDesc.location.id = device;
    accessDesc.flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;

    // Make the address accessible
    cuMemSetAccess(ptr, size, &accessDesc, 1);
}

VMM으로 노출되는 접근 제어 메커니즘은 사용자가 시스템의 다른 피어 디바이스와 공유하려는 할당이 무엇인지 명시적으로 지정할 수 있게 합니다. 앞서 지정했듯이, cudaEnablePeerAccess 는 cudaMalloc로 이루어진 모든 이전 및 이후 할당이 대상 피어 디바이스에 매핑되도록 강제합니다. 이는 사용자가 시스템의 모든 디바이스에 대해 모든 할당의 매핑 상태를 추적하는 것을 걱정할 필요가 없으므로, 많은 경우에 편리할 수 있습니다. 하지만 이 접근 방식은 성능에 영향을 미칩니다. 할당 그래뉼러리티(granularity)에서의 접근 제어를 통해, VMM은 최소한의 오버헤드로 피어 매핑을 허용합니다.

vectorAddMMAP 샘플은 Virtual Memory Management APIs를 사용하는 예로 활용할 수 있습니다.

4.16.3.5. 메모리 해제#

할당된 메모리와 주소 공간을 해제하려면, 소스 및 타깃 프로세스 모두 해당 순서대로 cuMemUnmap, cuMemRelease, cuMemAddressFree 함수를 사용해야 합니다. cuMemUnmap 함수는 이전에 매핑된 메모리 영역을 주소 범위에서 언매핑(un-maps)하여, 예약된 가상 주소 공간에서 물리 메모리를 효과적으로 분리합니다. 다음으로, cuMemRelease는 이전에 생성된 물리 메모리를 할당 해제하여 시스템으로 반환합니다. 마지막으로, cuMemAddressFree는 이전에 예약된 가상 주소 범위를 해제하여, 향후 사용을 위해 사용 가능하게 합니다. 이 특정 순서는 물리 메모리와 가상 주소 공간 모두를 깔끔하고 완전하게 할당 해제하도록 보장합니다.

cuMemUnmap(ptr, size);
cuMemRelease(handle);
cuMemAddressFree(ptr, size);

참고

OS별 케이스에서는, 내보낸 핸들을 fclose를 사용해 닫아야 합니다. 이 단계는 패브릭 기반 케이스에는 적용되지 않습니다.

4.16.4. 멀티캐스트 메모리 공유#

Multicast Object Management APIs 는 애플리케이션이 멀티캐스트 객체를 생성할 수 있는 방법을 제공하며, 위에서 설명한 Virtual Memory Management APIs 와 결합해, 애플리케이션이 NVSwitch로 연결된 지원되는 NVLink 연결 GPU에서 NVLink SHARP를 활용할 수 있게 합니다. NVLink SHARP 는 CUDA 애플리케이션이 패브릭 내 컴퓨팅(in-fabric computing)을 활용해, NVSwitch로 연결된 GPU 간 브로드캐스트 및 리덕션 같은 연산을 가속할 수 있게 합니다. 이를 위해 여러 NVLink 연결 GPU가 멀티캐스트 팀을 구성하고, 팀의 각 GPU가 물리 메모리로 멀티캐스트 객체를 백업합니다. 따라서 N개의 GPU로 구성된 멀티캐스트 팀은 멀티캐스트 객체의 N개 물리 복제본(replica)을 가지며, 각각은 참여하는 GPU 하나에 로컬입니다. multimem PTX instructions 는 멀티캐스트 객체의 매핑(mapping)을 사용해 멀티캐스트 객체의 모든 복제본에서 동작합니다.

멀티캐스트 객체로 작업하려면, 애플리케이션은 다음이 필요합니다

  • 멀티캐스트 지원을 쿼리

  • cuMulticastCreate로 멀티캐스트 핸들을 생성.

  • 멀티캐스트 팀에 참여해야 하는 GPU를 제어하는 모든 프로세스와 멀티캐스트 핸들을 공유. 이는 위에서 설명한 대로 cuMemExportToShareableHandle로 동작합니다.

  • cuMulticastAddDevice로 멀티캐스트 팀에 참여해야 하는 모든 GPU를 추가.

  • 각 참여 GPU에 대해, 위에서 설명한 대로 cuMemCreate로 할당된 물리 메모리를 멀티캐스트 핸들에 바인딩. 어떤 디바이스에서든 메모리를 바인딩하기 전에 모든 디바이스를 멀티캐스트 팀에 추가해야 합니다.

  • 주소 범위를 예약(reserving)하고, 멀티캐스트 핸들을 매핑(mapping)하며, 일반 유니캐스트 매핑에 대해 위에서 설명한 대로 접근 권한을 설정. 동일한 물리 메모리에 대한 유니캐스트 및 멀티캐스트 매핑이 가능합니다. 동일한 물리 메모리에 대한 여러 매핑 간 일관성을 보장하는 방법은 위의 가상 에일리어싱 지원 섹션을 참조하세요.

  • 사용 multimem PTX 명령어 멀티캐스트 매핑과 함께.

해당 multi_node_p2p 예제에서 멀티 GPU 프로그래밍 모델 GitHub 리포지토리에는 NVLink SHARP를 활용하기 위해 멀티캐스트 객체를 포함한 패브릭 메모리를 사용하는 완전한 예제가 포함되어 있습니다. 이 예제는 NCCL 또는 NVSHMEM 같은 라이브러리의 개발자를 위한 것임에 유의하세요. 이 예제는 NVSHMEM 같은 상위 수준 프로그래밍 모델이 (멀티 노드) NVLink 도메인 내에서 내부적으로 어떻게 동작하는지를 보여줍니다. 애플리케이션 개발자는 일반적으로 이 API 대신 상위 수준의 MPI, NCCL 또는 NVSHMEM 인터페이스를 사용해야 합니다.

4.16.4.1. 멀티캐스트 객체 할당#

멀티캐스트 객체는 cuMulticastCreate로 생성할 수 있습니다:

CUmemGenericAllocationHandle createMCHandle(int numDevices, size_t size) {
    CUmemAllocationProp mcProp = {};
    mcProp.numDevices = numDevices;
    mcProp.handleTypes = CU_MEM_HANDLE_TYPE_FABRIC; // or on single node CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR

    size_t granularity = 0;
    cuMulticastGetGranularity(&granularity, &mcProp, CU_MEM_ALLOC_GRANULARITY_MINIMUM);

    // Ensure size matches granularity requirements for the allocation
    size_t padded_size = ROUND_UP(size, granularity);

    mcProp.size = padded_size;

    // Create Multicast Object this has no devices and no physical memory associated yet
    CUmemGenericAllocationHandle mcHandle;
    cuMulticastCreate(&mcHandle, &mcProp);

    return mcHandle;
}

4.16.4.2. 멀티캐스트 객체에 디바이스 추가#

디바이스는 cuMulticastAddDevice로 멀티캐스트 팀에 추가할 수 있습니다:

cuMulticastAddDevice(&mcHandle, device);

이 단계는 어떤 디바이스의 메모리든 멀티캐스트 객체에 바인딩되기 전에, 멀티캐스트 팀에 참여하는 디바이스를 제어하는 모든 프로세스에서 완료되어야 합니다.

4.16.4.3. 멀티캐스트 객체에 메모리 바인딩#

멀티캐스트 객체가 생성되고 참여하는 모든 디바이스가 멀티캐스트 객체에 추가된 후에는, 각 디바이스에 대해 cuMemCreate로 할당된 물리 메모리로 백킹(backing)되어야 합니다:

cuMulticastBindMem(mcHandle, mcOffset, memHandle, memOffset, size, 0 /*flags*/);

4.16.4.4. 멀티캐스트 매핑 사용#

CUDA C++에서 멀티캐스트 매핑을 사용하려면, 인라인 PTX와 함께 multimem PTX 명령어를 사용하는 것이 필요합니다:

__global__ void all_reduce_norm_barrier_kernel(float* l2_norm,
                                               float* partial_l2_norm_mc,
                                               unsigned int* arrival_counter_uc, unsigned int* arrival_counter_mc,
                                               const unsigned int expected_count) {
    assert( 1 == blockDim.x * blockDim.y * blockDim.z * gridDim.x * gridDim.y * gridDim.z );
    float l2_norm_sum = 0.0;
#if __CUDA_ARCH__ >= 900

    // atomic reduction to all replicas
    // this can be conceptually thought of as __threadfence_system(); atomicAdd_system(arrival_counter_mc, 1);
    cuda::ptx::multimem_red(cuda::ptx::release_t, cuda::ptx::scope_sys_t, cuda::ptx::op_add_t, arrival_counter_mc, n);

    // Need a fence between Multicast (mc) and Unicast (uc) access to the same memory `arrival_counter_uc` and `arrival_counter_mc`:
    // - fence.proxy instructions establish an ordering between memory accesses that may happen through different proxies
    // - Value .alias of the .proxykind qualifier refers to memory accesses performed using virtually aliased addresses to the same memory location.
    // from https://docs.nvidia.com/cuda/parallel-thread-execution/#parallel-synchronization-and-communication-instructions-membar
    cuda::ptx::fence_proxy_alias();

    // spin wait with acquire ordering on UC mapping till all peers have arrived in this iteration
    // Note: all ranks need to reach another barrier after this kernel, such that it is not possible for the barrier to be unblocked by an
    // arrival of a rank for the next iteration if some other rank is slow.
    cuda::atomic_ref<unsigned int,cuda::thread_scope_system> ac(arrival_counter_uc);
    while (expected_count > ac.load(cuda::memory_order_acquire));

    // Atomic load reduction from all replicas. It does not provide ordering so it can be relaxed.
    asm volatile ("multimem.ld_reduce.relaxed.sys.global.add.f32 %0, [%1];" : "=f"(l2_norm_sum) : "l"(partial_l2_norm_mc) : "memory");

#else
    #error "ERROR: multimem instructions require compute capability 9.0 or larger."
#endif

    *l2_norm = std::sqrt(l2_norm_sum);
}

4.16.5. 고급 구성#

4.16.5.1. 메모리 유형#

VMM은 또한 특정 디바이스가 지원할 수 있는 특수한 유형의 메모리를 애플리케이션이 할당할 수 있는 메커니즘을 제공합니다. cuMemCreate를 통해 애플리케이션은 CUmemAllocationProp::allocFlags를 사용해 메모리 유형 요구 사항을 지정하여 특정 메모리 기능을 옵트인(opt-in)할 수 있습니다. 애플리케이션은 요청한 메모리 유형이 해당 디바이스에서 지원되는지 보장해야 합니다.

4.16.5.2. 압축 가능 메모리#

압축 가능 메모리는 비정형 희소성(unstructured sparsity) 및 기타 압축 가능한 데이터 패턴을 가진 데이터에 대한 접근을 가속하는 데 사용할 수 있습니다. 압축은 데이터에 따라 DRAM 대역폭, L2 읽기 대역폭 및 L2 용량을 절약할 수 있습니다. 컴퓨트 데이터 압축을 지원하는 디바이스에서 압축 가능 메모리를 할당하려는 애플리케이션은 CUmemAllocationProp::allocFlags::compressionType를 CU_MEM_ALLOCATION_COMP_GENERIC로 설정하여 이를 수행할 수 있습니다. 사용자는 CU_DEVICE_ATTRIBUTE_GENERIC_COMPRESSION_SUPPORTED를 사용하여 디바이스가 Compute Data Compression을 지원하는지 쿼리해야 합니다. 다음 코드 스니펫은 압축 가능 메모리 지원을 쿼리하는 방법을 보여줍니다 cuDeviceGetAttribute.

int compressionSupported = 0;
cuDeviceGetAttribute(&compressionSupported, CU_DEVICE_ATTRIBUTE_GENERIC_COMPRESSION_SUPPORTED, device);

컴퓨트 데이터 압축을 지원하는 디바이스에서는, 아래에 보인 것처럼 할당 시점에 사용자가 옵트인(opt in)해야 합니다:

prop.allocFlags.compressionType = CU_MEM_ALLOCATION_COMP_GENERIC;

제한된 하드웨어 리소스 같은 다양한 이유로, 할당에 압축 속성이 없을 수 있습니다. 플래그가 동작했는지 확인하려면, 사용자는 cuMemGetAllocationPropertiesFromHandle를 사용하여 할당된 메모리의 속성을 쿼리합니다.

CUmemAllocationProp allocationProp = {};
cuMemGetAllocationPropertiesFromHandle(&allocationProp, allocationHandle);

if (allocationProp.allocFlags.compressionType == CU_MEM_ALLOCATION_COMP_GENERIC)
{
    // Obtained compressible memory allocation
}

4.16.5.3. 가상 별칭 지원#

가상 메모리 관리 API는 서로 다른 가상 주소로 cuMemMap을 여러 번 호출하여, 동일한 할당에 대해 여러 가상 메모리 매핑 또는 “프록시(proxy)”를 생성하는 방법을 제공합니다. 이를 가상 별칭(virtual aliasing)이라고 합니다. PTX ISA에 별도로 명시되지 않는 한, 할당의 한 프록시에 대한 쓰기는 쓰기 디바이스 작업(그리드 런치, memcpy, memset 등) 이 완료될 때까지 동일한 메모리의 다른 어떤 프록시와도 불일치하며 비일관(incoherent)한 것으로 간주됩니다. 쓰기 디바이스 작업 이전에 GPU에 존재했지만 쓰기 디바이스 작업이 완료된 후에 읽는 그리드 역시 프록시가 불일치하고 비일관인 것으로 간주됩니다.

예를 들어, 디바이스 포인터 A와 B가 동일한 메모리 할당의 가상 별칭이라고 가정하면, 다음 스니펫은 미정의(undefined)로 간주됩니다:

__global__ void foo(char *A, char *B) {
  *A = 0x1;
  printf("%d\n", *B);    // Undefined behavior!  *B can take on either
// the previous value or some value in-between.
}

다음은, 이 두 커널이 단조(monotonically)하게(스트림 또는 이벤트에 의해) 순서가 지정되어 있다고 가정하면 정의된 동작입니다.

__global__ void foo1(char *A) {
  *A = 0x1;
}

__global__ void foo2(char *B) {
  printf("%d\n", *B);    // *B == *A == 0x1 assuming foo2 waits for foo1
// to complete before launching
}

cudaMemcpyAsync(B, input, size, stream1);    // Aliases are allowed at
// operation boundaries
foo1<<<1,1,0,stream1>>>(A);                  // allowing foo1 to access A.
cudaEventRecord(event, stream1);
cudaStreamWaitEvent(stream2, event);
foo2<<<1,1,0,stream2>>>(B);
cudaStreamWaitEvent(stream3, event);
cudaMemcpyAsync(output, B, size, stream3);  // Both launches of foo2 and
                                            // cudaMemcpy (which both
                                            // read) wait for foo1 (which writes)
                                            // to complete before proceeding

동일한 커널에서 서로 다른 “프록시”를 통해 같은 할당에 접근해야 한다면, 두 접근 사이에 fence.proxy.alias를 사용할 수 있습니다. 따라서 위 예제는 인라인 PTX 어셈블리로 합법적으로 만들 수 있습니다:

__global__ void foo(char *A, char *B) {
  *A = 0x1;
  cuda::ptx::fence_proxy_alias();
  printf("%d\n", *B);    // *B == *A == 0x1
}

4.16.5.4. IPC를 위한 OS별 핸들 세부 정보#

cuMemCreate를 사용하면, 사용자는 할당 시점에 특정 할당을 프로세스 간 통신 또는 그래픽스 인터롭(graphics interop) 용도로 지정(earmark)했음을 나타낼 수 있습니다. 애플리케이션은 CUmemAllocationProp::requestedHandleTypes을 플랫폼별 필드로 설정하여 이를 수행할 수 있습니다. Windows에서는, CUmemAllocationProp::requestedHandleTypes이 CU_MEM_HANDLE_TYPE_WIN32로 설정된 경우 애플리케이션은 또한 CUmemAllocationProp::win32HandleMetaData에 LPSECURITYATTRIBUTES 속성을 지정해야 합니다. 이 보안 속성은 내보낸 할당 중 어떤 것들이 다른 프로세스로 전송될 수 있는지의 범위를 정의합니다.

사용자는 cuMemCreate로 할당된 메모리를 내보내려고 시도하기 전에, 요청된 핸들 타입에 대한 지원을 쿼리하는지 반드시 보장해야 합니다. 다음 코드 스니펫은 플랫폼별 방식으로 핸들 타입 지원 쿼리를 보여줍니다.

int deviceSupportsIpcHandle;
#if defined(__linux__)
    cuDeviceGetAttribute(&deviceSupportsIpcHandle, CU_DEVICE_ATTRIBUTE_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR_SUPPORTED, device));
#else
    cuDeviceGetAttribute(&deviceSupportsIpcHandle, CU_DEVICE_ATTRIBUTE_HANDLE_TYPE_WIN32_HANDLE_SUPPORTED, device));
#endif

사용자는 아래에 표시된 것처럼 CUmemAllocationProp::requestedHandleTypes를 적절히 설정해야 합니다:

#if defined(__linux__)
    prop.requestedHandleTypes = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;
#else
    prop.requestedHandleTypes = CU_MEM_HANDLE_TYPE_WIN32;
    prop.win32HandleMetaData = // Windows specific LPSECURITYATTRIBUTES attribute.
#endif
