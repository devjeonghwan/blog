4.3. 스트림 순서 메모리 할당자

4.3.1. 소개#

cudaMalloc 및 cudaFree을 사용해 메모리 할당을 관리하면 GPU는 실행 중인 모든 CUDA 스트림 전체에 걸쳐 동기화하게 됩니다. 스트림 순서 메모리 할당자는 커널 실행 및 비동기 복사와 같이 CUDA 스트림으로 실행되는 다른 작업과 메모리 할당 및 해제를 순서화할 수 있게 해줍니다. 이는 스트림 순서(semantics)를 활용하여 메모리 할당을 재사용함으로써 애플리케이션의 메모리 사용을 개선합니다. 또한 이 할당자는 애플리케이션이 할당자의 메모리 캐싱 동작을 제어할 수 있게 합니다. 적절한 해제 임계값으로 설정하면, 애플리케이션이 더 큰 메모리 사용량(footprint)을 받아들일 의사가 있음을 나타낼 때, 캐싱 동작을 통해 OS로의 비용이 큰 호출을 피할 수 있습니다. 이 할당자는 프로세스 간 쉽고 안전한 할당 공유도 지원합니다.

스트림 순서 메모리 할당자:

  • 사용자 정의 메모리 관리 추상화의 필요성을 줄이고, 이를 필요로 하는 애플리케이션을 위해 고성능 사용자 정의 메모리 관리를 더 쉽게 만들 수 있습니다.

  • 여러 라이브러리가 드라이버가 관리하는 공통 메모리 풀을 공유할 수 있게 합니다. 이는 과도한 메모리 소비를 줄일 수 있습니다.

  • 드라이버가 할당자 및 기타 스트림 관리 API를 인지하고 있다는 점을 바탕으로 최적화를 수행할 수 있게 합니다.

참고

Nsight Compute와 차세대 CUDA 디버거는 CUDA 11.3부터 이 할당자를 인지합니다.

4.3.2. 메모리 관리#

cudaMallocAsync 및 cudaFreeAsync은 스트림 순서 메모리 관리를 가능하게 하는 API입니다. cudaMallocAsync는 할당을 반환하고, cudaFreeAsync는 할당을 해제합니다. 두 API 모두 스트림 인수를 받아 할당이 사용 가능해지는 시점과 사용 불가능해지는 시점을 정의합니다. 이 함수들은 메모리 작업을 특정 CUDA 스트림에 연결할 수 있게 하여, 호스트나 다른 스트림을 차단하지 않고 발생할 수 있도록 합니다. cudaMalloc 및 cudaFree의 잠재적으로 비용이 큰 동기화를 피함으로써 애플리케이션 성능을 향상시킬 수 있습니다.

이러한 API는 메모리 풀을 통해 추가적인 성능 최적화에 사용될 수 있으며, 메모리 풀은 더 효율적인 할당 및 해제를 위해 큰 메모리 블록을 관리하고 재사용합니다. 메모리 풀은 오버헤드를 줄이고 단편화를 방지하여, 빈번한 메모리 할당 작업이 있는 시나리오에서 성능을 개선합니다.

4.3.2.1. 메모리 할당#

cudaMallocAsync 함수는 특정 CUDA 스트림에 연결된 GPU에서 비동기 메모리 할당을 트리거합니다. cudaMallocAsync를 사용하면 호스트나 다른 스트림을 방해하지 않고 메모리 할당이 발생할 수 있으며, 비용이 큰 동기화가 필요하지 않게 됩니다.

참고

cudaMallocAsync은 할당이 어디에 상주할지 결정할 때 현재 디바이스/컨텍스트를 무시합니다. 대신, cudaMallocAsync는 지정된 메모리 풀 또는 제공된 스트림을 기반으로 적절한 디바이스를 결정합니다.

아래 목록은 기본적인 사용 패턴을 보여줍니다. 메모리를 할당하고, 사용한 다음, 동일한 스트림으로 다시 해제합니다.

void *ptr;
size_t size = 512;
cudaMallocAsync(&ptr, size, cudaStreamPerThread);
// do work using the allocation
kernel<<<..., cudaStreamPerThread>>>(ptr, ...);
// An asynchronous free can be specified without synchronizing the cpu and GPU
cudaFreeAsync(ptr, cudaStreamPerThread);

참고

할당을 만든 스트림이 아닌 다른 스트림에서 해당 할당에 접근할 때, 사용자는 접근이 할당 작업 이후에 발생하도록 보장해야 하며, 그렇지 않으면 동작은 정의되지 않습니다.

4.3.2.2. 메모리 해제#

cudaFreeAsync()은 스트림 순서 방식으로 디바이스 메모리를 비동기적으로 해제하며, 이는 메모리 할당 해제가 특정 CUDA 스트림에 할당되고 호스트나 다른 스트림을 블로킹하지 않음을 의미합니다.

사용자는 해제 작업이 할당 작업 및 해당 할당의 모든 사용 이후에 발생하도록 보장해야 합니다. 해제 작업이 시작된 이후에 해당 할당을 사용하는 모든 경우는 정의되지 않은 동작을 초래합니다.

다른 스트림에서 해당 할당에 접근하는 작업이 해제 작업이 시작되기 전에 완료되었음을 보장하기 위해, 이벤트 및/또는 스트림 동기화 작업을 사용해야 하며, 이는 다음 예시에서 보여줍니다.

cudaMallocAsync(&ptr, size, stream1);
cudaEventRecord(event1, stream1);
//stream2 must wait for the allocation to be ready before accessing
cudaStreamWaitEvent(stream2, event1);
kernel<<<..., stream2>>>(ptr, ...);
cudaEventRecord(event2, stream2);
// stream3 must wait for stream2 to finish accessing the allocation before
// freeing the allocation
cudaStreamWaitEvent(stream3, event2);
cudaFreeAsync(ptr, stream3);

cudaMalloc()로 할당된 메모리는 cudaFreeAsync()로 해제할 수 있습니다. 위와 마찬가지로, 메모리에 대한 모든 접근은 해제 작업이 시작되기 전에 완료되어야 합니다.

cudaMalloc(&ptr, size);
kernel<<<..., stream>>>(ptr, ...);
cudaFreeAsync(ptr, stream);

마찬가지로, cudaMallocAsync로 할당된 메모리는 cudaFree()로 해제할 수 있습니다. cudaFree() API를 통해 이러한 할당을 해제할 때, 드라이버는 해당 할당에 대한 모든 접근이 완료되었다고 가정하며 추가 동기화를 수행하지 않습니다. 사용자는 cudaStreamQuery / cudaStreamSynchronize / cudaEventQuery / cudaEventSynchronize / cudaDeviceSynchronize를 사용하여 적절한 비동기 작업이 완료되었고 GPU가 해당 할당에 접근하려고 시도하지 않음을 보장할 수 있습니다.

cudaMallocAsync(&ptr, size,stream);
kernel<<<..., stream>>>(ptr, ...);
// synchronize is needed to avoid prematurely freeing the memory
cudaStreamSynchronize(stream);
cudaFree(ptr);

4.3.3. 메모리 풀#

메모리 풀은 풀의 속성과 프로퍼티에 따라 할당 및 관리되는 가상 주소 및 물리 메모리 리소스를 캡슐화합니다. 메모리 풀의 주요 측면은 그것이 관리하는 메모리의 종류와 위치입니다.

cudaMallocAsync에 대한 모든 호출은 메모리 풀의 리소스를 사용합니다. 메모리 풀이 지정되지 않으면, cudaMallocAsync는 제공된 스트림의 디바이스에 대한 현재 메모리 풀을 사용합니다. 디바이스의 현재 메모리 풀은 cudaDeviceSetMempool로 설정하고 cudaDeviceGetMempool로 조회할 수 있습니다. 각 디바이스에는 기본 메모리 풀이 있으며, cudaDeviceSetMempool가 호출되지 않은 경우 활성 상태입니다.

API cudaMallocFromPoolAsync 및 cudaMallocAsync의 c++ 오버로드 를 사용하면, 사용자는 풀을 현재 풀로 설정하지 않고도 할당에 사용할 풀을 지정할 수 있습니다. API cudaDeviceGetDefaultMempool 및 cudaMemPoolCreate는 메모리 풀에 대한 핸들을 반환합니다. cudaMemPoolSetAttribute 및 cudaMemPoolGetAttribute는 메모리 풀의 속성을 제어합니다.

참고

디바이스의 현재 mempool은 해당 디바이스에 로컬입니다. 따라서 메모리 풀을 지정하지 않고 할당하면 항상 스트림의 디바이스에 로컬인 할당이 생성됩니다.

4.3.3.1. 기본/암시적 풀#

디바이스의 기본 메모리 풀은 cudaDeviceGetDefaultMempool를 호출하여 가져올 수 있습니다. 디바이스의 기본 메모리 풀에서의 할당은 해당 디바이스에 위치한, 마이그레이션 불가능한 디바이스 할당입니다. 이러한 할당은 항상 해당 디바이스에서 접근 가능합니다. 기본 메모리 풀의 접근성은 cudaMemPoolSetAccess로 수정하고 cudaMemPoolGetAccess로 조회할 수 있습니다. 기본 풀은 명시적으로 생성할 필요가 없으므로, 때때로 암시적 풀이라고도 합니다. 디바이스의 기본 메모리 풀은 IPC를 지원하지 않습니다.

4.3.3.2. 명시적 풀#

cudaMemPoolCreate는 명시적 풀을 생성합니다. 이를 통해 애플리케이션은 기본/암시적 풀이 제공하는 것 이상의 할당 프로퍼티를 요청할 수 있습니다. 여기에는 IPC 기능, 최대 풀 크기, 지원되는 플랫폼에서 특정 CPU NUMA 노드에 상주하는 할당 등과 같은 프로퍼티가 포함됩니다.

// create a pool similar to the implicit pool on device 0
int device = 0;
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = device;
poolProps.location.type = cudaMemLocationTypeDevice;

cudaMemPoolCreate(&memPool, &poolProps));

다음 코드 스니펫은 유효한 CPU NUMA 노드에서 IPC 가능 메모리 풀을 생성하는 예시를 보여줍니다.

// create a pool resident on a CPU NUMA node that is capable of IPC sharing (via a file descriptor).
int cpu_numa_id = 0;
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = cpu_numa_id;
poolProps.location.type = cudaMemLocationTypeHostNuma;
poolProps.handleType = cudaMemHandleTypePosixFileDescriptor;

cudaMemPoolCreate(&ipcMemPool, &poolProps));

4.3.3.3. 멀티 GPU 지원을 위한 디바이스 접근성#

가상 메모리 관리 API를 통해 제어되는 할당 접근성과 마찬가지로, 메모리 풀 할당 접근성은 cudaDeviceEnablePeerAccess 또는 cuCtxEnablePeerAccess를 따르지 않습니다. 메모리 풀의 경우, API cudaMemPoolSetAccess는 어떤 디바이스가 풀의 할당에 접근할 수 있는지를 수정합니다. 기본적으로 할당은 할당이 위치한 디바이스에서만 접근할 수 있습니다. 이 접근 권한은 철회할 수 없습니다. 다른 디바이스에서의 접근을 활성화하려면, 접근하는 디바이스는 메모리 풀의 디바이스와 피어 가능해야 합니다. 이는 cudaDeviceCanAccessPeer로 확인할 수 있습니다. 피어 기능을 확인하지 않으면, 접근 설정은 cudaErrorInvalidDevice로 실패할 수 있습니다. 하지만 풀에서 아직 어떤 할당도 수행되지 않았다면, 디바이스들이 피어 가능하지 않더라도 cudaMemPoolSetAccess 호출이 성공할 수 있습니다. 이 경우, 풀에서의 다음 할당은 실패합니다.

cudaMemPoolSetAccess는 메모리 풀에서의 모든 할당에 영향을 미치며 미래의 할당에만 영향을 미치는 것이 아니라는 점에 유의할 가치가 있습니다. 마찬가지로, 다음에 의해 보고되는 접근성 cudaMemPoolGetAccess는 풀에서의 모든 할당에 적용되며 미래의 할당에만 적용되는 것이 아닙니다. 특정 GPU에 대해 풀의 접근성 설정을 자주 변경하는 것은 권장되지 않습니다. 즉, 풀이 특정 GPU에서 접근 가능하게 되면 풀의 수명 동안 해당 GPU에서 계속 접근 가능해야 합니다.

// snippet showing usage of cudaMemPoolSetAccess:
cudaError_t setAccessOnDevice(cudaMemPool_t memPool, int residentDevice,
              int accessingDevice) {
    cudaMemAccessDesc accessDesc = {};
    accessDesc.location.type = cudaMemLocationTypeDevice;
    accessDesc.location.id = accessingDevice;
    accessDesc.flags = cudaMemAccessFlagsProtReadWrite;

    int canAccess = 0;
    cudaError_t error = cudaDeviceCanAccessPeer(&canAccess, accessingDevice,
              residentDevice);
    if (error != cudaSuccess) {
        return error;
    } else if (canAccess == 0) {
        return cudaErrorPeerAccessUnsupported;
    }

    // Make the address accessible
    return cudaMemPoolSetAccess(memPool, &accessDesc, 1);
}

4.3.3.4. IPC를 위한 메모리 풀 활성화#

메모리 풀은 프로세스 간 통신(IPC)을 위해 활성화하여 프로세스 간 GPU 메모리를 쉽고 효율적이며 안전하게 공유할 수 있습니다. CUDA의 IPC 메모리 풀은 CUDA의 가상 메모리 관리 API와 동일한 보안 이점을 제공합니다.

메모리 풀로 프로세스 간 메모리를 공유하는 데에는 두 단계가 있습니다. 먼저 프로세스가 풀에 대한 접근을 공유한 다음, 해당 풀에서의 특정 할당을 공유해야 합니다. 첫 번째 단계는 보안을 설정하고 강제합니다. 두 번째 단계는 각 프로세스에서 어떤 가상 주소가 사용되는지와 가져오는(importing) 프로세스에서 매핑이 언제 유효해야 하는지를 조정합니다.

4.3.3.4.1. IPC 메모리 풀 생성 및 공유#

풀에 대한 접근을 공유하려면, cudaMemPoolExportToShareableHandle()를 사용하여 풀에 대한 OS 네이티브 핸들을 가져오고, OS 네이티브 IPC 메커니즘을 사용해 그 핸들을 가져오는(importing) 프로세스로 전달한 다음, cudaMemPoolImportFromShareableHandle() API로 가져온 메모리 풀을 생성해야 합니다. cudaMemPoolExportToShareableHandle가 성공하려면, 메모리 풀은 풀 프로퍼티 구조체에 지정된 요청된 핸들 타입으로 생성되어 있어야 합니다.

프로세스 간에 OS 네이티브 핸들을 전달하기 위한 적절한 IPC 메커니즘은 samples 를 참고하십시오. 나머지 절차는 다음 코드 스니펫에서 확인할 수 있습니다.

// in exporting process
// create an exportable IPC capable pool on device 0
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = 0;
poolProps.location.type = cudaMemLocationTypeDevice;

// Setting handleTypes to a non zero value will make the pool exportable (IPC capable)
poolProps.handleTypes = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;

cudaMemPoolCreate(&memPool, &poolProps));

// FD based handles are integer types
int fdHandle = 0;


// Retrieve an OS native handle to the pool.
// Note that a pointer to the handle memory is passed in here.
cudaMemPoolExportToShareableHandle(&fdHandle,
             memPool,
             CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
             0);

// The handle must be sent to the importing process with the appropriate
// OS-specific APIs.

// in importing process
 int fdHandle;
// The handle needs to be retrieved from the exporting process with the
// appropriate OS-specific APIs.
// Create an imported pool from the shareable handle.
// Note that the handle is passed by value here.
cudaMemPoolImportFromShareableHandle(&importedMemPool,
          (void*)fdHandle,
          CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
          0);

4.3.3.4.2. 가져오는 프로세스에서 접근 설정#

가져온 메모리 풀은 초기에는 상주 디바이스에서만 접근할 수 있습니다. 가져온 메모리 풀은 내보내는(exporting) 프로세스가 설정한 어떠한 접근성도 상속하지 않습니다. 가져오는 프로세스는 메모리에 접근할 계획이 있는 모든 GPU에서 cudaMemPoolSetAccess를 사용해 접근을 활성화해야 합니다.

가져온 메모리 풀이 가져오는(importing) 프로세스에서 보이지 않는 디바이스에 속하는 경우, 사용자는 cudaMemPoolSetAccess API를 사용하여 할당이 사용될 GPU들에서의 접근을 활성화해야 합니다. (참조: 멀티 GPU 지원을 위한 디바이스 접근성)

4.3.3.4.3. 내보낸 풀에서 할당 생성 및 공유#

풀이 공유되면, 내보내는 프로세스에서 풀로부터 cudaMallocAsync()로 수행한 할당은 풀을 가져온 프로세스들과 공유할 수 있습니다. 풀의 보안 정책은 풀 수준에서 설정되고 검증되므로, OS는 특정 풀 할당에 대한 보안을 제공하기 위해 추가적인 부기(bookkeeping)를 할 필요가 없습니다. 다시 말해, 풀 할당을 가져오는 데 필요한 불투명한 cudaMemPoolPtrExportData는 어떤 메커니즘을 사용하든 가져오는 프로세스로 전송할 수 있습니다.

할당은 할당 스트림과 어떤 방식으로든 동기화하지 않고 내보내고 가져올 수 있지만, 가져오는 프로세스는 할당에 접근할 때 내보내는 프로세스와 동일한 규칙을 따라야 합니다. 구체적으로, 할당에 대한 접근은 할당 스트림에서의 할당 작업이 실행된 이후에 발생해야 합니다. 다음 두 코드 스니펫은 cudaMemPoolExportPointer() 및 cudaMemPoolImportPointer()가, 가져오는 프로세스에서 할당이 준비되기 전에 접근되지 않도록 보장하기 위해 IPC 이벤트를 사용하여 할당을 공유하는 모습을 보여줍니다.

// preparing an allocation in the exporting process
cudaMemPoolPtrExportData exportData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t readyIpcEventHandle;

// ipc event for coordinating between processes
// cudaEventInterprocess flag makes the event an ipc event
// cudaEventDisableTiming  is set for performance reasons

cudaEventCreate(&readyIpcEvent, cudaEventDisableTiming | cudaEventInterprocess)

// allocate from the exporting mem pool
cudaMallocAsync(&ptr, size,exportMemPool, stream);

// event for sharing when the allocation is ready.
cudaEventRecord(readyIpcEvent, stream);
cudaMemPoolExportPointer(&exportData, ptr);
cudaIpcGetEventHandle(&readyIpcEventHandle, readyIpcEvent);

// Share IPC event and pointer export data with the importing process using
//  any mechanism. Here we copy the data into shared memory
shmem->ptrData = exportData;
shmem->readyIpcEventHandle = readyIpcEventHandle;
// signal consumers data is ready

// Importing an allocation
cudaMemPoolPtrExportData *importData = &shmem->prtData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t *readyIpcEventHandle = &shmem->readyIpcEventHandle;

// Need to retrieve the ipc event handle and the export data from the
// exporting process using any mechanism.  Here we are using shmem and just
// need synchronization to make sure the shared memory is filled in.

cudaIpcOpenEventHandle(&readyIpcEvent, readyIpcEventHandle);

// import the allocation. The operation does not block on the allocation being ready.
cudaMemPoolImportPointer(&ptr, importedMemPool, importData);

// Wait for the prior stream operations in the allocating stream to complete before
// using the allocation in the importing process.
cudaStreamWaitEvent(stream, readyIpcEvent);
kernel<<<..., stream>>>(ptr, ...);

할당을 해제할 때에는, 내보내는 프로세스에서 해제하기 전에 가져오는 프로세스에서 먼저 해당 할당을 해제해야 합니다. 다음 코드 스니펫은 두 프로세스 모두에서 cudaFreeAsync 작업 간에 필요한 동기화를 제공하기 위해 CUDA IPC 이벤트를 사용하는 방법을 보여줍니다. 가져오는 프로세스에서의 해당 할당 접근은, 명백히 가져오는 프로세스 측의 해제 작업에 의해 제한됩니다. 또한 cudaFree를 사용하여 두 프로세스에서 해당 할당을 해제할 수 있으며, CUDA IPC 이벤트 대신 다른 스트림 동기화 API를 사용할 수도 있다는 점에 유의할 필요가 있습니다.

// The free must happen in importing process before the exporting process
kernel<<<..., stream>>>(ptr, ...);

// Last access in importing process
cudaFreeAsync(ptr, stream);

// Access not allowed in the importing process after the free
cudaIpcEventRecord(finishedIpcEvent, stream);

// Exporting process
// The exporting process needs to coordinate its free with the stream order
// of the importing process’s free.
cudaStreamWaitEvent(stream, finishedIpcEvent);
kernel<<<..., stream>>>(ptrInExportingProcess, ...);

// The free in the importing process doesn’t stop the exporting process
// from using the allocation.
cudFreeAsync(ptrInExportingProcess,stream);

4.3.3.4.4. IPC 내보내기 풀 제한 사항#

현재 IPC 풀은 물리 블록을 OS로 다시 반환하는 것을 지원하지 않습니다. 그 결과 cudaMemPoolTrimTo API는 아무런 효과가 없으며, cudaMemPoolAttrReleaseThreshold는 사실상 무시됩니다. 이 동작은 런타임이 아니라 드라이버에 의해 제어되며, 향후 드라이버 업데이트에서 변경될 수 있습니다.

4.3.3.4.5. IPC 가져오기 풀 제한 사항#

가져오기 풀에서 할당하는 것은 허용되지 않습니다. 구체적으로, 가져오기 풀은 현재 풀로 설정할 수 없으며 cudaMallocFromPoolAsync API에서 사용할 수도 없습니다. 따라서 이러한 풀에서는 할당 재사용 정책 속성이 의미가 없습니다.

IPC 가져오기 풀은 IPC 내보내기 풀과 마찬가지로, 현재 물리 블록을 OS로 다시 반환하는 것을 지원하지 않습니다.

리소스 사용량 통계 속성 쿼리는 프로세스로 가져온 할당과 그에 연관된 물리 메모리만을 반영합니다.

4.3.4. 모범 사례 및 튜닝#

4.3.4.1. 지원 여부 쿼리#

애플리케이션은 다음을 호출하여 디바이스가 스트림 순서 메모리 할당자를 지원하는지 여부를 확인할 수 있습니다. cudaDeviceGetAttribute() (참조 개발자 블로그) 디바이스 속성과 함께 cudaDevAttrMemoryPoolsSupported.

IPC 메모리 풀 지원 여부는 다음을 통해 쿼리할 수 있습니다. cudaDevAttrMemoryPoolSupportedHandleTypes 디바이스 속성입니다. 이 속성은 CUDA 11.3에서 추가되었으며, 더 오래된 드라이버는 반환합니다 cudaErrorInvalidValue 이 속성을 쿼리할 때 반환합니다.

int driverVersion = 0;
int deviceSupportsMemoryPools = 0;
int poolSupportedHandleTypes = 0;
cudaDriverGetVersion(&driverVersion);
if (driverVersion >= 11020) {
    cudaDeviceGetAttribute(&deviceSupportsMemoryPools,
                           cudaDevAttrMemoryPoolsSupported, device);
}
if (deviceSupportsMemoryPools != 0) {
    // `device` supports the Stream-Ordered Memory Allocator
}

if (driverVersion >= 11030) {
    cudaDeviceGetAttribute(&poolSupportedHandleTypes,
              cudaDevAttrMemoryPoolSupportedHandleTypes, device);
}
if (poolSupportedHandleTypes & cudaMemHandleTypePosixFileDescriptor) {
   // Pools on the specified device can be created with posix file descriptor-based IPC
}

쿼리 전에 드라이버 버전 확인을 수행하면, 해당 속성이 아직 정의되지 않은 드라이버에서 cudaErrorInvalidValue 오류가 발생하는 것을 피할 수 있습니다. 이를 피하는 대신 오류를 지우기 위해 cudaGetLastError를 사용할 수도 있습니다.

4.3.4.2. 물리 페이지 캐싱 동작#

기본적으로, 할당자는 풀에 의해 소유되는 물리 메모리를 최소화하려고 합니다. 물리 메모리를 할당하고 해제하기 위한 OS 호출을 최소화하기 위해, 애플리케이션은 각 풀에 대해 메모리 사용량(footprint)을 구성해야 합니다. 애플리케이션은 해제 임계값 속성 (cudaMemPoolAttrReleaseThreshold)을 사용하여 이를 수행할 수 있습니다.

해제 임계값은 풀이 OS로 메모리를 다시 반환하려고 시도하기 전에 유지해야 하는 메모리 양(바이트 단위)입니다. 메모리 풀이 해제 임계값 바이트를 초과하는 메모리를 보유하고 있으면, 할당자는 다음 스트림, 이벤트 또는 디바이스 동기화 호출에서 OS로 메모리를 다시 반환하려고 시도합니다. 해제 임계값을 UINT64_MAX로 설정하면, 동기화가 발생할 때마다 드라이버가 매번 풀을 축소하려는 시도를 하지 않게 됩니다.

Cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

cudaMemPoolAttrReleaseThreshold를 충분히 높게 설정하여 메모리 풀 축소를 사실상 비활성화한 애플리케이션은, 메모리 풀의 메모리 사용량(footprint)을 명시적으로 축소하고 싶을 수 있습니다. cudaMemPoolTrimTo는 애플리케이션이 이를 수행할 수 있도록 합니다. 메모리 풀의 사용량(footprint)을 트리밍(trim)할 때, minBytesToKeep 매개변수는 애플리케이션이 지정된 양의 메모리를 유지하도록 허용합니다. 예를 들어, 이후 실행 단계에서 필요할 것으로 예상하는 양입니다.

Cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

// application phase needing a lot of memory from the stream-ordered allocator
for (i=0; i<10; i++) {
    for (j=0; j<10; j++) {
        cudaMallocAsync(&ptrs[j],size[j], stream);
    }
    kernel<<<...,stream>>>(ptrs,...);
    for (j=0; j<10; j++) {
        cudaFreeAsync(ptrs[j], stream);
    }
}

// Process does not need as much memory for the next phase.
// Synchronize so that the trim operation will know that the allocations are no
// longer in use.
cudaStreamSynchronize(stream);
cudaMemPoolTrimTo(mempool, 0);

// Some other process/allocation mechanism can now use the physical memory
// released by the trimming operation.

4.3.4.3. 리소스 사용 통계#

풀의 cudaMemPoolAttrReservedMemCurrent 속성을 쿼리하면 풀이 소비하는 현재 총 물리 GPU 메모리가 보고됩니다. 풀의 cudaMemPoolAttrUsedMemCurrent를 쿼리하면 풀에서 할당되었고 재사용할 수 없는 모든 메모리의 총 크기가 반환됩니다.

cudaMemPoolAttr*MemHigh 속성은 워터마크로, 마지막 재설정 이후 각 cudaMemPoolAttr*MemCurrent 속성이 달성한 최대 값을 기록합니다. 이는 cudaMemPoolSetAttribute API를 사용하여 현재 값으로 재설정할 수 있습니다.

// sample helper functions for getting the usage statistics in bulk
struct usageStatistics {
    cuuint64_t reserved;
    cuuint64_t reservedHigh;
    cuuint64_t used;
    cuuint64_t usedHigh;
};

void getUsageStatistics(cudaMemoryPool_t memPool, struct usageStatistics *statistics)
{
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrReservedMemCurrent, statistics->reserved);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrReservedMemHigh, statistics->reservedHigh);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrUsedMemCurrent, statistics->used);
    cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrUsedMemHigh, statistics->usedHigh);
}


// resetting the watermarks will make them take on the current value.
void resetStatistics(cudaMemoryPool_t memPool)
{
    cuuint64_t value = 0;
    cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReservedMemHigh, &value);
    cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrUsedMemHigh, &value);
}

4.3.4.4. 메모리 재사용 정책#

할당 요청을 처리하기 위해, 드라이버는 OS로부터 더 많은 메모리를 할당하려고 시도하기 전에 cudaFreeAsync()를 통해 이전에 해제된 메모리를 재사용하려고 시도합니다. 예를 들어, 스트림에서 해제된 메모리는 동일한 스트림에서의 후속 할당 요청에서 즉시 재사용될 수 있습니다. 스트림이 CPU와 동기화되면, 해당 스트림에서 이전에 해제된 메모리는 어떤 스트림에서든 할당을 위해 재사용 가능해집니다. 재사용 정책은 기본 메모리 풀과 명시적 메모리 풀 모두에 적용될 수 있습니다.

스트림 순서 할당자는 몇 가지 제어 가능한 할당 정책을 갖습니다. 풀 속성 cudaMemPoolReuseFollowEventDependencies, cudaMemPoolReuseAllowOpportunistic, 및 cudaMemPoolReuseAllowInternalDependencies이 이러한 정책을 제어하며, 아래에 자세히 설명되어 있습니다. 이러한 정책은 cudaMemPoolSetAttribute 호출을 통해 활성화하거나 비활성화할 수 있습니다. 더 새로운 CUDA 드라이버로 업그레이드하면 재사용 정책의 열거(enumeration)가 변경, 개선, 확장 및/또는 재정렬될 수 있습니다.

4.3.4.4.1. cudaMemPoolReuseFollowEventDependencies#

더 많은 물리 GPU 메모리를 할당하기 전에, 할당자는 CUDA 이벤트로 설정된 종속성 정보를 검사하고 다른 스트림에서 해제된 메모리로부터 할당을 시도합니다.

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);
cudaEventRecord(event,originalStream);

// waiting on the event that captures the free in another stream
// allows the allocator to reuse the memory to satisfy
// a new allocation request in the other stream when
// cudaMemPoolReuseFollowEventDependencies is enabled.
cudaStreamWaitEvent(otherStream, event);
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.2. cudaMemPoolReuseAllowOpportunistic#

cudaMemPoolReuseAllowOpportunistic 정책이 활성화되면, 할당자는 해제된 할당을 검사하여 해제 작업의 스트림 순서(semantics)가 충족되었는지 확인합니다. 예를 들어, 스트림이 해제 작업에 의해 표시된 실행 지점을 통과했는지 여부를 확인합니다. 이 정책이 비활성화되면, 할당자는 스트림이 CPU와 동기화될 때 사용 가능해지는 메모리를 여전히 재사용합니다. 이 정책을 비활성화하더라도 cudaMemPoolReuseFollowEventDependencies의 적용이 중단되지는 않습니다.

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);


// after some time, the kernel finishes running
wait(10);

// When cudaMemPoolReuseAllowOpportunistic is enabled this allocation request
// can be fulfilled with the prior allocation based on the progress of originalStream.
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.3. cudaMemPoolReuseAllowInternalDependencies#

OS로부터 더 많은 물리 메모리를 할당하고 매핑하는 데 실패하면, 드라이버는 사용 가능 여부가 다른 스트림의 보류 중인 진행 상황에 의존하는 메모리를 찾습니다. 그러한 메모리가 발견되면, 드라이버는 할당하는 스트림에 필요한 종속성을 삽입하고 해당 메모리를 재사용합니다.

cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);

// When cudaMemPoolReuseAllowInternalDependencies is enabled
// and the driver fails to allocate more physical memory, the driver may
// effectively perform a cudaStreamWaitEvent in the allocating stream
// to make sure that future work in ‘otherStream’ happens after the work
// in the original stream that would be allowed to access the original allocation.
cudaMallocAsync(&ptr2, size, otherStream);

4.3.4.4.4. 재사용 정책 비활성화#

제어 가능한 재사용 정책은 메모리 재사용을 개선하지만, 사용자는 이를 비활성화하고 싶을 수 있습니다. 기회주의적(opportunistic) 재사용(예: cudaMemPoolReuseAllowOpportunistic)을 허용하면 CPU와 GPU 실행의 인터리빙(interleaving)에 따라 할당 패턴에 실행(run) 간 변동이 생깁니다. 내부 종속성 삽입(예: cudaMemPoolReuseAllowInternalDependencies)은 사용자가 할당 실패 시 이벤트 또는 스트림을 명시적으로 동기화하고자 하는 경우에도, 예상치 못하고 잠재적으로 비결정적인 방식으로 작업을 직렬화할 수 있습니다.

4.3.4.5. 동기화 API 작업#

할당자가 CUDA 드라이버의 일부로 포함되면서 제공되는 최적화 중 하나는 동기화 API와의 통합입니다. 사용자가 CUDA 드라이버에 동기화를 요청하면, 드라이버는 비동기 작업이 완료될 때까지 기다립니다. 반환하기 전에, 드라이버는 동기화로 인해 완료가 보장된 해제(free)가 무엇인지 판단합니다. 이러한 할당은 지정된 스트림이나 비활성화된 할당 정책과 관계없이 할당에 사용할 수 있게 됩니다. 또한 드라이버는 여기에서 cudaMemPoolAttrReleaseThreshold을 확인하고, 가능하다면 초과 물리 메모리를 모두 해제합니다.

4.3.5. 부록#

4.3.5.1. cudaMemcpyAsync의 현재 컨텍스트/디바이스 민감성#

현재 CUDA 드라이버에서, 모든 비동기(async) memcpy …로부터의 메모리를 포함하는 cudaMallocAsync 지정된 스트림의 컨텍스트를 호출 스레드의 현재 컨텍스트로 사용하여 수행해야 합니다. 이는 …에는 필요하지 않습니다. cudaMemcpyPeerAsync, API에서 지정된 디바이스 기본 컨텍스트가 현재 컨텍스트 대신 참조되기 때문입니다.

4.3.5.2. cudaPointerGetAttributes 쿼리#

cudaPointerGetAttributes을(를) 호출한 이후 해당 할당에 대해 cudaFreeAsync을(를) 호출하면 정의되지 않은 동작이 발생합니다. 구체적으로, 특정 스트림에서 할당에 계속 접근할 수 있는지 여부는 중요하지 않으며, 동작은 여전히 정의되지 않습니다.

4.3.5.3. cudaGraphAddMemsetNode#

cudaGraphAddMemsetNode는 스트림 순서 할당자를 통해 할당된 메모리에서는 동작하지 않습니다. 하지만 해당 할당에 대한 memset은 스트림 캡처될 수 있습니다.

4.3.5.4. 포인터 속성#

cudaPointerGetAttributes 쿼리는 스트림 순서 할당에서 동작합니다. 스트림 순서 할당은 컨텍스트에 연결(associated)되어 있지 않으므로, CU_POINTER_ATTRIBUTE_CONTEXT를 쿼리하면 성공하지만 *data에서는 NULL을 반환합니다. 속성 CU_POINTER_ATTRIBUTE_DEVICE_ORDINAL는 할당의 위치를 결정하는 데 사용할 수 있으며, 이는 cudaMemcpyPeerAsync를 사용해 p2h2p 복사를 수행할 컨텍스트를 선택할 때 유용할 수 있습니다. 속성 CU_POINTER_ATTRIBUTE_MEMPOOL_HANDLE는 CUDA 11.3에서 추가되었으며, 디버깅 및 IPC를 수행하기 전에 할당이 어떤 풀에서 왔는지 확인하는 데 유용할 수 있습니다.

4.3.5.5. CPU 가상 메모리#

CUDA 스트림 순서 메모리 할당자 API를 사용할 때는 지원되지 않으므로 “ulimit -v”로 VRAM 제한을 설정하지 마십시오.
