2.1. CUDA C++ 소개

이 장에서는 CUDA 프로그래밍 모델의 몇 가지 기본 개념을 C++에서 어떻게 노출되는지 보여줌으로써 소개합니다.

이 프로그래밍 가이드는 CUDA 런타임 API에 초점을 맞춥니다. CUDA 런타임 API는 C++에서 CUDA를 사용하는 가장 일반적인 방법이며, 더 낮은 수준의 CUDA 드라이버 API 위에 구축되어 있습니다.

CUDA Runtime API and CUDA Driver API에서는 API 간의 차이를 논의하고, CUDA driver API에서는 API를 혼합하여 코드를 작성하는 방법을 다룹니다.

이 가이드는 CUDA Toolkit과 NVIDIA Driver가 설치되어 있고, 지원되는 NVIDIA GPU가 존재한다고 가정합니다. 필요한 CUDA 구성 요소 설치 지침은 CUDA 퀵스타트 가이드를 참조하십시오.

2.1.1. NVCC로 컴파일#

C++로 작성된 GPU 코드는 NVIDIA Cuda Compiler인 nvcc를 사용하여 컴파일됩니다. nvcc는 C++ 또는 PTX 코드를 컴파일하는 과정을 단순화하는 컴파일러 드라이버입니다. 간단하고 익숙한 명령줄 옵션을 제공하고, 서로 다른 컴파일 단계들을 구현하는 도구 모음을 호출하여 이를 실행합니다.

이 가이드는 CUDA Toolkit이 설치된 모든 Linux 시스템에서, Windows 명령줄 또는 PowerShell에서, 또는 CUDA Toolkit이 설치된 Windows Subsystem for Linux에서 사용할 수 있는 nvcc 명령줄을 보여줄 것입니다. 이 가이드의 nvcc 장에서는 nvcc의 일반적인 사용 사례를 다루며, 전체 문서는 nvcc 사용자 매뉴얼에서 제공됩니다.

2.1.2. 커널#

CUDA 프로그래밍 모델 소개에서 언급했듯이, 호스트에서 호출할 수 있으며 GPU에서 실행되는 함수를 커널이라고 합니다. 커널은 많은 병렬 스레드가 동시에 실행하도록 작성됩니다.

2.1.2.1. 커널 지정#

커널의 코드는 __global__ 선언 지정자를 사용하여 지정합니다. 이는 컴파일러에 이 함수가 커널 실행(launch)에서 호출될 수 있도록 GPU용으로 컴파일될 것임을 나타냅니다. 커널 실행(launch)은 보통 CPU에서 커널 실행을 시작하는 작업입니다. 커널은 void 반환 타입을 갖는 함수입니다.

// Kernel definition
__global__ void vecAdd(float* A, float* B, float* C)
{

}

2.1.2.2. 커널 실행하기#

병렬로 커널을 실행할 스레드 수는 커널 실행(launch)의 일부로 지정됩니다. 이를 실행 구성(execution configuration)이라고 합니다. 동일한 커널에 대한 서로 다른 호출은 서로 다른 실행 구성을 사용할 수 있으며, 예를 들어 스레드 수나 스레드 블록 수가 다를 수 있습니다.

CPU 코드에서 커널을 실행(launch)하는 방법은 두 가지가 있는데, 트리플 셰브론 표기법과 cudaLaunchKernelEx입니다. 커널을 실행하는 가장 일반적인 방법인 트리플 셰브론 표기법을 여기에서 소개합니다. cudaLaunchKernelEx를 사용하여 커널을 실행하는 예시는 섹션 Section 3.1.1에서 자세히 보여주고 논의합니다.

2.1.2.2.1. 트리플 셰브론 표기법#

트리플 셰브론 표기법은 커널을 실행하는 데 사용되는 CUDA C++ 언어 확장입니다. 커널 실행을 위한 실행 구성을 감싸기 위해 세 개의 셰브론 문자를 사용하기 때문에 트리플 셰브론이라고 부르며, 즉 <<< >>>입니다. 실행 구성 파라미터는 함수 호출의 파라미터와 유사하게, 셰브론 안에 쉼표로 구분된 목록으로 지정됩니다. vecAdd 커널에 대한 커널 실행 구문은 아래에 나와 있습니다.

 __global__ void vecAdd(float* A, float* B, float* C)
 {

 }

int main()
{
    ...
    // Kernel invocation
    vecAdd<<<1, 256>>>(A, B, C);
    ...
}

트리플 셰브론 표기법의 처음 두 파라미터는 각각 그리드 차원과 스레드 블록 차원입니다. 1차원 스레드 블록 또는 그리드를 사용할 때는 정수를 사용하여 차원을 지정할 수 있습니다.

위 코드는 256개의 스레드를 포함하는 단일 스레드 블록을 실행합니다. 각 스레드는 정확히 동일한 커널 코드를 실행합니다. 스레드 및 그리드 인덱스 인트린식에서는 각 스레드가 스레드 블록 및 그리드 내에서의 인덱스를 사용하여 자신이 처리하는 데이터를 어떻게 바꿀 수 있는지 보여줍니다.

블록의 모든 스레드는 동일한 스트리밍 멀티프로세서(SM)에 상주하며 SM의 리소스를 공유해야 하므로, 블록당 스레드 수에는 제한이 있습니다. 현재 GPU에서는 스레드 블록에 최대 1024개의 스레드를 포함할 수 있습니다. 리소스가 허용된다면, 하나의 SM에서 둘 이상의 스레드 블록이 동시에 스케줄링될 수 있습니다.

커널 실행은 호스트 스레드에 대해 비동기입니다. 즉, GPU에서 실행되도록 커널이 설정되지만, 호스트 코드는 GPU에서 커널 실행이 완료(또는 시작)되기를 기다리지 않고 계속 진행합니다. 커널이 완료되었음을 확인하려면 GPU와 CPU 간 어떤 형태의 동기화를 사용해야 합니다. 전체 GPU를 완전히 동기화하는 가장 기본적인 버전은 CPU와 GPU 동기화에 나와 있습니다. 더 정교한 동기화 방법은 비동기 실행에서 다룹니다.

2차원 또는 3차원 그리드나 스레드 블록을 사용할 때는 CUDA 타입 dim3를 그리드 및 스레드 블록 차원 파라미터로 사용합니다. 아래 코드 조각은 16x16 스레드 블록 그리드를 사용하여 MatAdd 커널을 실행하는 예를 보여주며, 각 스레드 블록은 8x8입니다.

int main()
{
    ...
    dim3 grid(16,16);
    dim3 block(8,8);
    MatAdd<<<grid, block>>>(A, B, C);
    ...
}

2.1.2.3. 스레드 및 그리드 인덱스 인트린식#

커널 코드 내에서 CUDA는 실행 구성의 파라미터와 스레드 또는 블록의 인덱스에 접근하기 위한 인트린식을 제공합니다.

  • threadIdx는 스레드 블록 내에서 스레드의 인덱스를 제공합니다. 스레드 블록의 각 스레드는 서로 다른 인덱스를 갖습니다.

  • blockDim는 커널 실행의 실행 구성에서 지정된 스레드 블록의 차원을 제공합니다.

  • blockIdx는 그리드 내에서 스레드 블록의 인덱스를 제공합니다. 각 스레드 블록은 서로 다른 인덱스를 갖습니다.

  • gridDim는 커널이 실행될 때 실행 구성에서 지정된 그리드의 차원을 제공합니다.

이들 각 인트린식은 .x, .y, .z 멤버를 갖는 3-컴포넌트 벡터입니다. 실행 구성에서 지정되지 않은 차원은 기본값이 1이 됩니다. threadIdx와 blockIdx는 0부터 시작하는 인덱스입니다. 즉, threadIdx.x는 0부터 blockDim.x-1까지(포함) 값을 갖습니다. .y와 .z도 각 해당 차원에서 동일하게 동작합니다.

마찬가지로, blockIdx.x는 0부터 gridDim.x-1까지(포함) 값을 가지며, .y 및 .z 차원도 각각 동일합니다.

이들은 개별 스레드가 수행해야 할 작업이 무엇인지 식별할 수 있게 해줍니다. vecAdd 커널로 돌아가 보면, 이 커널은 세 개의 파라미터를 받으며 각각은 float 벡터입니다. 커널은 A과 B의 요소별 덧셈을 수행하고 결과를 C에 저장합니다. 커널은 각 스레드가 한 번의 덧셈을 수행하도록 병렬화됩니다. 어떤 요소를 계산할지는 스레드 및 그리드 인덱스로 결정됩니다.

__global__ void vecAdd(float* A, float* B, float* C)
{
   // calculate which element this thread is responsible for computing
   int workIndex = threadIdx.x + blockDim.x * blockIdx.x

   // Perform computation
   C[workIndex] = A[workIndex] + B[workIndex];
}

int main()
{
    ...
    // A, B, and C are vectors of 1024 elements
    vecAdd<<<4, 256>>>(A, B, C);
    ...
}

이 예에서는 256 스레드로 이루어진 4개의 스레드 블록을 사용하여 1024개 요소의 벡터를 더합니다. 첫 번째 스레드 블록에서는 blockIdx.x가 0이므로, 각 스레드의 workIndex는 단순히 자신의 threadIdx.x가 됩니다. 두 번째 스레드 블록에서는 blockIdx.x가 1이므로, blockDim.x * blockIdx.x는 blockDim.x과 같아지며 이 경우 256입니다. 두 번째 스레드 블록의 각 스레드에 대한 workIndex는 자신의 threadIdx.x + 256가 됩니다. 세 번째 스레드 블록에서는 workIndex가 threadIdx.x + 512가 됩니다.

이러한 workIndex의 계산은 1차원 병렬화에서 매우 흔합니다. 2차원 또는 3차원으로 확장하는 경우에도 각 차원에서 동일한 패턴을 따르는 경우가 많습니다.

2.1.2.3.1. 경계 검사#

위에서 제시한 예는 벡터 길이가 스레드 블록 크기의 배수라고 가정합니다(이 경우 256 스레드). 어떤 벡터 길이도 처리할 수 있도록 커널을 만들기 위해, 아래와 같이 메모리 접근이 배열의 경계를 초과하지 않는지 검사하는 체크를 추가할 수 있으며, 그런 다음 일부 비활성 스레드를 포함하게 될 하나의 스레드 블록을 실행할 수 있습니다.

__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
     // calculate which element this thread is responsible for computing
     int workIndex = threadIdx.x + blockDim.x * blockIdx.x

     if(workIndex < vectorLength)
     {
         // Perform computation
         C[workIndex] = A[workIndex] + B[workIndex];
     }
}

위 커널 코드에서는 필요한 것보다 더 많은 스레드를 실행하더라도 배열에 대한 경계 밖(out-of-bounds) 접근이 발생하지 않습니다. workIndex가 vectorLength를 초과하면 스레드는 종료하고 어떤 작업도 수행하지 않습니다. 블록에서 작업을 하지 않는 추가 스레드를 실행하는 것은 큰 오버헤드 비용을 유발하지 않지만, 어떤 스레드도 작업을 하지 않는 스레드 블록을 실행하는 것은 피해야 합니다. 이제 이 커널은 블록 크기의 배수가 아닌 벡터 길이도 처리할 수 있습니다.

필요한 스레드 수(이 경우 벡터 길이)를 블록당 스레드 수로 나눈 값을 올림(ceiling)하여 필요한 스레드 블록 수를 계산할 수 있습니다. 즉, 필요한 스레드 수를 블록당 스레드 수로 정수 나눗셈한 뒤 올림 처리한 값입니다. 이를 하나의 정수 나눗셈으로 표현하는 일반적인 방법은 아래와 같습니다. 정수 나눗셈 전에 threads - 1를 더하면 올림 함수처럼 동작하여, 벡터 길이가 블록당 스레드 수로 나누어떨어지지 않는 경우에만 스레드 블록을 하나 더 추가합니다.

// vectorLength is an integer storing number of elements in the vector
int threads = 256;
int blocks = (vectorLength + threads-1)/threads;
vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);

CUDA Core Compute Library (CCCL)는 커널 실행에 필요한 블록 수를 계산하기 위해 이 올림 나눗셈(ceiling divide)을 수행하는 편리한 유틸리티인 cuda::ceil_div를 제공합니다. 이 유틸리티는 헤더 <cuda/cmath>를 포함하면 사용할 수 있습니다.

// vectorLength is an integer storing number of elements in the vector
int threads = 256;
int blocks = cuda::ceil_div(vectorLength, threads);
vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);

여기에서 블록당 256 스레드를 선택한 것은 임의이지만, 이는 시작 값으로 꽤 자주 좋은 값입니다.

2.1.3. GPU 컴퓨팅에서의 메모리#

위에 표시된 vecAdd 커널을 사용하려면, 배열 A, B, C이 GPU에서 접근 가능한 메모리에 있어야 합니다. 이를 수행하는 방법에는 여러 가지가 있으며, 그중 두 가지를 여기에서 예시로 보여줍니다. 다른 방법들은 이후 통합 메모리에 대한 섹션에서 다룰 것입니다. GPU에서 실행되는 코드가 사용할 수 있는 메모리 공간은 GPU 메모리에서 소개되었으며, GPU 디바이스 메모리 공간에서 더 자세히 다룹니다.

2.1.3.1. 통합 메모리#

통합 메모리는 NVIDIA 드라이버가 호스트와 디바이스(들) 간 데이터 이동을 관리할 수 있게 해주는 CUDA 런타임의 기능입니다. 메모리는 cudaMallocManaged API를 사용하거나, __managed__ 지정자로 변수를 선언하여 할당합니다. NVIDIA 드라이버는 GPU 또는 CPU 중 어느 쪽이든 접근을 시도할 때마다 해당 메모리에 접근할 수 있도록 보장합니다.

아래 코드는 GPU에서 사용할 입력 및 출력 벡터에 통합 메모리를 사용하는 vecAdd 커널을 실행하기 위한 완전한 함수를 보여줍니다. cudaMallocManaged는 CPU 또는 GPU 어느 쪽에서든 접근할 수 있는 버퍼를 할당합니다. 이러한 버퍼는 cudaFree를 사용하여 해제합니다.

void unifiedMemExample(int vectorLength)
{
    // Pointers to memory vectors
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));

    // Use unified memory to allocate buffers
    cudaMallocManaged(&A, vectorLength*sizeof(float));
    cudaMallocManaged(&B, vectorLength*sizeof(float));
    cudaMallocManaged(&C, vectorLength*sizeof(float));

    // Initialize vectors on the host
    initArray(A, vectorLength);
    initArray(B, vectorLength);

    // Launch the kernel. Unified memory will make sure A, B, and C are
    // accessible to the GPU
    int threads = 256;
    int blocks = cuda::ceil_div(vectorLength, threads);
    vecAdd<<<blocks, threads>>>(A, B, C, vectorLength);
    // Wait for the kernel to complete execution
    cudaDeviceSynchronize();

    // Perform computation serially on CPU for comparison
    serialVecAdd(A, B, comparisonResult, vectorLength);

    // Confirm that CPU and GPU got the same answer
    if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
    {
        printf("Unified Memory: CPU and GPU answers match\n");
    }
    else
    {
        printf("Unified Memory: Error - CPU and GPU answers do not match\n");
    }

    // Clean Up
    cudaFree(A);
    cudaFree(B);
    cudaFree(C);
    free(comparisonResult);

}

통합 메모리는 CUDA가 지원하는 모든 운영체제와 GPU에서 지원되지만, 기본 메커니즘과 성능은 시스템 아키텍처에 따라 달라질 수 있습니다. 통합 메모리에서 더 자세한 내용을 제공합니다. 일부 Linux 시스템(예: 주소 변환 서비스 또는 이기종 메모리 관리가 있는 시스템)에서는 모든 시스템 메모리가 자동으로 통합 메모리가 되며, cudaMallocManaged 또는 __managed__ 지정자를 사용할 필요가 없습니다.

2.1.3.2. 명시적 메모리 관리#

메모리 공간 간의 메모리 할당과 데이터 마이그레이션을 명시적으로 관리하면 애플리케이션 성능을 개선하는 데 도움이 될 수 있지만, 코드가 더 장황해집니다. 아래 코드는 cudaMalloc를 사용하여 GPU에 메모리를 명시적으로 할당합니다. GPU의 메모리는 이전 예제에서 통합 메모리에 사용했던 것과 동일한 cudaFree API를 사용하여 해제합니다.

void explicitMemExample(int vectorLength)
{
    // Pointers for host memory
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));
    
    // Pointers for device memory
    float* devA = nullptr;
    float* devB = nullptr;
    float* devC = nullptr;

    //Allocate Host Memory using cudaMallocHost API. This is best practice
    // when buffers will be used for copies between CPU and GPU memory
    cudaMallocHost(&A, vectorLength*sizeof(float));
    cudaMallocHost(&B, vectorLength*sizeof(float));
    cudaMallocHost(&C, vectorLength*sizeof(float));

    // Initialize vectors on the host
    initArray(A, vectorLength);
    initArray(B, vectorLength);

    // start-allocate-and-copy
    // Allocate memory on the GPU
    cudaMalloc(&devA, vectorLength*sizeof(float));
    cudaMalloc(&devB, vectorLength*sizeof(float));
    cudaMalloc(&devC, vectorLength*sizeof(float));

    // Copy data to the GPU
    cudaMemcpy(devA, A, vectorLength*sizeof(float), cudaMemcpyDefault);
    cudaMemcpy(devB, B, vectorLength*sizeof(float), cudaMemcpyDefault);
    cudaMemset(devC, 0, vectorLength*sizeof(float));
    // end-allocate-and-copy

    // Launch the kernel
    int threads = 256;
    int blocks = cuda::ceil_div(vectorLength, threads);
    vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);
    // wait for kernel execution to complete
    cudaDeviceSynchronize();

    // Copy results back to host
    cudaMemcpy(C, devC, vectorLength*sizeof(float), cudaMemcpyDefault);

    // Perform computation serially on CPU for comparison
    serialVecAdd(A, B, comparisonResult, vectorLength);

    // Confirm that CPU and GPU got the same answer
    if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
    {
        printf("Explicit Memory: CPU and GPU answers match\n");
    }
    else
    {
        printf("Explicit Memory: Error - CPU and GPU answers to not match\n");
    }

    // clean up
    cudaFree(devA);
    cudaFree(devB);
    cudaFree(devC);
    cudaFreeHost(A);
    cudaFreeHost(B);
    cudaFreeHost(C);
    free(comparisonResult);
}

CUDA API cudaMemcpy는 CPU에 상주하는 버퍼에서 GPU에 상주하는 버퍼로 데이터를 복사하는 데 사용됩니다. 목적지 포인터, 소스 포인터, 바이트 단위 크기와 함께, cudaMemcpy의 마지막 매개변수는 cudaMemcpyKind_t입니다. 이는 CPU에서 GPU로의 복사에 대해 cudaMemcpyHostToDevice, CPU에서 GPU로의 복사에 대해 cudaMemcpyDeviceToHost, 또는 GPU 내부 또는 GPU 간 복사에 대해 cudaMemcpyDeviceToDevice 같은 값을 가질 수 있습니다.

이 예제에서는 cudaMemcpyDefault이 cudaMemcpy의 마지막 인수로 전달됩니다. 이렇게 하면 CUDA가 소스 및 목적지 포인터의 값을 사용하여 수행할 복사 유형을 결정합니다.

cudaMemcpy API는 동기식입니다. 즉, 복사가 완료될 때까지 반환하지 않습니다. 비동기 복사는 CUDA 스트림에서 메모리 전송 실행하기에서 소개합니다.

이 코드는 cudaMallocHost를 사용하여 CPU에 메모리를 할당합니다. 이는 호스트에 페이지 고정 메모리를 할당하며, 복사 성능을 향상시킬 수 있고 비동기 메모리 전송에 필요합니다. 일반적으로 GPU로의/으로부터의 데이터 전송에 사용할 CPU 버퍼에는 페이지 고정 메모리를 사용하는 것이 좋은 관행입니다. 호스트 메모리가 너무 많이 페이지 고정되면 일부 시스템에서 성능이 저하될 수 있습니다. 모범 사례는 GPU에서 데이터를 보내거나 받는 데 사용할 버퍼만 페이지 고정하는 것입니다.

2.1.3.3. 메모리 관리 및 애플리케이션 성능#

위 예제에서 볼 수 있듯이, 명시적 메모리 관리는 더 장황하며, 프로그래머가 호스트와 디바이스 간의 복사를 지정해야 합니다. 이것이 명시적 메모리 관리의 장점이자 단점입니다. 즉, 호스트와 디바이스 간에 데이터가 언제 복사되는지, 메모리가 어디에 상주하는지, 그리고 정확히 어떤 메모리가 어디에 할당되는지를 더 많이 제어할 수 있게 해줍니다. 명시적 메모리 관리는 메모리 전송을 제어하고 이를 다른 계산과 오버랩하여 성능상의 기회를 제공할 수 있습니다.

통합 메모리를 사용할 때에는 메모리를 관리하는 NVIDIA 드라이버에 힌트를 제공하는 CUDA API들이 있으며(이는 메모리 어드바이스 및 프리페치에서 다룰 예정), 통합 메모리를 사용하면서도 명시적 메모리 관리 사용 시의 일부 성능 이점을 가능하게 할 수 있습니다.

2.1.4. CPU 및 GPU 동기화#

커널 실행하기에서 언급했듯이, 커널 실행은 이를 호출한 CPU 스레드에 대해 비동기식입니다. 이는 CPU 스레드의 제어 흐름이 커널 실행이 완료되기 전에, 그리고 경우에 따라서는 커널이 실행되기도 전에 계속 진행된다는 뜻입니다. 호스트 코드에서 다음으로 진행하기 전에 커널이 실행을 완료했음을 보장하려면 어떤 동기화 메커니즘이 필요합니다.

GPU와 호스트 스레드를 동기화하는 가장 간단한 방법은 cudaDeviceSynchronize를 사용하는 것으로, 이는 GPU에서 이전에 발행된 모든 작업이 완료될 때까지 호스트 스레드를 블로킹합니다. 이 장의 예제에서는 GPU에서 단일 연산만 실행하므로 이것으로 충분합니다. 더 큰 애플리케이션에서는 GPU에서 작업을 실행하는 여러 스트림이 있을 수 있으며, cudaDeviceSynchronize는 모든 스트림의 작업이 완료될 때까지 기다립니다. 이러한 애플리케이션에서는 특정 스트림에 대해서만 동기화하는 스트림 동기화 API 또는 CUDA 이벤트를 사용하는 것을 권장합니다. 이는 비동기 실행 장에서 자세히 다룰 것입니다.

2.1.5. 전체 내용 종합하기#

    if(workIndex < vectorLength)
    {
        C[workIndex] = A[workIndex] + B[workIndex];
    }

    {
        A[i] = rand() / (float)RAND_MAX;
    }
}

{
    for(int i=0; i<length; i++)
    {
        C[i] = A[i] + B[i];
    }

이 예제들에서는 모든 스레드가 독립적인 작업을 수행하며 서로 협력하거나 동기화할 필요가 없습니다. 하지만 종종 스레드들은 작업을 수행하기 위해 다른 스레드와 협력하고 통신해야 합니다. 블록 내의 스레드들은 공유 메모리를 통해 데이터를 공유하고, 메모리 접근을 조정하기 위해 동기화할 수 있습니다.

블록 수준에서 동기화를 위한 가장 기본적인 메커니즘은 __syncthreads() 인트린식으로, 이는 블록 내 모든 스레드가 대기해야만 어떤 스레드든 진행할 수 있는 배리어로 동작합니다. 공유 메모리에서 공유 메모리 사용 예제를 제공합니다.

효율적인 협력을 위해 공유 메모리는 각 프로세서 코어 근처의 저지연 메모리(L1 캐시와 유사한)로 예상되며, __syncthreads()는 가벼운 연산으로 예상됩니다. __syncthreads()는 단일 스레드 블록 내의 스레드만 동기화합니다. 블록 간 동기화는 CUDA 프로그래밍 모델에서 지원되지 않습니다. 코오퍼러티브 그룹(Cooperative Groups)는 단일 스레드 블록 이외의 동기화 도메인을 설정하는 메커니즘을 제공합니다.

최상의 성능은 보통 동기화를 스레드 블록 내로 유지할 때 달성됩니다. 스레드 블록은 이후 절에서 다룰 원자적 메모리 함수를 사용하여 여전히 공통 결과에 대해 작업할 수 있습니다.

섹션 Section 3.2.4에서는 성능과 리소스 활용을 극대화하기 위해 매우 세밀한 제어를 제공하는 CUDA 동기화 프리미티브를 다룹니다.

2.1.6. 런타임 초기화#

CUDA 런타임은 시스템의 각 디바이스에 대해 CUDA 컨텍스트를 생성합니다. 이 컨텍스트는 해당 디바이스의 기본 컨텍스트이며, 이 디바이스에서 활성 컨텍스트가 필요로 하는 첫 번째 런타임 함수에서 초기화됩니다. 컨텍스트는 애플리케이션의 모든 호스트 스레드 간에 공유됩니다. 컨텍스트 생성의 일부로, 필요한 경우 디바이스 코드는 JIT(Just-In-Time) 컴파일되고 디바이스 메모리에 로드됩니다. 이 모든 과정은 투명하게 이루어집니다. CUDA 런타임이 생성한 기본 컨텍스트는 런타임 API와 드라이버 API 간 상호운용성에서 설명한 대로 상호운용성을 위해 드라이버 API에서 접근할 수 있습니다.

CUDA 12.0부터 cudaInitDevice 및 cudaSetDevice 호출은 런타임과 지정된 디바이스에 연결된 기본 컨텍스트를 초기화합니다. 런타임은 이러한 호출보다 먼저 런타임 API 요청을 처리해야 하는 경우 디바이스 0을 암묵적으로 사용하고 필요에 따라 자체적으로 초기화합니다. 이는 런타임 함수 호출의 시간을 측정할 때와 런타임에 대한 첫 번째 호출에서 반환된 오류 코드를 해석할 때 중요합니다. CUDA 12.0 이전에는 cudaSetDevice가 런타임을 초기화하지 않았습니다.

cudaDeviceReset는 현재 디바이스의 기본 컨텍스트를 파기합니다. 기본 컨텍스트가 파기된 이후에 CUDA 런타임 API를 호출하면, 해당 디바이스에 대한 새로운 기본 컨텍스트가 생성됩니다.

참고

CUDA 인터페이스는 호스트 프로그램 시작 시 초기화되고 호스트 프로그램 종료 시 파기되는 전역 상태를 사용합니다. 프로그램 시작 중 또는 main 이후 종료 중에 이러한 인터페이스 중 어느 것이든(암묵적으로 또는 명시적으로) 사용하면 정의되지 않은 동작이 발생합니다.

CUDA 12.0부터 cudaSetDevice는 호스트 스레드의 현재 디바이스를 변경한 후, 아직 초기화되지 않았다면 런타임을 명시적으로 초기화합니다. 이전 CUDA 버전에서는 cudaSetDevice 이후 첫 번째 런타임 호출이 이루어질 때까지 새 디바이스에서의 런타임 초기화를 지연했습니다. 이 때문에 초기화 오류를 확인하기 위해 cudaSetDevice의 반환 값을 확인하는 것이 매우 중요합니다.

레퍼런스 매뉴얼의 오류 처리 및 버전 관리 섹션에 있는 런타임 함수는 런타임을 초기화하지 않습니다.

2.1.7. CUDA에서 오류 확인#

모든 CUDA API는 열거형 타입인 cudaError_t의 값을 반환합니다. 예제 코드에서는 이러한 오류를 종종 확인하지 않습니다. 프로덕션 애플리케이션에서는 모든 CUDA API 호출의 반환 값을 항상 확인하고 관리하는 것이 모범 사례입니다. 오류가 없는 경우 반환되는 값은 cudaSuccess입니다. 많은 애플리케이션은 아래에 표시된 것과 같은 유틸리티 매크로를 구현하는 것을 선택합니다

#define CUDA_CHECK(expr_to_check) do {            \
    cudaError_t result  = expr_to_check;          \
    if(result != cudaSuccess)                     \
    {                                             \
        fprintf(stderr,                           \
                "CUDA Runtime Error: %s:%i:%d = %s\n", \
                __FILE__,                         \
                __LINE__,                         \
                result,\
                cudaGetErrorString(result));      \
    }                                             \
} while(0)

이 매크로는 cudaGetErrorString API를 사용하는데, 이는 특정 cudaError_t 값의 의미를 설명하는 사람이 읽을 수 있는 문자열을 반환합니다. 위의 매크로를 사용하면 애플리케이션은 아래에 보인 것처럼 CUDA_CHECK(expression) 매크로 안에서 CUDA 런타임 API 호출을 호출합니다:

    CUDA_CHECK(cudaMalloc(&devA, vectorLength*sizeof(float)));
    CUDA_CHECK(cudaMalloc(&devB, vectorLength*sizeof(float)));
    CUDA_CHECK(cudaMalloc(&devC, vectorLength*sizeof(float)));

이러한 호출 중 어떤 것이든 오류를 감지하면, 이 매크로를 사용하여 stderr에 출력됩니다. 이 매크로는 소규모 프로젝트에서 흔히 사용되지만, 더 큰 애플리케이션에서는 로깅 시스템이나 다른 오류 처리 메커니즘에 맞게 조정할 수 있습니다.

참고

어떤 CUDA API 호출에서든 반환되는 오류 상태는 이전에 발행된 비동기 작업에서 발생한 오류를 나타낼 수도 있다는 점에 유의하는 것이 중요합니다. 섹션 비동기 오류 처리에서 이를 더 자세히 다룹니다.

2.1.7.1. 오류 상태#

CUDA 런타임은 각 호스트 스레드에 대해 cudaError_t 상태를 유지합니다. 이 값은 기본적으로 cudaSuccess이며, 오류가 발생할 때마다 덮어써집니다. cudaGetLastError는 현재 오류 상태를 반환한 다음 이를 cudaSuccess로 재설정합니다. 또는 cudaPeekLastError는 재설정하지 않고 오류 상태를 반환합니다.

트리플 셰브론 표기법을 사용한 커널 실행은 cudaError_t를 반환하지 않습니다. 커널 실행에서 즉시 발생하는 오류 또는 커널 실행 이전의 비동기 오류를 감지하기 위해, 커널 실행 직후 오류 상태를 확인하는 것이 좋은 관행입니다. 커널 실행 직후 오류 상태를 확인했을 때 cudaSuccess 값이 나온다고 해서 커널이 성공적으로 실행되었거나 실행을 시작했다는 의미는 아닙니다. 이는 런타임에 전달된 커널 실행 매개변수와 실행 구성(execution configuration)이 어떤 오류도 유발하지 않았고, 오류 상태가 커널 시작 이전의 이전 오류 또는 비동기 오류가 아님을 확인할 뿐입니다.

2.1.7.2. 비동기 오류#

CUDA 커널 실행과 많은 런타임 API는 비동기 방식입니다. 비동기 CUDA 런타임 API는 비동기 실행에서 자세히 논의합니다. CUDA 오류 상태는 오류가 발생할 때마다 설정되고 덮어써집니다. 이는 비동기 작업 실행 중에 발생하는 오류가 다음에 오류 상태를 검사할 때만 보고된다는 뜻입니다. 앞서 언급했듯이, 이는 cudaGetLastError, cudaPeekLastError 호출일 수도 있고, cudaError_t를 반환하는 어떤 CUDA API일 수도 있습니다.

CUDA 런타임 API 함수에서 오류가 반환되더라도 오류 상태는 지워지지 않습니다. 즉, 커널에 의한 잘못된 메모리 접근과 같은 비동기 오류의 오류 코드는 cudaGetLastError를 호출하여 오류 상태가 지워질 때까지 모든 CUDA 런타임 API에서 계속 반환됩니다.

    vecAdd<<<blocks, threads>>>(devA, devB, devC);
    // check error state after kernel launch
    CUDA_CHECK(cudaGetLastError());
    // wait for kernel execution to complete
    // The CUDA_CHECK will report errors that occurred during execution of the kernel
    CUDA_CHECK(cudaDeviceSynchronize());

참고

cudaError_t 값인 cudaErrorNotReady은 cudaStreamQuery 및 cudaEventQuery에서 반환될 수 있지만 오류로 간주되지 않으며, cudaPeekAtLastError 또는 cudaGetLastError에 의해 보고되지도 않습니다.

2.1.7.3. CUDA_LOG_FILE#

CUDA 오류를 식별하는 또 다른 좋은 방법은 CUDA_LOG_FILE 환경 변수를 사용하는 것입니다. 이 환경 변수가 설정되면 CUDA 드라이버는 발생한 오류 메시지를 환경 변수에 지정된 경로의 파일에 기록합니다. 예를 들어, 어떤 아키텍처에서도 지원되는 최대값보다 큰 스레드 블록을 실행하려고 시도하는 다음의 잘못된 CUDA 코드를 살펴보십시오.

__global__ void k()
{ }

int main()
{
        k<<<8192, 4096>>>(); // Invalid block size
        CUDA_CHECK(cudaGetLastError());
        return 0;
}

이를 빌드하고 실행하면, 커널 실행 후의 검사가 Section 2.1.7에 설명된 매크로를 사용하여 오류를 감지하고 보고합니다.

$ nvcc errorLogIllustration.cu -o errlog
$ ./errlog
CUDA Runtime Error: /home/cuda/intro-cpp/errorLogIllustration.cu:24:1 = invalid argument

하지만 애플리케이션을 CUDA_LOG_FILE을 텍스트 파일로 설정한 상태에서 실행하면, 해당 파일에는 오류에 대한 정보가 조금 더 포함됩니다.

$ env CUDA_LOG_FILE=cudaLog.txt ./errlog
CUDA Runtime Error: /home/cuda/intro-cpp/errorLogIllustration.cu:24:1 = invalid argument
$ cat cudaLog.txt
[12:46:23.854][137216133754880][CUDA][E] One or more of block dimensions of (4096,1,1) exceeds corresponding maximum value of (1024,1024,64)
[12:46:23.854][137216133754880][CUDA][E] Returning 1 (CUDA_ERROR_INVALID_VALUE) from cuLaunchKernel

CUDA_LOG_FILE을 stdout 또는 stderr로 설정하면 각각 표준 출력과 표준 오류로 출력됩니다. CUDA_LOG_FILE 환경 변수를 사용하면, 애플리케이션이 CUDA 반환 값에 대해 적절한 오류 검사를 구현하지 않았더라도 CUDA 오류를 캡처하고 식별할 수 있습니다. 이 접근 방식은 디버깅에 매우 강력할 수 있지만, 환경 변수만으로는 애플리케이션이 런타임에 CUDA 오류를 처리하고 복구할 수는 없습니다. CUDA의 오류 로그 관리 기능은 또한 드라이버에 콜백 함수를 등록할 수 있게 해주며, 이 콜백은 오류가 감지될 때마다 호출됩니다. 이는 런타임에 오류를 캡처하고 처리하는 데 사용할 수 있으며, 또한 CUDA 오류 로깅을 애플리케이션의 기존 로깅 시스템에 매끄럽게 통합하는 데에도 사용할 수 있습니다.

Section 4.8에는 CUDA의 오류 로그 관리 기능에 대한 더 많은 예시가 나와 있습니다. 오류 로그 관리와 CUDA_LOG_FILE은 NVIDIA 드라이버 버전 r570 이상에서 사용할 수 있습니다.

2.1.8. 디바이스 및 호스트 함수#

__global__ 지정자는 커널의 진입점을 나타내기 위해 사용됩니다. 즉, GPU에서 병렬 실행을 위해 호출될 함수입니다. 대부분의 경우 커널은 호스트에서 실행되지만, 동적 병렬성을 사용하면 다른 커널 내부에서 커널을 실행할 수도 있습니다.

지정자 __device__는 함수가 GPU용으로 컴파일되어야 하며 다른 __device__ 또는 __global__ 함수에서 호출 가능해야 함을 나타냅니다. 클래스 멤버 함수, 펑터, 람다를 포함한 함수는 아래 예시와 같이 __device__ 및 __host__ 둘 다로 지정할 수 있습니다.

2.1.9. 변수 지정자#

CUDA 지정자는 배치를 제어하기 위해 정적 변수 선언에 사용할 수 있습니다.

  • __device__는 변수가 전역 메모리에 저장됨을 지정합니다.

  • __constant__는 변수가 상수 메모리에 저장됨을 지정합니다.

  • __managed__는 변수가 통합 메모리로 저장됨을 지정합니다.

  • __shared__는 변수가 Shared Memory에 저장됨을 지정합니다.

변수가 __device__ 또는 __global__ 함수 내부에서 지정자 없이 선언되면, 가능한 경우 레지스터에 할당되고, 필요할 때는 로컬 메모리에 할당됩니다. __device__ 또는 __global__ 함수 밖에서 지정자 없이 선언된 모든 변수는 시스템 메모리에 할당됩니다.

2.1.9.1. 디바이스 컴파일 감지#

함수가 __host__ __device__로 지정되면, 컴파일러는 이 함수에 대해 GPU 코드와 CPU 코드 모두를 생성하도록 지시받습니다. 이러한 함수에서는 전처리기를 사용하여 GPU용 코드 또는 함수의 CPU 사본에만 해당하는 코드를 지정하는 것이 바람직할 수 있습니다. __CUDA_ARCH_가 정의되어 있는지 확인하는 것이 이를 수행하는 가장 일반적인 방법이며, 아래 예에서 이를 보여줍니다.

2.1.10. 스레드 블록 클러스터#

컴퓨트 기능 9.0부터 CUDA 프로그래밍 모델에는 스레드 블록으로 구성되는 스레드 블록 클러스터라는 선택적 계층 수준이 포함됩니다. 스레드 블록 내의 스레드들이 스트리밍 멀티프로세서에서 함께 스케줄링되도록 보장되는 것과 유사하게, 클러스터 내의 스레드 블록들 또한 GPU 내의 GPU 처리 클러스터(GPC)에서 함께 스케줄링되도록 보장됩니다.

스레드 블록과 마찬가지로, 클러스터도 그림 5에 나와 있듯이 스레드 블록 클러스터의 1차원, 2차원 또는 3차원 그리드로 구성됩니다.

클러스터 내 스레드 블록 수는 사용자가 정의할 수 있으며, CUDA에서는 이식 가능한 클러스터 크기로 클러스터당 최대 8개의 스레드 블록을 지원합니다. 8개의 멀티프로세서를 지원하기에 너무 작은 GPU 하드웨어 또는 MIG 구성에서는 최대 클러스터 크기가 그에 따라 감소합니다. 이러한 더 작은 구성의 식별과, 8을 초과하는 스레드 블록 클러스터 크기를 지원하는 더 큰 구성의 식별은 아키텍처별이며, cudaOccupancyMaxPotentialClusterSize API를 사용하여 조회할 수 있습니다.

클러스터의 모든 스레드 블록은 단일 GPU 처리 클러스터(GPC)에서 동시에 실행되도록 함께 스케줄링되는 것이 보장되며, 클러스터 내 스레드 블록이 cooperative groups API cluster.sync()를 사용해 하드웨어 지원 동기화를 수행할 수 있도록 합니다. 클러스터 그룹은 또한 각각 num_threads() 및 num_blocks() API를 사용하여 스레드 수 또는 블록 수 측면에서 클러스터 그룹 크기를 조회하는 멤버 함수도 제공합니다. 클러스터 그룹에서 스레드 또는 블록의 순위(rank)는 각각 dim_threads() 및 dim_blocks() API를 사용하여 조회할 수 있습니다.

클러스터에 속한 스레드 블록은 분산 공유 메모리에 접근할 수 있는데, 이는 클러스터 내 모든 스레드 블록의 공유 메모리를 결합한 것입니다. 클러스터의 스레드 블록은 분산 공유 메모리의 어떤 주소에 대해서도 읽기, 쓰기 및 원자 연산(atomic)을 수행할 수 있는 능력이 있습니다. 분산 공유 메모리는 분산 공유 메모리에서 히스토그램을 수행하는 예를 제공합니다.

참고

클러스터 지원을 사용하여 실행된 커널에서, gridDim 변수는 호환성을 위해 여전히 스레드 블록 수 측면의 크기를 나타냅니다. 클러스터에서 블록의 순위는 코오퍼러티브 그룹(Cooperative Groups) API를 사용하여 찾을 수 있습니다.

2.1.10.1. 트리플 셰브론 표기법으로 클러스터 실행하기#

스레드 블록 클러스터는 __cluster_dims__(X,Y,Z)을 사용하는 컴파일 타임 커널 속성 또는 CUDA 커널 실행 API cudaLaunchKernelEx를 사용하여 커널에서 활성화할 수 있습니다. 아래 예는 컴파일 타임 커널 속성을 사용하여 클러스터를 실행하는 방법을 보여줍니다. 커널 속성을 사용하는 클러스터 크기는 컴파일 타임에 고정되며, 이후 커널은 고전적인 <<< , >>>를 사용하여 실행할 수 있습니다. 커널이 컴파일 타임 클러스터 크기를 사용하는 경우, 커널을 실행할 때 클러스터 크기를 수정할 수 없습니다.

// Kernel definition
// Compile time cluster size 2 in X-dimension and 1 in Y and Z dimension
__global__ void __cluster_dims__(2, 1, 1) cluster_kernel(float *input, float* output)
{

}

int main()
{
    float *input, *output;
    // Kernel invocation with compile time cluster size
    dim3 threadsPerBlock(16, 16);
    dim3 numBlocks(N / threadsPerBlock.x, N / threadsPerBlock.y);

    // The grid dimension is not affected by cluster launch, and is still enumerated
    // using number of blocks.
    // The grid dimension must be a multiple of cluster size.
    cluster_kernel<<<numBlocks, threadsPerBlock>>>(input, output);
}
