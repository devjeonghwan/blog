2.3. 비동기 실행

2.3.1. 비동기 동시 실행이란?#

CUDA는 여러 작업의 동시, 즉 오버랩(overlapping) 실행을 허용하며, 구체적으로는 다음과 같습니다:

  • 호스트에서의 계산

  • 디바이스에서의 계산

  • 호스트에서 디바이스로의 메모리 전송

  • 디바이스에서 호스트로의 메모리 전송

  • 주어진 디바이스의 메모리 내부에서의 메모리 전송

  • 디바이스 간 메모리 전송

동시성은 비동기 인터페이스를 통해 표현되며, 이때 디스패치 함수 호출 또는 커널 실행(launch)은 즉시 반환됩니다. 비동기 호출은 보통 디스패치된 작업이 완료되기 전에 반환되며, 비동기 작업이 시작되기 전에도 반환될 수 있습니다. 그러면 애플리케이션은 처음에 디스패치된 작업과 동시에 다른 작업을 자유롭게 수행할 수 있습니다. 처음 디스패치된 작업의 최종 결과가 필요할 때, 애플리케이션은 해당 작업이 완료되었는지 보장하기 위해 어떤 형태로든 동기화를 수행해야 합니다. 동시 실행 패턴의 전형적인 예는 호스트 및 디바이스 메모리 전송을 계산과 오버랩하여 오버헤드를 줄이거나 제거하는 것입니다.

일반적으로 비동기 인터페이스는 보통 디스패치된 작업과 동기화하기 위한 세 가지 주요 방법을 제공합니다.

  • 블로킹 방식: 애플리케이션이 작업이 완료될 때까지 블로킹(blocks), 즉 대기하는 함수를 호출

  • 논블로킹 방식 또는 폴링 방식: 애플리케이션이 즉시 반환되며 작업 상태에 대한 정보를 제공하는 함수를 호출

  • 콜백 방식: 작업이 완료되면 사전에 등록된 함수가 실행됨

프로그래밍 인터페이스는 비동기이지만, 실제로 다양한 작업을 동시에 수행할 수 있는 능력은 CUDA 버전과 사용 중인 하드웨어의 컴퓨트 기능에 따라 달라집니다. 이러한 세부 사항은 이 가이드의 이후 섹션에서 다룹니다(참조: 컴퓨트 기능).

CPU와 GPU 동기화에서는 CUDA 런타임 함수 cudaDeviceSynchronize()를 소개했는데, 이는 이전에 발행된 모든 작업이 완료될 때까지 기다리는 블로킹 호출입니다. cudaDeviceSynchronize() 호출이 필요했던 이유는 커널 실행(launch)이 비동기이며 즉시 반환되기 때문입니다. CUDA는 동기화를 위한 블로킹 및 논블로킹 방식 모두에 대한 API를 제공하며, 호스트 측 콜백 함수의 사용도 지원합니다.

CUDA에서 비동기 실행을 위한 핵심 API 구성 요소는 CUDA 스트림과 CUDA 이벤트입니다. 이 섹션의 나머지 부분에서는 이러한 요소를 사용하여 CUDA에서 비동기 실행을 어떻게 표현할 수 있는지 설명합니다.

관련된 주제로는 CUDA 그래프가 있는데, 이는 비동기 연산의 그래프를 미리 정의한 다음 최소한의 오버헤드로 반복 실행할 수 있게 해줍니다. CUDA 그래프는 섹션 2.4.9.2 스트림 캡처를 사용한 CUDA 그래프 소개에서 매우 기초 수준으로 다루며, 보다 포괄적인 논의는 섹션 4.1 CUDA 그래프에서 제공합니다.

2.3.2. CUDA 스트림#

가장 기본적인 수준에서 CUDA 스트림은 프로그래머가 연산들의 시퀀스를 표현할 수 있게 해주는 추상화입니다. 스트림은 프로그램이 메모리 복사나 커널 실행(launch)과 같은 연산을 순서대로 실행되도록 추가할 수 있는 작업 큐처럼 동작합니다. 특정 스트림에 대해 큐의 앞부분에 있는 연산이 실행된 뒤 디큐되어, 다음으로 큐에 들어온 연산이 앞부분으로 이동하고 실행 대상으로 고려될 수 있습니다. 스트림에서의 연산 실행 순서는 순차적이며, 연산들은 스트림에 인큐되는 순서대로 실행됩니다.

애플리케이션은 동시에 여러 스트림을 사용할 수 있습니다. 이러한 경우 런타임은 GPU 리소스 상태에 따라 작업이 가능한 스트림들로부터 실행할 태스크를 선택합니다. 스트림에는 스케줄링에 영향을 주도록 런타임에 힌트로 작용하는 우선순위를 할당할 수 있지만, 특정 실행 순서를 보장하지는 않습니다.

스트림에서 동작하는 API 함수 호출과 커널 실행(launch)은 호스트 스레드에 대해 비동기입니다. 애플리케이션은 스트림에 태스크가 하나도 남지 않을 때까지 기다림으로써 스트림과 동기화할 수 있으며, 또는 디바이스 수준에서 동기화할 수도 있습니다.

CUDA에는 기본 스트림이 있으며, 특정 스트림이 지정되지 않은 연산과 커널 실행(launch)은 이 기본 스트림에 큐잉됩니다. 스트림을 지정하지 않는 코드 예제는 암묵적으로 이 기본 스트림을 사용합니다. 기본 스트림에는 몇 가지 특정 시맨틱이 있으며, 이는 하위 섹션 블로킹 및 논블로킹 스트림과 기본 스트림에서 논의합니다.

2.3.2.1. CUDA 스트림 생성 및 삭제#

CUDA 스트림은 cudaStreamCreate() 함수를 사용하여 생성할 수 있습니다. 이 함수 호출은 이후의 함수 호출에서 스트림을 식별하는 데 사용할 수 있는 스트림 핸들을 초기화합니다.

cudaStream_t stream;        // Stream handle
cudaStreamCreate(&stream);  // Create a new stream

// stream based operations ...

cudaStreamDestroy(stream);  // Destroy the stream

디바이스가 여전히 stream에서 작업을 수행 중이라면 stream 애플리케이션이 호출할 때 cudaStreamDestroy(), 스트림은 삭제되기 전에 해당 스트림의 모든 작업을 완료합니다.

2.3.2.2. CUDA 스트림에서 커널 실행#

커널을 실행하기 위한 일반적인 삼중 꺾쇠(triple-chevron) 구문은 특정 스트림으로 커널을 실행하는 데에도 사용할 수 있습니다. 스트림은 커널 실행 시 추가 매개변수로 지정됩니다. 다음 예제에서는 kernel라는 이름의 커널이 핸들 stream을 가진 스트림으로 실행되며, 이 스트림은 cudaStream_t 타입이고 이전에 생성되었다고 가정합니다:

kernel<<<grid, block, shared_mem_size, stream>>>(...);

커널 실행(launch)은 비동기이며 함수 호출은 즉시 반환됩니다. 커널 실행이 성공했다고 가정하면, 커널은 스트림 stream에서 실행되며 애플리케이션은 커널이 실행되는 동안 CPU에서 또는 GPU의 다른 스트림에서 다른 작업을 자유롭게 수행할 수 있습니다.

2.3.2.3. CUDA 스트림에서 메모리 전송 실행#

스트림으로 메모리 전송을 실행(launch)하려면 다음 함수를 사용할 수 있습니다. cudaMemcpyAsync(). 이 함수는 …와 유사합니다. cudaMemcpy() 함수이지만, 메모리 전송에 사용할 스트림을 지정하는 추가 매개변수를 받습니다. 아래 코드 블록의 함수 호출은 복사합니다 size ...가 가리키는 호스트 메모리로부터 바이트를 src ...가 가리키는 디바이스 메모리로 dst 스트림에서 stream.

// Copy `size` bytes from `src` to `dst` in stream `stream`
cudaMemcpyAsync(dst, src, size, cudaMemcpyHostToDevice, stream);

다른 비동기 함수 호출과 마찬가지로, 이 함수 호출은 즉시 반환되는 반면, cudaMemcpy() 함수는 메모리 전송이 완료될 때까지 블로킹됩니다. 전송 결과에 안전하게 접근하기 위해 애플리케이션은 어떤 형태의 동기화를 사용하여 해당 연산이 완료되었음을 확인해야 합니다.

cudaMemcpy2D()와 같은 다른 CUDA 메모리 전송 함수에도 비동기 변형이 있습니다.

참고

CPU 메모리를 포함하는 메모리 복사를 비동기로 수행하려면, 호스트 버퍼는 핀(pinned) 및 페이지 락(page-locked)되어 있어야 합니다. 핀 및 페이지 락되지 않은 호스트 메모리를 사용하더라도 cudaMemcpyAsync()는 올바르게 동작하지만, 다른 작업과 오버랩되지 않는 동기식 동작으로 되돌아갑니다. 이는 비동기 메모리 전송을 사용할 때의 성능 이점을 저해할 수 있습니다. 프로그램에서는 GPU로 데이터를 보내거나 GPU에서 데이터를 수신하는 데 사용할 버퍼를 할당하기 위해 cudaMallocHost()를 사용할 것을 권장합니다.

2.3.2.4. 스트림 동기화#

스트림과 동기화하는 가장 간단한 방법은 스트림에 작업이 남아 있지 않도록, 즉 스트림이 비워질 때까지 기다리는 것입니다. 이는 cudaStreamSynchronize() 함수 또는 cudaStreamQuery() 함수를 사용하여 두 가지 방식으로 수행할 수 있습니다.

cudaStreamSynchronize() 함수는 스트림 내의 모든 작업이 완료될 때까지 블로킹됩니다.

// Wait for the stream to be empty of tasks
cudaStreamSynchronize(stream);

// At this point the stream is done
// and we can access the results of stream operations safely

블로킹을 원하지 않고 스트림이 비어 있는지 빠르게 확인만 하면 된다면, cudaStreamQuery() 함수를 사용할 수 있습니다.

// Have a peek at the stream
// returns cudaSuccess if the stream is empty
// returns cudaErrorNotReady if the stream is not empty
cudaError_t status = cudaStreamQuery(stream);

switch (status) {
    case cudaSuccess:
        // The stream is empty
        std::cout << "The stream is empty" << std::endl;
        break;
    case cudaErrorNotReady:
        // The stream is not empty
        std::cout << "The stream is not empty" << std::endl;
        break;
    default:
        // An error occurred - we should handle this
        break;
};

2.3.3. CUDA 이벤트#

CUDA 이벤트는 CUDA 스트림에 마커를 삽입하기 위한 메커니즘입니다. 이는 본질적으로 스트림 내 작업의 진행 상황을 추적하는 데 사용할 수 있는 추적자 입자(tracer particles)와 같습니다. 하나의 스트림에 두 개의 커널을 실행(launch)한다고 상상해 보십시오. 이러한 추적 이벤트가 없다면, 우리는 스트림이 비어 있는지 여부만 판단할 수 있습니다. 첫 번째 커널의 출력에 의존하는 연산이 있다면, 스트림이 비어 있음을 알게 될 때까지는 그 연산을 안전하게 시작할 수 없는데, 그 시점이면 두 커널이 모두 완료된 뒤일 것입니다.

CUDA 이벤트를 사용하면 더 나은 방법을 사용할 수 있습니다. 첫 번째 커널 바로 뒤에, 하지만 두 번째 커널 앞에 이벤트를 스트림에 큐잉(enqueue)함으로써, 이 이벤트가 스트림의 맨 앞에 도달할 때까지 기다릴 수 있습니다. 그러면 두 번째 커널이 시작되기 전에 첫 번째 커널이 완료되었음을 알고, 의존하는 연산을 안전하게 시작할 수 있습니다. 이러한 방식으로 CUDA 이벤트를 사용하면 연산과 스트림 간의 의존성 그래프를 구축할 수 있습니다. 이 그래프 비유는 이후 CUDA 그래프에 대한 논의로 직접 이어집니다.

CUDA 스트림은 커널 실행(launch)과 메모리 전송의 시간을 측정하는 데 사용할 수 있는 시간 정보도 유지합니다.

2.3.3.1. CUDA 이벤트 생성 및 파괴#

CUDA 이벤트는 cudaEventCreate() 및 cudaEventDestroy() 함수를 사용하여 생성하고 파괴할 수 있습니다.

cudaEvent_t event;

// Create the event
cudaEventCreate(&event);

// do some work involving the event

// Once the work is done and the event is no longer needed
// we can destroy the event
cudaEventDestroy(event);

애플리케이션은 더 이상 필요하지 않을 때 이벤트를 파괴할 책임이 있습니다.

2.3.3.2. CUDA 스트림에 이벤트 삽입#

CUDA 이벤트는 cudaEventRecord() 함수를 사용하여 스트림에 삽입할 수 있습니다.

cudaEvent_t event;
cudaStream_t stream;

// Create the event
cudaEventCreate(&event);

// Insert the event into the stream
cudaEventRecord(event, stream);

2.3.3.3. CUDA 스트림에서 연산 시간 측정#

CUDA 이벤트는 커널을 포함한 다양한 스트림 연산의 실행 시간을 측정하는 데 사용할 수 있습니다. 이벤트가 스트림의 맨 앞에 도달하면 타임스탬프를 기록합니다. 스트림에서 커널을 두 개의 이벤트로 둘러싸면, 아래 코드 스니펫에 보인 것처럼 커널 실행 지속 시간을 정확하게 측정할 수 있습니다:

cudaStream_t stream;
cudaStreamCreate(&stream);

cudaEvent_t start;
cudaEvent_t stop;

// create the events
cudaEventCreate(&start);
cudaEventCreate(&stop);

 // record the start event
cudaEventRecord(start, stream);

// launch the kernel
kernel<<<grid, block, 0, stream>>>(...);

// record the stop event
cudaEventRecord(stop, stream);

// wait for the stream to complete
// both events will have been triggered
cudaStreamSynchronize(stream);

// get the timing
float elapsedTime;
cudaEventElapsedTime(&elapsedTime, start, stop);
std::cout << "Kernel execution time: " << elapsedTime << " ms" << std::endl;

// clean up
cudaEventDestroy(start);
cudaEventDestroy(stop);
cudaStreamDestroy(stream);

2.3.3.4. CUDA 이벤트 상태 확인#

스트림 상태를 확인하는 경우와 마찬가지로, 이벤트의 상태도 블로킹 또는 논블로킹 방식으로 확인할 수 있습니다.

cudaEventSynchronize() 함수는 이벤트가 완료될 때까지 블록됩니다. 아래 코드 스니펫에서는 스트림에 커널을 실행(launch)한 다음 이벤트를 추가하고, 그 뒤에 두 번째 커널을 실행합니다. cudaEventSynchronize() 함수를 사용하면 첫 번째 커널 뒤의 이벤트가 완료될 때까지 기다린 다음, 원칙적으로는 의존 작업을 즉시 실행할 수 있으며, 잠재적으로 kernel2가 끝나기 전일 수도 있습니다.

cudaEvent_t event;
cudaStream_t stream;

// create the stream
cudaStreamCreate(&stream);

// create the event
cudaEventCreate(&event);

// launch a kernel into the stream
kernel<<<grid, block, 0, stream>>>(...);

// Record the event
cudaEventRecord(event, stream);

// launch a kernel into the stream
kernel2<<<grid, block, 0, stream>>>(...);

// Wait for the event to complete
// Kernel 1 will be  guaranteed to have completed
// and we can launch the dependent task.
cudaEventSynchronize(event);
dependentCPUtask();

// Wait for the stream to be empty
// Kernel 2 is guaranteed to have completed
cudaStreamSynchronize(stream);

// destroy the event
cudaEventDestroy(event);

// destroy the stream
cudaStreamDestroy(stream);

CUDA 이벤트는 cudaEventQuery() 함수를 사용하여 논블로킹 방식으로 완료 여부를 확인할 수 있습니다. 아래 예제에서는 2개의 커널을 하나의 스트림에 실행(launch)합니다. 첫 번째 커널인 kernel1은 일부 데이터를 생성하며, 이를 호스트로 복사하고자 하지만 CPU 측에서도 수행할 작업이 있습니다. 아래 코드에서는 kernel1을 큐잉(enqueue)한 다음 이벤트(event)를 추가하고, 그 뒤에 kernel2를 스트림 stream1에 큐잉합니다. 그런 다음 CPU 작업 루프에 들어가지만, 간간이 이벤트가 완료되었는지(즉 kernel1이 끝났는지) 확인합니다. 그렇다면 호스트에서 디바이스로의 복사를 스트림 stream2에 실행(launch)합니다. 이 접근법은 CPU 작업을 GPU 커널 실행과 디바이스에서 호스트로의 복사와 오버랩(중첩)할 수 있게 해줍니다.

cudaEvent_t event;
cudaStream_t stream1;
cudaStream_t stream2;

size_t size = LARGE_NUMBER;
float *d_data;

// Create some data
cudaMalloc(&d_data, size);
float *h_data = (float *)malloc(size);

// create the streams
cudaStreamCreate(&stream1);   // Processing stream
cudaStreamCreate(&stream2);   // Copying stream
bool copyStarted = false;

//  create the event
cudaEventCreate(&event);

// launch kernel1 into the stream
kernel1<<<grid, block, 0, stream1>>>(d_data, size);
// enqueue an event following kernel1
cudaEventRecord(event, stream1);

// launch kernel2 into the stream
kernel2<<<grid, block, 0, stream1>>>();

// while the kernels are running do some work on the CPU
// but check if kernel1 has completed because then we will start
// a device to host copy in stream2
while ( not allCPUWorkDone() || not copyStarted ) {
    doNextChunkOfCPUWork();

    // peek to see if kernel 1 has completed
    // if so enqueue a non-blocking copy into stream2
    if ( not copyStarted ) {
        if( cudaEventQuery(event) == cudaSuccess ) {
            cudaMemcpyAsync(h_data, d_data, size, cudaMemcpyDeviceToHost, stream2);
            copyStarted = true;
        }
    }
}

// wait for both streams to be done
cudaStreamSynchronize(stream1);
cudaStreamSynchronize(stream2);

// destroy the event
cudaEventDestroy(event);

// destroy the streams and free the data
cudaStreamDestroy(stream1);
cudaStreamDestroy(stream2);
cudaFree(d_data);
free(h_data);

2.3.4. 스트림에서의 콜백 함수#

CUDA는 스트림 내부에서 호스트에서 함수를 실행(launch)할 수 있는 메커니즘을 제공합니다. 현재 이 목적을 위해 사용할 수 있는 함수는 두 가지, 즉 cudaLaunchHostFunc() 및 cudaAddCallback()입니다. 하지만 cudaAddCallback()는 사용 중단(deprecation)될 예정이므로, 애플리케이션은 cudaLaunchHostFunc()를 사용해야 합니다.

cudaLaunchHostFunc() 사용

cudaLaunchHostFunc() 함수의 시그니처는 다음과 같습니다:

cudaError_t cudaLaunchHostFunc(cudaStream_t stream, void (*func)(void *), void *data);

여기서

  • stream: 콜백 함수를 실행(launch)할 스트림.

  • func: 실행(launch)할 콜백 함수.

  • data: 콜백 함수에 전달할 데이터에 대한 포인터.

호스트 함수 자체는 다음 시그니처를 갖는 간단한 C 함수입니다:

void hostFunction(void *data);

여기서 data 매개변수는 함수가 해석할 수 있는 사용자 정의 데이터 구조를 가리킵니다. 이러한 콜백 함수를 사용할 때 유의해야 할 몇 가지 사항이 있습니다. 특히, 호스트 함수는 어떤 CUDA API도 호출할 수 없습니다.

통합 메모리와 함께 사용하기 위한 목적으로, 다음과 같은 실행 보장이 제공됩니다: - 함수의 실행 기간 동안 스트림은 idle 상태로 간주됩니다. 따라서 예를 들어, 함수는 자신이 큐잉(enqueue)된 스트림에 연결된 메모리를 항상 사용할 수 있습니다. - 함수의 실행 시작은, 해당 함수 바로 직전에 동일한 스트림에 기록(record)된 이벤트를 동기화하는 것과 동일한 효과를 가집니다. 따라서 함수 이전에 “joined”된 스트림들을 동기화합니다. - 어떤 스트림에든 디바이스 작업을 추가하더라도, 선행하는 모든 호스트 함수 및 스트림 콜백이 실행될 때까지 그 스트림이 active 상태가 되는 효과는 없습니다. 따라서 예를 들어, 이벤트로 함수 호출 뒤에 순서가 정해진 작업이 다른 스트림에 추가되었더라도, 함수는 글로벌로 연결된 메모리를 사용할 수 있습니다. - 함수의 완료는 위에서 설명한 경우를 제외하고 스트림이 active 상태가 되게 하지 않습니다. 함수 뒤에 디바이스 작업이 없다면 스트림은 idle 상태로 유지되며, 중간에 디바이스 작업이 없는 연속적인 호스트 함수 또는 스트림 콜백에 걸쳐서도 idle 상태로 유지됩니다. 따라서 예를 들어, 스트림 동기화는 스트림 끝에서 호스트 함수가 신호를 보내는 방식으로 수행할 수 있습니다.

2.3.4.1. cudaStreamAddCallback() 사용#

참고

cudaStreamAddCallback() 함수는 사용 중단(deprecation) 및 제거될 예정이며, 여기서는 완전성을 위해 그리고 기존 코드에 여전히 나타날 수 있기 때문에 논의합니다. 애플리케이션은 cudaLaunchHostFunc()를 사용하거나 해당 사용으로 전환해야 합니다.

cudaStreamAddCallback() 함수의 시그니처는 다음과 같습니다:

cudaError_t cudaStreamAddCallback(cudaStream_t stream, cudaStreamCallback_t callback, void* userData, unsigned int flags);

여기서

  • stream: 콜백 함수를 실행(launch)할 스트림.

  • callback: 실행(launch)할 콜백 함수.

  • userData: 콜백 함수에 전달할 데이터에 대한 포인터.

  • flags: 현재 이 매개변수는 향후 호환성을 위해 0이어야 합니다.

callback 함수의 시그니처는 cudaLaunchHostFunc() 함수를 사용했던 경우와 약간 다릅니다. 이 경우 콜백 함수는 다음 시그니처를 갖는 C 함수입니다:

void callbackFunction(cudaStream_t stream, cudaError_t status, void *userData);

여기서 함수는 이제 다음을 전달받습니다

  • stream: 콜백 함수가 실행(launch)된 스트림 핸들.

  • status: 콜백을 트리거한 스트림 연산의 상태.

  • userData: 콜백 함수에 전달된 데이터에 대한 포인터.

특히 status 매개변수에는 이전 연산에 의해 설정되었을 수도 있는 스트림의 현재 오류 상태가 포함됩니다. cudaLaunchHostFunc() func 경우와 마찬가지로, 스트림은 호스트 함수가 완료될 때까지 active 상태가 아니며 작업으로 진행하지 않고, 콜백 함수 내부에서는 어떤 CUDA 함수도 호출할 수 없습니다.

2.3.4.2. 비동기 오류 처리#

cuda stream에서 오류는 스트림의 어떤 연산에서도 발생할 수 있으며, 커널 실행(launch)과 메모리 전송을 포함합니다. 이러한 오류는 예를 들어 이벤트를 기다리거나 cudaStreamSynchronize()를 호출하여 스트림을 동기화할 때까지 런타임에 사용자에게 전파되지 않을 수 있습니다. 스트림에서 발생했을 수 있는 오류를 알아내는 방법은 두 가지가 있습니다.

  • 함수 cudaGetLastError() 사용 - 이 함수는 현재 컨텍스트의 어떤 스트림에서든 마지막으로 발생한 오류를 반환하고 지웁니다(clear). 두 호출 사이에 다른 오류가 발생하지 않았다면, 즉시 두 번째로 cudaGetLastError()를 호출하면 cudaSuccess를 반환합니다.

  • 함수 cudaPeekAtLastError() 사용 - 이 함수는 현재 컨텍스트에서의 마지막 오류를 반환하지만, 이를 지우지는 않습니다.

이 두 함수는 모두 cudaError_t 타입의 값으로 오류를 반환합니다. 오류의 출력 가능한 이름은 cudaGetErrorName() 및 cudaGetErrorString() 함수를 사용해 생성할 수 있습니다.

이들 함수를 사용하는 예시는 아래에 나와 있습니다:

Listing 1 cudaGetLastError()와 cudaPeekAtLastError() 사용 예#
// Some work occurs in streams.
cudaStreamSynchronize(stream);

// Look at the last error but do not clear it
cudaError_t err = cudaPeekAtLastError();
if (err != cudaSuccess) {
    printf("Error with name: %s\n", cudaGetErrorName(err));
    printf("Error description: %s\n", cudaGetErrorString(err));
}

// Look at the last error and clear it
cudaError_t err2 = cudaGetLastError();
if (err2 != cudaSuccess) {
    printf("Error with name: %s\n", cudaGetErrorName(err2));
    printf("Error description: %s\n", cudaGetErrorString(err2));
}

if (err2 != err) {
    printf("As expected, cudaPeekAtLastError() did not clear the error\n");
}

// Check again
cudaError_t err3 = cudaGetLastError();
if (err3 == cudaSuccess) {
    printf("As expected, cudaGetLastError() cleared the error\n");
}

팁

오류가 동기화 시점에 나타날 때, 특히 많은 연산이 있는 스트림에서는 스트림의 정확히 어디에서 오류가 발생했는지 특정하기가 종종 어렵습니다. 이런 상황을 디버그하기 위한 유용한 요령으로는 환경 변수 CUDA_LAUNCH_BLOCKING=1를 설정한 다음 애플리케이션을 실행하는 방법이 있습니다. 이 환경 변수의 효과는 모든 단일 커널 실행(launch) 후에 동기화하는 것입니다. 이는 어떤 커널 또는 전송이 오류를 유발했는지 추적하는 데 도움이 될 수 있습니다. 동기화는 비용이 클 수 있으며, 이 환경 변수가 설정되면 애플리케이션이 상당히 느리게 실행될 수 있습니다.

2.3.5. CUDA 스트림 순서 지정#

이제 스트림, 이벤트 및 콜백 함수의 기본 메커니즘을 논의했으므로, 스트림에서 비동기 연산의 순서 지정 시맨틱을 고려하는 것이 중요합니다. 이러한 시맨틱은 애플리케이션 프로그래머가 스트림에서 연산의 순서를 안전한 방식으로 생각할 수 있도록 하기 위한 것입니다. 성능 최적화를 목적으로 이러한 시맨틱이 완화될 수 있는 몇 가지 특수한 경우가 있는데, 예를 들어 Programmatic Dependent Kernel Launch 시나리오에서는 특수한 속성과 커널 실행(launch) 메커니즘을 통해 두 커널을 오버랩(중첩)할 수 있으며, 또는 런타임이 겹치지 않는 배치 복사를 동시에 수행할 수 있을 때 cudaMemcpyBatchAsync() 함수를 사용해 메모리 전송을 배칭하는 경우가 그렇습니다. 이러한 최적화는 이후에 논의하겠습니다 link needed.

가장 중요한 점은 CUDA 스트림이 이른바 in-order 스트림이라는 것입니다. 이는 스트림 내 연산의 실행 순서가 해당 연산들이 큐잉(enqueue)된 순서와 동일하다는 뜻입니다. 스트림의 연산은 다른 연산을 앞질러 실행할 수 없습니다. 메모리 연산(예: 복사)은 런타임에 의해 추적되며, 의존 커널이 전송 중인 데이터에 안전하게 접근할 수 있도록 다음 연산 전에 항상 완료됩니다.

2.3.6. 블로킹 및 논블로킹 스트림과 기본 스트림#

CUDA에는 두 가지 유형의 스트림이 있습니다: 블로킹과 논블로킹. 이 이름은 다소 오해의 소지가 있을 수 있는데, 블로킹 및 논블로킹 시맨틱은 스트림이 기본 스트림과 어떻게 동기화하는지에만 관련되기 때문입니다. 기본적으로 cudaStreamCreate()로 생성된 스트림은 블로킹 스트림입니다. 논블로킹 스트림을 만들려면 cudaStreamCreateWithFlags() 함수를 cudaStreamNonBlocking 플래그와 함께 사용해야 합니다:

cudaStream_t stream;
cudaStreamCreateWithFlags(&stream, cudaStreamNonBlocking);

그리고 논블로킹 스트림은 일반적인 방식으로 cudaStreamDestroy()를 사용해 삭제할 수 있습니다.

2.3.6.1. 레거시 기본 스트림#

블로킹 및 논블로킹 스트림의 핵심적인 차이점은 기본 스트림과 어떻게 동기화되는지에 있습니다. CUDA는 레거시 기본 스트림( NULL 스트림 또는 stream ID 0을 가진 스트림이라고도 함)을 제공하며, 이는 커널 실행(launch)에서 또는 블로킹 cudaMemcpy() 호출에서 스트림이 지정되지 않았을 때 사용됩니다. 모든 호스트 스레드 간에 공유되던 이 기본 스트림은 블로킹 스트림입니다. 이 기본 스트림에 어떤 연산이 실행(launch)되면 다른 모든 블로킹 스트림과 동기화됩니다. 즉, 실행되기 전에 다른 모든 블로킹 스트림이 완료될 때까지 기다립니다.

cudaStream_t stream1, stream2;
cudaStreamCreate(&stream1);
cudaStreamCreate(&stream2);

kernel1<<<grid, block, 0, stream1>>>(...);
kernel2<<<grid, block>>>(...);
kernel3<<<grid, block, 0, stream2>>>(...);

cudaDeviceSynchronize();

기본 스트림 동작은 위의 코드 스니펫에서 kernel2가 kernel1이 완료될 때까지 기다리고, kernel3가 kernel2가 완료될 때까지 기다리게 함을 의미하며, 원칙적으로는 세 커널 모두가 동시에 실행될 수 있음에도 그렇습니다. 논블로킹 스트림을 생성하면 이러한 동기화 동작을 피할 수 있습니다. 아래 코드 스니펫에서는 두 개의 논블로킹 스트림을 생성합니다. 기본 스트림은 더 이상 이들 스트림과 동기화되지 않으며, 원칙적으로 세 커널 모두가 동시에 실행될 수 있습니다. 따라서 커널의 실행 순서에 대해 어떤 것도 가정할 수 없으며, 커널이 완료되었음을 보장하기 위해 (다소 강경한 cudaDeviceSynchronize() 호출과 같은) 명시적 동기화를 수행해야 합니다.

cudaStream_t stream1, stream2;
cudaStreamCreateWithFlags(&stream1, cudaStreamNonBlocking);
cudaStreamCreateWithFlags(&stream2, cudaStreamNonBlocking);

kernel1<<<grid, block, 0, stream1>>>(...);
kernel2<<<grid, block>>>(...);
kernel3<<<grid, block, 0, stream2>>>(...);

cudaDeviceSynchronize();

2.3.6.2. 스레드별 기본 스트림#

CUDA-7부터 CUDA는 공유 레거시 기본 스트림 대신, 각 호스트 스레드가 자체적으로 독립적인 기본 스트림을 갖도록 허용합니다. 이 동작을 활성화하려면 nvcc 컴파일러 옵션 --default-stream per-thread을 사용하거나, CUDA_API_PER_THREAD_DEFAULT_STREAM 전처리기 매크로를 정의해야 합니다. 이 동작이 활성화되면 각 호스트 스레드는 자체적인 독립 기본 스트림을 가지며, 이는 레거시 기본 스트림이 하던 것과 같은 방식으로 다른 스트림들과 동기화되지 않습니다. 이러한 상황에서는 레거시 기본 스트림 예제가 이제 논블로킹 스트림 예제와 동일한 동기화 동작을 보이게 됩니다.

2.3.7. 명시적 동기화#

스트림을 서로 명시적으로 동기화하는 방법은 여러 가지가 있습니다.

cudaDeviceSynchronize()는 모든 호스트 스레드의 모든 스트림에 있는 모든 선행 명령이 완료될 때까지 기다립니다.

cudaStreamSynchronize()는 스트림을 매개변수로 받아, 지정된 스트림에서 모든 선행 명령이 완료될 때까지 기다립니다. 이를 통해 호스트를 특정 스트림과 동기화할 수 있으며, 다른 스트림은 디바이스에서 계속 실행되도록 둘 수 있습니다.

cudaStreamWaitEvent()는 스트림과 이벤트를 매개변수로 받으며(이벤트에 대한 설명은 CUDA 이벤트 참조), cudaStreamWaitEvent() 호출 이후 지정된 스트림에 추가되는 모든 명령이 지정된 이벤트가 완료될 때까지 실행을 지연하도록 만듭니다.

cudaStreamQuery()는 애플리케이션이 스트림에서 모든 선행 명령이 완료되었는지 알 수 있는 방법을 제공합니다.

2.3.8. 암묵적 동기화#

서로 다른 스트림의 두 연산은, 그 사이에 NULL 스트림에서 어떤 CUDA 연산이 제출되면 동시에 실행될 수 없습니다. 단, 스트림이 논블로킹 스트림(cudaStreamNonBlocking 플래그로 생성됨)인 경우는 예외입니다.

애플리케이션은 동시 커널 실행 가능성을 개선하기 위해 다음 지침을 따라야 합니다:

  • 모든 독립 연산은 의존 연산보다 먼저 발행해야 하며,

  • 어떤 종류의 동기화든 가능한 한 늦춰야 합니다.

2.3.9. 기타 및 고급 주제#

2.3.9.1. 스트림 우선순위 지정#

앞서 언급했듯이, 개발자는 CUDA 스트림에 우선순위를 할당할 수 있습니다. 우선순위가 지정된 스트림은 cudaStreamCreateWithPriority() 함수를 사용해 생성해야 합니다. 이 함수는 스트림 핸들 및 우선순위 레벨이라는 두 매개변수를 받습니다. 일반적인 체계는 숫자가 낮을수록 우선순위가 높다는 것입니다. 주어진 디바이스 및 컨텍스트에 대한 우선순위 범위는 cudaDeviceGetStreamPriorityRange() 함수를 사용해 조회할 수 있습니다. 스트림의 기본 우선순위는 0입니다.

int minPriority, maxPriority;

// Query the priority range for the device
cudaDeviceGetStreamPriorityRange(&minPriority, &maxPriority);

// Create two streams with different priorities
// cudaStreamDefault indicates the stream should be created with default flags
// in other words they will be blocking streams with respect to the legacy default stream
// One could also use the option `cudaStreamNonBlocking` here to create a non-blocking streams
cudaStream_t stream1, stream2;
cudaStreamCreateWithPriority(&stream1, cudaStreamDefault, minPriority);  // Lowest priority
cudaStreamCreateWithPriority(&stream2, cudaStreamDefault, maxPriority);  // Highest priority

스트림의 우선순위는 런타임에 대한 힌트일 뿐이며 일반적으로 주로 커널 실행(launch)에 적용된다는 점을 유의해야 하며, 메모리 전송에 대해서는 존중되지 않을 수 있습니다. 스트림 우선순위는 이미 실행 중인 작업을 선점(preempt)하지 않으며, 어떤 특정 실행 순서도 보장하지 않습니다.

2.3.9.2. 스트림 캡처를 사용한 CUDA 그래프 소개#

CUDA 스트림을 사용하면 프로그램이 커널 또는 메모리 복사와 같은 연산들의 시퀀스를 순서대로 지정할 수 있습니다. 여러 스트림과 cudaStreamWaitEvent을 사용한 스트림 간 의존성을 활용하면, 애플리케이션은 연산들의 완전한 방향성 비순환 그래프(DAG)를 지정할 수 있습니다. 일부 애플리케이션은 실행 동안 여러 번 실행해야 하는 연산의 시퀀스 또는 DAG를 가질 수 있습니다.

이러한 상황을 위해 CUDA는 CUDA 그래프라는 기능을 제공합니다. 이 섹션에서는 CUDA 그래프와, 이를 생성하는 한 가지 메커니즘인 스트림 캡처를 소개합니다. CUDA 그래프에 대한 더 자세한 논의는 CUDA 그래프에서 제시됩니다. 그래프를 캡처하거나 생성하면 호스트 스레드에서 동일한 API 호출 체인을 반복적으로 호출할 때의 지연 시간과 CPU 오버헤드를 줄이는 데 도움이 될 수 있습니다. 대신, 그래프 연산을 지정하기 위한 API는 한 번만 호출하고, 그 결과로 생성된 그래프를 여러 번 실행할 수 있습니다.

CUDA 그래프는 다음과 같은 방식으로 동작합니다:

  1. 그래프는 애플리케이션에 의해 캡처됩니다. 이 단계는 그래프가 처음 실행될 때 한 번 수행됩니다. 그래프는 CUDA 그래프 API를 사용해 수동으로 구성할 수도 있습니다.

  2. 그래프가 인스턴스화됩니다. 이 단계는 그래프가 캡처된 후 한 번 수행됩니다. 이 단계에서는 그래프를 실행하는 데 필요한 다양한 런타임 구조를 모두 설정하여, 구성 요소를 가능한 한 빠르게 실행(launch)할 수 있도록 합니다.

  3. 나머지 단계에서는 미리 인스턴스화된 그래프가 필요할 때마다 여러 번 실행됩니다. 그래프 연산을 실행하는 데 필요한 모든 런타임 구조가 이미 준비되어 있으므로, 그래프 실행의 CPU 오버헤드는 최소화됩니다.

Listing 2 CUDA 그래프를 사용하여 단순 선형 그래프를 캡처, 인스턴스화 및 실행하는 단계(CUDA Developer Technical Blog에서 발췌, A. Gray, 2019)#
#define N 500000 // tuned such that kernel takes a few microseconds

// A very lightweight kernel
__global__ void shortKernel(float * out_d, float * in_d){
    int idx=blockIdx.x*blockDim.x+threadIdx.x;
    if(idx<N) out_d[idx]=1.23*in_d[idx];
}

bool graphCreated=false;
cudaGraph_t graph;
cudaGraphExec_t instance;

// The graph will be executed NSTEP times
for(int istep=0; istep<NSTEP; istep++){
    if(!graphCreated){
        // Capture the graph
        cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);

        // Launch NKERNEL kernels
        for(int ikrnl=0; ikrnl<NKERNEL; ikrnl++){
            shortKernel<<<blocks, threads, 0, stream>>>(out_d, in_d);
        }

        // End the capture
        cudaStreamEndCapture(stream, &graph);

        // Instantiate the graph
        cudaGraphInstantiate(&instance, graph, NULL, NULL, 0);
        graphCreated=true;
    }

    // Launch the graph
    cudaGraphLaunch(instance, stream);

    // Synchronize the stream
    cudaStreamSynchronize(stream);
}

CUDA 그래프에 대한 훨씬 더 자세한 내용은 CUDA 그래프에서 제공합니다.

2.3.10. 비동기 실행 요약#

이 섹션의 핵심 요점은 다음과 같습니다:

  • 비동기 API는 작업의 동시 실행을 표현할 수 있게 해주며, 다양한 연산의 오버랩(중첩)을 표현하는 방법을 제공합니다. 실제로 달성되는 동시성은 사용 가능한 하드웨어 리소스와 컴퓨트-캐퍼빌리티(compute-capabilities)에 따라 달라집니다.

  • CUDA에서 비동기 실행을 위한 핵심 추상화는 스트림, 이벤트 및 콜백 함수입니다.

  • 동기화는 이벤트, 스트림 및 디바이스 수준에서 가능합니다

  • 기본 스트림은 모든 다른 블로킹 스트림과 동기화되는 블로킹 스트림이지만, 논블로킹 스트림과는 동기화되지 않습니다

  • 기본 스트림 동작은 --default-stream per-thread 컴파일러 옵션 또는 CUDA_API_PER_THREAD_DEFAULT_STREAM 전처리기 매크로를 통해 스레드별 기본 스트림을 사용함으로써 피할 수 있습니다.

  • 스트림은 서로 다른 우선순위로 생성할 수 있으며, 이는 런타임에 대한 힌트이고 메모리 전송에 대해서는 존중되지 않을 수 있습니다.

  • CUDA는 CUDA 그래프, 배치 메모리 전송(Batched Memory Transfers), 프로그래머블 종속 커널 실행(launch)(Programmatic Dependent Kernel Launch)과 같이 커널 실행(launch)과 메모리 전송의 오버헤드를 줄이거나 오버랩(중첩)하기 위한 API 함수를 제공합니다.
