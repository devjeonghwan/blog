3.1. 고급 CUDA API 및 기능

이 섹션에서는 더 고급 CUDA API 및 기능의 사용을 다룹니다. 이러한 주제는 일반적으로 CUDA 커널 수정이 필요하지 않은 기법이나 기능을 다루지만, 호스트 측에서 GPU 작업 실행과 성능뿐 아니라 CPU 측 성능을 포함한 애플리케이션 수준의 동작에도 영향을 줄 수 있습니다.

3.1.1. cudaLaunchKernelEx#

세 개의 꺾쇠(triple chevron) 표기법이 처음 버전에 도입되었을 때, 커널의 커널 구성(Kernel Configuration)에는 프로그래밍 가능한 매개변수가 네 가지뿐이었습니다: - 스레드 블록 차원 - 그리드 차원 - 동적 공유 메모리(선택 사항, 지정하지 않으면 0) - 스트림(지정하지 않으면 기본 스트림 사용)

일부 CUDA 기능은 커널 실행과 함께 제공되는 추가 속성과 힌트의 이점을 누릴 수 있습니다. cudaLaunchKernelEx을 사용하면 프로그램이 cudaLaunchConfig_t 구조체를 통해 앞서 언급한 실행 구성 매개변수를 설정할 수 있습니다. 또한, cudaLaunchConfig_t 구조체를 사용하면 프로그램이 커널 실행의 다른 매개변수를 제어하거나 제안하기 위해 0개 이상의 cudaLaunchAttributes을 전달할 수 있습니다. 예를 들어, 이 장의 후반부에서 논의되는 cudaLaunchAttributePreferredSharedMemoryCarveout(L1/공유 메모리 균형 구성 참조)는 cudaLaunchKernelEx을 사용하여 지정됩니다. 이 장의 후반부에서 논의되는 cudaLaunchAttributeClusterDimension 속성은 커널 실행에 대해 원하는 클러스터 크기를 지정하는 데 사용됩니다.

지원되는 속성과 그 의미의 전체 목록은 CUDA Runtime API 참조 문서에 정리되어 있습니다.

3.1.2. 클러스터 실행:#

이전 섹션에서 소개된 스레드 블록 클러스터는 컴퓨트 기능 9.0 이상에서 사용할 수 있는 선택적 스레드 블록 조직화 수준으로, 애플리케이션이 클러스터의 스레드 블록들이 단일 GPC에서 동시에 실행됨을 보장할 수 있게 해줍니다. 이를 통해 단일 SM에 들어맞는 것보다 더 큰 스레드 그룹이 서로 데이터를 교환하고 동기화할 수 있습니다.

섹션 2.1.10.1에서는 클러스터를 사용하는 커널을 세 개의 꺾쇠(triple chevron) 표기법으로 지정하고 실행하는 방법을 보여주었습니다. 이 섹션에서는 __cluster_dims__ 애너테이션(annotation)을 사용하여 커널 실행에 사용해야 하는 클러스터의 차원을 지정했습니다. 세 개의 꺾쇠(triple chevron) 표기법을 사용할 때는 클러스터의 크기가 암묵적으로 결정됩니다.

3.1.2.1. cudaLaunchKernelEx를 사용한 클러스터 실행#

세 개의 꺾쇠(triple chevron) 표기법으로 클러스터를 사용해 커널 실행과 달리, 스레드 블록 클러스터의 크기는 실행(launch)마다 구성할 수 있습니다. 아래 코드 예제는 cudaLaunchKernelEx을 사용하여 클러스터 커널을 실행하는 방법을 보여줍니다.

// Kernel definition
// No compile time attribute attached to the kernel
__global__ void cluster_kernel(float *input, float* output)
{

}

int main()
{
    float *input, *output;
    dim3 threadsPerBlock(16, 16);
    dim3 numBlocks(N / threadsPerBlock.x, N / threadsPerBlock.y);

    // Kernel invocation with runtime cluster size
    {
        cudaLaunchConfig_t config = {0};
        // The grid dimension is not affected by cluster launch, and is still enumerated
        // using number of blocks.
        // The grid dimension should be a multiple of cluster size.
        config.gridDim = numBlocks;
        config.blockDim = threadsPerBlock;

        cudaLaunchAttribute attribute[1];
        attribute[0].id = cudaLaunchAttributeClusterDimension;
        attribute[0].val.clusterDim.x = 2; // Cluster size in X-dimension
        attribute[0].val.clusterDim.y = 1;
        attribute[0].val.clusterDim.z = 1;
        config.attrs = attribute;
        config.numAttrs = 1;

        cudaLaunchKernelEx(&config, cluster_kernel, input, output);
    }
}

스레드 블록 클러스터와 관련된 cudaLaunchAttribute 타입은 두 가지가 있습니다: cudaLaunchAttributeClusterDimension 및 cudaLaunchAttributePreferredClusterDimension.

attribute id cudaLaunchAttributeClusterDimension 클러스터를 실행하는 데 필요한 차원을 지정합니다. 이 attribute의 값은, clusterDim, 3차원 값입니다. 그리드의 해당 차원(x, y, z)은 지정된 클러스터 차원의 각 차원으로 나누어떨어져야 합니다. 이를 설정하는 것은 __cluster_dims__ 에 표시된 것처럼 컴파일 시간에 커널 정의에 attribute를 설정하는 것과 유사합니다. 세 개의 꺾쇠(triple chevron) 표기법에서 클러스터로 실행, 하지만 동일한 커널을 서로 다른 실행(launch)으로 실행할 때 런타임에 변경할 수 있습니다.

컴퓨트 성능(compute capability)이 10.0 이상인 GPU에서는, 또 다른 attribute id인 cudaLaunchAttributePreferredClusterDimension를 통해 애플리케이션이 클러스터에 대해 선호하는 차원(preferred dimension)을 추가로 지정할 수 있습니다. 선호 차원은 커널의 __cluster_dims__ attribute 또는 cudaLaunchAttributeClusterDimension attribute에서 cudaLaunchKernelEx에 지정된 최소 클러스터 차원의 정수 배여야 합니다. 즉, 선호 클러스터 차원에 더해 최소 클러스터 차원도 지정해야 합니다. 그리드의 해당 차원(x, y, z)은 지정된 선호 클러스터 차원의 각 차원으로 나누어떨어져야 합니다.

모든 스레드 블록은 최소 클러스터 차원 이상인 클러스터에서 실행됩니다. 가능한 경우 선호 차원의 클러스터가 사용되지만, 모든 클러스터가 선호 차원으로 실행되는 것이 보장되지는 않습니다. 모든 스레드 블록은 최소 또는 선호 클러스터 차원 중 하나를 갖는 클러스터에서 실행됩니다. 선호 클러스터 차원을 사용하는 커널은 최소 또는 선호 클러스터 차원 어느 쪽에서도 올바르게 동작하도록 작성되어야 합니다.

3.1.2.2. 클러스터로서의 블록#

커널이 __cluster_dims__ 애너테이션(annotation)으로 정의되면, 그리드 내 클러스터 수는 암묵적이며 지정된 클러스터 크기로 나눈 그리드 크기에서 계산할 수 있습니다.

__cluster_dims__((2, 2, 2)) __global__ void foo();

// 8x8x8 clusters each with 2x2x2 thread blocks.
foo<<<dim3(16, 16, 16), dim3(1024, 1, 1)>>>();

위 예제에서 커널은 16x16x16 스레드 블록의 그리드로 실행되며, 이는 8x8x8 클러스터의 그리드가 사용됨을 의미합니다.

커널은 대안으로 __block_size__ 애너테이션(annotation)을 사용할 수 있는데, 이는 커널이 정의될 때 필요한 블록 크기와 클러스터 크기를 모두 지정합니다. 이 애너테이션을 사용하면 아래와 같이 세 개의 꺾쇠(triple chevron) 실행은 스레드 블록이 아니라 클러스터 관점의 그리드 차원이 됩니다.

// Implementation detail of how many threads per block and blocks per cluster
// is handled as an attribute of the kernel.
__block_size__((1024, 1, 1), (2, 2, 2)) __global__ void foo();

// 8x8x8 clusters.
foo<<<dim3(8, 8, 8)>>>();

__block_size__ 각각 3개 요소로 이루어진 튜플(tuple)인 두 개의 필드가 필요합니다. 첫 번째 튜플은 블록 차원을 나타내고 두 번째는 클러스터 크기입니다. 두 번째 튜플은 ~로 가정됩니다. (1,1,1) 전달되지 않는 경우에 해당합니다. 스트림을 지정하려면 전달해야 합니다 1 및 0 내에서 두 번째 및 세 번째 인수로 <<<>>> 그리고 마지막으로 스트림입니다. 다른 값을 전달하면 정의되지 않은 동작(behavior)이 발생합니다.

두 번째 튜플이 다음과 같은 경우는 불법이라는 점에 유의하세요. __block_size__ 그리고 __cluster_dims__ 가 동시에 지정되는 것은 불법입니다. 또한 사용하는 것도 불법입니다. __block_size__ 비어 있는 __cluster_dims__. 두 번째 튜플의 경우 __block_size__ 가 지정되면, “Blocks as Clusters”가 활성화되었음을 의미하며 컴파일러는 내부의 첫 번째 인수를 인식합니다. <<<>>> 스레드 블록 대신 클러스터의 개수로.

3.1.3. 스트림 및 이벤트에 대한 추가 내용#

CUDA 스트림에서는 CUDA 스트림의 기초를 소개했습니다. 기본적으로, 주어진 CUDA 스트림에 제출된 작업은 직렬화됩니다. 즉, 이전 작업이 완료될 때까지 다음 작업을 실행하기 시작할 수 없습니다. 유일한 예외는 최근에 추가된 프로그래밍 방식 종속 런치 및 동기화 기능입니다. 여러 CUDA 스트림을 갖는 것은 동시 실행을 가능하게 하는 한 가지 방법이며, 또 다른 방법은 CUDA 그래프를 사용하는 것입니다. 이 두 접근 방식은 함께 결합할 수도 있습니다.

서로 다른 CUDA 스트림에 제출된 작업은 특정한 상황에서 동시 실행될 수도 있습니다. 예를 들어, 이벤트 종속성이 없고, 암묵적 동기화가 없으며, 충분한 리소스가 있는 경우 등입니다.

서로 다른 CUDA 스트림의 독립적인 작업은, 그 사이에 NULL 스트림에서 어떤 CUDA 작업이라도 제출되면(스트림이 non-blocking CUDA 스트림이 아닌 한) 동시 실행될 수 없습니다. non-blocking CUDA 스트림은 cudaStreamCreateWithFlags() 런타임 API를 cudaStreamNonBlocking 플래그와 함께 사용하여 생성한 스트림입니다. GPU 작업의 동시 실행 가능성을 높이기 위해, 사용자가 non-blocking CUDA 스트림을 생성할 것을 권장합니다.

또한 사용자는 자신의 문제에 충분한 가장 덜 일반적인 동기화 옵션을 선택하는 것이 권장됩니다. 예를 들어, 요구 사항이 CPU가 특정 CUDA 스트림에서의 모든 작업이 완료될 때까지 기다리도록(블로킹) 하는 것이라면, 해당 스트림에 대해 cudaStreamSynchronize()를 사용하는 것이 cudaDeviceSynchronize()를 사용하는 것보다 바람직합니다. 후자는 장치의 모든 CUDA 스트림에서의 GPU 작업이 완료될 때까지 불필요하게 기다리게 하기 때문입니다. 그리고 요구 사항이 CPU가 블로킹 없이 기다리는 것이라면, cudaStreamQuery()를 사용하고 폴링 루프에서 그 반환 값을 확인하는 것이 더 바람직할 수 있습니다.

유사한 동기화 효과는 CUDA 이벤트(CUDA Events)로도 달성할 수 있습니다. 예를 들어, 해당 스트림에서 이벤트를 기록하고 cudaEventSynchronize()를 호출하여, 해당 이벤트에 캡처된 작업이 완료될 때까지 블로킹 방식으로 기다릴 수 있습니다. 다시 말해, 이는 cudaDeviceSynchronize()를 사용하는 것보다 바람직하며 더 집중된 방법입니다. cudaEventQuery()를 호출하고, 예를 들어 폴링 루프에서 그 반환 값을 확인하는 것은 블로킹이 없는 대안이 될 수 있습니다.

명시적 동기화 방법의 선택은 이 작업이 애플리케이션의 크리티컬 패스에서 발생하는 경우 특히 중요합니다. 표 4는 호스트와의 다양한 동기화 옵션에 대한 상위 수준 요약을 제공합니다

cudaDeviceSynchronize()

CUDA 스트림 간의 동기화, 즉 의존성을 표현하기 위해서는 CUDA 이벤트에 설명된 대로 타이밍이 없는 CUDA 이벤트를 사용하는 것이 권장됩니다. 사용자는 cudaStreamWaitEvent()를 호출하여 특정 스트림에 향후 제출될 작업이, 이전에 기록된 이벤트(예: 다른 스트림에서)의 완료를 기다리도록 강제할 수 있습니다. 이벤트를 기다리거나 쿼리하는 어떤 CUDA API에 대해서도, 기록되지 않은 이벤트는 항상 성공을 반환하므로 cudaEventRecord API가 이미 호출되었는지 보장하는 것은 사용자의 책임임에 유의하세요.

CUDA 이벤트는 기본적으로, cudaEventElapsedTime() API 호출에서 사용할 수 있으므로 타이밍 정보를 담고 있습니다. 하지만 스트림 간 의존성을 표현하는 데에만 사용되는 CUDA 이벤트에는 타이밍 정보가 필요하지 않습니다. 이러한 경우 성능 향상을 위해 타이밍 정보를 비활성화한 상태로 이벤트를 생성하는 것이 권장됩니다. 이는 cudaEventCreateWithFlags() API를 cudaEventDisableTiming 플래그와 함께 사용하여 가능합니다.

3.1.3.1. 스트림 우선순위#

스트림의 상대적 우선순위는 생성 시점에 cudaStreamCreateWithPriority()를 사용하여 지정할 수 있습니다. [가장 높은 우선순위, 가장 낮은 우선순위] 순으로 정렬된 허용 우선순위 범위는 cudaDeviceGetStreamPriorityRange() 함수를 사용하여 얻을 수 있습니다. 런타임에서 GPU 스케줄러는 스트림 우선순위를 활용하여 작업 실행 순서를 결정하지만, 이러한 우선순위는 보장이라기보다는 힌트로 작동합니다. 실행할 작업을 선택할 때는 더 높은 우선순위 스트림에 대기 중인 작업이 더 낮은 우선순위 스트림의 작업보다 우선합니다. 더 높은 우선순위 작업이 이미 실행 중인 더 낮은 우선순위 작업을 선점(preempt)하지는 않습니다. GPU는 작업 실행 중에 작업 큐를 재평가하지 않으며, 스트림의 우선순위를 높여도 진행 중인 작업이 중단되지는 않습니다. 스트림 우선순위는 엄격한 순서를 강제하지 않고 작업 실행에 영향을 미치므로, 사용자는 엄격한 순서 보장에 의존하지 않고도 스트림 우선순위를 활용해 작업 실행에 영향을 줄 수 있습니다.

다음 코드 샘플은 현재 장치에서 허용되는 우선순위 범위를 가져오고, 사용 가능한 가장 높은 우선순위와 가장 낮은 우선순위로 두 개의 비블로킹 CUDA 스트림을 생성합니다.

// get the range of stream priorities for this device
int leastPriority, greatestPriority;
cudaDeviceGetStreamPriorityRange(&leastPriority, &greatestPriority);

// create streams with highest and lowest available priorities
cudaStream_t st_high, st_low;
cudaStreamCreateWithPriority(&st_high, cudaStreamNonBlocking, greatestPriority));
cudaStreamCreateWithPriority(&st_low, cudaStreamNonBlocking, leastPriority);

3.1.3.2. 명시적 동기화#

앞서 설명했듯이, 스트림이 다른 스트림과 동기화할 수 있는 방법은 여러 가지가 있습니다. 다음은 서로 다른 세분화 수준에서의 일반적인 방법을 제공합니다: - cudaDeviceSynchronize()는 모든 호스트 스레드의 모든 스트림에 있는 모든 선행 명령이 완료될 때까지 기다립니다. - cudaStreamSynchronize()는 스트림을 매개변수로 받아, 해당 스트림에서 모든 선행 명령이 완료될 때까지 기다립니다. 이를 사용하면 호스트를 특정 스트림과 동기화할 수 있어, 다른 스트림은 장치에서 계속 실행할 수 있습니다. - cudaStreamWaitEvent()는 스트림과 이벤트를 매개변수로 받으며(이벤트에 대한 설명은 CUDA 이벤트 참조), cudaStreamWaitEvent() 호출 이후 주어진 스트림에 추가된 모든 명령이 주어진 이벤트가 완료될 때까지 실행을 지연하도록 만듭니다. - cudaStreamQuery()는 애플리케이션이 스트림에서 모든 선행 명령이 완료되었는지 알 수 있는 방법을 제공합니다.

3.1.3.3. 암묵적 동기화#

호스트 스레드가 두 스트림의 서로 다른 두 명령 사이에 다음 작업 중 하나라도 발행하면, 이 두 명령은 동시에 실행될 수 없습니다:

  • 페이지 잠금(page-locked) 호스트 메모리 할당

  • 장치 메모리 할당

  • 장치 메모리 설정

  • 같은 장치 메모리로의 두 주소 간 메모리 복사

  • NULL 스트림으로의 모든 CUDA 명령

  • L1/shared 메모리 구성 간 전환

종속성 검사가 필요한 작업에는, 검사 중인 실행(launch)과 같은 스트림 내의 다른 모든 명령과 해당 스트림에서 cudaStreamQuery()을 호출하는 모든 경우가 포함됩니다. 따라서 애플리케이션은 커널 동시 실행 가능성을 높이기 위해 다음 지침을 따라야 합니다:

  • 모든 독립적인 작업은 종속적인 작업보다 먼저 발행해야 하며,

  • 어떤 종류의 동기화든 가능한 한 오래 지연해야 합니다.

3.1.4. 프로그래밍 방식 종속 커널 실행#

앞서 논의했듯이, CUDA 스트림의 의미론은 커널이 순서대로 실행된다는 것입니다. 이는 두 개의 연속된 커널이 있고 두 번째 커널이 첫 번째 커널의 결과에 의존하는 경우, 프로그래머가 두 번째 커널이 실행을 시작할 때쯤이면 종속 데이터가 사용 가능하다는 점을 안전하게 확신할 수 있도록 하기 위함입니다. 하지만 첫 번째 커널이 이후 커널이 의존하는 데이터를 이미 전역 메모리에 써 두었음에도 불구하고 여전히 더 수행할 작업이 남아 있을 수 있습니다. 마찬가지로, 종속적인 두 번째 커널도 첫 번째 커널의 데이터가 필요해지기 전까지 수행할 수 있는 독립적인 작업이 일부 있을 수 있습니다. 이런 상황에서는(하드웨어 리소스를 사용할 수 있다는 가정 하에) 두 커널의 실행을 부분적으로 오버랩할 수 있습니다. 오버랩은 두 번째 커널의 실행 오버헤드도 함께 오버랩할 수 있습니다. 하드웨어 리소스의 가용성 외에도, 달성 가능한 오버랩의 정도는 다음과 같은 커널의 구체적인 구조에 따라 달라집니다.

  • 첫 번째 커널은 실행 중 어느 시점에 두 번째 커널이 의존하는 작업을 완료하는가?

  • 두 번째 커널은 실행 중 어느 시점에 첫 번째 커널의 데이터에 대한 작업을 시작하는가?

이는 해당 커널들 자체에 매우 크게 의존하므로 완전히 자동화하기가 어렵고, 따라서 CUDA는 애플리케이션 개발자가 두 커널 사이의 동기화 지점을 지정할 수 있는 메커니즘을 제공합니다. 이는 프로그래밍 방식 종속 커널 실행(Programmatic Dependent Kernel Launch)으로 알려진 기법을 통해 이루어집니다. 아래 그림은 이 상황을 보여줍니다.

PDL은 세 가지 주요 구성 요소로 이루어져 있습니다.

  1. 첫 번째 커널(소위 주(primary) 커널)은 이후의 종속 커널( 보조(secondary) 커널이라고도 함)이 필요로 하는 모든 작업을 끝냈음을 나타내기 위해 특수 함수를 호출해야 합니다. 이는 함수 cudaTriggerProgrammaticLaunchCompletion()를 호출함으로써 수행됩니다.

  2. 그에 따라 종속적인 보조 커널은 주 커널과 독립적인 작업 부분에 도달했으며 이제 자신이 의존하는 작업을 주 커널이 완료하기를 기다리고 있음을 나타내야 합니다. 이는 함수 cudaGridDependencySynchronize()로 수행됩니다.

  3. 두 번째 커널은 특수 attribute cudaLaunchAttributeProgrammaticStreamSerialization을 사용하여 실행되어야 하며, 그 programmaticStreamSerializationAllowed 필드는 ‘1’로 설정되어야 합니다.

다음 코드 스니펫은 이를 수행하는 방법의 예를 보여줍니다.

Listing 3 두 개의 커널을 사용한 프로그래밍 방식 종속 커널 실행 예#
__global__ void primary_kernel() {
    // Initial work that should finish before starting secondary kernel

    // Trigger the secondary kernel
    cudaTriggerProgrammaticLaunchCompletion();

    // Work that can coincide with the secondary kernel
}

__global__ void secondary_kernel()
{
    // Initialization, Independent work, etc.

    // Will block until all primary kernels the secondary kernel is dependent on have
    // completed and flushed results to global memory
    cudaGridDependencySynchronize();

    // Dependent work
}

// Launch the secondary kernel with the special attribute

// Set Up the attribute
cudaLaunchAttribute attribute[1];
attribute[0].id = cudaLaunchAttributeProgrammaticStreamSerialization;
attribute[0].val.programmaticStreamSerializationAllowed = 1;

// Set the attribute in a kernel launch configuration
 cudaLaunchConfig_t config = {0};

// Base launch configuration
config.gridDim = grid_dim;
config.blockDim = block_dim;
config.dynamicSmemBytes= 0;
config.stream = stream;

// Add special attribute for PDL
config.attrs = attribute;
config.numAttrs = 1;

// Launch primary kernel
primary_kernel<<<grid_dim, block_dim, 0, stream>>>();

// Launch secondary (dependent) kernel using the configuration with
// the attribute
cudaLaunchKernelEx(&config, secondary_kernel);

3.1.5. 배치 메모리 전송#

CUDA 개발에서 흔한 패턴은 배칭(batching) 기법을 사용하는 것입니다. 배칭이란 느슨하게 말해 여러 개(일반적으로 작은) 작업을 하나의(일반적으로 더 큰) 작업으로 묶는 것을 의미합니다. 배치를 구성하는 요소들이 반드시 모두 동일할 필요는 없지만, 종종 동일합니다. 이 아이디어의 한 예로 cuBLAS가 제공하는 배치 행렬 곱셈 연산이 있습니다.

일반적으로 CUDA 그래프 및 PDL과 마찬가지로, 배칭의 목적은 개별 배치 작업을 각각 별도로 디스패치할 때 수반되는 오버헤드를 줄이는 것입니다. 메모리 전송 관점에서 메모리 전송을 실행(launch)하면 일부 CPU 및 드라이버 오버헤드가 발생할 수 있습니다. 또한 현재 형태의 일반 cudaMemcpyAsync() 함수는 드라이버가 전송을 최적화하는 데 필요한 충분한 정보를 반드시 제공하지는 않는데, 예를 들어 소스와 목적지에 대한 힌트와 같은 것들입니다. Tegra 플랫폼에서는 전송을 수행하기 위해 SM 또는 Copy Engine(CE)을 사용할지를 선택할 수 있습니다. 어떤 것을 사용할지는 현재 드라이버의 휴리스틱에 의해 지정됩니다. 이는 SM을 사용하면 더 빠른 전송이 가능할 수 있지만 사용 가능한 컴퓨트 성능 일부를 묶어두게 된다는 점에서 중요할 수 있습니다. 반면 CE를 사용하면 전송은 더 느릴 수 있지만, SM을 다른 작업에 사용할 수 있게 해 주므로 전체 애플리케이션 성능은 더 높아질 수 있습니다.

이러한 고려 사항은 cudaMemcpyBatchAsync() 함수(및 그 관련 함수인 cudaMemcpyBatch3DAsync())의 설계 동기가 되었습니다. 이러한 함수들은 배치 메모리 전송을 최적화할 수 있게 해줍니다. 소스 및 목적지 포인터 목록 외에도, API는 메모리 복사 attribute를 사용하여 순서(ordering)에 대한 기대치를 지정하고, 소스 및 목적지 위치에 대한 힌트뿐만 아니라 전송을 연산과 오버랩하는 것을 선호하는지 여부(현재 CE가 있는 Tegra 플랫폼에서만 지원됨)에 대한 힌트도 제공합니다.

먼저 핀 고정(pinned) 호스트 메모리에서 핀 고정(pinned) 장치 메모리로 데이터를 간단히 배치 전송하는 가장 단순한 경우를 고려해 보겠습니다

Listing 4 핀 고정(pinned) 호스트 메모리에서 핀 고정(pinned) 장치 메모리로의 균질(homogeneous) 배치 메모리 전송 예#
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// Allocate the source and destination buffers
// initialize with the stream number
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// Setup attributes for this batch of copies
cudaMemcpyAttributes attrs = {};
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// All copies in the batch have same copy attributes.
size_t attrsIdxs = 0;  // Index of the attributes

// Launch the batched memory transfer
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /*numAttrs*/, nullptr /*failIdx*/, stream);

cudaMemcpyBatchAsync() 함수의 처음 몇 개 매개변수는 즉각적으로 타당해 보입니다. 이는 소스 및 목적지 포인터를 담은 배열과 전송 크기를 담은 배열로 구성됩니다. 각 배열은 ``batch_size`` 요소를 가져야 합니다. 새로운 정보는 attribute에서 나옵니다. 이 함수는 attribute 배열에 대한 포인터와, 이에 대응하는 attribute 인덱스 배열이 필요합니다. 원칙적으로는 size_t 배열을 전달할 수도 있고, 이 배열에 실패한 전송의 인덱스를 기록할 수 있습니다. 그러나 여기에는 nullptr를 전달해도 안전하며, 이 경우 실패 인덱스는 단순히 기록되지 않습니다.

이제 attribute를 살펴보면, 이 예에서는 전송이 균질(homogeneous)합니다. 따라서 하나의 attribute만 사용하며, 이는 모든 전송에 적용됩니다. 이는 attrIndex 매개변수로 제어됩니다. 원칙적으로 이는 배열이 될 수 있습니다. 배열의 i번째 요소에는 attribute 배열의 i번째 요소가 적용되는 첫 번째 전송의 인덱스가 들어 있습니다. 이 경우 attrIndex는 단일 요소 배열로 취급되며, 값 ‘0’은 attribute[0]이 인덱스 0 이상, 즉 모든 전송에 적용됨을 의미합니다.

마지막으로, srcAccessOrder attribute를 cudaMemcpySrcAccessOrderStream로 설정했음을 알 수 있습니다. 이는 소스 데이터가 일반 스트림 순서로 접근됨을 의미합니다. 다시 말해 memcpy는 이러한 소스 및 목적지 포인터 중 어느 것이든 해당 데이터와 관련된 이전 커널이 완료될 때까지 블로킹됩니다.

다음 예에서는 더 복잡한 이종(heterogeneous) 배치 전송의 경우를 살펴보겠습니다.

Listing 5 일부 수명 짧은(ephemeral) 호스트 메모리를 사용하여 핀 고정(pinned) 장치 메모리로 이종(heterogeneous) 배치 메모리 전송을 수행하는 예#
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// Allocate the src and dst buffers
for (size_t i = 0; i < batch_size - 10; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
}

int buffer[10];

for (size_t i = batch_size - 10; i < batch_size; i++) {
    srcs[i] = &buffer[10 - (batch_size - i];
    cudaMalloc(&dsts[i], sizes[i]);
}

// Setup attributes for this batch of copies
cudaMemcpyAttributes attrs[2] = {};
attrs[0].srcAccessOrder = cudaMemcpySrcAccessOrderStream;
attrs[1].srcAccessOrder = cudaMemcpySrcAccessOrderDuringApiCall;

size_t attrsIdxs[2];
attrsIdxs[0] = 0;
attrsIdxs[1] = batch_size - 10;

// Launch the batched memory transfer
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 2 /*numAttrs*/, nullptr /*failIdx*/, stream);

여기에는 두 종류의 전송이 있습니다: 핀 고정(pinned) 호스트 메모리에서 핀 고정(pinned) 장치 메모리로의 batch_size-10 전송과, 호스트 배열에서 핀 고정(pinned) 장치 메모리로의 10개 전송입니다. 또한 buffer 배열은 호스트에 있을 뿐만 아니라 현재 스코프에서만 존재하며, 그 주소는 수명 짧은 포인터(ephemeral pointer)로 알려져 있습니다. 이 포인터는 API 호출이 완료된 후(비동기이므로)에는 유효하지 않을 수 있습니다. 이러한 수명 짧은 포인터로 복사를 수행하려면 attribute의 srcAccessOrder를 cudaMemcpySrcAccessOrderDuringApiCall로 설정해야 합니다.

이제 속성은 두 개입니다. 첫 번째 속성은 인덱스가 0 이상이고 batch_size-10 미만인 모든 전송에 적용됩니다. 두 번째 속성은 인덱스가 batch_size-10 이상이고 batch_size 미만인 모든 전송에 적용됩니다.

buffer 배열을 스택이 아니라 malloc으로 힙에 할당했다면, 이 데이터는 더 이상 수명 짧은(ephemeral) 데이터가 아닙니다. 포인터를 명시적으로 해제할 때까지 유효하기 때문입니다. 이 경우 복사를 어떻게 스테이징할지가 최적인지는 시스템이 하드웨어 관리 메모리(hardware managed memory)를 갖추었는지, 또는 주소 변환을 통해 호스트 메모리에 대한 일관된 GPU 접근(coherent GPU access)을 지원하는지에 따라 달라집니다. 그런 경우에는 스트림 순서(stream ordering)를 사용하는 편이 가장 좋고, 그렇지 않다면 전송을 즉시 스테이징하는 편이 더 합리적입니다. 이런 상황에서는 attribute의 srcAccessOrder에 cudaMemcpyAccessOrderAny 값을 사용해야 합니다.

cudaMemcpyBatchAsync 함수는 소스 위치와 목적지 위치에 대한 힌트도 프로그래머가 제공할 수 있게 해줍니다. 이는 cudaMemcpyAttributes 구조체의 srcLocation 및 dstLocation 필드를 설정함으로써 이루어집니다. 이 두 필드는 모두 위치의 유형과 위치 ID를 담는 cudaMemLocation 타입입니다. 이 cudaMemLocation 구조체는 cudaMemPrefetchAsync()를 사용할 때 런타임에 프리페치 힌트를 제공하는 데 쓰이는 것과 동일한 구조체입니다. 아래 코드 예제는 디바이스에서 호스트의 특정 NUMA 노드로 전송할 때 이러한 힌트를 설정하는 방법을 보여줍니다.

예제 6 소스 및 목적지 위치 힌트 설정 예#
// Allocate the source and destination buffers
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<void *> sizes(batch_size);

// cudaMemLocation structures we will use tp provide location hints
// Device device_id
cudaMemLocation srcLoc = {cudaMemLocationTypeDevice, dev_id};

// Host with numa Node numa_id
cudaMemLocation dstLoc = {cudaMemLocationTypeHostNuma, numa_id};

// Allocate the src and dst buffers
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocManaged(&srcs[i], sizes[i]);
    cudaMallocManaged(&dsts[i], sizes[i]);

    cudaMemPrefetchAsync(srcs[i], sizes[i], srcLoc, 0, stream);
    cudaMemPrefetchAsync(dsts[i], sizes[i], dstLoc, 0, stream);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// Setup attributes for this batch of copies
cudaMemcpyAttributes attrs = {};

// These are managed memory pointers so Stream Order is appropriate
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// Now we can specify the location hints here.
attrs.srcLocHint = srcLoc;
attrs.dstlocHint = dstLoc;

// All copies in the batch have same copy attributes.
size_t attrsIdxs = 0;

// Launch the batched memory transfer
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /*numAttrs*/, nullptr /*failIdx*/, stream);

마지막으로 살펴볼 것은 전송에 SM을 사용할지, 아니면 CE(복사 엔진)를 사용할지에 대한 힌트용 플래그입니다. 이를 위한 필드는 cudaMemcpyAttributesflags::flags이며, 가능한 값은 다음과 같습니다.

  • cudaMemcpyFlagDefault - 기본 동작

  • cudaMemcpyFlagPreferOverlapWithCompute - 전송과 연산이 겹치는 경우, 시스템이 전송에 CE를 우선 사용하도록 힌트를 줍니다. 이 플래그는 Tegra가 아닌 플랫폼에서는 무시됩니다.

정리하면, cudaMemcpyBatchAsync의 핵심 사항은 다음과 같습니다.

  • cudaMemcpyBatchAsync 함수와 그 3D 변형은 프로그래머가 메모리 전송 배치를 지정할 수 있게 해주며, 이를 통해 전송 설정 오버헤드를 여러 전송에 분산할 수 있습니다.

  • 이 함수는 소스/목적지 포인터와 전송 크기 외에도 하나 이상의 메모리 복사 attribute를 받을 수 있습니다. 이 attribute에는 전송 대상 메모리의 종류, 소스 포인터에 대응하는 스트림 순서 동작, 소스 및 목적지 위치 힌트, 그리고 가능한 경우 연산과 전송을 겹치도록 할지 또는 전송에 SM을 사용할지를 결정하기 위한 힌트가 포함될 수 있습니다.

  • 런타임은 이러한 정보를 바탕으로 전송을 가능한 한 최대한 최적화하려고 시도할 수 있습니다.

3.1.6. 환경 변수#

CUDA는 실행과 성능에 영향을 줄 수 있는 여러 환경 변수( Section 5.2 참고)를 제공합니다. 이 변수들을 명시적으로 설정하지 않으면 CUDA는 합리적인 기본값을 사용합니다. 다만 디버깅 목적이나 성능 개선이 필요한 경우처럼, 사례에 따라 별도의 처리가 필요할 수 있습니다.

예를 들어, 서로 다른 CUDA 스트림의 독립적인 작업이 거짓 의존성(false dependency) 때문에 직렬화될 가능성을 줄이려면 CUDA_DEVICE_MAX_CONNECTIONS 환경 변수 값을 높여야 할 수 있습니다. 이러한 거짓 의존성은 동일한 기반 리소스를 사용할 때 생길 수 있습니다. 우선 기본값으로 시작하고, 사용 가능한 SM 리소스 부족 같은 다른 요인으로 설명할 수 없는 CUDA 스트림 간 독립 작업의 예기치 않은 직렬화처럼 성능 문제가 있을 때만 이 환경 변수의 영향을 살펴보는 것이 좋습니다. 참고로 MPS를 사용하는 경우 이 환경 변수의 기본값은 더 낮게 설정됩니다.

마찬가지로 지연 시간에 민감한 애플리케이션에서는 CUDA_MODULE_LOADING 환경 변수를 EAGER로 설정하는 편이 더 적합할 수 있습니다. 이렇게 하면 모듈 로딩에 따른 오버헤드를 모두 애플리케이션 초기화 단계로 옮겨, 실제 중요 구간 바깥에서 처리할 수 있습니다. 현재 기본 모드는 지연 모듈 로딩(lazy module loading)입니다. 이 기본 모드에서도 애플리케이션 초기화 단계에서 여러 커널에 대한 워밍업 호출을 추가해 모듈이 더 일찍 로드되도록 만들면 eager 모듈 로딩과 유사한 효과를 얻을 수 있습니다.

여러 CUDA 환경 변수에 대한 자세한 내용은 CUDA 환경 변수를 참조하십시오. 환경 변수 값은 애플리케이션을 실행하기 전에 설정하는 것이 좋습니다. 애플리케이션 내부에서 값을 바꾸면 효과가 없을 수 있습니다.
