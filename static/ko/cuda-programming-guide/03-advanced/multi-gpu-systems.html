3.4. 다중 GPU를 갖춘 시스템 프로그래밍

멀티 GPU 프로그래밍을 통해 애플리케이션은 멀티 GPU 시스템이 제공하는 더 큰 총(aggregate) 산술 성능, 메모리 용량, 그리고 메모리 대역폭을 활용함으로써, 단일 GPU로는 불가능한 문제 크기를 다루고 그 이상의 성능 수준을 달성할 수 있습니다.

CUDA는 호스트 API, 드라이버 인프라스트럭처, 그리고 이를 지원하는 GPU 하드웨어 기술을 통해 멀티 GPU 프로그래밍을 가능하게 합니다:

  • 호스트 스레드 CUDA 컨텍스트 관리

  • 시스템의 모든 프로세서를 위한 통합 메모리 주소 지정

  • GPU 간 피어 투 피어(peer-to-peer) 대용량 메모리 전송

  • 세밀한 피어 투 피어 GPU 로드/스토어 메모리 액세스

  • NCCL을 사용하는 병렬 리덕션, NVSHMEM 및 MPI와 같은 API와 함께 NVLink 및/또는 GPU-Direct RDMA를 사용하는 통신, 그리고 CUDA 프로세스 간 통신과 같은 고수준 추상화 및 지원 시스템 소프트웨어

가장 기본적인 수준에서, 멀티 GPU 프로그래밍을 위해서는 애플리케이션이 여러 활성 CUDA 컨텍스트를 동시에 관리하고, 데이터를 GPU로 분배하며, GPU에서 커널을 런치하여 작업을 완료하고, 그 결과가 애플리케이션에 의해 처리될 수 있도록 통신하거나 수집해야 합니다. 이를 수행하는 방법의 세부 사항은 애플리케이션의 알고리즘, 사용 가능한 병렬성, 그리고 기존 코드 구조를 적절한 멀티 GPU 프로그래밍 접근 방식에 얼마나 효과적으로 매핑할 수 있는지에 따라 달라집니다. 가장 일반적인 멀티 GPU 프로그래밍 접근 방식에는 다음이 포함됩니다:

  • 여러 GPU를 구동하는 단일 호스트 스레드

  • 각자 자신의 GPU를 구동하는 여러 호스트 스레드

  • 각자 자신의 GPU를 구동하는 여러 단일 스레드 호스트 프로세스

  • 각자 자신의 GPU를 구동하는 여러 스레드를 포함하는 여러 호스트 프로세스

  • NVLink로 연결된 멀티 노드 클러스터로, 클러스터 노드 전반의 여러 운영 체제 인스턴스 내에서 실행되는 스레드와 프로세스에 의해 GPU가 구동됨

GPU는 위에 나열된 각 멀티 디바이스 작업 분배 접근 방식을 모두 포괄하여, 디바이스 메모리 간의 메모리 전송 및 피어 액세스를 통해 서로 통신할 수 있습니다. 고성능, 저지연 GPU 통신은 피어 투 피어 GPU 메모리 액세스 사용을 질의하고 활성화하며, NVLink를 활용하여 디바이스 간 고대역폭 전송과 더 세밀한 로드/스토어 연산을 달성함으로써 지원됩니다.

CUDA 통합 가상 주소 지정은, 예를 들어 NVLink를 통해, 고성능 피어 투 피어 메모리 액세스 및 전송의 사용을 질의하고 활성화하기 위한 최소한의 추가 단계만으로 동일한 호스트 프로세스 내에서 여러 GPU 간 통신을 허용합니다.

서로 다른 호스트 프로세스에 의해 관리되는 여러 GPU 간의 통신은 프로세스 간 통신(IPC)과 가상 메모리 관리(VMM) API를 통해 지원됩니다. 고수준 IPC 개념과 노드 내(intra-node) CUDA IPC API에 대한 소개는 프로세스 간 통신 섹션에서 다룹니다. 고급 가상 메모리 관리(VMM) API는 노드 내 및 멀티 노드 IPC를 모두 지원하며, Linux 및 Windows 운영 체제 모두에서 사용할 수 있고, 가상 메모리 관리에 설명된 바와 같이 메모리 버퍼의 IPC 공유에 대해 할당 단위별(per-allocation) 세분성 제어를 허용합니다.

CUDA 자체는 GPU 그룹 내에서, 잠재적으로 호스트를 포함할 수도 있는 집합(collective) 연산을 구현하는 데 필요한 API를 제공하지만, 고수준 멀티 GPU 집합 API 자체를 제공하지는 않습니다. 멀티 GPU 집합 연산은 NCCL 및 NVSHMEM과 같은 더 높은 추상화 수준의 CUDA 통신 라이브러리에서 제공됩니다.

3.4.1. 다중 디바이스 컨텍스트 및 실행 관리#

애플리케이션이 여러 GPU를 사용하기 위해 필요한 첫 단계는 사용 가능한 GPU 디바이스를 열거하고, 하드웨어 속성, CPU 친화도(affinity), 피어에 대한 연결성을 기반으로 사용 가능한 디바이스 중에서 적절히 선택한 다음, 애플리케이션이 사용할 각 디바이스에 대해 CUDA 컨텍스트를 생성하는 것입니다.

3.4.1.1. 디바이스 열거#

다음 코드 샘플은 CUDA 지원 디바이스 수를 조회하고, 각 디바이스를 열거하며, 해당 속성을 조회하는 방법을 보여줍니다.

int deviceCount;
cudaGetDeviceCount(&deviceCount);
int device;
for (device = 0; device < deviceCount; ++device) {
    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, device);
    printf("Device %d has compute capability %d.%d.\n",
           device, deviceProp.major, deviceProp.minor);
}

3.4.1.2. 디바이스 선택#

호스트 스레드는 cudaSetDevice()을(를) 호출하여 현재 동작 중인 디바이스를 언제든지 설정할 수 있습니다. 디바이스 메모리 할당과 커널 런치는 현재 디바이스에서 수행되며, 스트림과 이벤트는 현재 설정된 디바이스와 연관되어 생성됩니다. 호스트 스레드가 cudaSetDevice()을(를) 호출하기 전까지는 현재 디바이스의 기본값이 디바이스 0입니다.

다음 코드 샘플은 현재 디바이스 설정이 이후의 메모리 할당 및 커널 실행 연산에 어떤 영향을 미치는지 설명합니다.

size_t size = 1024 * sizeof(float);
cudaSetDevice(0);            // Set device 0 as current
float* p0;
cudaMalloc(&p0, size);       // Allocate memory on device 0
MyKernel<<<1000, 128>>>(p0); // Launch kernel on device 0

cudaSetDevice(1);            // Set device 1 as current
float* p1;
cudaMalloc(&p1, size);       // Allocate memory on device 1
MyKernel<<<1000, 128>>>(p1); // Launch kernel on device 1

3.4.1.3. 다중 디바이스 스트림, 이벤트 및 메모리 복사 동작#

다음 코드 샘플에 설명된 바와 같이, 현재 디바이스에 연관되지 않은 스트림에 커널 런치를 발행하면 실패합니다.

cudaSetDevice(0);               // Set device 0 as current
cudaStream_t s0;
cudaStreamCreate(&s0);          // Create stream s0 on device 0
MyKernel<<<100, 64, 0, s0>>>(); // Launch kernel on device 0 in s0

cudaSetDevice(1);               // Set device 1 as current
cudaStream_t s1;
cudaStreamCreate(&s1);          // Create stream s1 on device 1
MyKernel<<<100, 64, 0, s1>>>(); // Launch kernel on device 1 in s1

// This kernel launch will fail, since stream s0 is not associated to device 1:
MyKernel<<<100, 64, 0, s0>>>(); // Launch kernel on device 1 in s0

메모리 복사는 현재 디바이스에 연관되지 않은 스트림에 발행되더라도 성공합니다.

cudaEventRecord()은(는) 입력 이벤트와 입력 스트림이 서로 다른 디바이스에 연관되어 있으면 실패합니다.

cudaEventElapsedTime()은(는) 두 입력 이벤트가 서로 다른 디바이스에 연관되어 있으면 실패합니다.

cudaEventSynchronize() 및 cudaEventQuery()은(는) 입력 이벤트가 현재 디바이스와 다른 디바이스에 연관되어 있더라도 성공합니다.

cudaStreamWaitEvent()은(는) 입력 스트림과 입력 이벤트가 서로 다른 디바이스에 연관되어 있더라도 성공합니다. 따라서 cudaStreamWaitEvent()은(는) 여러 디바이스를 서로 동기화하는 데 사용할 수 있습니다.

각 디바이스는 자체 기본 스트림을 가지므로, 한 디바이스의 기본 스트림에 발행된 명령은 다른 어떤 디바이스의 기본 스트림에 발행된 명령에 대해 순서가 어긋나게 실행되거나 동시에 실행될 수 있습니다.

3.4.2. 다중 디바이스 피어-투-피어 전송 및 메모리 액세스#

3.4.2.1. 피어-투-피어 메모리 전송#

CUDA는 디바이스 간 메모리 전송을 수행할 수 있으며, 피어-투-피어 메모리 액세스가 가능한 경우 성능을 최대화하기 위해 전용 복사 엔진과 NVLink 하드웨어를 활용합니다.

cudaMemcpy은(는) 복사 타입 cudaMemcpyDeviceToDevice 또는 cudaMemcpyDefault과 함께 사용할 수 있습니다.

그렇지 않으면, 다음 코드 샘플에 설명된 바와 같이 복사는 cudaMemcpyPeer(), cudaMemcpyPeerAsync(), cudaMemcpy3DPeer(), 또는 cudaMemcpy3DPeerAsync()을(를) 사용하여 수행해야 합니다.

cudaSetDevice(0);                   // Set device 0 as current
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // Allocate memory on device 0

cudaSetDevice(1);                   // Set device 1 as current
float* p1;
cudaMalloc(&p1, size);              // Allocate memory on device 1

cudaSetDevice(0);                   // Set device 0 as current
MyKernel<<<1000, 128>>>(p0);        // Launch kernel on device 0

cudaSetDevice(1);                   // Set device 1 as current
cudaMemcpyPeer(p1, 1, p0, 0, size); // Copy p0 to p1
MyKernel<<<1000, 128>>>(p1);        // Launch kernel on device 1

서로 다른 두 디바이스의 메모리 간 복사(암시적 NULL 스트림에서):

  • 어느 한 디바이스에 이전에 발행된 모든 명령이 완료될 때까지 시작되지 않으며

  • 복사 이후 어느 한 디바이스에 발행된 어떤 명령( 비동기 실행 참조)도 시작되기 전에 완료될 때까지 실행됩니다.

스트림의 일반적인 동작과 일관되게, 두 디바이스의 메모리 간 비동기 복사는 다른 스트림의 복사나 커널과 오버랩될 수 있습니다.

피어-투-피어 메모리 액세스에 설명된 바와 같이 두 디바이스 간 피어-투-피어 액세스가 활성화된 경우, 이 두 디바이스 간 피어-투-피어 메모리 복사는 더 이상 호스트를 통해 스테이징할 필요가 없으므로 더 빠릅니다.

3.4.2.2. 피어-투-피어 메모리 액세스#

시스템 속성, 특히 PCIe 및/또는 NVLink 토폴로지에 따라 디바이스는 서로의 메모리를 주소 지정할 수 있습니다(즉, 한 디바이스에서 실행되는 커널이 다른 디바이스의 메모리에 대한 포인터를 역참조할 수 있습니다). 피어-투-피어 메모리 액세스는 지정된 디바이스에 대해 cudaDeviceCanAccessPeer()이(가) true를 반환하는 경우 두 디바이스 간에 지원됩니다.

피어-투-피어 메모리 액세스는 다음 코드 샘플에 설명된 바와 같이 cudaDeviceEnablePeerAccess()을(를) 호출하여 두 디바이스 간에 활성화해야 합니다. NVSwitch가 활성화되지 않은 시스템에서는 각 디바이스가 시스템 전체에서 최대 8개의 피어 연결을 지원할 수 있습니다.

두 디바이스 모두에 대해 통합 가상 주소 공간이 사용되므로(통합 가상 주소 공간 참조), 아래 코드 샘플에 보이는 것처럼 동일한 포인터를 사용하여 두 디바이스에서 메모리를 주소 지정할 수 있습니다.

cudaSetDevice(0);                   // Set device 0 as current
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // Allocate memory on device 0
MyKernel<<<1000, 128>>>(p0);        // Launch kernel on device 0

cudaSetDevice(1);                   // Set device 1 as current
cudaDeviceEnablePeerAccess(0, 0);   // Enable peer-to-peer access
                                    // with device 0

// Launch kernel on device 1
// This kernel launch can access memory on device 0 at address p0
MyKernel<<<1000, 128>>>(p0);

참고

cudaDeviceEnablePeerAccess()을(를) 사용하여 피어 메모리 액세스를 활성화하는 것은 피어 디바이스에서 이전 및 이후의 모든 GPU 메모리 할당에 대해 전역적으로 동작합니다. cudaDeviceEnablePeerAccess()을(를) 통해 디바이스에 대한 피어 액세스를 활성화하면, 할당을 즉시 현재 디바이스 및 액세스 권한을 가진 다른 모든 피어가 접근 가능하도록 만들어야 하므로 해당 피어에서의 디바이스 메모리 할당 연산에 런타임 비용이 추가되며, 피어 디바이스 수에 따라 스케일되는 곱셈적 오버헤드가 더해집니다.

모든 디바이스 메모리 할당에 대해 피어 메모리 액세스를 활성화하는 것보다 더 확장성 있는 대안은 CUDA Virtual Memory Management API를 사용하여 필요할 때만, 할당 시점에 명시적으로 피어 액세스 가능한 메모리 영역을 할당하는 것입니다. 메모리 할당 중 피어 접근성을 명시적으로 요청하면, 피어가 접근할 수 없는 할당에 대해서는 메모리 할당의 런타임 비용이 영향을 받지 않으며, 피어 액세스 가능한 데이터 구조는 소프트웨어 디버깅 및 신뢰성 향상을 위해 올바르게 스코프가 지정됩니다(ref::virtual-memory-management 참조).

3.4.2.3. 피어-투-피어 메모리 일관성#

여러 디바이스에 분산된 그리드에서 동시에 실행되는 스레드에 의한 메모리 액세스의 순서와 정확성을 강제하기 위해 동기화 연산을 사용해야 합니다. 디바이스 간 동기화하는 스레드는 thread_scope_system 동기화 스코프에서 동작합니다. 유사하게, 메모리 연산은 thread_scope_system 메모리 동기화 도메인에 속합니다.

CUDA ref::atomic-functions는 단일 GPU만 해당 객체에 접근하는 경우 피어 디바이스 메모리에 있는 객체에 대해 읽기-수정-쓰기 연산을 수행할 수 있습니다. 피어 원자성(peer atomicity)에 대한 요구사항과 제한 사항은 CUDA 메모리 모델의 원자성 요구사항 논의에 설명되어 있습니다.

3.4.2.4. 다중 디바이스 관리형 메모리#

관리형 메모리는 피어-투-피어를 지원하는 멀티 GPU 시스템에서 사용할 수 있습니다. 동시 다중 디바이스 관리형 메모리 액세스에 대한 상세 요구사항과 관리형 메모리에 대한 GPU 전용 액세스를 위한 API는 Multi-GPU에 설명되어 있습니다.

3.4.2.5. 호스트 IOMMU 하드웨어, PCI 액세스 제어 서비스, 및 VM#

특히 Linux에서는 CUDA와 디스플레이 드라이버가 IOMMU가 활성화된 베어메탈 PCIe 피어-투-피어 메모리 전송을 지원하지 않습니다. 하지만 CUDA와 디스플레이 드라이버는 가상 머신 패스스루(pass through)를 통한 IOMMU는 지원합니다. Linux를 베어메탈 시스템에서 실행할 때는 사일런트(silent) 디바이스 메모리 손상을 방지하기 위해 IOMMU를 비활성화해야 합니다. 반대로, 가상 머신의 PCIe 패스스루에는 IOMMU를 활성화하고 VFIO 드라이버를 사용해야 합니다.

Windows에서는 위의 IOMMU 제한이 존재하지 않습니다.

64비트 플랫폼에서 DMA 버퍼 할당도 참조하십시오.

또한, IOMMU를 지원하는 시스템에서는 PCI 액세스 제어 서비스(ACS)를 활성화할 수 있습니다. PCI ACS 기능은 모든 PCI 포인트-투-포인트 트래픽을 CPU 루트 컴플렉스를 통해 리디렉션하며, 전체 바이섹션 대역폭 감소로 인해 상당한 성능 손실을 야기할 수 있습니다.
