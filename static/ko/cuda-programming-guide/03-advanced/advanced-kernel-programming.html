3.2. 고급 커널 프로그래밍

이 장에서는 먼저 NVIDIA GPU의 하드웨어 모델을 더 깊이 있게 살펴본 다음, 커널 성능을 개선하기 위해 CUDA 커널 코드에서 사용할 수 있는 더 고급 기능 몇 가지를 소개합니다. 또한 이 장에서는 스레드 스코프, 비동기 실행, 그리고 관련 동기화 프리미티브와 관련된 몇 가지 개념을 소개합니다. 이러한 개념적 논의는 커널 코드 내에서 사용할 수 있는 일부 고급 성능 기능을 위한 필수적인 기반을 제공합니다.

이러한 기능 중 일부에 대한 자세한 설명은 이 프로그래밍 가이드의 다음 파트에서 해당 기능에 전용된 장에 포함되어 있습니다.

  • 이 장에서 소개된 고급 동기화 프리미티브는 Section 4.9 및 Section 4.10에서 완전히 다룹니다.

  • 텐서 메모리 가속기(TMA)를 포함한 비동기 데이터 복사는 이 장에서 소개되며, Section 4.11에서 완전히 다룹니다.

3.2.1. PTX 사용#

Parallel Thread Execution(PTX)은 CUDA가 하드웨어 ISA를 추상화하기 위해 사용하는 가상 머신 명령어 집합 아키텍처(ISA)로, Section 1.3.3에서 소개되었습니다. PTX로 직접 코드를 작성하는 것은 매우 고급 최적화 기법으로, 대부분의 개발자에게는 필요하지 않으며 최후의 수단 도구로 간주되어야 합니다. 그럼에도 불구하고, PTX를 직접 작성함으로써 가능한 세밀한 제어가 특정 애플리케이션에서 성능 개선을 가능하게 하는 상황이 있습니다. 이러한 상황은 일반적으로 성능에 매우 민감한 애플리케이션의 일부 구간에서 발생하며, 성능 개선이 1%의 일부에 불과하더라도 상당한 이점을 가져오는 경우입니다. 사용 가능한 모든 PTX 명령어는 PTX ISA 문서에 있습니다.

cuda::ptx 네임스페이스

코드에서 PTX를 직접 사용하는 한 가지 방법은 libcu++가 제공하는 cuda::ptx 네임스페이스(namespace)를 사용하는 것입니다. 이 네임스페이스는 PTX 명령어에 직접 매핑되는 C++ 함수를 제공하여 C++ 애플리케이션 안에서 PTX를 더 쉽게 사용할 수 있게 해줍니다. 자세한 내용은 cuda::ptx 네임스페이스 문서를 참조하십시오.

인라인 PTX

코드에 PTX를 포함하는 또 다른 방법은 인라인 PTX를 사용하는 것입니다. 이 방법은 해당 문서에 자세히 설명되어 있습니다. 이는 CPU에서 어셈블리 코드를 작성하는 것과 매우 유사합니다.

3.2.2. 하드웨어 구현#

스트리밍 멀티프로세서 또는 SM(참조 GPU 하드웨어 모델)은 수백 개의 스레드를 동시에 실행하도록 설계되었습니다. 이처럼 많은 수의 스레드를 관리하기 위해, 다음과 같은 고유한 병렬 컴퓨팅 모델을 사용합니다. 단일 명령, 다중 스레드, 또는 SIMT, 즉 SIMT 실행 모델. 명령어는 파이프라인화되어, 단일 스레드 내의 명령어 수준 병렬성을 활용할 뿐만 아니라, 아래에서 자세히 설명된 동시 하드웨어 멀티스레딩을 통한 광범위한 스레드 수준 병렬성도 활용합니다 하드웨어 멀티스레딩. CPU 코어와 달리, SM은 명령어를 순서대로 발행하며 분기 예측이나 추측 실행을 수행하지 않습니다.

SIMT 실행 모델과 하드웨어 멀티스레딩 섹션에서는 모든 디바이스에 공통적인 SM의 아키텍처적 특징을 설명합니다. 컴퓨트 기능 섹션에서는 서로 다른 컴퓨트 기능을 가진 디바이스에 대한 구체적인 내용을 제공합니다.

NVIDIA GPU 아키텍처는 리틀 엔디언 표현을 사용합니다.

3.2.2.1. SIMT 실행 모델#

각 SM은 워프(warp)라고 불리는 32개의 병렬 스레드 그룹 단위로 스레드를 생성, 관리, 스케줄링 및 실행합니다. 워프를 구성하는 개별 스레드는 동일한 프로그램 주소에서 함께 시작하지만, 각자 고유한 명령어 주소 카운터와 레지스터 상태를 가지므로 자유롭게 분기하고 독립적으로 실행할 수 있습니다. 워프(warp)라는 용어는 최초의 병렬 스레드 기술인 직조(weaving)에서 유래했습니다. 하프 워프(half-warp)는 워프의 전반부 또는 후반부 중 하나입니다. 쿼터 워프(quarter-warp)는 워프의 1/4 단위로, 첫 번째, 두 번째, 세 번째 또는 네 번째 1/4 중 하나입니다.

워프는 한 번에 하나의 공통 명령어를 실행하므로, 워프의 32개 스레드가 실행 경로에 대해 모두 합의할 때 최대 효율이 실현됩니다. 워프의 스레드가 데이터 의존 조건 분기를 통해 분기(diverge)하면, 워프는 실제로 선택된 각 분기 경로를 실행하면서 해당 경로에 있지 않은 스레드를 비활성화합니다. 분기 다이버전스(branch divergence)는 워프 내부에서만 발생하며, 서로 다른 워프는 공통 코드 경로를 실행하든 분리된 코드 경로를 실행하든 상관없이 독립적으로 실행됩니다.

SIMT 아키텍처는 단일 명령어가 여러 처리 요소를 제어한다는 점에서 SIMD(Single Instruction, Multiple Data) 벡터 구성과 유사합니다. 핵심적인 차이점은 SIMD 벡터 구성이 소프트웨어에 SIMD 폭(width)을 노출하는 반면, SIMT 명령어는 단일 스레드의 실행 및 분기 동작을 지정한다는 것입니다. SIMD 벡터 머신과 달리, SIMT는 프로그래머가 독립적인 스칼라 스레드를 위한 스레드 수준 병렬 코드뿐 아니라, 조율된 스레드를 위한 데이터 병렬 코드도 작성할 수 있게 합니다. 정확성의 관점에서 프로그래머는 본질적으로 SIMT 동작을 무시할 수 있습니다. 그러나 워프 내 스레드가 분기하는 일이 드물도록 주의하면 상당한 성능 향상을 얻을 수 있습니다. 실제로 이는 캐시 라인의 역할과 유사합니다. 정확성을 위해 설계할 때는 캐시 라인 크기를 안전하게 무시할 수 있지만, 최고 성능을 위해 설계할 때는 코드 구조에서 이를 고려해야 합니다. 반면 벡터 아키텍처는 소프트웨어가 로드를 벡터로 병합(coalesce)하고 다이버전스를 수동으로 관리해야 합니다.

3.2.2.1.1. 독립적인 스레드 스케줄링#

컴퓨트 기능이 7.0보다 낮은 GPU에서 워프는 워프 내 32개 모든 스레드가 공유하는 단일 프로그램 카운터와, 워프의 활성 스레드를 지정하는 활성 마스크를 함께 사용했습니다. 그 결과, 다이버전트 영역에 있거나 실행 상태가 서로 다른 동일 워프의 스레드들은 서로 신호를 보내거나 데이터를 교환할 수 없으며, 락(lock) 또는 뮤텍스(mutex)로 보호되는 세밀한 수준의 데이터 공유를 요구하는 알고리즘은 경쟁하는 스레드가 어느 워프에서 왔는지에 따라 데드락을 초래할 수 있습니다.

컴퓨트 기능 7.0 이상의 GPU에서 독립적인 스레드 스케줄링은 워프와 무관하게 스레드 간 완전한 동시성을 허용합니다. 독립적인 스레드 스케줄링에서는 GPU가 프로그램 카운터와 호출 스택을 포함하여 스레드별 실행 상태를 유지하며, 실행 리소스를 더 잘 활용하거나 한 스레드가 다른 스레드가 생성할 데이터를 기다릴 수 있도록 스레드 단위의 세분성으로 실행을 양보(yield)할 수 있습니다. 스케줄 최적화기가 동일 워프의 활성 스레드를 SIMT 유닛으로 어떻게 묶을지 결정합니다. 이는 이전 NVIDIA GPU와 마찬가지로 SIMT 실행의 높은 처리량을 유지하면서도, 훨씬 더 큰 유연성을 제공합니다. 이제 스레드는 서브 워프 세분성에서 다이버전스 및 리컨버전스가 가능합니다.

독립적인 스레드 스케줄링은 이전 GPU 아키텍처의 암묵적 워프 동기(implicit warp-synchronous) 동작에 의존하는 코드를 깨뜨릴 수 있습니다. 워프 동기(warp-synchronous) 코드는 동일 워프의 스레드가 모든 명령어에서 락스텝(lockstep)으로 실행된다고 가정하지만, 서브 워프 세분성에서 스레드가 다이버전스 및 리컨버전스할 수 있게 되면서 이러한 가정은 더 이상 유효하지 않습니다. 이는 의도한 것과 다른 스레드 집합이 실행된 코드에 참여하게 만들 수 있습니다. CC 7.0 이전 GPU(예: 동기화 없는 워프 내 리덕션)를 위해 개발된 모든 워프 동기 코드는 호환성을 보장하기 위해 재검토해야 합니다. 개발자는 모든 GPU 세대에서 올바른 동작을 보장하기 위해 __syncwarp()를 사용하여 이러한 코드를 명시적으로 동기화해야 합니다.

참고

현재 명령어에 참여하고 있는 워프의 스레드는 활성(active) 스레드라고 하며, 현재 명령어에 있지 않은 스레드는 비활성(inactive)(비활성화됨)입니다. 스레드가 비활성 상태가 되는 이유는 다양하며, 여기에는 워프의 다른 스레드보다 먼저 종료했거나, 워프가 현재 실행 중인 분기 경로와 다른 분기 경로를 택했거나, 스레드 수가 워프 크기의 배수가 아닌 블록에서 마지막에 해당하는 스레드인 경우 등이 포함됩니다.

워프에서 실행되는 비원자(non-atomic) 명령어가 워프의 둘 이상의 스레드에서 전역 또는 공유 메모리의 동일한 위치에 기록하는 경우, 해당 위치에서 발생하는 직렬화된 기록 횟수는 디바이스의 컴퓨트 기능에 따라 달라질 수 있습니다. 그러나 모든 컴퓨트 기능에서, 어떤 스레드가 최종 기록을 수행하는지는 정의되지 않습니다.

워프에서 실행되는 atomic 명령어가 워프의 둘 이상의 스레드에 대해 전역 메모리의 동일한 위치를 읽고, 수정하고, 기록하는 경우, 해당 위치에 대한 각 읽기/수정/기록은 모두 발생하며 모두 직렬화되지만, 발생하는 순서는 정의되지 않습니다.

3.2.2.2. 하드웨어 멀티스레딩#

SM이 실행할 하나 이상의 스레드 블록을 할당받으면, 이를 워프로 분할하고 각 워프는 워프 스케줄러(warp scheduler)에 의해 실행 스케줄링을 받습니다. 블록이 워프로 분할되는 방식은 항상 동일합니다. 각 워프에는 연속적이며 증가하는 스레드 ID를 가진 스레드들이 포함되고, 첫 번째 워프에는 스레드 0이 포함됩니다. Thread Hierarchy는 스레드 ID가 블록 내 스레드 인덱스와 어떻게 관련되는지를 설명합니다.

블록 내 워프의 총 개수는 다음과 같이 정의됩니다:

\(\text{ceil}\left( \frac{T}{W_{size}}, 1 \right)\)

  • T는 블록당 스레드 수이고,

  • Wsize는 워프 크기이며, 32와 같습니다,

  • ceil(x, y)는 x를 y의 가장 가까운 배수로 올림한 값과 같습니다.

SM이 처리하는 각 워프의 실행 컨텍스트(프로그램 카운터, 레지스터 등)는 워프의 수명 동안 칩 내에서 유지됩니다. 따라서 워프 간 전환에는 비용이 들지 않습니다. 각 명령어 발행 사이클마다 워프 스케줄러는 다음 명령어를 실행할 준비가 된 스레드(워프의 활성 스레드)를 가진 워프를 선택하고, 해당 스레드들에 명령어를 발행합니다.

각 SM에는 워프들 사이에 분할되는 32비트 레지스터 집합과, 스레드 블록들 사이에 분할되는 공유 메모리가 있습니다. 주어진 커널에 대해 SM에서 동시에 상주하고 병렬로 처리될 수 있는 블록과 워프의 수는, 커널이 사용하는 레지스터와 공유 메모리의 양뿐만 아니라 SM에서 사용 가능한 레지스터와 공유 메모리의 양에 따라 달라집니다. 또한 SM당 상주 가능한 블록과 워프의 최대 개수가 있습니다. 이러한 한계는 SM에서 사용 가능한 레지스터 및 공유 메모리의 양과 마찬가지로 디바이스의 컴퓨트 기능에 따라 달라지며, 컴퓨트 기능에 명시되어 있습니다. SM당 최소한 하나의 블록을 처리할 수 있을 만큼의 리소스가 충분하지 않으면, 커널은 실행을 시작하지 못합니다. 블록에 할당된 레지스터와 공유 메모리의 총량은 Occupancy 섹션에 문서화된 여러 방법으로 확인할 수 있습니다.

3.2.2.3. 비동기 실행 기능#

최근 NVIDIA GPU 세대에는 GPU 내에서 데이터 이동, 연산, 동기화의 오버랩을 더 많이 허용하기 위해 비동기 실행 기능이 포함되어 왔습니다. 이러한 기능을 통해 GPU 코드에서 호출된 특정 작업이 동일한 스레드 블록 내의 다른 GPU 코드에 대해 비동기적으로 실행될 수 있습니다. 이러한 비동기 실행은 Section 2.3에서 논의된 비동기 CUDA API와 혼동해서는 안 되는데, 이는 GPU 커널 런치 또는 메모리 작업이 서로 또는 CPU에 대해 비동기적으로 동작하도록 해줍니다.

컴퓨트 기능 8.0(NVIDIA Ampere GPU 아키텍처)은 전역 메모리에서 공유 메모리로의 하드웨어 가속 비동기 데이터 복사와 비동기 배리어(참조 NVIDIA A100 Tensor Core GPU Architecture )를 도입했습니다.

컴퓨트 기능 9.0(NVIDIA Hopper GPU 아키텍처)은 전역 메모리에서 공유 메모리로 그리고 그 반대로 대규모 데이터 블록과 다차원 텐서를 전송할 수 있는 텐서 메모리 가속기(TMA) 유닛, 비동기 트랜잭션 배리어, 그리고 비동기 행렬 곱-누산(multiply-accumulate) 연산으로 비동기 실행 기능을 확장했습니다(자세한 내용은 Hopper Architecture in Depth 블로그 게시물을 참조하십시오.).

CUDA는 이러한 기능을 사용하기 위해 디바이스 코드에서 스레드가 호출할 수 있는 API를 제공합니다. 비동기 프로그래밍 모델은 CUDA 스레드에 대한 비동기 연산의 동작을 정의합니다.

비동기 연산은 CUDA 스레드에 의해 시작되지만, 마치 다른 스레드에 의해 실행되는 것처럼 비동기적으로 실행되는 연산이며, 이를 비동기 스레드(async thread)라고 부르겠습니다. 올바르게 구성된(well-formed) 프로그램에서는 하나 이상의 CUDA 스레드가 비동기 연산과 동기화합니다. 비동기 연산을 시작한 CUDA 스레드는 동기화하는 스레드들 중 하나일 필요는 없습니다. 비동기 스레드는 항상 해당 연산을 시작한 CUDA 스레드와 연관됩니다.

비동기 연산은 완료를 신호하기 위해 동기화 객체를 사용하는데, 이는 배리어(barrier) 또는 파이프라인일 수 있습니다. 이러한 동기화 객체는 고급 동기화 프리미티브에서 자세히 설명되며, 비동기 메모리 연산을 수행하는 데서의 역할은 비동기 데이터 복사에서 시연됩니다.

3.2.2.3.1. 비동기 스레드(Async Thread) 및 비동기 프록시(Async Proxy)#

비동기 연산은 일반 연산과는 다르게 메모리에 접근할 수 있습니다. 이러한 서로 다른 메모리 접근 방법을 구분하기 위해, CUDA는 async thread, generic proxy, async proxy의 개념을 도입합니다. 일반 연산(load 및 store)은 generic proxy를 거칩니다. LDGSTS 및 STAS/REDAS와 같은 일부 비동기 명령은 generic proxy에서 동작하는 async thread를 사용해 모델링됩니다. TMA를 사용한 벌크 비동기 복사와 일부 텐서 코어 연산(tcgen05.*, wgmma.mma_async.*)과 같은 다른 비동기 명령은 async proxy에서 동작하는 async thread를 사용해 모델링됩니다.

generic proxy에서 동작하는 Async thread. 비동기 연산이 시작되면, 이는 async thread와 연관되며, 이 async thread는 해당 연산을 시작한 CUDA 스레드와는 다릅니다. 동일한 주소에 대한 이전의 generic proxy(일반) load 및 store는 비동기 연산보다 앞서도록 순서가 보장됩니다. 그러나 동일한 주소에 대한 이후의 일반 load 및 store는 순서를 유지한다고 보장되지 않으며, async thread가 완료될 때까지 잠재적으로 경쟁 상태(race condition)가 발생할 수 있습니다.

async proxy에서 동작하는 Async thread. 비동기 연산이 시작되면, 이는 async thread와 연관되며, 이 async thread는 해당 연산을 시작한 CUDA 스레드와는 다릅니다. 동일한 주소에 대한 이전 및 이후의 일반 load 및 store는 순서를 유지한다고 보장되지 않습니다. 올바른 메모리 순서를 보장하기 위해, 서로 다른 proxy 전반에서 이들을 동기화하려면 proxy fence가 필요합니다. Tensor Memory Accelerator(TMA) 사용 섹션은 TMA로 비동기 복사를 수행할 때 정확성을 보장하기 위해 proxy fence를 사용하는 방법을 보여줍니다.

이러한 개념에 대한 자세한 내용은 PTX ISA 문서를 참조하십시오.

3.2.3. 스레드 범위#

3.2.4.1. 범위 지정 원자적 연산#

Section 5.4.5 CUDA에서 사용할 수 있는 원자적 함수에 대한 개요를 제공합니다. 이 섹션에서는 다음에 초점을 맞춥니다 범위 지정 지원하는 원자적 연산 C++ 표준 원자적 메모리 시맨틱으로, 다음을 통해 사용할 수 있습니다 libcu++ 라이브러리를 통해서 또는 컴파일러 내장(built-in) 함수를 통해 사용할 수 있습니다. 범위 지정 원자적 연산은 CUDA 스레드 계층 구조의 적절한 수준에서 효율적인 동기화를 위한 도구를 제공하여, 복잡한 병렬 알고리즘에서 정확성과 성능을 모두 가능하게 합니다.

3.2.4.1.1. 스레드 범위와 메모리 순서 지정#

범위 지정 원자적 연산은 두 가지 핵심 개념을 결합합니다:

  • 스레드 범위: 어떤 스레드가 원자적 연산의 효과를 관측할 수 있는지를 정의합니다(참조 스레드 범위).

  • 메모리 순서 지정: 다른 메모리 작업에 대한 순서 제약을 정의합니다(참조 C++ 표준 원자적 메모리 시맨틱).

#include <cuda/atomic>

__global__ void block_scoped_counter() {
    // Shared atomic counter visible only within this block
    __shared__ cuda::atomic<int, cuda::thread_scope_block> counter;

    // Initialize counter (only one thread should do this)
    if (threadIdx.x == 0) {
        counter.store(0, cuda::memory_order_relaxed);
    }
    __syncthreads();

    // All threads in block atomically increment
    int old_value = counter.fetch_add(1, cuda::memory_order_relaxed);

    // Use old_value...
}

__global__ void block_scoped_counter() {
    // Shared counter visible only within this block
    __shared__ int counter;

    // Initialize counter (only one thread should do this)
    if (threadIdx.x == 0) {
        __nv_atomic_store_n(&counter, 0,
                            __NV_ATOMIC_RELAXED,
                            __NV_THREAD_SCOPE_BLOCK);
    }
    __syncthreads();

    // All threads in block atomically increment
    int old_value = __nv_atomic_fetch_add(&counter, 1,
                                          __NV_ATOMIC_RELAXED,
                                          __NV_THREAD_SCOPE_BLOCK);

    // Use old_value...
}

이 예제는 범위 지정 원자적 연산의 기본 개념을 보여주는 블록 범위 지정 원자적 카운터를 구현합니다:

  • 공유 변수: 단일 카운터는 __shared__ 메모리를 사용하여 블록 내 모든 스레드 간에 공유됩니다.

  • 원자적 타입 선언: cuda::atomic<int, cuda::thread_scope_block>는 블록 수준 가시성을 갖는 원자적 정수를 생성합니다.

  • 단일 초기화: 설정 중 레이스 컨디션을 방지하기 위해 스레드 0만 카운터를 초기화합니다.

  • 블록 동기화: __syncthreads()는 진행하기 전에 모든 스레드가 초기화된 카운터를 보도록 보장합니다.

  • 원자적 증가: 각 스레드는 카운터를 원자적으로 증가시키고 이전 값을 받습니다.

여기서는 서로 다른 메모리 위치 간의 순서 제약 없이 원자성(분할 불가능한 read-modify-write)만 필요하므로 cuda::memory_order_relaxed를 선택했습니다. 이는 단순한 카운팅 작업이므로, 증가 순서는 정확성에 영향을 주지 않습니다.

프로듀서-컨슈머 패턴에서는 acquire-release 시맨틱이 올바른 순서를 보장합니다:

__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ cuda::atomic<bool, cuda::thread_scope_block> ready;

    if (threadIdx.x == 0) {
        // Producer: write data then signal ready
        data = 42;
        ready.store(true, cuda::memory_order_release);  // Release ensures data write is visible
    } else {
        // Consumer: wait for ready signal then read data
        while (!ready.load(cuda::memory_order_acquire)) {  // Acquire ensures data read sees the write
            // spin wait
        }
        int value = data;
        // Process value...
    }
}

__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ bool ready; // Only ready flag needs atomic operations

    if (threadIdx.x == 0) {
        // Producer: write data then signal ready
        data = 42;
        __nv_atomic_store_n(&ready, true,
                            __NV_ATOMIC_RELEASE,
                            __NV_THREAD_SCOPE_BLOCK);  // Release ensures data write is visible
    } else {
        // Consumer: wait for ready signal then read data
        while (!__nv_atomic_load_n(&ready,
                                   __NV_ATOMIC_ACQUIRE,
                                   __NV_THREAD_SCOPE_BLOCK)) {  // Acquire ensures data read sees the write
            // spin wait
        }
        int value = data;
        // Process value...
    }
}

3.2.4.1.2. 성능 고려사항#

  • 가능한 한 가장 좁은 범위를 사용: 블록 범위 지정 원자적 연산은 시스템 범위 지정 원자적 연산보다 훨씬 빠릅니다.

  • 더 약한 순서 지정을 선호: 정확성에 필요할 때만 더 강한 순서 지정을 사용합니다.

  • 메모리 위치를 고려: 공유 메모리 원자적 연산이 전역 메모리 원자적 연산보다 더 빠릅니다.

3.2.4.2. 비동기 배리어#

비동기 배리어는 일반적인 단일 단계 배리어(와 다릅니다__syncthreads())에서, 스레드가 배리어에 도달했음을 알리는 동작(“arrival”)이 다른 스레드들이 배리어에 도달하기를 기다리는 동작(“wait”)과 분리되어 있다는 점이 다릅니다. 이러한 분리는 스레드가 배리어와 무관한 추가 작업을 수행할 수 있게 하여 실행 효율을 높이고, 대기 시간을 더 효율적으로 활용하게 합니다. 비동기 배리어는 CUDA 스레드로 프로듀서-컨슈머 패턴을 구현하거나, 복사 작업이 완료 시 배리어에 신호(“arrive on”)를 보내도록 하여 메모리 계층 구조 내에서 비동기 데이터 복사를 가능하게 하는 데 사용할 수 있습니다.

비동기 배리어는 컴퓨트 기능 7.0 이상 디바이스에서 사용할 수 있습니다. 컴퓨트 기능 8.0 이상 디바이스는 공유 메모리에서 비동기 배리어에 대한 하드웨어 가속과 동기화 세분성의 중요한 발전을 제공하는데, 이는 블록 내에서 CUDA 스레드의 어떤 부분집합에 대해서도 하드웨어 가속 동기화를 허용하기 때문입니다. 이전 아키텍처는 전체 워프(에서만 동기화를 가속합니다__syncwarp()) 또는 전체 블록(__syncthreads()) 수준.

CUDA 프로그래밍 모델은 다음을 통해 비동기 배리어를 제공합니다 cuda::std::barrier, ISO C++에 부합하는 배리어로, 다음에서 사용할 수 있습니다 libcu++ 라이브러리. 구현하는 것에 더해 std::barrier, 이 라이브러리는 성능 향상을 위해 배리어의 스레드 범위를 선택할 수 있는 CUDA 전용 확장을 제공하고 더 낮은 수준의 cuda::ptx API. A cuda::barrier 와 상호 운용될 수 있습니다 cuda::ptx 를 사용하여 friend 함수 cuda::device::barrier_native_handle() 배리어의 네이티브 핸들을 가져와 이를 cuda::ptx 함수. CUDA는 또한 프리미티브 API 스레드 블록 범위에서 공유 메모리 내 비동기 배리어를 위한

동기화의 시간적 분할

비동기 arrive-wait 배리어가 없으면, 스레드 블록 내 동기화는 __syncthreads()를 사용하거나, 코오퍼러티브 그룹(Cooperative Groups)을 사용하는 경우 block.sync()로 수행합니다.

#include <cooperative_groups.h>

__global__ void simple_sync(int iteration_count) {
    auto block = cooperative_groups::this_thread_block();

    for (int i = 0; i < iteration_count; ++i) {
        /* code before arrive */

         // Wait for all threads to arrive here.
        block.sync();

        /* code after wait */
    }
}

스레드는 동기화 지점에서 블로킹됩니다(block.sync()) 모든 스레드가 동기화 지점에 도달할 때까지. 또한 동기화 지점 이전에 발생한 메모리 업데이트는 동기화 지점 이후에 블록 내의 모든 스레드에서 볼 수 있음이 보장됩니다.

이 패턴에는 세 단계가 있습니다:

  • 동기화 이전의 코드는 동기화 이후에 읽힐 메모리 업데이트를 수행합니다.

  • 동기화 지점.

  • 동기화 이후의 코드로, 동기화 이전에 발생한 메모리 업데이트가 보입니다.

대신 비동기 배리어를 사용하면, 시간적으로 분할된 동기화 패턴은 다음과 같습니다.

#include <cuda/barrier>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  using barrier_t = cuda::barrier<cuda::thread_scope_block>;
  __shared__ barrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // Initialize barrier with expected arrival count.
    init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* code before arrive */

    // This thread arrives. Arrival does not block a thread.
    barrier_t::arrival_token token = bar.arrive();

    compute(data, i);

    // Wait for all threads participating in the barrier to complete bar.arrive().
    bar.wait(std::move(token));

    /* code after wait */
  }
}

#include <cuda/ptx>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ uint64_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // Initialize barrier with expected arrival count.
    cuda::ptx::mbarrier_init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* code before arrive */

    // This thread arrives. Arrival does not block a thread.
    uint64_t token = cuda::ptx::mbarrier_arrive(&bar);

    compute(data, i);

    // Wait for all threads participating in the barrier to complete mbarrier_arrive().
    while(!cuda::ptx::mbarrier_try_wait(&bar, token)) {}

    /* code after wait */
  }
}

#include <cuda_awbarrier_primitives.h>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ __mbarrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // Initialize barrier with expected arrival count.
    __mbarrier_init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* code before arrive */

    // This thread arrives. Arrival does not block a thread.
    __mbarrier_token_t token = __mbarrier_arrive(&bar);

    compute(data, i);

    // Wait for all threads participating in the barrier to complete __mbarrier_arrive().
    while(!__mbarrier_try_wait(&bar, token, 1000)) {}

    /* code after wait */
  }
}

이 패턴에서는 동기화 지점이 도착(arrive) 지점(으로 분할됩니다(bar.arrive()) 및 대기(wait) 지점(bar.wait(std::move(token))). 스레드는 다음에 참여하기 시작합니다 cuda::barrier 첫 번째 호출을 통해 bar.arrive(). 스레드가 호출할 때 bar.wait(std::move(token)) 참여하는 스레드들이 완료할 때까지 블로킹됩니다 bar.arrive() 예상된 횟수, 즉 다음에 전달되는 예상 도착 횟수 인수 init(). 참여하는 스레드의 다음 호출 이전에 발생하는 메모리 업데이트 bar.arrive() 은(는) 참여하는 스레드가 다음을 호출한 이후에 참여하는 스레드에서 볼 수 있음이 보장됩니다 bar.wait(std::move(token)). 다음 호출에 유의하십시오 bar.arrive() 는 스레드를 블로킹하지 않으므로, 다른 참여 스레드가 를 호출하기 전에 발생하는 메모리 업데이트에 의존하지 않는 다른 작업을 계속 진행할 수 있습니다 bar.arrive().

arrive and wait 패턴에는 다섯 단계가 있습니다:

  • arrive 이전의 코드는 wait 이후에 읽히게 될 메모리 업데이트를 수행합니다.

  • 암시적 메모리 펜스가 있는 arrive 지점(즉, cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_block)와 동등).

  • arrive와 wait 사이의 코드.

  • wait 지점.

  • wait 이후의 코드로, arrive 이전에 수행된 업데이트가 보입니다.

비동기 배리어를 사용하는 방법에 대한 포괄적인 가이드는 Asynchronous Barriers를 참조하십시오.

3.2.4.3. 파이프라인#

CUDA 프로그래밍 모델은 비동기 메모리 복사를 여러 단계로 순차화하기 위한 조정 메커니즘으로 파이프라인 동기화 객체를 제공하여, 더블 버퍼링 또는 멀티 버퍼링 생산자-소비자 패턴의 구현을 용이하게 합니다. 파이프라인은 head와 tail을 갖는 양쪽 끝 큐로, 선입선출(FIFO) 순서로 작업을 처리합니다. 생산자 스레드는 파이프라인의 head에 작업을 커밋하고, 소비자 스레드는 파이프라인의 tail에서 작업을 가져옵니다.

파이프라인은 다음을 통해 노출됩니다 cuda::pipeline 의 API에서 libcu++ 라이브러리를 통해서뿐만 아니라 프리미티브 API. 다음 표는 두 API의 주요 기능을 설명합니다.

3.2.5. 비동기 데이터 복사#

메모리 계층 구조 내에서의 효율적인 데이터 이동은 GPU 컴퓨팅에서 높은 성능을 달성하는 데 근본적입니다. 전통적인 동기 메모리 작업은 데이터 전송 동안 스레드가 유휴 상태로 대기하도록 강제합니다. GPU는 병렬성을 통해 본질적으로 메모리 지연 시간을 숨깁니다. 즉, 메모리 작업이 완료되는 동안 SM은 다른 warp를 실행하도록 전환합니다. 이러한 병렬성을 통한 지연 시간 숨김이 있더라도, 메모리 지연 시간이 메모리 대역폭 활용과 연산 리소스 효율 모두에서 병목이 될 수는 여전히 있습니다. 이러한 병목을 해결하기 위해, 최신 GPU 아키텍처는 스레드가 다른 작업을 계속 실행하는 동안 메모리 전송이 독립적으로 진행될 수 있게 하는 하드웨어 가속 비동기 데이터 복사 메커니즘을 제공합니다.

비동기 데이터 복사는 메모리 전송의 시작을 그 완료를 기다리는 것과 분리함으로써, 연산을 데이터 이동과 오버랩할 수 있게 합니다. 이렇게 하면 스레드는 메모리 지연 시간 구간 동안 유용한 작업을 수행할 수 있어, 전체 처리량과 리소스 활용이 개선됩니다.

참고

이 섹션의 기반이 되는 개념과 원칙은 앞선 장의 비동기 실행에서 논의된 내용과 유사하지만, 해당 장은 cudaMemcpyAsync에 의해 호출되는 것과 같은 커널과 메모리 전송의 비동기 실행을 다루었습니다. 이는 애플리케이션의 서로 다른 구성 요소들 간의 비동기성으로 볼 수 있습니다.

이 섹션에서 설명하는 비동기성은 GPU 스레드를 블로킹하지 않으면서 GPU의 DRAM, 즉 전역 메모리와 공유 메모리 또는 텐서 메모리와 같은 on-SM 메모리 사이의 데이터 전송을 가능하게 하는 것을 의미합니다. 이는 단일 커널 런치의 실행 내부에서의 비동기성입니다.

비동기 복사가 어떻게 성능을 개선할 수 있는지 이해하려면, 일반적인 GPU 컴퓨팅 패턴을 살펴보는 것이 유용합니다. CUDA 애플리케이션은 종종 다음과 같은 copy and compute 패턴을 사용합니다:

  • 전역 메모리에서 데이터를 가져오고,

  • 데이터를 공유 메모리에 저장하고,

  • 공유 메모리 데이터에 대해 연산을 수행하며, 잠재적으로 결과를 전역 메모리에 다시 씁니다.

이 패턴의 copy 단계는 일반적으로 shared[local_idx] = global[global_idx]로 표현됩니다. 이 전역 메모리에서 공유 메모리로의 복사는 컴파일러에 의해 전역 메모리에서 레지스터로의 읽기 다음 레지스터에서 공유 메모리로의 쓰기로 확장됩니다.

이 패턴이 반복 알고리즘 내에서 발생할 때, 각 스레드 블록은 shared[local_idx] = global[global_idx] 할당 이후 동기화가 필요하며, 이는 연산 단계가 시작되기 전에 공유 메모리에 대한 모든 쓰기가 완료되었음을 보장하기 위해서입니다. 또한 스레드 블록은 연산 단계 이후에 다시 동기화가 필요하며, 이는 모든 스레드가 연산을 완료하기 전에 공유 메모리가 덮어써지는 것을 방지하기 위해서입니다. 이 패턴은 다음 코드 스니펫에 예시되어 있습니다.

#include <cooperative_groups.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // Computes using all values of current batch from shared memory.
    // Stores this thread's result back to global memory.
}

__global__ void without_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // Exposition: input size fits batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) bytes

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // Compute the index of the current batch for this block in global memory.
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;
    size_t global_idx = block_batch_idx + threadIdx.x;
    shared[local_idx] = global_in[global_idx];

    // Wait for all copies to complete.
    block.sync();

    // Compute and write result to global memory.
    compute(global_out + block_batch_idx, shared);

    // Wait for compute using shared memory to finish.
    block.sync();
  }
}

비동기 데이터 복사를 사용하면, 데이터가 도착하기를 기다리는 동안 SM을 더 효율적으로 사용하도록 전역 메모리에서 공유 메모리로의 데이터 이동을 비동기적으로 수행할 수 있습니다.

#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // Computes using all values of current batch from shared memory.
    // Stores this thread's result back to global memory.
}

__global__ void with_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // Exposition: input size fits batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) bytes

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // Compute the index of the current batch for this block in global memory.
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;

    // Whole thread-group cooperatively copies whole batch to shared memory.
    cooperative_groups::memcpy_async(block, shared, global_in + block_batch_idx, block.size());

    // Compute on different data while waiting.

    // Wait for all copies to complete.
    cooperative_groups::wait(block);

    // Compute and write result to global memory.
    compute(global_out + block_batch_idx, shared);

    // Wait for compute using shared memory to finish.
    block.sync();
  }
}

cooperative_groups::memcpy_async 함수는 전역 메모리에서 block.size() 요소를 shared 데이터로 복사합니다. 이 작업은 마치 다른 스레드에 의해 수행되는 것처럼 발생하며, 복사가 완료된 후 현재 스레드의 cooperative_groups::wait 호출과 동기화됩니다. 복사 작업이 완료될 때까지 전역 데이터를 수정하거나 공유 데이터를 읽거나 쓰면 데이터 레이스가 발생합니다.

이 예시는 모든 비동기 복사 작업의 근본적인 개념을 보여줍니다. 즉, 메모리 전송의 시작과 완료를 분리하여 데이터가 백그라운드에서 이동하는 동안 스레드가 다른 작업을 수행할 수 있게 합니다. CUDA 프로그래밍 모델은 이러한 기능에 접근하기 위한 여러 API를 제공하며, 여기에는 memcpy_async 에서 사용할 수 있는 함수 코오퍼러티브 그룹(Cooperative Groups) 및 libcu++ 라이브러리뿐만 아니라, 더 낮은 수준의 cuda::ptx 및 프리미티브 API입니다. 이러한 API는 유사한 시맨틱을 공유합니다. 즉, 다른 스레드가 수행하는 것처럼 소스에서 대상으로 객체를 복사하며, 복사가 완료되면 서로 다른 완료 메커니즘을 사용해 동기화할 수 있습니다.

현대 GPU 아키텍처는 비동기 데이터 이동을 위한 여러 하드웨어 메커니즘을 제공합니다.

  • LDGSTS(컴퓨트 기능 8.0+)는 전역 메모리에서 공유 메모리로의 효율적인 소규모 비동기 전송을 허용합니다.

  • 텐서 메모리 가속기(TMA, 컴퓨트 기능 9.0+)는 이러한 기능을 확장하여, 대규모 다차원 데이터 전송에 최적화된 대량-비동기 복사 작업을 제공합니다

  • STAS 명령어(컴퓨트 기능 9.0+)는 클러스터 내에서 레지스터에서 분산 공유 메모리로의 소규모 비동기 전송을 가능하게 합니다.

이러한 메커니즘은 서로 다른 데이터 경로, 전송 크기, 정렬 요구 사항을 지원하여, 개발자가 자신의 특정 데이터 접근 패턴에 가장 적절한 접근 방식을 선택할 수 있도록 합니다. 다음 표는 GPU 내에서의 비동기 복사를 위해 지원되는 데이터 경로의 개요를 제공합니다.

3.2.6. L1/공유 메모리 균형 구성#

L1 데이터 캐시에서 언급했듯이, SM의 L1 및 공유 메모리는 통합 데이터 캐시(unified data cache)로 알려진 동일한 물리적 리소스를 사용합니다. 대부분의 아키텍처에서 커널이 공유 메모리를 거의 사용하지 않거나 전혀 사용하지 않으면, 통합 데이터 캐시는 아키텍처에서 허용하는 최대 L1 캐시 용량을 제공하도록 구성될 수 있습니다.

공유 메모리에 예약된 통합 데이터 캐시는 커널별로 구성할 수 있습니다. 애플리케이션은 carveout(즉, 선호 공유 메모리 용량)을 커널이 런치되기 전에 호출되는 cudaFuncSetAttribute 함수로 설정할 수 있습니다.

cudaFuncSetAttribute(kernel_name, cudaFuncAttributePreferredSharedMemoryCarveout, carveout);

애플리케이션은 carveout을 해당 아키텍처에서 지원되는 최대 공유 메모리 용량에 대한 정수 백분율로 설정할 수 있습니다. 정수 백분율 외에도, carveout 값으로 사용할 수 있는 세 가지 편의 enum이 제공됩니다.

  • cudaSharedmemCarveoutDefault

  • cudaSharedmemCarveoutMaxL1

  • cudaSharedmemCarveoutMaxShared

최대 지원 공유 메모리 및 지원되는 carveout 크기는 아키텍처에 따라 다릅니다. 자세한 내용은 컴퓨트 기능별 공유 메모리 용량을 참조하십시오.

선택한 정수 백분율 carveout이 지원되는 공유 메모리 용량에 정확히 매핑되지 않는 경우, 다음으로 더 큰 용량이 사용됩니다. 예를 들어 최대 공유 메모리 용량이 100KB인 컴퓨트 기능 12.0 디바이스의 경우, carveout을 50%로 설정하면 50KB가 아니라 64KB의 공유 메모리가 됩니다. 컴퓨트 기능 12.0 디바이스는 0, 8, 16, 32, 64, 100 크기의 공유 메모리를 지원하기 때문입니다.

cudaFuncSetAttribute에 전달되는 함수는 __global__ 지정자로 선언되어야 합니다. cudaFuncSetAttribute은(는) 드라이버에서 힌트로 해석되며, 드라이버는 커널을 실행하기 위해 필요하다면 다른 carveout 크기를 선택할 수 있습니다.

참고

또 다른 CUDA API인 cudaFuncSetCacheConfig 역시 애플리케이션이 커널에 대해 L1과 공유 메모리 간의 균형을 조정할 수 있게 해줍니다. 하지만 이 API는 커널 런치에 대해 공유/L1 균형에 대한 엄격한 요구사항을 설정합니다. 그 결과, 서로 다른 공유 메모리 구성을 가진 커널을 번갈아 실행하면 공유 메모리 재구성 뒤에서 불필요하게 런치를 직렬화하게 됩니다. cudaFuncSetAttribute은(는) 드라이버가 함수 실행에 필요하거나 스래싱(thrashing)을 피하기 위해 필요할 경우 다른 구성을 선택할 수 있으므로 더 선호됩니다.

블록당 48 KB를 초과하는 공유 메모리 할당에 의존하는 커널은 아키텍처 종속적입니다. 따라서 정적으로 크기가 지정된 배열 대신 동적 공유 메모리를 사용해야 하며, 다음과 같이 cudaFuncSetAttribute을(를) 사용한 명시적 opt-in이 필요합니다.

// Device code
__global__ void MyKernel(...)
{
  extern __shared__ float buffer[];
  ...
}

// Host code
int maxbytes = 98304; // 96 KB
cudaFuncSetAttribute(MyKernel, cudaFuncAttributeMaxDynamicSharedMemorySize, maxbytes);
MyKernel <<<gridDim, blockDim, maxbytes>>>(...);
