3.5. CUDA 기능 둘러보기

이 프로그래밍 가이드의 1~3절에서는 CUDA와 GPU 프로그래밍을 소개하면서, 개념적으로 그리고 간단한 코드 예제를 통해 기초 주제를 다루었습니다. 이 가이드의 4부에서 특정 CUDA 기능을 설명하는 절에서는 이 가이드의 1~3절에서 다룬 개념에 대한 지식을 전제로 합니다.

CUDA에는 다양한 문제에 적용되는 많은 기능이 있습니다. 모든 기능이 모든 사용 사례에 적용되는 것은 아닙니다. 이 장은 이러한 각 기능을 소개하고, 의도된 사용 방식과 해결에 도움을 줄 수 있는 문제를 설명하기 위해 마련되었습니다. 기능은 의도된 해결 문제의 유형에 따라 대략적으로 범주로 분류되어 있습니다. CUDA 그래프와 같은 일부 기능은 둘 이상의 범주에 들어갈 수도 있습니다.

Section 4에서는 이러한 CUDA 기능을 더 완전하게 자세히 다룹니다.

3.5.1. 커널 성능 개선#

이 절에 개요로 제시된 기능은 모두 커널 개발자가 커널의 성능을 최대화하는 데 도움이 되도록 의도되었습니다.

3.5.1.1. 비동기 배리어#

비동기 배리어는 Section 3.2.4.2에서 소개되었으며, 스레드 간 동기화에 대해 더 세밀한 제어를 가능하게 합니다. 비동기 배리어는 배리어의 도착(arrival)과 대기(wait)를 분리합니다. 이를 통해 애플리케이션은 다른 스레드가 도착하기를 기다리는 동안에도 배리어에 의존하지 않는 작업을 수행할 수 있습니다. 비동기 배리어는 서로 다른 스레드 스코프에 대해 지정할 수 있습니다. 비동기 배리어의 전체 세부 사항은 Section 4.9에 있습니다.

3.5.1.2. 비동기 데이터 복사와 텐서 메모리 가속기(TMA)#

CUDA 커널 코드의 맥락에서 비동기 데이터 복사는 연산을 계속 수행하면서 공유 메모리와 GPU DRAM 간에 데이터를 이동할 수 있는 능력을 의미합니다. 이는 CPU와 GPU 간의 비동기 메모리 복사와 혼동해서는 안 됩니다. 이 기능은 비동기 배리어를 사용합니다. Section 4.11에서는 비동기 복사의 사용을 자세히 다룹니다.

3.5.1.3. 파이프라인#

파이프라인은 작업을 단계적으로 배치하고 다중 버퍼 생산자–소비자 패턴을 조정하기 위한 메커니즘으로, 일반적으로 연산을 비동기 데이터 복사와 오버랩하는 데 사용됩니다. Section 4.10에는 CUDA에서 파이프라인을 사용하는 방법에 대한 세부 사항과 예제가 있습니다.

3.5.1.4. 클러스터 런치 제어를 통한 워크 스틸링#

워크 스틸링(work stealing)은 작업을 완료한 워커가 다른 워커로부터 작업을 ‘훔칠’ 수 있는, 불균등한 워크로드에서 활용률을 유지하기 위한 기법입니다. 컴퓨트 기능 10.0(Blackwell)에서 도입된 기능인 클러스터 런치 제어는, 커널이 비행 중(in-flight) 블록 스케줄링을 직접 제어할 수 있게 해 주어 불균등한 워크로드에 실시간으로 적응할 수 있습니다. 스레드 블록은 아직 시작되지 않은 다른 스레드 블록 또는 클러스터의 런치를 취소하고, 해당 인덱스를 획득한 다음, 훔친 작업의 실행을 즉시 시작할 수 있습니다. 이러한 워크 스틸링 흐름은 SM을 바쁘게 유지하고 불규칙한 데이터 또는 런타임 변동 하에서 유휴 시간을 줄여—하드웨어 스케줄러에만 의존하지 않고도 더 세밀한 로드 밸런싱을 제공합니다.

Section 4.12에서는 이 기능을 사용하는 방법에 대한 세부 사항을 제공합니다.

3.5.2. 지연 시간 개선#

이 섹션에서 개괄한 기능들은 어떤 유형의 지연 시간을 줄이는 것을 목표로 한다는 공통된 주제를 공유하지만, 다루는 지연 시간의 유형은 기능마다 다릅니다. 대체로 이들은 커널 런치 수준 또는 그 이상의 지연 시간에 초점을 맞춥니다. 커널 내부의 GPU 메모리 접근 지연 시간은 여기에서 고려하는 지연 시간 중 하나가 아닙니다.

3.5.2.1. 그린 컨텍스트#

그린 컨텍스트는 실행 컨텍스트라고도 하며, 프로그램이 GPU의 SM 일부에서만 작업을 실행하는 CUDA 컨텍스트를 생성할 수 있게 하는 CUDA 기능에 붙여진 이름입니다. 기본적으로 커널 런치의 스레드 블록은 커널의 리소스 요구사항을 충족할 수 있는 GPU 내 임의의 SM으로 디스패치됩니다. 공유 메모리 사용, 레지스터 사용, 클러스터 사용, 스레드 블록의 총 스레드 수 등을 포함하되 이에 한정되지 않는 매우 많은 요인이 어떤 SM이 스레드 블록을 실행할 수 있는지에 영향을 줄 수 있습니다.

실행 컨텍스트는 커널을 특별히 생성된 컨텍스트로 런치하여, 커널을 실행할 수 있는 SM의 수를 추가로 제한할 수 있게 합니다. 중요한 점은, 프로그램이 어떤 SM 집합을 사용하는 그린 컨텍스트를 생성하면, GPU 상의 다른 컨텍스트는 그린 컨텍스트에 할당된 SM에 스레드 블록을 스케줄링하지 않는다는 것입니다. 여기에는 CUDA 런타임이 사용하는 기본 컨텍스트(primary context)도 포함됩니다. 이를 통해 이러한 SM은 우선순위가 높거나 지연 시간에 민감한 워크로드를 위해 예약될 수 있습니다.

Section 4.6에서는 그린 컨텍스트 사용에 대한 전체 세부 사항을 제공합니다. 그린 컨텍스트는 CUDA 13.1 및 이후 버전에서 CUDA 런타임으로 사용할 수 있습니다.

3.5.2.2. 스트림 순서 메모리 할당#

스트림 순서 메모리 할당자는 프로그램이 GPU 메모리의 할당 및 해제를 CUDA 스트림에 시퀀싱할 수 있게 합니다. 즉시 실행되는 cudaMalloc 및 cudaFree와 달리, cudaMallocAsync 및 cudaFreeAsync는 메모리 할당 또는 해제 연산을 CUDA 스트림에 삽입합니다. Section 4.3는 이들 API의 모든 세부 사항을 다룹니다.

3.5.2.3. CUDA 그래프#

CUDA 그래프는 애플리케이션이 커널 런치 또는 메모리 복사와 같은 CUDA 연산의 시퀀스와, 이러한 연산들 간의 의존성을 지정하여 GPU에서 효율적으로 실행될 수 있도록 합니다. 유사한 동작은 CUDA 스트림을 사용해서도 얻을 수 있으며, 실제로 그래프를 생성하는 메커니즘 중 하나는 스트림 캡처라고 하며, 이는 스트림의 연산을 CUDA 그래프에 기록할 수 있게 합니다. 그래프는 CUDA 그래프 API를 사용해서도 생성할 수 있습니다.

그래프가 생성되면, 이를 인스턴스화하여 여러 번 실행할 수 있습니다. 이는 반복될 워크로드를 지정하는 데 유용합니다. 그래프는 CUDA 연산 호출과 관련된 CPU 런치 비용을 줄이는 데 있어 일부 성능 이점을 제공할 뿐 아니라, 전체 워크로드가 사전에 지정될 때에만 가능한 최적화도 가능하게 합니다.

Section 4.2에서는 CUDA 그래프 사용 방법을 설명하고 시연합니다.

3.5.2.4. 프로그래밍 방식 종속 런치#

프로그래밍 방식 종속 런치는 종속 커널, 즉 이전 커널의 출력에 의존하는 커널이, 의존 대상인 기본 커널이 완료되기 전에 실행을 시작할 수 있게 하는 CUDA 기능입니다. 종속 커널은 기본 커널의 데이터가 필요해질 때까지 설정 코드와 관련 없는 작업을 실행하고, 그 지점에서 블록될 수 있습니다. 기본 커널은 종속 커널이 필요로 하는 데이터가 준비되었을 때 이를 신호로 알릴 수 있으며, 그러면 종속 커널이 해제되어 실행을 계속합니다. 이는 커널들 간에 일부 오버랩을 가능하게 하여, 핵심 데이터 경로의 지연 시간을 최소화하면서 GPU 활용률을 높게 유지하는 데 도움이 될 수 있습니다. Section 4.5는 프로그래밍 방식 종속 런치를 다룹니다.

3.5.2.5. 지연 로딩#

지연 로딩은 애플리케이션 시작 시 JIT 컴파일러의 동작 방식을 제어할 수 있게 하는 기능입니다. PTX에서 cubin으로 JIT 컴파일해야 하는 커널이 많은 애플리케이션은, 애플리케이션 시작의 일부로 모든 커널을 JIT 컴파일하면 긴 시작 시간을 경험할 수 있습니다. 기본 동작은 모듈이 필요해질 때까지 컴파일되지 않는 것입니다. 이는 환경 변수를 사용하여 변경할 수 있으며, Section 4.7에 자세히 설명되어 있습니다.

3.5.3. 기능성 기능#

여기에 설명된 기능들은 추가적인 기능 또는 동작을 가능하게 하는 것을 목적으로 한다는 공통된 특성을 공유합니다.

3.5.3.1. 확장 GPU 메모리#

확장 GPU 메모리는 NVLink-C2C로 연결된 시스템에서 사용할 수 있는 기능으로, GPU 내부에서 시스템 내 모든 메모리에 효율적으로 접근할 수 있게 합니다. EGM은 Section 4.17에서 자세히 다룹니다.

3.5.3.2. 동적 병렬성#

CUDA 애플리케이션은 가장 일반적으로 CPU에서 실행되는 코드에서 커널을 런치합니다. GPU에서 실행 중인 커널에서 새로운 커널 호출을 생성하는 것도 가능합니다. 이 기능을 CUDA 동적 병렬 처리라고 합니다. Section 4.18는 GPU에서 실행되는 코드로부터 새로운 GPU 커널 런치를 생성하는 세부 사항을 다룹니다.

3.5.4. CUDA 상호운용성#

3.5.4.1. 다른 API와의 CUDA 상호운용성#

GPU에서 코드를 실행하기 위한 메커니즘은 CUDA 외에도 존재합니다. 애플리케이션 GPU는 원래 컴퓨터 그래픽스를 가속하기 위해 구축되었으며, Direct3D와 Vulkan과 같은 자체 API 집합을 사용합니다. 애플리케이션은 3D 렌더링에는 그래픽 API 중 하나를 사용하면서, 계산은 CUDA에서 수행하고자 할 수 있습니다. CUDA는 CUDA 컨텍스트와 3D API가 사용하는 GPU 컨텍스트 간에 GPU에 저장된 데이터를 교환하기 위한 메커니즘을 제공합니다. 예를 들어, 애플리케이션은 CUDA를 사용하여 시뮬레이션을 수행한 다음, 3D API를 사용해 결과의 시각화를 생성할 수 있습니다. 이는 일부 버퍼를 CUDA와 그래픽 API 모두에서 읽기 및/또는 쓰기 가능하게 함으로써 달성됩니다.

그래픽 API와 버퍼를 공유할 수 있게 하는 동일한 메커니즘은, 다중 노드 환경 내에서 빠르고 직접적인 GPU-to-GPU 통신을 가능하게 할 수 있는 통신 메커니즘과 버퍼를 공유하는 데에도 사용됩니다.

Section 4.19는 CUDA가 다른 GPU API와 어떻게 상호운용되는지, 그리고 CUDA와 다른 API 간에 데이터를 공유하는 방법을 설명하며, 여러 서로 다른 API에 대한 구체적인 예를 제공합니다.

3.5.4.2. 프로세스 간 통신#

매우 큰 규모의 계산의 경우, 하나의 문제에 대해 더 많은 메모리와 더 많은 연산 자원이 함께 동작하도록 여러 GPU를 함께 사용하는 것이 일반적입니다. 단일 시스템, 또는 클러스터 컴퓨팅 용어로 노드(node) 내에서는, 단일 호스트 프로세스에서 여러 GPU를 사용할 수 있습니다. 이는 Section 3.4에 설명되어 있습니다.

또한 단일 컴퓨터 또는 여러 컴퓨터에 걸쳐 분리된 호스트 프로세스를 사용하는 것도 일반적입니다. 여러 프로세스가 함께 동작할 때, 이들 사이의 통신은 프로세스 간 통신(interprocess communication)으로 알려져 있습니다. CUDA 프로세스 간 통신(CUDA IPC)은 서로 다른 프로세스 간에 GPU 버퍼를 공유하기 위한 메커니즘을 제공합니다. Section 4.15는 CUDA IPC를 사용하여 서로 다른 호스트 프로세스 간을 조정하고 통신하는 방법을 설명하고 시연합니다.

3.5.5. 세밀한 제어#

3.5.5.1. 가상 메모리 관리#

Section 2.4.1에서 언급했듯이, 시스템의 모든 GPU는 CPU 메모리와 함께 단일 통합 가상 주소 공간을 공유합니다. 대부분의 애플리케이션은 동작을 변경할 필요 없이 CUDA가 제공하는 기본 메모리 관리를 사용할 수 있습니다. 그러나 CUDA 드라이버 API는 필요로 하는 사용자를 위해 이 가상 메모리 공간의 레이아웃에 대한 고급이고 상세한 제어를 제공합니다. 이는 주로 단일 시스템 내 및 여러 시스템에 걸쳐 GPU 간에 공유할 때 버퍼의 동작을 제어하는 데 적용됩니다.

Section 4.16은 CUDA 드라이버 API가 제공하는 제어, 그것들이 어떻게 동작하는지, 그리고 개발자가 언제 이를 유리하다고 느낄 수 있는지를 다룹니다.

3.5.5.2. 드라이버 엔트리 포인트 액세스#

드라이버 엔트리 포인트 액세스는 CUDA 11.3부터 CUDA 드라이버 API와 CUDA 런타임 API에 대한 함수 포인터를 가져올 수 있는 기능을 의미합니다. 또한 개발자가 드라이버 함수의 특정 변형(variant)에 대한 함수 포인터를 가져올 수 있게 하며, CUDA 툴킷에 포함된 것보다 더 최신 드라이버의 드라이버 함수에 액세스할 수 있게 해 줍니다. Section 4.20은 드라이버 엔트리 포인트 액세스를 다룹니다.

3.5.5.3. 오류 로그 관리#

오류 로그 관리는 CUDA API에서 발생하는 오류를 처리하고 로깅하기 위한 유틸리티를 제공합니다. 단일 환경 변수 CUDA_LOG_FILE를 설정하면 CUDA 오류를 stderr, stdout 또는 파일로 직접 캡처할 수 있습니다. 오류 로그 관리는 또한 CUDA가 오류를 만나면 트리거되는 콜백을 애플리케이션이 등록할 수 있게 합니다. Section 4.8은 오류 로그 관리에 대한 추가 세부 정보를 제공합니다.
