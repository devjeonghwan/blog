3.3. CUDA 드라이버 API

이 가이드의 이전 섹션에서는 CUDA 런타임을 다루었습니다. CUDA 런타임 API와 CUDA 드라이버 API에서 언급했듯이, CUDA 런타임은 더 낮은 수준의 CUDA 드라이버 API 위에 작성되어 있습니다. 이 섹션에서는 CUDA 런타임과 드라이버 API 간의 차이점 일부와, 이를 서로 혼용하는 방법을 다룹니다. 대부분의 애플리케이션은 CUDA 드라이버 API와 상호작용할 필요 없이도 완전한 성능으로 동작할 수 있습니다. 그러나 새로운 인터페이스는 때때로 런타임 API보다 드라이버 API에서 더 일찍 제공되며, 가상 메모리 관리와 같은 일부 고급 인터페이스는 드라이버 API에서만 노출됩니다.

드라이버 API는 장치 드라이버 설치 중 시스템에 복사되는 cuda 동적 라이브러리(cuda.dll 또는 cuda.so)에 구현되어 있습니다. 모든 엔트리 포인트는 cu로 시작합니다.

이는 핸들 기반의 명령형 API입니다. 대부분의 객체는 불투명 핸들로 참조되며, 이러한 핸들은 함수를 통해 지정되어 객체를 조작할 수 있습니다.

드라이버 API는 드라이버 API의 어떤 함수를 호출하기 전에 cuInit()로 초기화되어야 합니다. 그런 다음 특정 디바이스에 연결된 CUDA 컨텍스트를 생성하고, 컨텍스트에 자세히 설명된 대로 이를 호출하는 호스트 스레드의 현재 컨텍스트로 만들어야 합니다.

CUDA 컨텍스트 내에서 커널은 모듈에 설명된 대로 호스트 코드에 의해 PTX 또는 바이너리 객체로 명시적으로 로드됩니다. 따라서 C++로 작성된 커널은 PTX 또는 바이너리 객체로 별도로 컴파일되어야 합니다. 커널은 커널 실행에 설명된 대로 API 엔트리 포인트를 사용해 런치됩니다.

향후 디바이스 아키텍처에서 실행되기를 원하는 모든 애플리케이션은 바이너리 코드가 아니라 PTX를 로드해야 합니다. 이는 바이너리 코드가 아키텍처별이어서 향후 아키텍처와 호환되지 않는 반면, PTX 코드는 로드 시 디바이스 드라이버에 의해 바이너리 코드로 컴파일되기 때문입니다.

다음은 드라이버 API를 사용하여 작성된 커널의 샘플 호스트 코드입니다:

int main()
{
    int N = ...;
    size_t size = N * sizeof(float);

    // Allocate input vectors h_A and h_B in host memory
    float* h_A = (float*)malloc(size);
    float* h_B = (float*)malloc(size);

    // Initialize input vectors
    ...

    // Initialize
    cuInit(0);

    // Get number of devices supporting CUDA
    int deviceCount = 0;
    cuDeviceGetCount(&deviceCount);
    if (deviceCount == 0) {
        printf("There is no device supporting CUDA.\n");
        exit (0);
    }

    // Get handle for device 0
    CUdevice cuDevice;
    cuDeviceGet(&cuDevice, 0);

    // Create context
    CUcontext cuContext;
    cuCtxCreate(&cuContext, 0, cuDevice);

    // Create module from binary file
    CUmodule cuModule;
    cuModuleLoad(&cuModule, "VecAdd.ptx");

    // Allocate vectors in device memory
    CUdeviceptr d_A;
    cuMemAlloc(&d_A, size);
    CUdeviceptr d_B;
    cuMemAlloc(&d_B, size);
    CUdeviceptr d_C;
    cuMemAlloc(&d_C, size);

    // Copy vectors from host memory to device memory
    cuMemcpyHtoD(d_A, h_A, size);
    cuMemcpyHtoD(d_B, h_B, size);

    // Get function handle from module
    CUfunction vecAdd;
    cuModuleGetFunction(&vecAdd, cuModule, "VecAdd");

    // Invoke kernel
    int threadsPerBlock = 256;
    int blocksPerGrid =
            (N + threadsPerBlock - 1) / threadsPerBlock;
    void* args[] = { &d_A, &d_B, &d_C, &N };
    cuLaunchKernel(vecAdd,
                   blocksPerGrid, 1, 1, threadsPerBlock, 1, 1,
                   0, 0, args, 0);

    ...
}

전체 코드는 vectorAddDrv CUDA 샘플에서 찾을 수 있습니다.

3.3.1. 컨텍스트#

CUDA 컨텍스트는 CPU 프로세스에 비유할 수 있습니다. 드라이버 API 내에서 수행되는 모든 리소스와 작업은 CUDA 컨텍스트 안에 캡슐화되며, 컨텍스트가 파괴되면 시스템이 자동으로 이러한 리소스를 정리합니다. 모듈 및 텍스처 또는 서피스 레퍼런스 같은 객체 외에도, 각 컨텍스트는 고유한 별도의 주소 공간을 가집니다. 그 결과, 서로 다른 컨텍스트의 CUdeviceptr 값은 서로 다른 메모리 위치를 참조합니다.

호스트 스레드는 한 번에 하나의 디바이스 컨텍스트만 현재 컨텍스트로 가질 수 있습니다. 컨텍스트가 cuCtxCreate()로 생성되면, 이를 호출한 호스트 스레드의 현재 컨텍스트로 설정됩니다. 컨텍스트에서 동작하는 CUDA 함수(디바이스 열거 또는 컨텍스트 관리를 포함하지 않는 대부분의 함수)는 유효한 컨텍스트가 스레드의 현재 컨텍스트가 아니면 CUDA_ERROR_INVALID_CONTEXT를 반환합니다.

각 호스트 스레드는 현재 컨텍스트의 스택을 가집니다. cuCtxCreate()는 새로운 컨텍스트를 스택의 맨 위에 푸시합니다. cuCtxPopCurrent()를 호출하여 호스트 스레드에서 컨텍스트를 분리(detach)할 수 있습니다. 그러면 컨텍스트는 “부유(floating)” 상태가 되며, 어떤 호스트 스레드에 대해서든 현재 컨텍스트로 푸시될 수 있습니다. cuCtxPopCurrent()는 또한(있다면) 이전의 현재 컨텍스트를 복원합니다.

각 컨텍스트에 대해서는 사용 카운트도 유지됩니다. cuCtxCreate()는 사용 카운트가 1인 컨텍스트를 생성합니다. cuCtxAttach()는 사용 카운트를 증가시키고, cuCtxDetach()는 이를 감소시킵니다. cuCtxDetach() 또는 cuCtxDestroy()를 호출할 때 사용 카운트가 0이 되면 컨텍스트가 파괴됩니다.

드라이버 API는 런타임과 상호 운용 가능하며, 기본 컨텍스트에 접근할 수 있습니다(참조 런타임 초기화) 런타임이 관리하는 것을 드라이버 API에서 다음을 통해 cuDevicePrimaryCtxRetain().

사용 카운트는 동일한 컨텍스트에서 동작하는 서드파티 작성 코드 간의 상호운용성을 용이하게 합니다. 예를 들어, 동일한 컨텍스트를 사용하기 위해 세 개의 라이브러리가 로드되는 경우, 각 라이브러리는 사용 카운트를 증가시키기 위해 cuCtxAttach()를 호출하고, 라이브러리가 컨텍스트 사용을 마치면 사용 카운트를 감소시키기 위해 cuCtxDetach()를 호출합니다. 대부분의 라이브러리에서는 애플리케이션이 라이브러리를 로드하거나 초기화하기 전에 컨텍스트를 생성해 두었을 것으로 예상됩니다. 이렇게 하면 애플리케이션이 자체 휴리스틱을 사용해 컨텍스트를 생성할 수 있고, 라이브러리는 자신에게 전달된 컨텍스트에서 단순히 동작합니다. 자체 컨텍스트를 생성하려는 라이브러리(자신들의 API 클라이언트가 자체적으로 컨텍스트를 생성했을 수도 있고 생성하지 않았을 수도 있지만, 이를 알지 못하는 상태에서)는 다음 그림에 표시된 대로 cuCtxPushCurrent() 및 cuCtxPopCurrent()를 사용합니다.

3.3.2. 모듈#

모듈은 Windows의 DLL과 유사하게, nvcc가 출력하는 디바이스 코드 및 데이터의 동적 로드 가능 패키지입니다(NVCC로 컴파일 참조). 함수, 전역 변수, 텍스처 또는 서피스 레퍼런스를 포함한 모든 심볼의 이름은 모듈 범위에서 유지되므로, 독립적인 제3자가 작성한 모듈도 동일한 CUDA 컨텍스트에서 상호 운용할 수 있습니다.

이 코드 샘플은 모듈을 로드하고 일부 커널에 대한 핸들을 가져옵니다:

CUmodule cuModule;
cuModuleLoad(&cuModule, "myModule.ptx");
CUfunction myKernel;
cuModuleGetFunction(&myKernel, cuModule, "MyKernel");

이 코드 샘플은 PTX 코드에서 새 모듈을 컴파일하고 로드한 다음 컴파일 오류를 파싱합니다:

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* PTXCode = "some PTX code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_TARGET_FROM_CUCONTEXT;
values[2]  = 0;
err = cuModuleLoadDataEx(&cuModule, PTXCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);

이 코드 샘플은 여러 PTX 코드에서 새 모듈을 컴파일, 링크 및 로드한 다음 링크 및 컴파일 오류를 파싱합니다:

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[6];
void* values[6];
float walltime;
char error_log[BUFFER_SIZE], info_log[BUFFER_SIZE];
char* PTXCode0 = "some PTX code";
char* PTXCode1 = "some other PTX code";
CUlinkState linkState;
int err;
void* cubin;
size_t cubinSize;
options[0] = CU_JIT_WALL_TIME;
values[0] = (void*)&walltime;
options[1] = CU_JIT_INFO_LOG_BUFFER;
values[1] = (void*)info_log;
options[2] = CU_JIT_INFO_LOG_BUFFER_SIZE_BYTES;
values[2] = (void*)BUFFER_SIZE;
options[3] = CU_JIT_ERROR_LOG_BUFFER;
values[3] = (void*)error_log;
options[4] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[4] = (void*)BUFFER_SIZE;
options[5] = CU_JIT_LOG_VERBOSE;
values[5] = (void*)1;
cuLinkCreate(6, options, values, &linkState);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode0, strlen(PTXCode0) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode1, strlen(PTXCode1) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
cuLinkComplete(linkState, &cubin, &cubinSize);
printf("Link completed in %fms. Linker Output:\n%s\n", walltime, info_log);
cuModuleLoadData(cuModule, cubin);
cuLinkDestroy(linkState);

cubin을 로드할 때를 포함하여, 여러 스레드를 사용해 모듈 링크/로드 프로세스의 일부를 가속하는 것이 가능합니다. 이 코드 샘플은 모듈 로딩을 빠르게 하기 위해 CU_JIT_BINARY_LOADER_THREAD_COUNT를 사용합니다.

#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* cubinCode = "some cubin code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_BINARY_LOADER_THREAD_COUNT;
values[2]  = 0; // Use as many threads as CPUs on the machine
err = cuModuleLoadDataEx(&cuModule, cubinCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);

전체 코드는 ptxjit CUDA 샘플에서 찾을 수 있습니다.

3.3.3. 커널 실행#

cuLaunchKernel()는 지정된 실행 구성으로 커널을 런치합니다.

매개변수는 포인터 배열( cuLaunchKernel()의 끝에서 두 번째 매개변수)로 전달되는데, 여기서 n번째 포인터는 n번째 매개변수에 해당하며 매개변수가 복사되는 메모리 영역을 가리키거나, 또는 추가 옵션 중 하나( cuLaunchKernel()의 마지막 매개변수)로 전달됩니다.

매개변수가 추가 옵션( CU_LAUNCH_PARAM_BUFFER_POINTER 옵션)으로 전달될 때에는, 매개변수들이 디바이스 코드에서 각 매개변수 타입의 정렬 요구사항을 만족하도록 서로에 대해 적절히 오프셋되어 있다고 가정되는 단일 버퍼에 대한 포인터로 전달됩니다.

내장 벡터 타입에 대한 디바이스 코드의 정렬 요구사항은 Table 42에 나열되어 있습니다. 다른 모든 기본 타입에 대해서는, 디바이스 코드의 정렬 요구사항이 호스트 코드의 정렬 요구사항과 일치하므로 __alignof()를 사용하여 얻을 수 있습니다. 유일한 예외는 호스트 컴파일러가 double 및 long long(그리고 64비트 시스템에서는 long)를 두 단어 경계가 아닌 한 단어 경계에 정렬하는 경우(예: gcc의 컴파일 플래그 -mno-align-double 사용)인데, 디바이스 코드에서는 이러한 타입들이 항상 두 단어 경계에 정렬되기 때문입니다.

CUdeviceptr는 정수이지만 포인터를 나타내므로, 해당 정렬 요구사항은 __alignof(void*)입니다.

다음 코드 샘플은 매크로(ALIGN_UP())를 사용해 각 매개변수의 오프셋을 조정하여 정렬 요구사항을 만족시키고, 또 다른 매크로(ADD_TO_PARAM_BUFFER())를 사용해 CU_LAUNCH_PARAM_BUFFER_POINTER 옵션에 전달되는 매개변수 버퍼에 각 매개변수를 추가합니다.

#define ALIGN_UP(offset, alignment) \
      (offset) = ((offset) + (alignment) - 1) & ~((alignment) - 1)

char paramBuffer[1024];
size_t paramBufferSize = 0;

#define ADD_TO_PARAM_BUFFER(value, alignment)                   \
    do {                                                        \
        paramBufferSize = ALIGN_UP(paramBufferSize, alignment); \
        memcpy(paramBuffer + paramBufferSize,                   \
               &(value), sizeof(value));                        \
        paramBufferSize += sizeof(value);                       \
    } while (0)

int i;
ADD_TO_PARAM_BUFFER(i, __alignof(i));
float4 f4;
ADD_TO_PARAM_BUFFER(f4, 16); // float4's alignment is 16
char c;
ADD_TO_PARAM_BUFFER(c, __alignof(c));
float f;
ADD_TO_PARAM_BUFFER(f, __alignof(f));
CUdeviceptr devPtr;
ADD_TO_PARAM_BUFFER(devPtr, __alignof(devPtr));
float2 f2;
ADD_TO_PARAM_BUFFER(f2, 8); // float2's alignment is 8

void* extra[] = {
    CU_LAUNCH_PARAM_BUFFER_POINTER, paramBuffer,
    CU_LAUNCH_PARAM_BUFFER_SIZE,    &paramBufferSize,
    CU_LAUNCH_PARAM_END
};
cuLaunchKernel(cuFunction,
               blockWidth, blockHeight, blockDepth,
               gridWidth, gridHeight, gridDepth,
               0, 0, 0, extra);

구조체의 정렬 요구사항은 해당 필드들의 정렬 요구사항 중 최대값과 같습니다. 내장 벡터 타입을 포함하는 구조체의 정렬 요구사항은, CUdeviceptr, 또는 정렬되지 않은 double 그리고 long long, 따라서 디바이스 코드와 호스트 코드 간에 다를 수 있습니다. 또한 이러한 구조체는 다르게 패딩될 수도 있습니다. 예를 들어, 다음 구조체는 호스트 코드에서는 전혀 패딩되지 않지만, 디바이스 코드에서는 필드 뒤에 12바이트가 패딩됩니다 f 필드의 정렬 요구사항이 f4 은(는) 16입니다.

typedef struct {
    float  f;
    float4 f4;
} myStruct;

3.3.4. 런타임 API와 드라이버 API 간 상호운용성#

애플리케이션은 런타임 API 코드와 드라이버 API 코드를 혼용할 수 있습니다.

드라이버 API를 통해 컨텍스트가 생성되고 현재 컨텍스트로 설정되면, 이후의 런타임 호출은 새 컨텍스트를 생성하는 대신 이 컨텍스트를 사용합니다.

런타임이 초기화된 경우, cuCtxGetCurrent()를 사용하여 초기화 중 생성된 컨텍스트를 가져올 수 있습니다. 이 컨텍스트는 이후의 드라이버 API 호출에서 사용할 수 있습니다.

런타임에서 암묵적으로 생성된 컨텍스트는 기본 컨텍스트(primary context)라고 합니다( 런타임 초기화 참조). 이는 기본 컨텍스트 관리 함수로 드라이버 API에서 관리할 수 있습니다.

디바이스 메모리는 어느 API를 사용하든 할당 및 해제할 수 있습니다. CUdeviceptr는 일반 포인터로 캐스팅할 수 있으며 그 반대도 가능합니다:

CUdeviceptr devPtr;
float* d_data;

// Allocation using driver API
cuMemAlloc(&devPtr, size);
d_data = (float*)devPtr;

// Allocation using runtime API
cudaMalloc(&d_data, size);
devPtr = (CUdeviceptr)d_data;

특히 이는 드라이버 API를 사용해 작성된 애플리케이션이 런타임 API를 사용해 작성된 라이브러리(예: cuFFT, cuBLAS, …)를 호출할 수 있음을 의미합니다.

레퍼런스 매뉴얼의 디바이스 및 버전 관리 섹션에 있는 모든 함수는 서로 바꿔 사용될 수 있습니다.
