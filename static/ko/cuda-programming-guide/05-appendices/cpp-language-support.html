5.3. C++ 언어 지원

nvcc은(는) 다음 사양에 따라 CUDA 및 디바이스 코드를 처리합니다:

  • C++03 (ISO/IEC 14882:2003), --std=c++03 플래그.

  • C++11 (ISO/IEC 14882:2011), --std=c++11 플래그.

  • C++14 (ISO/IEC 14882:2014), --std=c++14 플래그.

  • C++17 (ISO/IEC 14882:2017), --std=c++17 플래그.

  • C++20 (ISO/IEC 14882:2020), --std=c++20 플래그.

nvcc -std=c++<version> 플래그를 전달하면 지정된 버전과 관련된 모든 C++ 기능이 켜지며, 해당 C++ 방언 옵션으로 호스트 전처리기, 컴파일러 및 링커도 호출합니다.

컴파일러는 다음 섹션에서 보고된 제한 사항의 적용을 받으며, 지원되는 표준의 모든 언어 기능을 지원합니다.

5.3.5. CUDA C++ 표준 라이브러리#

CUDA는 libcu++라고 불리는 C++ 표준 라이브러리(STL) 구현을 제공합니다. 이 라이브러리는 다음과 같은 이점을 제공합니다:

  • 기능을 호스트와 디바이스 모두에서 사용할 수 있습니다.

  • CUDA Toolkit이 지원하는 모든 Linux 및 Windows 플랫폼과 호환됩니다.

  • CUDA Toolkit의 최근 두 개 메이저 버전에서 지원하는 모든 GPU 아키텍처와 호환됩니다.

  • 현재 및 이전 메이저 버전의 모든 CUDA Toolkit과 호환됩니다.

  • C++20, C++23, C++26을 포함하여 최근 표준 버전에서 사용할 수 있는 C++ 표준 라이브러리 기능의 C++17 백포트(backport)를 제공합니다.

  • 128비트 정수(__int128), 반정밀도(half-precision) 부동소수점(__half), Bfloat16(__nv_bfloat16), 사중정밀도(quad-precision) 부동소수점(__float128)과 같은 확장 데이터 타입을 지원합니다.

  • 디바이스 코드에 대해 고도로 최적화되어 있습니다.

또한, libcu++는 생산성과 애플리케이션 성능을 향상하기 위해 C++ 표준 라이브러리에서는 사용할 수 없는 확장 기능을 제공합니다. 이러한 기능에는 수학 함수, 메모리 연산, 동기화 프리미티브, 컨테이너 확장, CUDA 인트린식(intrinsic)의 고수준 추상화, C++ PTX 래퍼 등이 포함됩니다.

libcu++는 CUDA Toolkit의 일부로 제공되며, 오픈 소스 CCCL 리포지토리의 일부로도 제공됩니다.

5.3.6. C 표준 라이브러리 함수#

5.3.6.1. clock() 및 clock64()#

__host__ __device__ clock_t   clock();
__device__          long long clock64();

디바이스 코드에서 실행되면, 매 클록 사이클마다 증가하는 멀티프로세서별 카운터의 값을 반환합니다. 커널의 시작과 끝에서 이 카운터를 샘플링하고 두 값을 빼서 각 스레드의 결과를 기록하면, 디바이스가 해당 스레드를 실행하는 데 소비한 클록 사이클 수의 추정치를 얻을 수 있습니다. 하지만 이 값은 디바이스가 스레드의 명령을 실행하는 데 실제로 소비한 클록 사이클 수를 나타내지는 않습니다. 스레드는 타임 슬라이싱(time-slicing)되기 때문에 전자의 값이 후자의 값보다 큽니다.

힌트

  • 해당 CUDA C++ 함수 cuda::std::clock()는 <cuda/std/ctime> 헤더에 제공됩니다.

  • 유사한 목적을 위해, 이식 가능한 C++ <chrono> 구현도 <cuda/std/chrono> 헤더에 제공됩니다.

5.3.6.2. printf()#

int printf(const char* format[, arg, ...]);

이 함수는 커널에서 호스트 측 출력 스트림으로 서식이 지정된 출력을 인쇄합니다.

커널 내 printf() 함수는 표준 C 라이브러리 printf() 함수와 유사하게 동작합니다. 사용자는 printf() 동작에 대한 완전한 설명을 위해 자신의 호스트 시스템 매뉴얼 페이지를 참조해야 합니다. 본질적으로, format로 전달된 문자열이 호스트의 스트림으로 출력됩니다.

printf() 명령은 다른 모든 디바이스 측 함수와 마찬가지로 스레드별로, 그리고 호출한 스레드의 컨텍스트에서 실행됩니다. 멀티스레드 커널에서 printf()를 단순히 호출하면 각 스레드가 해당 스레드가 지정한 데이터를 사용하여 이를 실행하게 됩니다. 결과적으로 호스트 스트림에는 출력 문자열의 여러 버전이 나타나며, 각각은 printf()를 만난 스레드에 해당합니다.

인쇄된 문자 수를 반환하는 C 표준 printf()와 달리, CUDA의 printf()는 파싱된 인자 수를 반환합니다. 포맷 문자열 뒤에 인자가 없으면 0이 반환됩니다. 포맷 문자열이 NULL이면 -1가 반환됩니다. 내부 오류가 발생하면 -2가 반환됩니다.

내부적으로 printf()는 공유 데이터 구조를 사용하므로, printf()를 호출하면 스레드의 실행 순서가 바뀔 수 있습니다. 특히 printf()를 호출하는 스레드는 printf()를 호출하지 않는 스레드보다 더 긴 실행 경로를 택할 수 있으며, 그 경로의 길이는 printf()의 매개변수에 따라 달라집니다. 다만 CUDA는 명시적인 __syncthreads() 배리어를 제외하고는 스레드 실행 순서에 대해 어떠한 보장도 하지 않습니다. 따라서 실행 순서가 printf()에 의해 수정되었는지, 또는 하드웨어의 다른 스케줄링 동작에 의한 것인지 판단하는 것은 불가능합니다.

포맷 지정자

표준 printf()와 마찬가지로, 포맷 지정자는 다음 형태를 취합니다: %[flags][width][.precision][size]type

다음 필드가 지원됩니다. 모든 동작에 대한 완전한 설명은 널리 알려진 문서를 참조하십시오.

  • 플래그: #, ' ', 0, +, -

  • 너비: *, 0-9

  • 정밀도: 0-9

  • 크기: h, l, ll

  • 타입: %cdiouxXpeEfgGaAs

제한 사항

printf() 출력의 최종 포맷팅은 호스트 시스템에서 이루어집니다. 이는 포맷 문자열을 호스트 시스템의 컴파일러와 C 라이브러리가 이해할 수 있어야 함을 의미합니다. CUDA의 printf() 함수가 지원하는 포맷 지정자가 가장 일반적인 호스트 컴파일러가 지원하는 것들의 보편적인 부분집합이 되도록 모든 노력을 기울였지만, 정확한 동작은 호스트 운영 체제에 따라 달라집니다.

printf()는 플래그와 타입의 모든 유효한 조합을 허용합니다. 이는 최종 출력이 포맷팅되는 호스트 시스템에서 무엇이 유효하고 유효하지 않은지를 판단할 수 없기 때문입니다. 결과적으로 프로그램이 유효하지 않은 조합을 포함하는 포맷 문자열을 내보내면 출력은 정의되지 않을 수 있습니다.

printf() 함수는 포맷 문자열 외에 최대 32개의 인자를 받을 수 있습니다. 추가 인자는 무시되며, 포맷 지정자는 있는 그대로 출력됩니다.

Windows 플랫폼(32비트)과 Linux 플랫폼(64비트)에서 long 타입의 크기가 다르기 때문에, Linux 머신에서 컴파일한 커널을 Windows 머신에서 실행하면 %ld를 포함하는 모든 포맷 문자열에 대해 손상된 출력을 생성합니다. 안전을 위해 컴파일 및 실행 플랫폼을 일치시키는 것을 권장합니다.

호스트 측 버퍼

printf()의 출력 버퍼는 커널 실행 전에 고정 크기로 설정됩니다. 버퍼는 원형(circular)이므로, 커널 실행 중 버퍼에 담을 수 있는 것보다 더 많은 출력이 생성되면 이전 출력이 덮어써집니다. 버퍼는 다음 작업 중 하나가 수행될 때만 플러시됩니다:

  • <<< >>> 또는 cuLaunchKernel()를 통한 커널 실행: 실행 시작 시, 그리고 CUDA_LAUNCH_BLOCKING 환경 변수가 1로 설정된 경우 실행 종료 시에도,

  • cudaDeviceSynchronize(), cuCtxSynchronize(), cudaStreamSynchronize(), cuStreamSynchronize(), cudaEventSynchronize(), 또는 cuEventSynchronize()를 통한 동기화,

  • cudaMemcpy*() 또는 cuMemcpy*()의 임의의 블로킹 버전을 통한 메모리 복사,

  • cuModuleLoad() 또는 cuModuleUnload()를 통한 모듈 로드/언로드,

  • cudaDeviceReset() 또는 cuCtxDestroy()를 통한 컨텍스트 파괴.

  • cudaLaunchHostFunc() 또는 cuLaunchHostFunc()로 추가된 스트림 콜백을 실행하기 전에.

프로그램이 종료될 때 버퍼가 자동으로 플러시되지 않는다는 점에 유의하십시오.

다음 API 함수는 printf() 인자와 내부 메타데이터를 호스트로 전송하는 데 사용되는 버퍼의 크기를 설정하고 가져옵니다. 기본 크기는 1메가바이트입니다.

  • cudaDeviceGetLimit(size_t* size,cudaLimitPrintfFifoSize)

  • cudaDeviceSetLimit(cudaLimitPrintfFifoSize, size_t size)

int main() {
    helloCUDA<<<1, 5>>>(1.2345f);

Hello thread 0, value=1.2345

5.3.6.4. malloc() 및 free()#

__host__ __device__ void* malloc(size_t size);
// or cuda::std::malloc(), cuda::std::calloc() in the <cuda/std/cstdlib> header

malloc() (디바이스 측), cuda::std::malloc(), 그리고 cuda::std::calloc() 함수는 디바이스 힙에서 최소 size 바이트를 할당하고 할당된 메모리에 대한 포인터를 반환합니다. 요청을 충족하기에 메모리가 충분하지 않으면 NULL을 반환합니다. 반환된 포인터는 16바이트 경계에 정렬(alignment)되는 것이 보장됩니다.

__device__ void* __nv_aligned_device_malloc(size_t size, size_t align);
// or cuda::std::aligned_alloc() in the <cuda/std/cstdlib> header

__nv_aligned_device_malloc() 함수와 C++ cuda::std::aligned_alloc()는 디바이스 힙에서 최소 size 바이트를 할당하고 할당된 메모리에 대한 포인터를 반환합니다. 요청된 크기 또는 정렬을 충족하기에 메모리가 충분하지 않으면 NULL을 반환합니다. 할당된 메모리의 주소는 align의 배수입니다. align는 0이 아닌 2의 거듭제곱이어야 합니다.

__host__ __device__ void free(void* ptr);
// or cuda::std::free() in the <cuda/std/cstdlib> header

디바이스 측 함수 free() 및 cuda::std::free() 가 가리키는 메모리를 할당 해제합니다 ptr, 이는 이전 호출에서 반환된 것이어야 합니다 malloc(), cuda::std::malloc(), cuda::std::calloc(), __nv_aligned_device_malloc(), 또는 cuda::std::aligned_alloc(). 만약 ptr 이면 NULL, 호출은 free() 또는 cuda::std::free() 은 무시됩니다. 반복 호출은 free() 또는 cuda::std::free() 동일한 ptr 정의되지 않은 동작을 합니다.

주어진 CUDA 스레드가 malloc(), cuda::std::malloc(), cuda::std::calloc(), __nv_aligned_device_malloc(), 또는 cuda::std::aligned_alloc()을 통해 할당한 메모리는 CUDA 컨텍스트의 수명 동안, 또는 free() 또는 cuda::std::free() 호출로 명시적으로 해제될 때까지 할당된 상태로 유지됩니다. 이 메모리는 이후 커널 런치의 스레드를 포함하여 다른 CUDA 스레드가 사용할 수 있습니다. 어떤 CUDA 스레드든 다른 스레드가 할당한 메모리를 해제할 수 있지만, 동일한 포인터가 두 번 이상 해제되지 않도록 주의해야 합니다.

힙 메모리 API

디바이스 코드에서 메모리를 할당하거나 해제하는 모든 프로그램( new 및 delete 키워드를 포함)보다 먼저 디바이스 메모리 힙의 크기를 지정해야 합니다. 어떤 프로그램이 힙 크기를 명시적으로 지정하지 않고 디바이스 메모리 힙을 사용하면, 기본값으로 8메가바이트 힙이 할당됩니다.

다음 API 함수는 힙 크기를 가져오고 설정합니다:

  • cudaDeviceGetLimit(size_t* size, cudaLimitMallocHeapSize)

  • cudaDeviceSetLimit(cudaLimitMallocHeapSize, size_t size)

부여되는 힙 크기는 최소 size 바이트입니다. cuCtxGetLimit() 및 cudaDeviceGetLimit()는 현재 요청된 힙 크기를 반환합니다.

힙에 대한 실제 메모리 할당은 모듈이 컨텍스트에 로드될 때 발생하며, CUDA 드라이버 API를 통해 명시적으로( 모듈 참조) 또는 CUDA 런타임 API를 통해 암시적으로 수행됩니다. 메모리 할당에 실패하면, 모듈 로드는 CUDA_ERROR_SHARED_OBJECT_INIT_FAILED 오류를 발생시킵니다.

모듈이 로드된 이후에는 힙 크기를 변경할 수 없으며, 필요에 따라 동적으로 크기가 조정되지도 않습니다.

디바이스 힙을 위해 예약된 메모리는 cudaMalloc()와 같은 호스트 측 CUDA API 호출을 통해 할당된 메모리에 추가로 제공됩니다.

호스트 메모리 API와의 상호운용성

디바이스 측 함수 malloc(), cuda::std::malloc(), cuda::std::calloc(), __nv_aligned_device_malloc(), cuda::std::aligned_alloc(), 또는 new 키워드를 통해 할당된 메모리는 cudaMalloc, cudaMemcpy, 또는 cudaMemset와 같은 런타임 또는 드라이버 API 호출로 사용할 수 없으며 해제할 수도 없습니다. 마찬가지로 호스트 런타임 API를 통해 할당된 메모리는 디바이스 측 함수 free(), cuda::std::free(), 또는 delete 키워드를 사용하여 해제할 수 없습니다.

스레드별 할당 예:

#include <stdlib.h>
#include <stdio.h>

__global__ void single_thread_allocation_kernel() {
    size_t size = 123;
    char*  ptr  = (char*) malloc(size);
    memset(ptr, 0, size);
    printf("Thread %d got pointer: %p\n", threadIdx.x, ptr);
    free(ptr);
}

int main() {
    // Set a heap size of 128 megabytes.
    // Note that this must be done before any kernel is launched.
    cudaDeviceSetLimit(cudaLimitMallocHeapSize, 128 * 1024 * 1024);
    single_thread_allocation_kernel<<<1, 5>>>();
    cudaDeviceSynchronize();
    return 0;
}

스레드 블록별 할당 예:

#include <stdlib.h>

__global__ void block_level_allocation_kernel() {
    __shared__ int* data;
    // The first thread in the block performs the allocation and shares the pointer
    // with all other threads through shared memory, so that access can be coalesced.
    if (threadIdx.x == 0) {
        size_t size = blockDim.x * 64; // 64 bytes per thread are allocated.
        data = (int*) malloc(size);
    }
    __syncthreads();
    // Check for failure
    if (data == nullptr)
        return;

    // Threads index into the memory, ensuring coalescence
    for (int i = 0; i < 64; ++i)
        data[i * blockDim.x + threadIdx.x] = threadIdx.x;
    // Ensure all threads complete before freeing
    __syncthreads();

    // Only one thread may free the memory!
    if (threadIdx.x == 0)
        free(data);
}

int main() {
    cudaDeviceSetLimit(cudaLimitMallocHeapSize, 128 * 1024 * 1024);
    block_level_allocation_kernel<<<10, 128>>>();
    cudaDeviceSynchronize();
    return 0;
}

#include <stdlib.h>
#include <stdio.h>

const int NUM_BLOCKS = 20;

__device__ int* data_ptrs[NUM_BLOCKS]; // Per-block pointer

__global__ void allocate_memory_kernel() {
    // Only the first thread in the block performs the allocation
    // since we need only one allocation per block.
    if (threadIdx.x == 0)
        data_ptrs[blockIdx.x] = (int*) malloc(blockDim.x * 4);
    __syncthreads();
    // Check for failure
    if (data_ptrs[blockIdx.x] == nullptr)
        return;
    // Zero the data with all threads in parallel
    data_ptrs[blockIdx.x][threadIdx.x] = 0;
}

// Simple example: store the thread ID into each element
__global__ void use_memory_kernel() {
    int* ptr = data_ptrs[blockIdx.x];
    if (ptr != nullptr)
        ptr[threadIdx.x] += threadIdx.x;
}

// Print the content of the buffer before freeing it
__global__ void free_memory_kernel() {
    int* ptr = data_ptrs[blockIdx.x];
    if (ptr != nullptr)
        printf("Block %d, Thread %d: final value = %d\n",
            blockIdx.x, threadIdx.x, ptr[threadIdx.x]);
    // Only free from one thread!
    if (threadIdx.x == 0)
        free(ptr);
}

int main() {
    cudaDeviceSetLimit(cudaLimitMallocHeapSize, 128*1024*1024);
    // Allocate memory
    allocate_memory_kernel<<<NUM_BLOCKS, 10>>>();

    // Use memory
    use_memory_kernel<<<NUM_BLOCKS, 10>>>();
    use_memory_kernel<<<NUM_BLOCKS, 10>>>();
    use_memory_kernel<<<NUM_BLOCKS, 10>>>();

    // Free memory
    free_memory_kernel<<<NUM_BLOCKS, 10>>>();
    cudaDeviceSynchronize();
    return 0;
}

5.3.6.5. alloca()#

__host__ __device__ void* alloca(size_t size);

alloca() 함수는 호출자의 스택 프레임 내에서 size 바이트의 메모리를 할당합니다. 반환 값은 할당된 메모리를 가리키는 포인터입니다. 이 함수가 디바이스 코드에서 호출되면, 메모리의 시작은 16바이트 정렬(alignment)됩니다. 메모리는 호출자가 alloca()에서 반환할 때 자동으로 해제됩니다.

참고

Windows 플랫폼에서는 <malloc.h> 헤더 파일을 alloca() 함수를 사용하기 전에 포함해야 합니다. alloca() 호출은 스택 오버플로를 유발할 수 있으므로, 사용자는 그에 맞게 스택 크기를 조정해야 합니다.

예:

__device__ void device_function(int num_items) {
    int4* ptr = (int4*) alloca(num_items * sizeof(int4));
    // use of ptr
    ...
}

5.3.7. 람다 표현식#

컴파일러는 람다 표현식 또는 클로저 타입(C++11)의 실행 공간을, 이를 가장 안쪽으로 둘러싼 함수 스코프의 실행 공간과 연결하여 결정합니다. 둘러싼 함수 스코프가 없으면, 실행 공간은 __host__로 지정됩니다.
실행 공간은 확장 람다 구문을 사용하여 명시적으로 지정할 수도 있습니다.

예:

auto global_lambda = [](){ return 0; }; // __host__

}

__host__ __device__ void host_device_function() {
    auto lambda4 = [](){ return 4; };   // __host__ __device__
}

using function_ptr_t = int (*)();

__device__ void device_function(float          value,
                                function_ptr_t ptr = [](){ return 4; } /* __host__ */) {}

5.3.7.2. 확장 람다#

이 nvcc 플래그 --extended-lambda 람다 표현식에서 실행 공간에 대한 명시적 어노테이션을 허용합니다. 이러한 어노테이션은 람다 도입자 뒤에, 그리고 선택적인 람다 선언자 앞에 나타나야 합니다.
nvcc 매크로를 정의합니다 __CUDACC_EXTENDED_LAMBDA__ 일 때 --extended-lambda 플래그가 지정된 경우입니다.

  • 한 확장 람다 는 즉시 또는 중첩된 블록의 스코프 내에서 정의됩니다 __host__ 또는 __host__ __device__ 함수.

  • An 확장 디바이스 람다 는 다음으로 어노테이션된 람다 표현식입니다 __device__ 키워드.

  • 확장 호스트-디바이스 람다는 __host__ __device__ 키워드로 어노테이션된 람다 표현식입니다.

표준 람다 표현식과 달리, 확장 람다는 __global__ 함수에서 타입 인수로 사용할 수 있습니다.

예:

void host_function() {
    auto lambda1 = [] {};                      // NOT an extended lambda: no explicit execution space annotations
    auto lambda2 = [] __device__ {};           // extended lambda
    auto lambda3 = [] __host__ __device__ {};  // extended lambda
    auto lambda4 = [] __host__ {};             // NOT an extended lambda
}

__host__ __device__ void host_device_function() {
    auto lambda1 = [] {};                      // NOT an extended lambda: no explicit execution space annotations
    auto lambda2 = [] __device__ {};           // extended lambda
    auto lambda3 = [] __host__ __device__ {};  // extended lambda
    auto lambda4 = [] __host__ {};             // NOT an extended lambda
}

__device__ void device_function() {
    // none of the lambdas within this function are extended lambdas,
    // because the enclosing function is not a __host__ or __host__ __device__  function.
    auto lambda1 = [] {};
    auto lambda2 = [] __device__ {};
    auto lambda3 = [] __host__ __device__ {};
    auto lambda4 = [] __host__ {};
}

auto global_lambda = [] __host__ __device__ { }; // NOT an extended lambda because it is not defined
                                                 // within a __host__ or __host__ __device__ function

5.3.7.3. 확장 람다 타입 트레이트#

컴파일러는 컴파일 시점에 확장 람다의 클로저 타입을 감지하기 위한 타입 트레잇(type traits)을 제공합니다.

bool __nv_is_extended_device_lambda_closure_type(type);

이 함수는 반환합니다 true if type 확장에 대해 생성된 클로저 클래스입니다 __device__ 람다, false 그렇지 않으면.

bool __nv_is_extended_device_lambda_with_preserved_return_type(type);

이 함수는 반환합니다 true if type 확장에 대해 생성된 클로저 클래스입니다 __device__ 람다이며, 해당 람다가 후행 반환 타입으로 정의된 경우, false 그렇지 않으면. 후행 반환 타입 정의가 어떤 람다 매개변수 이름을 참조하는 경우, 반환 타입은 보존되지 않습니다.

bool __nv_is_extended_host_device_lambda_closure_type(type);

이 함수는 반환합니다 true if type 확장에 대해 생성된 클로저 클래스입니다 __host__ __device__ 람다, false 그렇지 않으면.

람다 타입 트레이트는 람다 또는 확장 람다가 활성화되어 있는지 여부와 관계없이 모든 컴파일 모드에서 사용할 수 있습니다. 확장 람다 모드가 비활성화되어 있으면, 이 트레이트는 항상 false를 반환합니다.

예:

auto lambda0 = [] __host__ __device__ { };

void host_function() {
    auto lambda1 = [] { };
    auto lambda2 = [] __device__ { };
    auto lambda3 = [] __host__ __device__ { };
    auto lambda4 = [] __device__ () -> double { return 3.14; }
    auto lambda5 = [] __device__ (int x) -> decltype(&x) { return 0; }

    using lambda0_t = decltype(lambda0);
    using lambda1_t = decltype(lambda1);
    using lambda2_t = decltype(lambda2);
    using lambda3_t = decltype(lambda3);
    using lambda4_t = decltype(lambda4);
    using lambda5_t = decltype(lambda5);

    // 'lambda0' is not an extended lambda because it is defined outside function scope
    static_assert(!__nv_is_extended_device_lambda_closure_type(lambda0_t));
    static_assert(!__nv_is_extended_device_lambda_with_preserved_return_type(lambda0_t));
    static_assert(!__nv_is_extended_host_device_lambda_closure_type(lambda0_t));

    // 'lambda1' is not an extended lambda because it has no execution space annotations
    static_assert(!__nv_is_extended_device_lambda_closure_type(lambda1_t));
    static_assert(!__nv_is_extended_device_lambda_with_preserved_return_type(lambda1_t));
    static_assert(!__nv_is_extended_host_device_lambda_closure_type(lambda1_t));

    // 'lambda2' is an extended device-only lambda
    static_assert(__nv_is_extended_device_lambda_closure_type(lambda2_t));
    static_assert(!__nv_is_extended_device_lambda_with_preserved_return_type(lambda2_t));
    static_assert(!__nv_is_extended_host_device_lambda_closure_type(lambda2_t));

    // 'lambda3' is an extended host-device lambda
    static_assert(!__nv_is_extended_device_lambda_closure_type(lambda3_t));
    static_assert(!__nv_is_extended_device_lambda_with_preserved_return_type(lambda3_t));
    static_assert(__nv_is_extended_host_device_lambda_closure_type(lambda3_t));

    // 'lambda4' is an extended device-only lambda with preserved return type
    static_assert(__nv_is_extended_device_lambda_closure_type(lambda4_t));
    static_assert(__nv_is_extended_device_lambda_with_preserved_return_type(lambda4_t));
    static_assert(!__nv_is_extended_host_device_lambda_closure_type(lambda4_t));

    // 'lambda5' is not an extended device-only lambda with preserved return type
    // because it references the operator()'s parameter types in the trailing return type.
    static_assert(__nv_is_extended_device_lambda_closure_type(lambda5_t));
    static_assert(!__nv_is_extended_device_lambda_with_preserved_return_type(lambda5_t));
    static_assert(!__nv_is_extended_host_device_lambda_closure_type(lambda5_t));
}

5.3.7.4. 확장 람다 제약 사항#

호스트 컴파일러를 호출하기 전에, CUDA 컴파일러는 확장 람다 표현식을 네임스페이스 스코프에 정의된 플레이스홀더 타입의 인스턴스로 대체합니다. 플레이스홀더 타입의 템플릿 인수는 원래의 확장 람다 표현식을 둘러싸는 함수의 주소를 취해야 합니다. 이는 템플릿 인수가 확장 람다의 클로저 타입을 포함하는 모든 __global__ 함수 템플릿을 올바르게 실행하기 위해 필요합니다. 둘러싸는 함수는 다음과 같이 계산됩니다.

정의에 따르면, 확장 람다는 __host__ 또는 __host__ __device__ 함수의 즉시 또는 중첩 블록 스코프 내에 존재합니다.

  • 함수가 람다 표현식의 operator()가 아니면, 해당 함수는 확장 람다의 둘러싸는 함수로 간주됩니다.

  • 그렇지 않으면, 확장 람다는 하나 이상의 둘러싸는 람다 표현식의 operator()의 즉시 또는 중첩 블록 스코프 내에 정의됩니다.

    • 가장 바깥쪽 람다 표현식이 함수 F의 즉시 또는 중첩 블록 스코프 내에 정의되어 있다면, F가 계산된 둘러싸는 함수입니다.

    • 그렇지 않으면, 둘러싸는 함수는 존재하지 않습니다.

예:

void host_function() {
    auto lambda1 = [] __device__ { }; // enclosing function for lambda1 is "host_function()"
    auto lambda2 = [] {
        auto lambda3 = [] {
            auto lambda4 = [] __host__ __device__ { }; // enclosing function for lambda4 is "host_function"
        };
    };
}

auto global_lambda = [] {
    auto lambda5 = [] __host__ __device__ { }; // enclosing function for lambda5 does not exist
};

확장 람다 제약 사항

  1. 확장 람다는 다른 확장 람다 표현식 내부에 정의할 수 없습니다. 예:

    void host_function() {
    auto lambda1 = [] __host__ __device__  {
         // ERROR, extended lambda defined within another extended lambda
        auto lambda2 = [] __host__ __device__ { };
    };
}

  2. 확장 람다는 제네릭 람다 표현식 내부에 정의할 수 없습니다. 예:

    void host_function() {
    auto lambda1 = [] (auto) {
         // ERROR, extended lambda defined within a generic lambda
        auto lambda2 = [] __host__ __device__ { };
    };
}

  3. 확장 람다가 하나 이상의 중첩 람다 표현식의 즉시 또는 중첩 블록 스코프 내에 정의된 경우, 가장 바깥쪽 람다 표현식은 함수의 즉시 또는 중첩 블록 스코프 내에 정의되어야 합니다. 예:

    auto lambda1 = []  {
    // ERROR, outer enclosing lambda is not defined within a non-lambda-operator() function
    auto lambda2 = [] __host__ __device__ { };
};

  4. 확장 람다의 둘러싸는 함수는 이름이 있어야 하며, 그 주소에 접근할 수 있어야 합니다. 둘러싸는 함수가 클래스 멤버인 경우, 다음 조건을 충족해야 합니다:

    • 멤버 함수를 둘러싸는 모든 클래스에는 이름이 있어야 합니다.

    • 멤버 함수는 부모 클래스 내에서 private 또는 protected 접근을 가져서는 안 됩니다.

    • 모든 둘러싸는 클래스는 각자의 부모 클래스 내에서 private 또는 protected 접근을 가져서는 안 됩니다.

    예:

    void host_function() {
    auto lambda1 = [] __device__ { return 0; }; // OK
    {
        auto lambda2 = [] __device__          { return 0; }; // OK
        auto lambda3 = [] __device__ __host__ { return 0; }; // OK
    }
}

struct MyStruct1 {
    MyStruct1() {
        auto lambda4 = [] __device__ { return 0; }; // ERROR, address of the enclosing function is not accessible
    }
};

class MyStruct2 {
    void foo() {
        auto temp1 = [] __device__ { return 10; }; // ERROR, enclosing function has private access in parent class
    }

    struct MyStruct3 {
        void foo() {
            auto temp1 = [] __device__ { return 10; };  // ERROR, enclosing class MyStruct3 has private access in its parent class
        }
    };
};

  5. 확장 람다가 정의된 지점에서는, 둘러싸는 루틴의 주소를 모호함 없이 취할 수 있어야 합니다. 그러나 예를 들어 별칭 선언이 동일한 이름의 템플릿 타입 인수를 가리는 경우처럼, 이것이 항상 가능하지는 않을 수 있습니다. 예:

    template <typename T>
struct A {
    using Bar = void;
    void test();
};

template<>
struct A<void> { };

template <typename Bar>
void A<Bar>::test() {
    // In code sent to host compiler, nvcc will inject an address expression here, of the form:
    //   (void (A< Bar> ::*)(void))(&A::test))
    //  However, the class typedef 'Bar' (to void) shadows the template argument 'Bar',
    //  causing the address expression in A<int>::test to actually refer to:
    //    (void (A< void> ::*)(void))(&A::test))
    //  which doesn't take the address of the enclosing routine 'A<int>::test' correctly.
    auto lambda1 = [] __host__ __device__ { return 4; };
}

int main() {
    A<int> var;
    var.test();
}

  6. 확장 람다는 함수에 로컬인 클래스 안에 정의할 수 없습니다. 예:

    void host_function() {
    struct MyStruct {
        void bar() {
            // ERROR, bar() is member of a class that is local to a function
            auto lambda2 = [] __host__ __device__ { return 0; };
        }
    };
}

  7. 확장 람다의 둘러싸는 함수는 추론된 반환 타입을 가질 수 없습니다. 예:

    auto host_function() {
    // ERROR, the return type of host_function() is deduced
    auto lambda3 = [] __host__ __device__ { return 0; };
}

  8. 호스트-디바이스 확장 람다는 제네릭 람다, 즉 auto 매개변수 타입을 가진 람다가 될 수 없습니다. 예:

    void host_function() {
    // ERROR, __host__ __device__ extended lambdas cannot be a generic lambda
    auto lambda1 = [] __host__ __device__ (auto i) { return i; };

    // ERROR, a host-device extended lambda cannot be a generic lambda
    auto lambda2 = [] __host__ __device__ (auto... i) {
        return sizeof...(i);
    };
}

  9. 둘러싸는 함수가 함수 또는 멤버 템플릿의 인스턴스화이거나, 또는 함수가 클래스 템플릿의 멤버인 경우, 템플릿(들)은 다음 제약을 충족해야 합니다:

    • 템플릿은 가변 인자를 최대 하나만 가질 수 있으며, 템플릿 매개변수 목록의 마지막에 나열되어야 합니다.

    • 템플릿 매개변수에는 이름이 있어야 합니다.

    • 템플릿 인스턴스화 인수 타입은 함수에 로컬인 타입(확장 람다의 클로저 타입은 예외) 또는 private 또는 protected 클래스 멤버인 타입을 포함할 수 없습니다.

    예 1:

    template <template <typename...> class T,
          typename... P1,
          typename... P2>
void bar1(const T<P1...>, const T<P2...>) {
    // ERROR, enclosing function has multiple parameter packs
    auto lambda = [] __device__ { return 10; };
}

template <template <typename...> class T,
          typename... P1,
          typename    T2>
void bar2(const T<P1...>, T2) {
    // ERROR, for enclosing function, the parameter pack is not last in the template parameter list
    auto lambda = [] __device__ { return 10; };
}

template <typename T, T>
void bar3() {
    // ERROR, for enclosing function, the second template parameter is not named
    auto lambda = [] __device__ { return 10; };
}

    예 2:

    template <typename T>
void bar4() {
    auto lambda1 = [] __device__ { return 10; };
}

class MyStruct {
    struct MyNestedStruct {};

    friend int main();
};

int main() {
    struct MyLocalStruct {};
    // ERROR, enclosing function for device lambda in bar4() is instantiated with a type local to main
    bar4<MyLocalStruct>();

    // ERROR, enclosing function for device lambda in bar4 is instantiated with a type
    //        that is a private member of a class
    bar4<MyStruct::MyNestedStruct>();
}

  10. Microsoft Visual Studio 호스트 컴파일러를 사용하는 경우, 둘러싸는 함수는 외부 링키지(external linkage)를 가져야 합니다. 이 제약은 호스트 컴파일러가 비-extern 링키지 함수의 주소를 템플릿 인수로 사용하는 것을 지원하지 않기 때문에 존재합니다. CUDA 컴파일러 변환은 확장 람다를 지원하기 위해 이러한 주소를 필요로 합니다.

  11. Microsoft Visual Studio 호스트 컴파일러를 사용하는 경우, 확장 람다는 if constexpr 블록의 본문 내에 정의되어서는 안 됩니다.

  12. 확장 람다는 캡처된 변수에 대해 다음 제약을 가집니다:

    • 변수는 확장 람다의 클로저 타입을 나타내는 클래스 타입의 필드를 직접 초기화하는 데 사용되기 전에, 호스트 컴파일러로 보내지는 코드에서 일련의 헬퍼 함수들에 값으로 전달될 수 있습니다. 그러나 C++ 표준은 캡처된 변수가 클로저 타입의 필드를 직접 초기화하는 데 사용되어야 한다고 명시합니다.

    • 변수는 값으로만 캡처할 수 있습니다.

    • 배열 차원 수가 7보다 크면 배열 타입 변수는 캡처할 수 없습니다.

    • 배열 타입 변수의 경우, 클로저 타입의 배열 필드는 먼저 기본 초기화된 다음, 호스트 컴파일러로 보내지는 코드에서 캡처된 배열 변수의 해당 요소로부터 각 배열 요소가 복사 대입됩니다. 따라서 배열 요소 타입은 호스트 코드에서 기본 생성 가능하고 복사 대입 가능해야 합니다.

    • 가변 인자 팩의 요소인 함수 매개변수는 캡처할 수 없습니다.

    • 캡처된 변수 타입은 함수에 로컬인 타입(확장 람다 클로저 타입은 예외) 또는 private 또는 protected 클래스 멤버인 타입일 수 없습니다.

    • Init-capture는 호스트-디바이스 확장 람다에서는 지원되지 않습니다. 그러나 디바이스 확장 람다에서는 지원되며, 단 초기화자가 배열이거나 타입이 std::initializer_list인 경우는 예외입니다.

    • 확장 람다의 함수 호출 연산자는 constexpr가 아닙니다. 확장 람다의 클로저 타입은 리터럴 타입이 아닙니다. 확장 람다를 선언할 때는 constexpr 및 consteval 지정자를 사용할 수 없습니다.

    • 변수가 if-constexpr 블록 밖에서 암시적으로 캡처되었거나, 또는 확장 람다의 명시적 캡처 목록에 나타나는 경우가 아니라면, 확장 람다 내부에 어휘적으로 중첩된 if-constexpr 블록 안에서는 변수를 암시적으로 캡처할 수 없습니다.

    예:

    void host_function() {
    // CORRECT, an init-capture is allowed for an extended device-only lambda
    auto lambda1 = [x = 1] __device__ () { return x; };

    // ERROR, an init-capture is not allowed for an extended host-device lambda
    auto lambda2 = [x = 1] __host__ __device__ () { return x; };

    int a = 1;
    // ERROR, an extended __device__ lambda cannot capture variables by reference
    auto lambda3 = [&a] __device__ () { return a; };

    // ERROR, by-reference capture is not allowed for an extended device-only lambda
    auto lambda4 = [&x = a] __device__ () { return x; };

    struct MyStruct {};
    MyStruct s1;
    // ERROR, a type local to a function cannot be used in the type of a captured variable
    auto lambda6 = [s1] __device__ () { };

    // ERROR, an init-capture cannot be of type std::initializer_list
    auto lambda7 = [x = {11}] __device__ () { };

    std::initializer_list<int> b = {11,22,33};
    // ERROR, an init-capture cannot be of type std::initializer_list
    auto lambda8 = [x = b] __device__ () { };

    int  var     = 4;
    auto lambda9 = [=] __device__ {
        int result = 0;
        if constexpr(false) {
            //ERROR, An extended device-only lambda cannot first-capture 'var' in if-constexpr context
            result += var;
        }
        return result;
    };

    auto lambda10 = [var] __device__ {
        int result = 0;
        if constexpr(false) {
            // CORRECT, 'var' already listed in explicit capture list for the extended lambda
            result += var;
        }
        return result;
    };

    auto lambda11 = [=] __device__ {
        int result = var;
        if constexpr(false) {
            // CORRECT, 'var' already implicit captured outside the 'if-constexpr' block
            result += var;
        }
        return result;
    };
}

  13. 함수를 파싱할 때 CUDA 컴파일러는 함수 내의 각 확장 람다에 카운터 값을 할당합니다. 이 카운터 값은 호스트 컴파일러로 전달되는 대체된 명명된 타입에 사용됩니다. 따라서 함수 내에서 확장 람다의 존재 여부는 __CUDA_ARCH__의 특정 값에 의존해서는 안 되며, 또한 __CUDA_ARCH__가 정의되지 않은 것에도 의존해서는 안 됩니다. 예:

    template <typename T>
__global__ void kernel(T in) { in(); }

__host__ __device__ void host_device_function() {
    // ERROR, the number and relative declaration order of
    //        extended lambdas depend on __CUDA_ARCH__
#if defined(__CUDA_ARCH__)
    auto lambda1 = [] __device__ { return 0; };
    auto lambda2 = [] __host__ __device__ { return 10; };
#endif
    auto lambda3 = [] __device__ { return 4; };
    kernel<<<1, 1>>>(lambda3);
}

  14. 위에서 설명한 대로, CUDA 컴파일러는 호스트 함수에 정의된 디바이스 확장 람다를 네임스페이스 범위에 정의된 플레이스홀더 타입으로 대체합니다. 플레이스홀더 타입은 을 정의하지 않습니다. operator() 트레이트가 원래 람다 선언과 동등한 함수를 제공하지 않는 한 __nv_is_extended_device_lambda_with_preserved_return_type() 반환합니다 true 확장 람다의 클로저 타입에 대해. 따라서 반환 타입 또는 매개변수 타입을 결정하려는 시도는 operator() 이러한 람다의 함수는 호스트 컴파일러가 처리하는 코드가 CUDA 컴파일러가 처리하는 입력 코드와 의미적으로 다르기 때문에 호스트 코드에서 올바르게 동작하지 않을 수 있습니다. 그러나 반환 타입 또는 매개변수 타입을 인트로스펙션하는 것은 operator() 디바이스 코드 내의 함수는 허용됩니다. 참고: 이 제약 사항은 트레이트가 적용되는 호스트 또는 디바이스 확장 람다에는 적용되지 않습니다. __nv_is_extended_device_lambda_with_preserved_return_type() 반환 true. 예:

    #include <cuda/std/type_traits>

const char& getRef(const char* p) { return *p; }

void foo() {
    auto lambda1 = [] __device__ { return "10"; };

    // ERROR, attempt to extract the return type of a device lambda in host code
    cuda::std::result_of<decltype(lambda1)()>::type xx1 = "abc";

    auto lambda2 = [] __host__ __device__ { return "10"; };

    // CORRECT, lambda2 represents a host-device extended lambda
    cuda::std::result_of<decltype(lambda2)()>::type xx2 = "abc";

    auto lambda3 = [] __device__ () -> const char* { return "10"; };

    // CORRECT, lambda3 represents a device extended lambda with preserved return type
    cuda::std::result_of<decltype(lambda3)()>::type xx2 = "abc";
    static_assert(cuda::std::is_same_v<cuda::std::result_of<decltype(lambda3)()>::type, const char*>);

    auto lambda4 = [] __device__ (char x) -> decltype(getRef(&x)) { return 0; };
    // lambda4's return type is not preserved because it references the operator()'s
    // parameter types in the trailing return type.
    static_assert(!__nv_is_extended_device_lambda_with_preserved_return_type(decltype(lambda4)));
}

  15. 확장 디바이스 전용 람다의 경우:

    • operator()의 매개변수 타입 인트로스펙션은 디바이스 코드에서만 지원됩니다.

    • operator()의 반환 타입 인트로스펙션은, 트레이트 함수 __nv_is_extended_device_lambda_with_preserved_return_type()가 true를 반환하지 않는 한, 디바이스 코드에서만 지원됩니다.

  16. 예를 들어 확장 람다가 __global__ 함수의 인수로서 호스트에서 디바이스 코드로 전달되는 경우, 람다 본문에서 변수를 캡처하는 모든 표현식은 __CUDA_ARCH__ 매크로가 정의되어 있는지 여부 및 그 값과 관계없이 변경되지 않은 상태로 유지되어야 합니다. 이 제약은 컴파일러가 람다 표현식을 처리할 때 캡처된 변수를 만나는 순서에 따라 람다의 클로저 클래스 레이아웃이 달라지기 때문에 발생합니다. 디바이스와 호스트 컴파일에서 클로저 클래스 레이아웃이 다르면 프로그램이 올바르지 않게 실행될 수 있습니다. 예:

    __device__ int result;

template <typename T>
__global__ void kernel(T in) { result = in(); }

void foo(void) {
    int x1 = 1;
    // ERROR, "x1" is only captured when __CUDA_ARCH__ is defined.
    auto lambda1 = [=] __host__ __device__ {
#ifdef __CUDA_ARCH__
        return x1 + 1;
#else
        return 10;
#endif
    };
    kernel<<<1, 1>>>(lambda1);
}

  17. 앞서 설명한 대로, CUDA 컴파일러는 확장된 디바이스 전용 람다 표현식을 호스트 컴파일러로 보내는 코드에서 플레이스홀더 타입 인스턴스로 대체합니다. 플레이스홀더 타입은 호스트 코드에서 함수 포인터로의 변환 연산자를 정의하지 않습니다. 그러나 변환 연산자는 디바이스 코드에서 제공됩니다. 참고로, 이 제약은 호스트-디바이스 확장 람다에는 적용되지 않습니다. 예:

    template <typename T>
__global__ void kernel(T in) {
    int (*fp)(double) = in;
    fp(0); // CORRECT, conversion in device code is supported
    auto lambda1 = [](double) { return 1; };
}

void foo() {
    auto lambda_device      = [] __device__ (double) { return 1; };
    auto lambda_host_device = [] __host__ __device__ (double) { return 1; };
    kernel<<<1, 1>>>(lambda_device);
    kernel<<<1, 1>>>(lambda_host_device);

    // CORRECT, conversion for a __host__ __device__ lambda is supported in host code
    int (*fp1)(double) = lambda_host_device;

    // ERROR, conversion for a device lambda is not supported in host code
    int (*fp2)(double) = lambda_device;
}

  18. 앞서 설명한 대로, CUDA 컴파일러는 확장된 디바이스 전용 또는 호스트-디바이스 람다 표현식을 호스트 컴파일러로 보내는 코드에서 플레이스홀더 타입 인스턴스로 대체합니다. 이 플레이스홀더 타입은 생성자와 소멸자와 같은 C++ 특수 멤버 함수를 정의할 수 있습니다. 그 결과, 일부 표준 C++ 타입 트레이트는 CUDA 프런트엔드 컴파일러에서 확장 람다의 클로저 타입에 대해 호스트 컴파일러에서와 다른 결과를 산출할 수 있습니다. 영향을 받는 타입 트레이트는 다음과 같습니다: : std::is_trivially_copyable, std::is_trivially_constructible, std::is_trivially_copy_constructible, std::is_trivially_move_constructible, std::is_trivially_destructible. 이러한 트레이트의 결과가 __global__, __device__, __constant__, 또는 __managed__ 함수 또는 변수 템플릿의 인스턴스화에 사용되지 않도록 주의해야 합니다. 예:

    #include <cstdio>
#include <type_traits>

template <bool b>
void __global__ kernel() { printf("hi"); }

template <typename T>
void kernel_launch() {
    // ERROR, this kernel launch may fail, because CUDA frontend compiler and host compiler
    //        may disagree on the result of std::is_trivially_copyable_v trait on the
    //        closure type of the extended lambda
    kernel<std::is_trivially_copyable_v<T>><<<1,1>>>();
    cudaDeviceSynchronize();
}

int main() {
    int  x       = 0;
    auto lambda1 = [=] __host__ __device__ () { return x; };
    kernel_launch<decltype(lambda1)>();
}

CUDA 컴파일러는 1-12에 설명된 경우의 일부 하위 집합에 대해 컴파일러 진단을 생성합니다. 13-17의 경우에는 진단이 생성되지 않지만, 호스트 컴파일러가 생성된 코드를 컴파일하지 못할 수 있습니다.

5.3.7.5. 호스트-디바이스 람다 최적화 참고 사항#

디바이스 전용 람다와 달리, 호스트-디바이스 람다는 호스트 코드에서 호출할 수 있습니다. 앞서 언급했듯이, CUDA 컴파일러는 호스트 코드에서 정의된 확장 람다 표현식을 이름이 있는 플레이스홀더 타입의 인스턴스로 대체합니다. 확장 호스트-디바이스 람다에 대한 플레이스홀더 타입은 간접 함수 호출로 원래 람다의 operator()를 호출합니다. 확장 람다 모드가 활성화되어 있지 않으면, 이 트레이트는 항상 false를 반환합니다.

간접 함수 호출이 존재하면, 호스트 컴파일러가 암시적 또는 명시적으로 __host__ 전용인 람다에 비해 확장 호스트-디바이스 람다를 덜 최적화할 수 있습니다. 후자의 경우, 호스트 컴파일러는 호출 컨텍스트에 람다 본문을 쉽게 인라인할 수 있습니다. 그러나 확장 호스트-디바이스 람다를 만나면, 호스트 컴파일러가 원래 람다 본문을 쉽게 인라인하지 못할 수도 있습니다.

5.3.7.6. *this 값을 통한 캡처#

C++11/C++14 규칙에 따르면, 람다가 비-static 클래스 멤버 함수 내에서 정의되고 람다의 본문이 클래스 멤버 변수(멤버 필드)를 참조하는 경우, 참조된 멤버 변수 대신 클래스의 this 포인터를 값으로 캡처해야 합니다. 람다가 호스트 함수에서 정의되고 GPU에서 실행되는 확장 디바이스 전용 또는 호스트-디바이스 람다라면, this 포인터가 호스트 메모리를 가리키는 경우 GPU에서 참조된 멤버 변수에 접근하면 런타임 오류가 발생합니다.

예:

#include <cstdio>

template <typename T>
__global__ void foo(T in) { printf("value = %d\n", in()); }

struct MyStruct {
    int var;

    __host__ __device__ MyStruct() : var(10) {};

    void run() {
        auto lambda1 = [=] __device__ {
            // reference to "var" causes the 'this' pointer (MyStruct*) to be captured by value
            return var + 1;
        };
        // Kernel launch fails at run time because 'this->var' is not accessible from the GPU
        foo<<<1, 1>>>(lambda1);
        cudaDeviceSynchronize();
    }
};

int main() {
    MyStruct s1;
    s1.run();
}

C++17은 새로운 것을 도입함으로써 이 문제를 해결합니다 *this 캡처 모드. 이 모드에서는, 컴파일러가 다음이 가리키는 객체를 복사합니다 *this 캡처하는 대신 this 포인터를 값으로 캡처합니다. 이 *this 캡처 모드는 다음에서 더 자세히 설명됩니다 P0018R3.

CUDA 컴파일러는 다음을 지원합니다. *this 내부에 정의된 람다에 대한 캡처 모드 __device__ 그리고 __global__ 함수 및 호스트 코드에 정의된 확장 디바이스 전용 람다의 경우, --extended-lambda 플래그가 사용되는 경우.

다음은 위의 예를 *this 캡처 모드를 사용하도록 수정한 것입니다:

#include <cstdio>

template <typename T>
__global__ void foo(T in) { printf("\n value = %d", in()); }

struct MyStruct {
    int var;
    __host__ __device__ MyStruct() : var(10) { };

    void run() {
        // note the "*this" capture specification
        auto lambda1 = [=, *this] __device__ {
            // reference to "var" causes the object denoted by '*this' to be captured by
            // value, and the GPU code will access 'copy_of_star_this->var'
            return var + 1;
        };
        // Kernel launch succeeds
        foo<<<1, 1>>>(lambda1);
        cudaDeviceSynchronize();
    }
};

int main() {
    MyStruct s1;
    s1.run();
}

*this 캡처 모드는, 선택된 언어 방언에서 *this 캡처가 활성화되어 있지 않는 한, 호스트 코드에 정의된 어노테이션이 없는 람다 또는 확장 호스트-디바이스 람다에는 허용되지 않습니다. 다음은 지원되는 사용과 지원되지 않는 사용의 예입니다:

struct MyStruct {
    int var;
    __host__ __device__ MyStruct() : var(10) { };

    void host_function() {
        // CORRECT, use in an extended device-only lambda
        auto lambda1 = [=, *this] __device__ { return var; };

        // Use in an extended host-device lambda
        // Error if *this capture not enabled by language dialect
        auto lambda2 = [=, *this] __host__ __device__ { return var; };

        // Use in an non-annotated lambda in host function
        // Error if *this capture not enabled by language dialect
        auto lambda3 = [=, *this]  { return var; };
    }

    __device__ void device_function() {
        // CORRECT, use in a lambda defined in a device-only function
        auto lambda1 = [=, *this] __device__ { return var; };

        // CORRECT, use in a lambda defined in a device-only function
        auto lambda2 = [=, *this] __host__ __device__ { return var; };

        // CORRECT, use in a lambda defined in a device-only function
        auto lambda3 = [=, *this]  { return var; };
    }

    __host__ __device__ void host_device_function() {
        // CORRECT, use in an extended device-only lambda
        auto lambda1 = [=, *this] __device__ { return var; };

        // Use in an extended host-device lambda
        // Error if *this capture not enabled by language dialect
        auto lambda2 = [=, *this] __host__ __device__ { return var; };

        // Use in an unannotated lambda in a host-device function
        // Error if *this capture not enabled by language dialect
        auto lambda3 = [=, *this]  { return var; };
    }
};

5.3.7.7. 인수 종속 조회(ADL)#

앞서 언급했듯이, CUDA 컴파일러는 호스트 컴파일러를 호출하기 전에 확장 람다 표현식을 플레이스홀더 타입으로 대체합니다. 플레이스홀더 타입의 템플릿 인수 중 하나는 원래 람다 표현식을 둘러싸는 함수의 주소를 사용합니다. 이로 인해 확장 람다 표현식의 클로저 타입을 포함하는 인수 타입을 갖는 모든 호스트 함수 호출에 대해 인수 종속 조회(ADL)에 추가 네임스페이스가 참여할 수 있습니다. 그 결과, 호스트 컴파일러가 잘못된 함수를 선택할 수 있습니다.

예:

namespace N1 {

struct MyStruct {};

template <typename T>
void my_function(T);

}; // namespace N1

namespace N2 {

template <typename T>
int my_function(T);

template <typename T>
void run(T in) { my_function(in); }

} // namespace N2

void bar(N1::MyStruct in) {
    // For extended device-only lambda, the code sent to the host compiler is replaced with
    // the placeholder type instantiation expression
    //    ' __nv_dl_wrapper_t< __nv_dl_tag<void (*)(N1::MyStruct in),(&bar),1> > { }'
    //
    // As a result, the namespace 'N1' participates in ADL lookup of the
    // call to "my_function()" in the body of N2::run, causing ambiguity.
    auto lambda1 = [=] __device__ { };
    N2::run(lambda1);
}

위의 예에서, CUDA 컴파일러는 확장 람다를 다음을 포함하는 플레이스홀더 타입으로 대체했습니다. N1 네임스페이스. 그 결과, N1 네임스페이스가 다음에 대한 ADL 조회에 참여합니다. my_function(in) 본문에서 N2::run(), 그 결과 여러 오버로드 후보가 발견되어 호스트 컴파일 실패가 발생합니다: N1::my_function 그리고 N2::my_function.

5.3.8. 다형적 함수 래퍼#

nvfunctional 헤더는 다형적 함수 래퍼 클래스 템플릿인 nvstd::function(을)를 제공합니다. 이 클래스 템플릿의 인스턴스는 람다 표현식과 같은 호출 가능한 모든 대상을 저장, 복사 및 호출할 수 있습니다. nvstd::function는 호스트 코드와 디바이스 코드 모두에서 사용할 수 있습니다.

예:

#include <nvfunctional>

__host__            int host_function()        { return 1; }
__device__          int device_function()      { return 2; }
__host__ __device__ int host_device_function() { return 3; }

__global__ void kernel(int* result) {
    nvstd::function<int()> fn1 = device_function;
    nvstd::function<int()> fn2 = host_device_function;
    nvstd::function<int()> fn3 = [](){ return 10; };
    *result                    = fn1() + fn2() + fn3();
}

__host__ __device__ void host_device_test(int* result) {
    nvstd::function<int()> fn1 = host_device_function;
    nvstd::function<int()> fn2 = [](){ return 10; };
    *result                    = fn1() + fn2();
}

__host__ void host_test(int* result) {
    nvstd::function<int()> fn1 = host_function;
    nvstd::function<int()> fn2 = host_device_function;
    nvstd::function<int()> fn3 = [](){ return 10; };
    *result                    = fn1() + fn2() + fn3();
}

유효하지 않은 경우:

  • 호스트 코드의 nvstd::function 인스턴스는 __device__ 함수의 주소 또는 operator()가 __device__ 함수인 함수 객체(functor)로 초기화할 수 없습니다.

  • 마찬가지로 디바이스 코드의 nvstd::function 인스턴스도 __host__ 함수의 주소나, operator()가 __host__ 함수인 함수 객체(functor)로 초기화할 수 없습니다.

  • nvstd::function 인스턴스는 런타임에 호스트 코드에서 디바이스 코드로, 또는 그 반대로 전달할 수 없습니다.

  • __global__ 함수가 호스트 코드에서 런치되는 경우, 그 __global__ 함수의 파라미터 타입으로 nvstd::function을 사용할 수 없습니다.

유효하지 않은 경우의 예:

#include <nvfunctional>

__device__ int device_function() { return 1; }
__host__   int host_function() { return 3; }
auto       lambda_host  = [] { return 0; };

__global__ void k() {
    nvstd::function<int()> fn1 = host_function; // ERROR, initialized with address of __host__ function
    nvstd::function<int()> fn2 = lambda_host;   // ERROR, initialized with address of functor with
                                                //        __host__ operator() function
}

__global__ void kernel(nvstd::function<int()> f1) {}

void foo(void) {
    auto lambda_device = [=] __device__ { return 1; };

    nvstd::function<int()> fn1 = device_function; // ERROR, initialized with address of __device__ function
    nvstd::function<int()> fn2 = lambda_device;   // ERROR, initialized with address of functor with
                                                  //        __device__ operator() function
    kernel<<<1, 1>>>(fn2);                        // ERROR, passing nvstd::function from host to device
}

nvstd::function은(는) nvfunctional 헤더에 다음과 같이 정의되어 있습니다:

namespace nvstd {

template <typename RetType, typename ...ArgTypes>
class function<RetType(ArgTypes...)> {
public:
    // constructors
    __device__ __host__ function() noexcept;
    __device__ __host__ function(nullptr_t) noexcept;
    __device__ __host__ function(const function&);
    __device__ __host__ function(function&&);

    template<typename F>
    __device__ __host__ function(F);

    // destructor
    __device__ __host__ ~function();

    // assignment operators
    __device__ __host__ function& operator=(const function&);
    __device__ __host__ function& operator=(function&&);
    __device__ __host__ function& operator=(nullptr_t);
    template<typename F>
    __device__ __host__ function& operator=(F&&);

    // swap
    __device__ __host__ void swap(function&) noexcept;

    // function capacity
    __device__ __host__ explicit operator bool() const noexcept;

    // function invocation
    __device__ RetType operator()(ArgTypes...) const;
};

// null pointer comparisons
template <typename R, typename... ArgTypes>
__device__ __host__
bool operator==(const function<R(ArgTypes...)>&, nullptr_t) noexcept;

template <typename R, typename... ArgTypes>
__device__ __host__
bool operator==(nullptr_t, const function<R(ArgTypes...)>&) noexcept;

template <typename R, typename... ArgTypes>
__device__ __host__
bool operator!=(const function<R(ArgTypes...)>&, nullptr_t) noexcept;

template <typename R, typename... ArgTypes>
__device__ __host__
bool operator!=(nullptr_t, const function<R(ArgTypes...)>&) noexcept;

// specialized algorithms
template <typename R, typename... ArgTypes>
__device__ __host__
void swap(function<R(ArgTypes...)>&, function<R(ArgTypes...)>&);

} // namespace nvstd

5.3.9. C/C++ 언어 제약 사항#

5.3.9.1. 지원되지 않는 기능#

  • 런타임 타입 정보(RTTI) 및 예외는 디바이스 코드에서 지원되지 않습니다:

    • typeid 키워드

    • dynamic_cast 키워드

    • try/catch/throw 키워드

  • long double은(는) 디바이스 코드에서 지원되지 않습니다.

  • 트라이그래프(trigraph)는 어떤 플랫폼에서도 지원되지 않습니다. 다이그래프(digraph)는 Windows에서 지원되지 않습니다.

  • 사용자 정의 operator new, operator new[], operator delete, 또는 operator delete[]은(는) 컴파일러가 제공하는 해당 빌트인을 대체하는 데 사용할 수 없으며, 호스트와 디바이스 모두에서 정의되지 않은 동작으로 간주됩니다.

5.3.9.2. 네임스페이스 예약#

달리 명시되지 않는 한, 최상위 네임스페이스 cuda::, nv::, 또는 cooperative_groups::에, 또는 그 안의 어떤 중첩 네임스페이스에 정의를 추가하는 것은 정의되지 않은 동작입니다. 아래에 표시된 대로, 하위 네임스페이스로서 cuda::는 허용합니다:

예:

namespace cuda {   // same for "nv" and "cooperative_groups" namespaces

struct foo;        // ERROR, class declaration in the "cuda" namespace

void bar();        // ERROR, function declaration in the "cuda" namespace

namespace utils {} // ERROR, namespace declaration in the "cuda" namespace

} // namespace cuda

namespace utils {
namespace cuda {

// CORRECT, namespace "cuda" may be used nested within a non-reserved namespace
void bar();

} // namespace cuda
} // namespace utils

// ERROR, Equivalent to adding symbols to namespace "cuda" at global scope
using namespace utils;

5.3.9.3. 포인터 및 메모리 주소#

포인터 역참조(*pointer, pointer->member, pointer[0])는 관련 메모리가 존재하는 동일한 실행 공간에서만 허용됩니다. 다음 경우에는 정의되지 않은 동작이 발생하며, 대부분 세그멘테이션 폴트가 발생하고 애플리케이션이 종료됩니다.

  • 호스트에서 전역 메모리, 공유 메모리 또는 상수 메모리에 대한 포인터를 역참조하는 경우.

  • 디바이스 코드에서 호스트 메모리에 대한 포인터를 역참조하는 경우.

함수에는 다음 제약이 적용됩니다:

  • 호스트 코드에서 __device__ 함수의 주소를 취하는 것은 허용되지 않습니다.

  • 호스트 코드에서 취한 __global__ 함수의 주소는 디바이스 코드에서 사용할 수 없습니다. 마찬가지로, 디바이스 코드에서 취한 __global__ 함수의 주소는 호스트 코드에서 사용할 수 없습니다.

다음의 주소 __device__ 또는 __constant__ 을 통해 얻은 변수 cudaGetSymbolAddress() 에서 설명한 대로 메모리 공간 지정자 섹션은 호스트 코드에서만 사용할 수 있습니다.

5.3.9.4. 변수#

5.3.9.4.1. 로컬 변수#

__device__, __shared__, __managed__, 그리고 __constant__ 메모리 공간 지정자는 호스트에서 실행되는 함수 내의 비-extern 변수 선언에 허용되지 않습니다.

예:

__host__ void host_function() {
    int x;                   // CORRECT, __host__ variable
    __device__   int y;      // ERROR,   __device__ variable declaration within a host function
    __shared__   int z;      // ERROR,   __shared__ variable declaration within a host function
    __managed__  int w;      // ERROR,   __managed__ variable  declaration within a host function
    __constant__ int h;      // ERROR,   __constant__ variable declaration within a host function
    extern __device__ int k; // CORRECT, extern __device__ variable
}

The __device__, __constant__, 그리고 __managed__ 메모리 공간 지정자는 디바이스에서 실행되는 함수 내에서 extern도 static도 아닌 변수 선언에는 허용되지 않습니다.

__device__ void device_function() {
    int x;                   // CORRECT, __device__ variable
    __constant__      int y; // ERROR,   __constant__ variable declaration within a device function
    __managed__       int z; // ERROR,   __managed__ variable  declaration within a device function
    extern __device__ int k; // CORRECT, extern __device__ variable
}

정적 변수 섹션도 참조하십시오.

5.3.9.4.2. const-한정 변수#

A const메모리 공간 애너테이션이 없는 -한정 변수 (__device__ 또는 __constant__) 전역, 네임스페이스 또는 클래스 스코프에 선언된 것은 호스트 변수로 간주됩니다. 디바이스 코드는 해당 변수를 참조하거나 그 주소를 취할 수 없습니다.

해당 변수는 디바이스 코드에서 직접 사용할 수 있습니다, 만약

  • 사용 지점 이전에 상수 표현식으로 초기화되어 있는 경우,

  • 타입이 ...이 아님 volatile-한정이며,

  • 다음 타입 중 하나입니다:

    • 내장 정수 타입 또는

    • 호스트 컴파일러가 Microsoft Visual Studio인 경우를 제외한 내장 부동소수점 타입,

C++14부터는 다음을 사용하는 것이 권장됩니다 constexpr 또는 inline constexpr (C++17) 변수를 대신하여 const-한정인 것들. constexpr 변수는 동일한 타입 제한의 적용을 받지 않으며 디바이스 코드에서 직접 활용할 수 있습니다.

__managed__ 변수는 지원하지 않습니다 const-한정 타입.

예:

const            int   ConstVar          = 10;
const            float ConstFloatVar     = 5.0f;
inline constexpr float ConstexprFloatVar = 5.0f; // C++17

struct MyStruct {
    static const            int   ConstVar          = 20;
//  static const             float ConstFloatVar     = 5.0f; // ERROR, static const variables cannot be float
    static inline constexpr float ConstexprFloatVar = 5.0f; // CORRECT
};

extern const int ExternVar;

__device__ void foo() {
    int array1[ConstVar];                     // CORRECT
    int array2[MyStruct::ConstVar];           // CORRECT

    const     float var1 = ConstFloatVar;     // CORRECT, except when the host compiler is Microsoft Visual Studio.
    constexpr float var2 = ConstexprFloatVar; // CORRECT
//  int             var3 = ExternVar;          // ERROR, "ExternVar" is not initialized with a constant expression
//  int&            var4 = ConstVar;           // ERROR, reference to host variable
//  int*            var5 = &ConstVar;          // ERROR, address of host variable
}

5.3.9.4.3. volatile-한정 변수#

참고

volatile 키워드는 ISO C++와의 호환성을 유지하기 위해 지원됩니다. 하지만 GPU에 적용되는 남아 있는 (사용 중단되지 않은) 용례는 거의 없거나 아예 없을 수 있습니다.

volatile-한정 객체에 대한 읽기 및 쓰기는 원자적이지 않으며, 다음을 보장하지 않는 하나 이상의 volatile 명령으로 컴파일됩니다:

  • 메모리 연산의 순서, 또는

  • 하드웨어가 수행한 메모리 연산의 수가 PTX 명령의 수와 일치한다는 것.

CUDA C++ volatile는 다음 용도에 적합하지 않습니다:

  • 스레드 간 동기화: 대신 cuda::atomic_ref, cuda::atomic를 통한 원자 연산 또는 원자 함수를 사용하십시오.

    원자적 메모리 연산은 스레드 간 동기화 보장을 제공하며 volatile 연산보다 더 나은 성능을 제공합니다. 그러나 CUDA C++ volatile 연산은 어떤 스레드 간 동기화 보장도 제공하지 않으므로, 이 목적에는 적합하지 않습니다. 다음 예제는 원자 연산을 사용하여 두 스레드 사이에서 메시지를 전달하는 방법을 보여줍니다.

    #include <cuda/atomic>

__global__ void kernel(int* flag, int* data) {
    cuda::atomic_ref<int, cuda::thread_scope_device> atomic_ref{*flag};
    if (threadIdx.x == 0) {
        // Consumer: blocks until flag is set by producer, then reads data
        while(atomic_ref.load(cuda::memory_order_acquire) == 0)
            ;
        if (*data != 42)
            __trap(); // Errors if wrong data read
    }
    else if (threadIdx.x == 1) {
        // Producer: writes data then sets flag
        *data = 42;
        atomic_ref.store(1, cuda::memory_order_release);
    }
}

    #include <cuda/atomic>

__global__ void kernel(cuda::atomic<int, cuda::thread_scope_device>* flag, int* data) {
    if (threadIdx.x == 0) {
        // Consumer: blocks until flag is set by producer, then reads data
        while(flag->load(cuda::memory_order_acquire) == 0)
            ;
        if (*data != 42)
            __trap(); // Errors if wrong data read
    }
    else if (threadIdx.x == 1) {
        // Producer: writes data then sets flag
        *data = 42;
        flag->store(1, cuda::memory_order_release);
    }
}

    __global__ void kernel(int* flag, int* data) {
    if (threadIdx.x == 0) {
        // Consumer: blocks until flag is set by producer, then reads data
        while(atomicAdd(flag, 0) == 0)
            ;                // Load with Relaxed Read-Modify-Write
        __threadfence();     // SequentiallyConsistent fence
        if (*data != 42)
            __trap();        // Errors if wrong data read
    } else if (threadIdx.x == 1) {
        // Producer: writes data then sets flag
        *data = 42;
        __threadfence();     // SequentiallyConsistent fence
        atomicExch(flag, 1); // Store with Relaxed Read-Modify-Write
    }
}

  • 메모리 매핑 IO(MMIO): 대신 인라인 PTX를 통해 PTX MMIO 연산을 사용하십시오.

    PTX MMIO 연산은 수행되는 메모리 접근 횟수를 엄격하게 보존합니다. 그러나 CUDA C++ volatile 연산은 수행되는 메모리 접근 횟수를 보존하지 않으며, 불확정한 방식으로 요청된 것보다 더 많은 또는 더 적은 접근을 수행할 수도 있습니다. 이로 인해 MMIO에는 적합하지 않습니다. 다음 예제는 PTX MMIO 연산을 사용하여 레지스터에서 읽고 레지스터에 쓰는 방법을 보여줍니다.

    __global__ void kernel(int* mmio_reg0, int* mmio_reg1) {
    // Write to MMIO register:
    int value = 13;
    asm volatile("st.relaxed.mmio.sys.u32 [%0], %1;"
        :
        : "l"(mmio_reg0), "r"(value) : "memory");

    // Read MMIO register:
    asm volatile("ld.relaxed.mmio.sys.u32 %0, [%1];"
        : "=r"(value)
        : "l"(mmio_reg1) : "memory");

    if (value != 42)
        __trap(); // Errors if wrong data read
}

5.3.9.4.4. static-변수#

static 변수는 다음 경우에 디바이스 코드에서 허용됩니다:

  • __global__ 또는 __device__-전용 함수 내.

  • __host__ __device__ 함수 내:

    • 명시적 메모리 공간이 없는 static 변수(자동 추론).

    • static 명시적 메모리 공간이 있는 변수(예: static __device__/__constant__/__shared__/__managed__, 은(는) 오직 다음 경우에만 허용됩니다 __CUDA_ARCH__ 가 정의됩니다.

5.3.9.4.5. extern-변수#

전체 프로그램 컴파일 모드에서 컴파일할 때, __device__, __shared__, __managed__, 및 __constant__ 변수는 extern 키워드를 사용하여 외부 링크로 정의할 수 없습니다.

유일한 예외는 동적으로 할당된 경우입니다. __shared__ 앞에서 설명한 대로, -변수는 공유 메모리의 동적 할당 섹션.

__device__        int x; // OK
extern __device__ int y; // ERROR in whole program compilation mode
extern __shared__ int z; // OK

5.3.9.5. 함수#

5.3.9.5.1. 재귀#

__global__ 함수는 재귀를 지원하지 않지만, __device__ 및 __host__ __device__ 함수에는 이러한 제한이 없습니다.

5.3.9.5.2. 외부 링크#

외부 링크를 갖는 디바이스 변수 또는 함수는 여러 번역 단위에 걸쳐 별도 컴파일 모드가 필요합니다.

별도 컴파일 모드에서, 특정 번역 단위에 __device__ 또는 __global__ 함수 정의가 존재해야 하는 경우, 해당 함수의 매개변수와 반환 타입은 그 번역 단위에서 완전한 타입이어야 합니다. 이 개념은 One Definition Rule-use, 또는 ODR-use라고도 알려져 있습니다.

예:

//first.cu:
struct S;                   // forward declaration
__device__ void foo(S);     // ERROR, type 'S' is an incomplete type
__device__ auto* ptr = foo; // ODR-use, address taken

int main() {}

//second.cu:
struct S {};               // struct definition
__device__ void foo(S) {}  // function definition

5.3.9.5.3. 형식 매개변수#

__device__, __shared__, __managed__ 및 __constant__ 메모리 공간 지정자는 형식 매개변수에 허용되지 않습니다.

void device_function1(__device__ int x) { } // ERROR, __device__ parameter
void device_function2(__shared__ int x) { } // ERROR, __shared__ parameter

5.3.9.5.4. __global__ 함수 매개변수#

__global__ 함수에는 다음 제약이 있습니다:

  • 가변 개수의 인수를 가질 수 없으며, 즉 C 줄임표 구문 ... 및 va_list 타입을 사용할 수 없습니다. C++11 가변 템플릿은 __global__ 가변 템플릿 섹션에 설명된 제약을 따르는 경우 허용됩니다.

  • 함수 매개변수는 상수 메모리를 통해 디바이스로 전달되며, 총 크기는 32,764바이트로 제한됩니다.

  • 함수 매개변수는 참조에 의한 전달 또는 rvalue 참조에 의한 전달이 될 수 없습니다.

  • 함수 매개변수는 std::initializer_list 타입일 수 없습니다.

  • 다형성 클래스 매개변수(virtual)는 정의되지 않은 동작으로 간주됩니다.

  • 람다 표현식 및 클로저 타입은 람다 표현식 및 __global__ 함수 매개변수 섹션에 설명된 제약을 따르는 경우 허용됩니다.

5.3.9.5.5. __global__ 함수 인수 전달#

실행을 시작할 때 __global__ 함수 디바이스 코드에서, 각 인수는 trivially copyable이고 trivially destructible이어야 합니다.

When a __global__ 함수가 호스트 코드에서 실행될 때, 각 인수 타입은 비-자명하게 복사 가능하거나 비-자명하게 소멸 가능할 수 있습니다. 그러나 아래에 설명된 대로, 이러한 타입의 처리는 표준 C++ 모델을 따르지 않습니다. 사용자 코드는 이 워크플로가 프로그램의 정확성에 영향을 미치지 않도록 보장해야 합니다. 이 워크플로는 두 가지 영역에서 표준 C++와 다릅니다:

  1. 복사 생성자 호출 대신 원시 메모리 복사

    CUDA 런타임은 원시 메모리 내용을 복사하여 커널 인수를 __global__ 함수에 전달하며, 최종적으로 memcpy을(를) 사용합니다. 인수가 비-자명하게 복사 가능하고 사용자 정의 복사 생성자를 제공하는 경우, 호스트-디바이스 복사에서는 해당 호출의 연산과 부수 효과가 건너뛰어집니다.

    예:

    #include <cassert>

struct MyStruct {
    int  value = 1;
    int* ptr;

    MyStruct() = default;

    __host__ __device__ MyStruct(const MyStruct&) { ptr = &value; }
};

__global__ void device_function(MyStruct my_struct) {
    // this assert fails because "my_struct" is obtained by copying
    // the raw memory content and the copy constructor is skipped.
    assert(my_struct.ptr == &my_struct.value); // FAIL
}

void host_function(MyStruct my_struct) {
    assert(my_struct.ptr == &my_struct.value); // CORRECT
}

int main() {
    MyStruct my_struct;
    host_function(my_struct);
    device_function<<<1, 1>>>(my_struct); // copy constructor invoked in the host-side only
    cudaDeviceSynchronize();
}

    Compiler Explorer의 예제를 참조하십시오.

  2. 소멸자는 __global__ 함수가 완료되기 전에 호출될 수 있습니다

    커널 실행은 호스트 실행과 비동기입니다. 그 결과, __global__ 함수 인수에 비-자명한 소멸자가 있는 경우, __global__ 함수가 실행을 완료하기 전에도 소멸자가 호스트 코드에서 실행될 수 있습니다. 이는 소멸자에 부수 효과가 있는 프로그램을 망가뜨릴 수 있습니다.

    예:

    #include <cassert>

__managed__ int var = 0;

struct MyStruct {
    __host__ __device__ ~MyStruct() { var = 3; }
};

__global__ void device_function(MyStruct my_struct) {
    assert(var == 0); // FAIL, MyStruct::~MyStruct() sets the value to 3
}

int main() {
    MyStruct my_struct;
    // GPU kernel execution is asynchronous with host execution.
    // As a result, MyStruct::~MyStruct() could be executed before
    // the kernel finishes executing.
    device_function<<<1, 1>>>(my_struct);
    cudaDeviceSynchronize();
}

5.3.9.6. 클래스#

5.3.9.6.1. 클래스 타입 변수#

__device__, __constant__, __managed__ 또는 __shared__ 메모리 공간을 갖는 변수 정의는 비어 있지 않은 생성자 또는 비어 있지 않은 소멸자를 갖는 클래스 타입일 수 없습니다. 클래스 타입에 대한 생성자는 번역 단위 내의 한 지점에서 자명(trivial)하거나 다음 조건을 모두 만족하는 경우 비어 있는 것으로 간주됩니다:

  • 생성자 함수가 정의되었습니다.

  • 생성자 함수는 매개변수가 없고, 초기화자 목록이 비어 있으며, 복합문(compound statement) 함수 본문이 비어 있습니다.

  • 해당 클래스에는 virtual 함수, virtual 베이스 클래스, 또는 non-static 데이터 멤버 초기화자가 없습니다.

  • 해당 클래스의 모든 베이스 클래스의 기본 생성자는 비어 있는 것으로 간주될 수 있습니다.

  • 클래스의 non-static 데이터 멤버 중 클래스 타입(또는 그 배열)인 모든 멤버에 대해, 기본 생성자는 비어 있는 것으로 간주될 수 있습니다.

클래스의 소멸자는 번역 단위 내의 한 지점에서 자명(trivial)하거나 다음 조건을 모두 만족하는 경우 비어 있는 것으로 간주됩니다:

  • 소멸자 함수가 정의되었습니다.

  • 소멸자 함수 본문은 비어 있는 복합문(compound statement)입니다.

  • 해당 클래스에는 virtual 함수 또는 virtual 베이스 클래스가 없습니다.

  • 해당 클래스의 모든 베이스 클래스의 소멸자는 비어 있는 것으로 간주될 수 있습니다.

  • 클래스의 non-static 데이터 멤버 중 클래스 타입(또는 그 배열)인 모든 멤버에 대해, 소멸자는 비어 있는 것으로 간주될 수 있습니다.

5.3.9.6.2. 데이터 멤버#

__device__, __shared__, __managed__ 및 __constant__ 메모리 공간 지정자는 class, struct, 및 union 데이터 멤버에 허용되지 않습니다.

컴파일 시간에 평가되는 static 데이터 멤버만 지원되며, 예를 들어 const-qualified 및 constexpr 변수가 해당됩니다.

struct MyStruct {
   static inline constexpr int value1 = 10; // C++17
   static constexpr        int value2 = 10; // C++11
   static const            int value3 = 10;
// static                  int value4; // ERROR
};

5.3.9.6.3. 함수 멤버#

__global__ 함수는 struct, class, 또는 union의 멤버일 수 없습니다.

__global__ 함수는 friend 선언에서 허용되지만, 정의할 수 없습니다.

예:

struct MyStruct {
    friend __global__ void f();   // CORRECT, friend declaration only

//  friend __global__ void g() {} // ERROR, friend definition
};

5.3.9.6.4. 암시적으로 선언된 및 비-가상 명시적 기본값 지정 함수#

암시적으로 선언된 특수 멤버 함수는 사용자가 이를 선언하지 않을 때 컴파일러가 클래스에 대해 선언하는 함수입니다; 명시적으로 기본값으로 지정된 함수는 사용자가 선언하되 = default로 표시하는 함수입니다. 암시적으로 선언되거나 명시적으로 기본값으로 지정되는 특수 멤버 함수는 기본 생성자, 복사 생성자, 이동 생성자, 복사 대입 연산자, 이동 대입 연산자 및 소멸자입니다.

F를, 첫 번째 선언에서 암시적으로 선언되거나 명시적으로 기본값으로 지정된 non-virtual 함수로 나타내겠습니다. F에 대한 실행 공간 지정자는 이를 호출하는 모든 함수의 실행 공간 지정자의 합집합입니다. 이 분석을 위해, __global__ 호출자는 __device__ 호출자로 취급됩니다. 예를 들어:

class Base {
    int x;
public:
    __host__ __device__ Base() : x(10) {}
};

class Derived : public Base {
    int y;
};

class Other: public Base {
    int z;
};

__device__ void foo() {
    Derived D1;
    Other D2;
}

__host__ void bar() {
    Other D3;
}

이 경우, 암시적으로 선언된 생성자 함수 Derived::Derived() 는 다음과 같이 취급됩니다. __device__ 오직 다음에서만 호출되기 때문에 함수로 취급됩니다. __device__ 함수 foo(). 암시적으로 선언된 생성자 함수 Other::Other() 로 취급됩니다. __host__ __device__ 함수인데, 이는 둘 다에서 호출되기 때문입니다. a __device__ 함수 foo() 및 a __host__ 함수 bar().

또한, 만약 F 암시적으로 선언된 경우입니다 virtual 함수(예를 들어, a virtual 소멸자), 각 가상 함수의 실행 공간 D 에 의해 오버라이드되는 F 에 대한 실행 공간 집합에 추가됩니다. F 만약 D 암시적으로 선언되지 않았습니다.

예를 들어:

struct Base1 {
    virtual __host__ __device__ ~Base1() {}
};

struct Derived1 : Base1 {}; // implicitly-declared virtual destructor
                            // ~Derived1() has __host__ __device__  execution space specifiers

struct Base2 {
    virtual __device__ ~Base2() = default;
};

struct Derived2 : Base2 {}; // implicitly-declared virtual destructor
                            // ~Derived2() has __device__ execution space specifiers

5.3.9.6.5. 다형적 클래스#

다형적 클래스, 즉 virtual 함수를 갖거나, 다른 다형적 클래스로부터 파생되었거나, 다형적 데이터 멤버를 갖는 클래스는 다음 제약의 적용을 받습니다:

  • 디바이스에서 호스트로 또는 호스트에서 디바이스로 다형적 객체를 복사하는 것은, __global__ 함수 인수를 포함하여, 정의되지 않은 동작입니다.

  • 오버라이드된 virtual 함수의 실행 공간은 베이스 클래스에 있는 함수의 실행 공간과 일치해야 합니다.

int main() {

5.3.10. C++11 제한 사항#

5.3.10.1. inline 네임스페이스#

둘러싸는 네임스페이스에 동일한 이름과 타입 시그니처를 가진 다른 엔티티가 정의되어 있을 때, inline 네임스페이스 내에서 다음 엔티티 중 하나를 정의하는 것은 허용되지 않습니다:

  • __global__ 함수.

  • __device__, __constant__, __managed__, __shared__ 변수.

  • cudaSurfaceObject_t 또는 cudaTextureObject_t와 같은, surface 또는 texture 타입의 변수.

예:

__device__ int my_var; // global scope

inline namespace NS {

__device__ int my_var; // namespace scope

} // namespace NS

5.3.10.2. inline 이름 없는 네임스페이스#

다음 엔티티는 inline 이름 없는 네임스페이스 내에서 네임스페이스 스코프에 선언할 수 없습니다:

  • __global__ 함수.

  • __device__, __constant__, __managed__, __shared__ 변수.

  • cudaSurfaceObject_t 또는 cudaTextureObject_t와 같은, surface 또는 texture 타입의 변수.

5.3.10.3. constexpr 함수#

기본적으로, a constexpr 함수는 표준 함수와 동일한 방식으로, 호환되지 않는 실행 공간을 가진 함수에서 호출될 수 없습니다.

  • 디바이스-전용을 호출하는 constexpr 호스트 코드 생성 단계 동안 호스트 함수에서 함수를 호출하는 경우, 즉 __CUDA_ARCH__ 매크로가 정의되지 않았습니다. 예:

    constexpr __device__ int device_function() { return 0; }

int main() {
    int x = device_function();  // ERROR, calling a device-only constexpr function from host code
}

  • 호스트 전용을 호출하는 constexpr a에서 함수를 __device__ 또는 __global__ 함수, 디바이스 코드 생성 단계 동안, 즉 __CUDA_ARCH__ 매크로가 정의된 경우입니다. 예:

    constexpr int host_function() { return 0; }

__device__ void device_function() {
    int x = host_function();  // ERROR, calling a host-only constexpr function from device code
}

함수 템플릿 특수화는 다음과 같지 않을 수 있다는 점에 유의하십시오. constexpr 해당하는 템플릿 함수가 키워드로 표시되어 있더라도 함수일 수는 없습니다 constexpr.

완화된 constexpr-함수 지원

실험적 nvcc 플래그 --expt-relaxed-constexpr 는 이 제약을 완화하기 위해 둘 다에 사용할 수 있습니다 __host__ 및 __device__ 함수. 그러나, a __global__ 함수는 다음과 같이 선언될 수 없습니다 constexpr. nvcc 또한 매크로를 정의합니다 __CUDACC_RELAXED_CONSTEXPR__.

이 플래그를 지정하면, 컴파일러는 위에서 설명한 교차 실행 공간 호출을 다음과 같이 지원합니다:

  1. 교차 실행 공간에서의 constexpr 함수 호출은, constexpr 변수의 초기화자와 같이 상수 평가가 필요한 컨텍스트에서 발생하는 경우 지원됩니다. 예:

    constexpr __host__ int host_function(int x) { return x + 1; };

__global__ void kernel() {
    constexpr int val = host_function(1); // CORRECT, the call is in a context that requires constant evaluation.
}

constexpr __device__ int device_function(int x) { return x + 1; }

int main() {
    constexpr int val = device_function(1); // CORRECT, the call is in a context that requires constant evaluation.
}

  2. 디바이스 코드는 호스트-전용 constexpr 함수의 본문에 대해 디바이스 코드 생성 중에 생성됩니다. 단, 사용되지 않거나 constexpr 컨텍스트에서만 호출되는 경우는 예외입니다. 예:

    // NOTE: "host_function" is emitted in generated device code because
//       it is called from device code in a non-constexpr context
constexpr int host_function(int x) { return x + 1; }

__device__ int device_function(int in) {
    return host_function(in);  // CORRECT, even though argument is not a constant expression
}

  3. 디바이스 함수에 적용되는 모든 코드 제한은, 디바이스 코드에서 호출되는 constexpr 호스트-전용 함수에도 적용됩니다. 그러나 컴파일러는 컴파일 프로세스와 관련된 제한에 대해서는 빌드 시간 진단을 전혀 내보내지 않을 수 있습니다.

    예를 들어, 다음 코드 패턴은 호스트 함수의 본문에서 지원되지 않습니다. 이는 어떤 디바이스 함수와도 유사합니다; 그러나 컴파일러 진단이 생성되지 않을 수 있습니다.

    • 호스트 변수 또는 호스트-전용 non-constexpr 함수의 단일 정의 규칙(ODR) 사용. 예:

      int host_var1, host_var2;

constexpr int* host_function(bool b) { return b ? &host_var1 : &host_var2; };

__device__ int device_function(bool flag) {
    return *host_function(flag); // ERROR, host_function() attempts to refer to the host variables
                                 //        'host_var1' and 'host_var2'.
                                 //        The code will compile, but will NOT execute correctly.
}

    • 예외 throw/catch 및 런타임 타입 정보(RTTI) typeid/dynamic_cast 사용. 예:

      struct Base { };
struct Derived : public Base { };

// NOTE: "host_function" is emitted in generated device code
constexpr int host_function(bool b, Base *ptr) {
    if (b) {
        return 1;
    }
    else if (typeid(ptr) == typeid(Derived)) { // ERROR, use of typeid in code executing on the GPU
        return 2;
    }
    else {
        throw int{4}; // ERROR, use of throw in code executing on the GPU
    }
}

__device__ void device_function(bool flag) {
    Derived d;
    int val = host_function(flag, &d); //ERROR, host_function() attempts use typeid and throw(),
                                       //       which are not allowed in code that executes on the GPU
}

  4. 호스트 코드 생성 중에는, 디바이스-전용 constexpr 함수의 본문이 호스트 컴파일러로 전송되는 코드에서 보존됩니다. 그러나 디바이스 함수의 본문이 네임스페이스-스코프 디바이스 변수 또는 non-constexpr 디바이스 함수를 ODR-사용하려고 시도하는 경우, 호스트 코드에서 디바이스 함수로의 호출은 지원되지 않습니다. 코드는 컴파일러 진단 없이 빌드될 수 있지만, 런타임에 올바르지 않게 동작할 수 있습니다. 예:

    __device__ int device_var1, device_var2;

constexpr __device__ int* device_function(bool b) { return b ? &device_var1 : &device_var2; };

int host_function(bool flag) {
    return *device_function(flag); // ERROR, device_function() attempts to refer to device variables
                                   //        'device_var1' and 'device_var2'
                                   // The code will compile, but will NOT execute correctly.
}

경고

위 제한 사항과 잘못된 사용에 대한 컴파일러 진단의 부재로 인해, 디바이스 코드에서 표준 C++ 헤더의 함수 std::를 호출하는 것은 피하는 것이 권장됩니다. 이러한 함수의 구현은 호스트 플랫폼에 따라 달라집니다. 대신, CUDA C++ 표준 라이브러리 libcu++의, cuda::std:: 네임스페이스에 있는 동등한 기능을 호출할 것을 강력히 제안합니다.

5.3.10.4. constexpr 변수#

기본적으로, constexpr 변수는 표준 변수와 동일한 방식으로, 호환되지 않는 실행 공간을 가진 함수에서 사용할 수 없습니다.

constexpr 변수는 다음 경우에 디바이스 코드에서 직접 사용할 수 있습니다:

  • 포인터 및 멤버 포인터 타입을 제외한 C++ 스칼라 타입:

    • nullptr_t.

    • bool.

    • 정수 타입: char, signed char, unsigned, long long, 등.

    • 부동소수점 타입: float, double.

    • 열거자: enum 및 enum class.

  • 클래스 타입: class, struct, 및 union (단, constexpr 생성자를 갖는 경우).

  • 위 타입들의 로우 배열(예: int[])은, constexpr __device__ 또는 __host__ __device__ 함수 내부에서 사용될 때에만 허용됩니다.

constexpr __managed__ 및 constexpr __shared__ 변수는 허용되지 않습니다.

예:

constexpr int ConstexprVar = 4; // scalar type

struct MyStruct {
    static constexpr int ConstexprVar = 100;
};

constexpr MyStruct my_struct = MyStruct{}; // class type

constexpr int array[] = {1, 2, 3};

__device__ constexpr int get_value(int idx) {
    return array[idx];                      // CORRECT
}

__device__ void foo(int idx) {
    int        v1 = ConstexprVar;           // CORRECT
    int        v2 = MyStruct::ConstexprVar; // CORRECT
//  const int &v3 = ConstexprVar1;          // ERROR, reference to host constexpr variable
//  const int *v4 = &ConstexprVar1;         // ERROR, address of host constexpr variable
    int        v5 = get_value(2);           // CORRECT, 'get_value(2)' is a constant expression.
//  int        v6 = get_value(idx);         // ERROR, 'get_value(idx)' is not a constant expression
//  int        v7 = array[2];               // ERROR, 'array' is not scalar type.
    MyStruct   v8 = my_struct;              // CORRECT
}

5.3.10.6. 기본값으로 지정된 함수 = default#

CUDA 컴파일러는 암시적으로 선언된 및 명시적으로 기본값으로 지정된 함수에 설명된 대로, 명시적으로 기본값으로 지정된 멤버 함수의 실행 공간을 추론합니다.

명시적으로 기본값으로 지정된 함수에 대한 실행 공간 지정자는, 해당 함수가 out-of-line으로 정의되거나 virtual 함수인 경우를 제외하고 컴파일러가 무시합니다.

예:

struct MyStruct1 {
    MyStruct1() = default;
};

void host_function() {
    MyStruct1 my_struct; // __host__ __device__ constructor
}

__device__ void device_function() {
    MyStruct1 my_struct; // __host__ __device__ constructor
}

struct MyStruct2 {
    __device__ MyStruct2() = default; // WARNING: __device__ annotation is ignored
};

struct MyStruct3 {
    __host__ MyStruct3();
};
MyStruct3::MyStruct3() = default; // out-of-line definition, not ignored

__device__ void device_function2() {
//  MyStruct3 my_struct; // ERROR, __host__ constructor
}

struct MyStruct4 {
    //  MyStruct4::~MyStruct4 has host execution space, not ignored because virtual
    virtual __host__ ~MyStruct4() = default;
};

__device__ void device_function3() {
    MyStruct4 my_struct4;
    // implicit destructor call for 'my_struct4':
    //    ERROR: call from a __device__ function 'device_function3' to a
    //    __host__ function 'MyStruct4::~MyStruct4'
}

5.3.10.7. [cuda::]std::initializer_list#

기본적으로, CUDA 컴파일러는 [cuda::]std::initializer_list의 멤버 함수를 암시적으로 __host__ __device__ 실행 공간 지정자를 갖는 것으로 간주하며, 따라서 디바이스 코드에서 직접 호출할 수 있습니다.
nvcc 플래그 --no-host-device-initializer-list는 이 동작을 비활성화합니다; 그러면 [cuda::]std::initializer_list의 멤버 함수는 __host__ 함수로 간주되며 디바이스 코드에서 직접 호출할 수 없습니다.

__global__ 함수는 [cuda::]std::initializer_list 타입의 매개변수를 가질 수 없습니다.

예:

#include <initializer_list>

__device__ void foo(std::initializer_list<int> in) {}

__device__ void bar() {
    foo({4,5,6}); // (a) initializer list containing only constant expressions.
    int i = 4;
    foo({i,5,6}); // (b) initializer list with at least one  non-constant element.
                  // This form may have better performance than (a).
}

5.3.10.8. [cuda::]std::move, [cuda::]std::forward#

기본적으로 CUDA 컴파일러는 std::move 및 std::forward 함수 템플릿이 암시적으로 __host__ __device__ 실행 공간 지정자를 갖는 것으로 간주하며, 따라서 디바이스 코드에서 직접 호출할 수 있습니다. nvcc 플래그 --no-host-device-move-forward는 이 동작을 비활성화합니다; 그러면 std::move 및 std::forward는 __host__ 함수로 간주되며 디바이스 코드에서 직접 호출할 수 없습니다.

힌트

반대로 cuda::std::move 및 cuda::std::forward는 항상 __host__ __device__ 실행 공간을 갖습니다.

5.3.11. C++14 제한 사항#

5.3.11.1. 추론된 반환 타입을 갖는 함수#

__global__ 함수는 추론된 반환 타입 auto을 가질 수 없습니다.

추론된 반환 타입을 갖는 __device__ 함수의 반환 타입을 인트로스펙션하는 것은 호스트 코드에서 허용되지 않습니다.

참고

CUDA 프런트엔드 컴파일러는 호스트 컴파일러를 호출하기 전에, 함수 선언이 void 반환 타입을 갖도록 변경합니다. 이는 호스트 코드에서 __device__ 함수의 추론된 반환 타입에 대한 인트로스펙션을 깨뜨릴 수 있습니다. 따라서 CUDA 컴파일러는 디바이스 함수 본문 밖에서 이러한 추론된 반환 타입을 참조하는 경우 컴파일 시간 오류를 발생시킵니다.

예:

 __device__ auto device_function(int x) { // deduced return type
     return x;                            // decltype(auto) has the same behavior
 }

 __global__ void kernel() {
     int x = sizeof(device_function(2));         // CORRECT, device code scope
 }

 // const int size = sizeof(device_function(2)); // ERROR, return type deduction on host

 void host_function() {
 //  using T = decltype(device_function(2));     // ERROR, return type deduction on host
 }

void host_fn1() {
  // ERROR, referenced outside device function bodies
  int (*p1)(int) = fn1;

  struct S_local_t {
    // ERROR, referenced outside device function bodies
    decltype(fn2(10)) m1;

    S_local_t() : m1(10) { }
  };
}

// ERROR, referenced outside device function bodies
template <typename T = decltype(fn2)>
void host_fn2() { }

template<typename T> struct MyStruct { };

// ERROR, referenced outside device function bodies
struct S1_derived_t : MyStruct<decltype(fn1)> { };

5.3.11.2. 변수 템플릿#

Microsoft 컴파일러를 사용할 때, __device__ 또는 __constant__ 변수 템플릿은 const-한정될 수 없습니다.

예:

// ERROR on Windows (non-portable), const-qualified
template <typename T>
__device__ const T var = 0;

 // CORRECT, ptr1 is not const-qualified
template <typename T>
__device__ const T* ptr1 = nullptr;

// ERROR on Windows (non-portable), ptr2 is const-qualified
template <typename T>
__device__ const T* const ptr2 = nullptr;

5.3.12. C++17 제한 사항#

5.3.12.1. inline 변수#

단일 번역 단위에서, inline 변수를 사용하는 것은 일반 변수에 비해 추가 기능을 제공하지 않으며, 실질적인 이점도 제공하지 않습니다.
nvcc 허용합니다 inline 다음과 같은 변수를 __device__, __constant__, 또는 __managed__ 메모리 공간에서만 별도 컴파일 모드 또는 내부 링키지를 가진 변수에 대해.

참고

사용할 때 gcc/g++ 호스트 컴파일러, an inline 로 선언된 변수 __managed__ 메모리 공간 지정자가 디버거에 표시되지 않을 수 있습니다.

예:

inline        __device__ int device_var1;  // CORRECT, when compiled in Separate Compilation mode (-rdc=true or -dc)
                                           // ERROR, when compiled in Whole Program Compilation mode

static inline __device__ int device_var2;  // CORRECT, internal linkage

namespace {

inline __device__ int device_var3;         // CORRECT, internal linkage

inline __shared__ int shared_var;          // CORRECT, internal linkage

static inline __device__ int device_var4;  // CORRECT, internal linkage

inline __device__ int device_var5;         // CORRECT, internal linkage

} // namespace

5.3.12.2. 구조적 바인딩#

구조적 바인딩은 __device__, __shared__, __constant__, 또는 __managed__와 같은 메모리 공간 지정자로 선언할 수 없습니다.

예:

struct S {
    int x, y;
};
// __device__ auto [a, b] = S{4, 5}; // ERROR

5.3.13. C++20 제한 사항#

5.3.13.1. 3방향 비교 연산자#

3방향 비교 연산자 (<=>)는 디바이스 코드에서 지원되지만, 일부 사용은 호스트 구현이 제공하는 C++ 표준 라이브러리의 기능에 암묵적으로 의존합니다. 이러한 연산자를 사용하려면 경고를 억제하기 위해 플래그 --expt-relaxed-constexpr를 지정해야 할 수 있으며, 해당 기능을 사용하려면 호스트 구현이 디바이스 코드의 요구 사항을 충족해야 합니다.

예:

#include <compare> // std::strong_ordering implementation

struct S {
    int x, y;

    auto operator<=>(const S&) const = default; // (a)

    __host__ __device__ bool operator<=>(int rhs) const { return false; } // (b)
};

__host__ __device__ bool host_device_function(S a, S b) {
    if (a <=> 1)  // CORRECT, calls a user-defined host-device overload (b)
        return true;
    return a < b; // CORRECT, call to an implicitly-declared function (a)
                  // Note: it requires a device-compatible std::strong_ordering
                  //       implementation provided in the header <compare>
                  //       and the flag --expt-relaxed-constexpr
}

다음의 예를 참조하십시오 Compiler Explorer.

5.3.13.2. consteval 함수#

consteval 함수는 실행 공간과 무관하게 호스트 및 디바이스 코드 모두에서 호출될 수 있습니다.

예:

consteval int host_consteval() {
    return 10;
}

__device__ consteval int device_consteval() {
    return 10;
}

__device__ int device_function() {
    return host_consteval();   // CORRECT, even if called from device code
}

__host__ __device__ int host_device_function() {
    return device_function();  // CORRECT, even if called from host-device code
}
