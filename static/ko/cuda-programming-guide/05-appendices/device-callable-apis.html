5.6. 디바이스에서 호출 가능한 API 및 인트린식

이 장에는 CUDA 커널과 디바이스 코드에서 호출할 수 있는 API 및 인트린식에 대한 참조 자료와 API 문서가 포함되어 있습니다.

5.6.1. 메모리 배리어 프리미티브 인터페이스#

프리미티브 API는 cuda::barrier 기능에 대한 C 유사 인터페이스입니다. 이러한 프리미티브는 <cuda_awbarrier_primitives.h> 헤더를 포함하면 사용할 수 있습니다.

5.6.1.1. 데이터 타입#

typedef /* implementation defined */ __mbarrier_t;
typedef /* implementation defined */ __mbarrier_token_t;

5.6.1.2. 메모리 배리어 프리미티브 API#

uint32_t __mbarrier_maximum_count();
void __mbarrier_init(__mbarrier_t* bar, uint32_t expected_count);

  • bar는 __shared__ 메모리에 대한 포인터여야 합니다.

  • expected_count <= __mbarrier_maximum_count()

  • 현재 및 다음 페이즈에 대해 *bar 예상 도착 개수를 expected_count로 초기화합니다.

void __mbarrier_inval(__mbarrier_t* bar);

  • bar는 공유 메모리에 상주하는 배리어 객체에 대한 포인터여야 합니다.

  • 해당 공유 메모리를 다른 용도로 재사용하기 전에 *bar의 무효화가 필요합니다.

__mbarrier_token_t __mbarrier_arrive(__mbarrier_t* bar);

  • 이 호출 전에 *bar의 초기화가 이루어져야 합니다.

  • 대기 중인 카운트는 0이면 안 됩니다.

  • 배리어의 현재 페이즈에 대한 대기 중인 카운트를 원자적으로 감소시킵니다.

  • 감소 직전의 배리어 상태와 연관된 도착 토큰을 반환합니다.

__mbarrier_token_t __mbarrier_arrive_and_drop(__mbarrier_t* bar);

  • 이 호출 전에 *bar의 초기화가 이루어져야 합니다.

  • 대기 중인 카운트는 0이면 안 됩니다.

  • 배리어의 현재 페이즈에 대한 대기 중인 카운트와 다음 페이즈에 대한 예상 카운트를 원자적으로 감소시킵니다.

  • 감소 직전의 배리어 상태와 연관된 도착 토큰을 반환합니다.

bool __mbarrier_test_wait(__mbarrier_t* bar, __mbarrier_token_t token);

  • token은 *bar의 바로 직전 페이즈 또는 현재 페이즈와 연관되어 있어야 합니다.

  • token이 *bar의 바로 직전 페이즈와 연관되어 있으면 true를 반환하고, 그렇지 않으면 false를 반환합니다.

bool __mbarrier_test_wait_parity(__mbarrier_t* bar, bool phase_parity);

  • phase_parity는 *bar의 현재 페이즈 또는 바로 직전 페이즈의 패리티를 나타내야 합니다. 값이 true이면 홀수 번호 페이즈를, false이면 짝수 번호 페이즈를 의미합니다.

  • phase_parity가 *bar의 바로 직전 페이즈의 패리티를 나타내면 true를, 그렇지 않으면 false를 반환합니다.

bool __mbarrier_try_wait(__mbarrier_t* bar, __mbarrier_token_t token, uint32_t max_sleep_nanosec);

  • token은 *bar의 현재 페이즈 또는 바로 직전 페이즈와 연관되어 있어야 합니다.

  • token이 *bar의 바로 직전 페이즈와 연관되어 있으면 true를 반환합니다. 그렇지 않으면 실행 중인 스레드가 일시 중단될 수 있으며, 지정한 페이즈가 완료되면 true를 반환하면서 재개되고, 시스템 의존 시간 제한이 먼저 만료되면 false를 반환합니다.

  • max_sleep_nanosec는 시스템 의존 시간 제한 대신 사용할 수 있는 최대 대기 시간을 나노초 단위로 지정합니다.

bool __mbarrier_try_wait_parity(__mbarrier_t* bar, bool phase_parity, uint32_t max_sleep_nanosec);

  • phase_parity는 *bar의 현재 페이즈 또는 바로 직전 페이즈의 패리티를 나타내야 합니다. 값이 true이면 홀수 번호 페이즈를, false이면 짝수 번호 페이즈를 의미합니다.

  • phase_parity가 *bar의 바로 직전 페이즈의 패리티를 나타내면 true를 반환합니다. 그렇지 않으면 실행 중인 스레드가 일시 중단될 수 있으며, 지정한 페이즈가 완료되면 true를 반환하면서 재개되고, 시스템 의존 시간 제한이 먼저 만료되면 false를 반환합니다.

  • max_sleep_nanosec는 시스템 의존 시간 제한 대신 사용할 수 있는 최대 대기 시간을 나노초 단위로 지정합니다.

5.6.2. 파이프라인 프리미티브 인터페이스#

파이프라인 프리미티브는 다음에서 사용할 수 있는 기능에 대해 C와 유사한 인터페이스를 제공합니다 <cuda/pipeline>. 파이프라인 프리미티브 인터페이스는 다음을 포함하면 사용할 수 있습니다 <cuda_pipeline.h> 헤더입니다. ISO C++ 2011 호환성 없이 컴파일하는 경우, 다음을 포함하십시오 <cuda_pipeline_primitives.h> 헤더.

참고

파이프라인 프리미티브 API는 특정 크기 및 정렬 요구 사항을 갖는 전역 메모리에서 공유 메모리로의 비동기 복사 추적만 지원합니다. 이는 다음과 동등한 기능을 제공합니다 cuda::pipeline 다음과 함께 있는 객체 cuda::thread_scope_thread.

5.6.2.1. memcpy_async 프리미티브#

void __pipeline_memcpy_async(void* __restrict__ dst_shared,
                             const void* __restrict__ src_global,
                             size_t size_and_align,
                             size_t zfill=0);

  • 다음 연산이 비동기적으로 평가되도록 제출되기를 요청합니다:

    size_t i = 0;
for (; i < size_and_align - zfill; ++i) ((char*)dst_shared)[i] = ((char*)src_global)[i]; /* copy */
for (; i < size_and_align; ++i) ((char*)dst_shared)[i] = 0; /* zero-fill */

  • 요구 사항:

    • dst_shared는 memcpy_async의 공유 메모리 목적지에 대한 포인터여야 합니다.

    • src_global는 memcpy_async의 전역 메모리 소스에 대한 포인터여야 합니다.

    • size_and_align는 4, 8 또는 16이어야 합니다.

    • zfill <= size_and_align.

    • size_and_align는 dst_shared 및 src_global의 정렬(alignment)이어야 합니다.

  • 어떤 스레드든 memcpy_async 작업이 완료될 때까지 기다리기 전에 소스 메모리를 수정하거나 목적지 메모리를 관찰하는 것은 레이스 컨디션입니다. memcpy_async 작업을 제출하고 그 완료를 기다리는 사이에, 다음 동작 중 어느 하나라도 레이스 컨디션을 유발합니다:

    • dst_shared에서 로드합니다.

    • dst_shared 또는 src_global에 저장합니다.

    • dst_shared 또는 src_global에 원자적 업데이트를 적용합니다.

5.6.2.2. 커밋 프리미티브#

void __pipeline_commit();

  • 제출된 memcpy_async를 현재 배치로 파이프라인에 커밋합니다.

5.6.2.3. 대기 프리미티브#

void __pipeline_wait_prior(size_t N);

  • Let {0, 1, 2, ..., L} 의 호출과 연관된 인덱스 시퀀스라고 하자 __pipeline_commit() 주어진 스레드에 의해.

  • 배치의 완료를 기다립니다 적어도 최대 ~까지(포함) L-N.

5.6.2.4. 배리어 프리미티브에서 도착(Arrive)#

void __pipeline_arrive_on(__mbarrier_t* bar);

  • bar 공유 메모리에 있는 배리어를 가리킵니다.

  • 배리어 도착 카운트를 1 증가시키며, 이 호출 전에 시퀀싱된 모든 memcpy_async 작업이 완료되면 도착 카운트가 1 감소하므로 결과적으로 도착 카운트에 대한 순효과는 0입니다. 도착 카운트 증가가 __mbarrier_maximum_count()를 초과하지 않도록 하는 것은 사용자의 책임입니다.

5.6.3. 코오퍼러티브 그룹(Cooperative Groups) API#

5.6.3.1. cooperative_groups.h#

5.6.3.1.1. class thread_block#

모든 CUDA 프로그래머는 이미 특정 스레드 그룹, 즉 스레드 블록에 익숙합니다. 코오퍼러티브 그룹(Cooperative Groups) 확장은 커널 내에서 이 개념을 명시적으로 표현하기 위해 새로운 데이터 타입인 thread_block를 도입합니다.

class thread_block;

다음을 통해 생성됩니다:

thread_block g = this_thread_block();

공개 멤버 함수:

static void sync(): 그룹에서 이름이 지정된 스레드를 동기화하며, g.barrier_wait(g.barrier_arrive())와 동등합니다.

thread_block::arrival_token barrier_arrive(): thread_block 배리어에 도착하며, barrier_wait()에 전달해야 하는 토큰을 반환합니다.

void barrier_wait(thread_block::arrival_token&& t): thread_block 배리어에서 대기하며, barrier_arrive()에서 반환된 도착 토큰을 rvalue 참조로 받습니다.

static unsigned int thread_rank(): [0, num_threads) 내에서 호출 스레드의 순위

static dim3 group_index(): 실행된 그리드 내에서 블록의 3차원 인덱스

static dim3 thread_index(): 실행된 블록 내에서 스레드의 3차원 인덱스

static dim3 dim_threads(): 스레드 단위로 표현한 실행된 블록의 차원

static unsigned int num_threads(): 그룹 내 총 스레드 수

레거시 멤버 함수(별칭):

static unsigned int size(): 그룹 내 총 스레드 수(num_threads()의 별칭)

static dim3 group_dim(): 실행된 블록의 차원(dim_threads()의 별칭)

예:

/// Loading an integer from global into shared memory
__global__ void kernel(int *globalInput) {
    __shared__ int x;
    thread_block g = this_thread_block();
    // Choose a leader in the thread block
    if (g.thread_rank() == 0) {
        // load from global into shared for all threads to work with
        x = (*globalInput);
    }
    // After loading data into shared memory, you want to synchronize
    // if all threads in your thread block need to see it
    g.sync(); // equivalent to __syncthreads();
}

참고: 그룹의 모든 스레드는 집합 연산에 참여해야 하며, 그렇지 않으면 동작이 정의되지 않습니다.

관련: thread_block 데이터 타입은 더 일반적인 thread_group 데이터 타입에서 파생되며, 이는 더 넓은 범주의 그룹을 표현하는 데 사용할 수 있습니다.

5.6.3.1.2. class cluster_group#

이 그룹 객체는 단일 클러스터에서 실행된 모든 스레드를 나타냅니다. API는 Compute Capability 9.0+를 갖춘 모든 하드웨어에서 사용할 수 있습니다. 이러한 경우 클러스터가 아닌 그리드를 실행하면, API는 1x1x1 클러스터를 가정합니다.

class cluster_group;

다음을 통해 생성됩니다:

cluster_group g = this_cluster();

공개 멤버 함수:

static void sync(): 그룹에 명명된 스레드를 동기화하며, g.barrier_wait(g.barrier_arrive())와 동일합니다.

static cluster_group::arrival_token barrier_arrive(): 클러스터 배리어에 도착하며, barrier_wait()에 전달해야 하는 토큰을 반환합니다.

static void barrier_wait(cluster_group::arrival_token&& t): 클러스터 배리어에서 대기하며, barrier_arrive()에서 반환된 도착 토큰을 rvalue 참조로 받습니다.

static unsigned int thread_rank(): [0, num_threads) 내에서 호출 스레드의 순위

static unsigned int block_rank(): [0, num_blocks) 내에서 호출 블록의 순위

static unsigned int num_threads(): 그룹 내 총 스레드 수

static unsigned int num_blocks(): 그룹 내 총 블록 수

static dim3 dim_threads(): 스레드 단위로 본 실행된 클러스터의 차원

static dim3 dim_blocks(): 블록 단위로 본 실행된 클러스터의 차원

static dim3 block_index(): 실행된 클러스터 내에서 호출 블록의 3차원 인덱스

static unsigned int query_shared_rank(const void *addr): 공유 메모리 주소가 속한 블록 순위를 가져옵니다.

static T* map_shared_rank(T *addr, int rank): 클러스터 내 다른 블록의 공유 메모리 변수 주소를 가져옵니다.

레거시 멤버 함수(별칭):

static unsigned int size(): 그룹 내 총 스레드 수(num_threads()의 별칭)

5.6.3.1.3. class grid_group#

이 그룹 객체는 단일 그리드에서 실행된 모든 스레드를 나타냅니다. sync() 이외의 API는 항상 사용할 수 있지만, 그리드 전체에서 동기화할 수 있으려면 cooperative launch API를 사용해야 합니다.

class grid_group;

다음을 통해 생성됩니다:

grid_group g = this_grid();

공개 멤버 함수:

bool is_valid() const: grid_group이 동기화할 수 있는지 여부를 반환합니다.

void sync() const: 그룹에 지정된 스레드를 동기화하며, g.barrier_wait(g.barrier_arrive())와 동일합니다.

grid_group::arrival_token barrier_arrive(): 그리드 배리어에 도착하며, barrier_wait()에 전달해야 하는 토큰을 반환합니다.

void barrier_wait(grid_group::arrival_token&& t): 그리드 배리어에서 대기하며, barrier_arrive()에서 반환된 도착 토큰을 rvalue 참조로 받습니다.

5.6.3.1.4. class thread_block_tile#

타일형 그룹의 템플릿 버전으로, 템플릿 매개변수를 사용해 타일의 크기를 지정합니다. 이를 컴파일 시점에 알 수 있으므로 더 최적화된 실행이 가능할 수 있습니다.

template <unsigned int Size, typename ParentT = void>
class thread_block_tile;

다음을 통해 생성됩니다:

template <unsigned int Size, typename ParentT>
_CG_QUALIFIER thread_block_tile<Size, ParentT> tiled_partition(const ParentT& g)

Size는 2의 거듭제곱이어야 하며 1024 이하이어야 합니다. 참고(Notes) 섹션에서는 Compute Capability 7.5 이하의 하드웨어에서 32보다 큰 크기의 타일을 생성하기 위해 필요한 추가 단계를 설명합니다.

참고:

  • 여기서는 thread_block_tile 템플릿 데이터 구조가 사용되므로, 그룹 크기는 인수가 아니라 템플릿 매개변수로서 tiled_partition 호출에 전달됩니다.

  • shfl, shfl_up, shfl_down, and shfl_xor 함수는 C++11 이상으로 컴파일할 때 모든 타입의 객체를 허용합니다. 이는 아래 제약 조건을 만족하는 한 비정수 타입도 셔플할 수 있음을 의미합니다:

    • 사소하게 복사 가능(trivially copyable)으로 간주됨, 즉 is_trivially_copyable<T>::value == true

    • 타일 크기가 32 이하인 경우 sizeof(T) <= 32, 더 큰 타일의 경우 sizeof(T) <= 8

  • Compute Capability 7.5 이하의 하드웨어에서는 크기가 32보다 큰 타일에 대해 소량의 메모리를 예약해야 합니다. 이는 공유 메모리 또는 전역 메모리 중 하나에 상주해야 하는 cooperative_groups::block_tile_memory struct 템플릿을 사용하여 수행할 수 있습니다.

    template <unsigned int MaxBlockSize = 1024>
struct block_tile_memory;

    MaxBlockSize 현재 스레드 블록에서 스레드의 최대 개수를 지정합니다. 이 매개변수는 다음의 공유 메모리 사용량을 최소화하는 데 사용할 수 있습니다. block_tile_memory 더 작은 스레드 카운트로만 실행되는 커널에서.

    이 block_tile_memory 그런 다음 cooperative_groups::this_thread_block, 결과적으로 생성된 thread_block 32보다 큰 크기의 타일로 분할될 수 있도록 합니다. 오버로드 this_thread_block 수락하는 block_tile_memory 인수는 집합적 연산이며 다음의 모든 스레드와 함께 호출해야 합니다. thread_block.

    block_tile_memory는 여러 가지 서로 다른 Compute Capability를 대상으로 하는 단일 소스를 작성할 수 있도록 Compute Capability 8.0 이상 하드웨어에서 사용할 수 있습니다. 필요하지 않은 경우 공유 메모리에 인스턴스화되었을 때 메모리를 전혀 소비하지 않아야 합니다.

예제:

/// The following code will create two sets of tiled groups, of size 32 and 4 respectively:
/// The latter has the provenance encoded in the type, while the first stores it in the handle
thread_block block = this_thread_block();
thread_block_tile<32> tile32 = tiled_partition<32>(block);
thread_block_tile<4, thread_block> tile4 = tiled_partition<4>(block);

/// The following code will create tiles of size 128 on all Compute Capabilities.
/// block_tile_memory can be omitted on Compute Capability 8.0 or higher.
__global__ void kernel(...) {
    // reserve shared memory for thread_block_tile usage,
    //   specify that block size will be at most 256 threads.
    __shared__ block_tile_memory<256> shared;
    thread_block thb = this_thread_block(shared);

    // Create tiles with 128 threads.
    auto tile = tiled_partition<128>(thb);

    // ...
}

5.6.3.1.5. class coalesced_group#

CUDA의 SIMT 아키텍처에서 하드웨어 수준에서 멀티프로세서는 워프(warp)라고 불리는 32개 스레드의 그룹으로 스레드를 실행합니다. 애플리케이션 코드에 워프 내 스레드가 디버전스(diverge)하도록 만드는 데이터 종속 조건 분기(conditional branch)가 존재하면, 워프는 해당 경로에 있지 않은 스레드를 비활성화한 채 각 분기를 직렬로 실행합니다. 경로에서 활성 상태로 남아 있는 스레드를 coalesced라고 합니다. 코오퍼러티브 그룹에는 모든 coalesced 스레드를 포함하는 그룹을 발견하고 생성하는 기능이 있습니다.

coalesced_threads()를 통해 그룹 핸들을 구성하는 것은 기회주의적(opportunistic)입니다. 이는 그 시점의 활성 스레드 집합을 반환하며, (활성 상태인 한) 어떤 스레드가 반환되는지에 대해서도, 또는 실행 전반에 걸쳐 coalesced 상태가 유지된다는 것에 대해서도 보장하지 않습니다(집합 연산(collective) 실행을 위해 다시 함께 모이지만 이후 다시 디버전스할 수 있습니다).

5.6.3.2. cooperative_groups/async.h#

5.6.3.2.1. memcpy_async#

memcpy_async는 전역 메모리에서 공유 메모리로의 비차단 메모리 트랜잭션에 대한 하드웨어 가속 지원을 활용하는 그룹 전체 집합 memcpy입니다. 그룹에 명명된 스레드 집합이 주어지면, memcpy_async는 단일 파이프라인 단계에서 입력 타입의 지정된 바이트 수 또는 요소를 이동합니다. 또한 memcpy_async API를 사용할 때 최상의 성능을 달성하려면 공유 메모리와 전역 메모리 모두에 대해 16바이트 정렬이 필요합니다. 이것이 일반적인 경우에는 memcpy이지만, 소스가 전역 메모리이고 목적지가 공유 메모리이며 둘 다 16, 8 또는 4바이트 정렬로 주소 지정될 수 있는 경우에만 비동기라는 점에 유의하는 것이 중요합니다. 비동기로 복사된 데이터는, 해당 단계가 공유 메모리로 데이터 이동을 완료했음을 알리는 wait 또는 wait_prior 호출 이후에만 읽어야 합니다.

모든 미완료 요청을 기다려야 하면 유연성이 일부 줄어들 수 있습니다(하지만 단순성은 얻습니다). 데이터 전송과 실행을 효율적으로 오버랩하려면 an을 시작할 수 있는 것이 중요합니다. N+1memcpy_async 요청을 기다리고 해당 요청에 대해 작업하는 동안 요청을 N. 이를 위해 memcpy_async 그리고 집합적 단계 기반을 사용하여 이에 대해 대기하십시오 wait_prior API. 참조하십시오 wait 및 wait_prior 자세한 내용은

사용법 1

template <typename TyGroup, typename TyElem, typename TyShape>
void memcpy_async(
  const TyGroup &group,
  TyElem *__restrict__ _dst,
  const TyElem *__restrict__ _src,
  const TyShape &shape
);

shape 바이트를 복사합니다.

사용법 2

template <typename TyGroup, typename TyElem, typename TyDstLayout, typename TySrcLayout>
void memcpy_async(
  const TyGroup &group,
  TyElem *__restrict__ dst,
  const TyDstLayout &dstLayout,
  const TyElem *__restrict__ src,
  const TySrcLayout &srcLayout
);

min(dstLayout, srcLayout) 개의 요소를 복사합니다. 레이아웃이 cuda::aligned_size_t<N> 타입인 경우, 둘 다 동일한 정렬(alignment)을 지정해야 합니다.

정오표 CUDA 11.1에서 src 및 dst 입력 레이아웃 모두와 함께 도입된 memcpy_async API는 레이아웃이 바이트가 아니라 요소 단위로 제공되기를 기대합니다. 요소 타입은 TyElem에서 추론되며 크기는 sizeof(TyElem)입니다. cuda::aligned_size_t<N> 타입이 레이아웃으로 사용되는 경우, 지정된 요소 개수에 sizeof(TyElem)를 곱한 값은 N의 배수여야 하며, 요소 타입으로 std::byte 또는 char를 사용하는 것이 권장됩니다.

복사의 지정된 shape 또는 레이아웃이 cuda::aligned_size_t<N> 타입이면, 정렬은 최소 min(16, N)으로 보장됩니다. 이 경우 dst 및 src 포인터는 모두 N 바이트로 정렬되어야 하며, 복사되는 바이트 수는 N의 배수여야 합니다.

코드 생성(Codegen) 요구 사항: 최소 Compute Capability 5.0, 비동기성을 위해 Compute Capability 8.0, C++11

cooperative_groups/memcpy_async.h 헤더를 포함해야 합니다.

예:

/// This example streams elementsPerThreadBlock worth of data from global memory
/// into a limited sized shared memory (elementsInShared) block to operate on.
#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

namespace cg = cooperative_groups;

__global__ void kernel(int* global_data) {
    cg::thread_block tb = cg::this_thread_block();
    const size_t elementsPerThreadBlock = 16 * 1024;
    const size_t elementsInShared = 128;
    __shared__ int local_smem[elementsInShared];

    size_t copy_count;
    size_t index = 0;
    while (index < elementsPerThreadBlock) {
        cg::memcpy_async(tb, local_smem, elementsInShared, global_data + index, elementsPerThreadBlock - index);
        copy_count = min(elementsInShared, elementsPerThreadBlock - index);
        cg::wait(tb);
        // Work with local_smem
        index += copy_count;
    }
}

5.6.3.2.2. wait 및 wait_prior#

template <typename TyGroup>
void wait(TyGroup & group);

template <unsigned int NumStages, typename TyGroup>
void wait_prior(TyGroup & group);

wait 및 wait_prior 집합 연산(collective)은 memcpy_async 복사가 완료될 때까지 대기할 수 있게 해줍니다. wait는 이전의 모든 복사가 완료될 때까지 호출 스레드를 블록합니다. wait_prior는 최신 NumStages가 아직 완료되지 않은 상태를 허용하고, 그 이전의 모든 요청을 기다립니다. 따라서 총 N개의 복사가 요청된 경우, 처음 N-NumStages개가 완료될 때까지 대기하며 마지막 NumStages개는 여전히 진행 중일 수 있습니다. wait와 wait_prior 모두 명명된 그룹을 동기화합니다.

코드 생성 요구 사항: 최소 Compute Capability 5.0, 비동기성을 위해 Compute Capability 8.0, C++11

cooperative_groups/memcpy_async.h 헤더를 포함해야 합니다.

예제:

/// This example streams elementsPerThreadBlock worth of data from global memory
/// into a limited sized shared memory (elementsInShared) block to operate on in
/// multiple (two) stages. As stage N is kicked off, we can wait on and operate on stage N-1.
#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

namespace cg = cooperative_groups;

__global__ void kernel(int* global_data) {
    cg::thread_block tb = cg::this_thread_block();
    const size_t elementsPerThreadBlock = 16 * 1024 + 64;
    const size_t elementsInShared = 128;
    __align__(16) __shared__ int local_smem[2][elementsInShared];
    int stage = 0;
    // First kick off an extra request
    size_t copy_count = elementsInShared;
    size_t index = copy_count;
    cg::memcpy_async(tb, local_smem[stage], elementsInShared, global_data, elementsPerThreadBlock - index);
    while (index < elementsPerThreadBlock) {
        // Now we kick off the next request...
        cg::memcpy_async(tb, local_smem[stage ^ 1], elementsInShared, global_data + index, elementsPerThreadBlock - index);
        // ... but we wait on the one before it
        cg::wait_prior<1>(tb);

        // Its now available and we can work with local_smem[stage] here
        // (...)
        //

        // Calculate the amount fo data that was actually copied, for the next iteration.
        copy_count = min(elementsInShared, elementsPerThreadBlock - index);
        index += copy_count;

        // A cg::sync(tb) might be needed here depending on whether
        // the work done with local_smem[stage] can release threads to race ahead or not
        // Wrap to the next stage
        stage ^= 1;
    }
    cg::wait(tb);
    // The last local_smem[stage] can be handled here
}

  • cg::bit_xor: 두 값을 받아 operator^의 결과를 반환합니다.

reduce는 전달된 그룹에 명명된 각 스레드가 제공한 데이터에 대해 리덕션(reduction) 연산을 수행합니다. 이는 산술 덧셈, min 또는 max 연산과 논리 AND, OR 또는 XOR에 대해 (compute 80 이상 디바이스에서) 하드웨어 가속을 활용하며, 구세대 하드웨어에서는 소프트웨어 폴백도 제공합니다. 하드웨어로 가속되는 것은 4B 타입만입니다.

exclusive_scan을 사용한 스트림 컴팩션 예:

#include <cooperative_groups.h>
#include <cooperative_groups/scan.h>
namespace cg = cooperative_groups;

// put data from input into output only if it passes test_fn predicate
template<typename Group, typename Data, typename TyFn>
__device__ int stream_compaction(Group &g, Data *input, int count, TyFn&& test_fn, Data *output) {
    int per_thread = count / g.num_threads();
    int thread_start = min(g.thread_rank() * per_thread, count);
    int my_count = min(per_thread, count - thread_start);

    // get all passing items from my part of the input
    //  into a contagious part of the array and count them.
    int i = thread_start;
    while (i < my_count + thread_start) {
        if (test_fn(input[i])) {
            i++;
        }
        else {
            my_count--;
            input[i] = input[my_count + thread_start];
        }
    }

    // scan over counts from each thread to calculate my starting
    //  index in the output
    int my_idx = cg::exclusive_scan(g, my_count);

    for (i = 0; i < my_count; ++i) {
        output[my_idx + i] = input[thread_start + i];
    }
    // return the total number of items in the output
    return g.shfl(my_idx + my_count, g.num_threads() - 1);
}

exclusive_scan_update를 사용한 동적 버퍼 공간 할당 예:

#include <cooperative_groups.h>
#include <cooperative_groups/scan.h>
namespace cg = cooperative_groups;

// Buffer partitioning is static to make the example easier to follow,
// but any arbitrary dynamic allocation scheme can be implemented by replacing this function.
__device__ int calculate_buffer_space_needed(cg::thread_block_tile<32>& tile) {
    return tile.thread_rank() % 2 + 1;
}

__device__ int my_thread_data(int i) {
    return i;
}

__global__ void kernel() {
    __shared__ extern int buffer[];
    __shared__ cuda::atomic<int, cuda::thread_scope_block> buffer_used;

    auto block = cg::this_thread_block();
    auto tile = cg::tiled_partition<32>(block);
    buffer_used = 0;
    block.sync();

    // each thread calculates buffer size it needs
    int buf_needed = calculate_buffer_space_needed(tile);

    // scan over the needs of each thread, result for each thread is an offset
    // of that thread’s part of the buffer. buffer_used is atomically updated with
    // the sum of all thread's inputs, to correctly offset other tile’s allocations
    int buf_offset =
        cg::exclusive_scan_update(tile, buffer_used, buf_needed);

    // each thread fills its own part of the buffer with thread specific data
    for (int i = 0 ; i < buf_needed ; ++i) {
        buffer[buf_offset + i] = my_thread_data(i);
    }

    block.sync();
    // buffer_used now holds total amount of memory allocated
    // buffer is {0, 0, 1, 0, 0, 1 ...};
}

void T::barrier_wait(T::arrival_token&&);

barrier_arrive 및 barrier_wait 멤버 함수는 cuda::barrier와 유사한 동기화 API를 제공합니다 (더 읽기). 코오퍼러티브 그룹은 그룹 배리어를 자동으로 초기화하지만, 도착(arrive) 및 대기(wait) 연산에는 이러한 연산의 집합적(collective) 성격에서 비롯되는 추가 제약이 있습니다. 그룹 내 모든 스레드는 페이즈(phase)당 한 번 배리어에 도착하고 대기해야 합니다. When barrier_arrive 그룹과 함께 호출되면, 해당 그룹으로 어떤 집합 연산(collective) 또는 다른 배리어 도착(barrier arrival) 호출의 결과는 배리어 단계의 완료가 다음으로 관측될 때까지 정의되지 않습니다 barrier_wait 호출. 다음에서 차단된 스레드 barrier_wait 다른 스레드가 호출하기 전에 동기화에서 해제될 수 있습니다 barrier_wait, 하지만 그룹 내 모든 스레드가 호출한 이후에만 barrier_arrive. 그룹 타입 T 다음 중 어느 것이든 될 수 있습니다 암시적 그룹. 이를 통해 스레드는 도착한 후 동기화가 완료될 때까지 기다리기 전에 독립적인 작업을 수행할 수 있으며, 그 결과 일부 동기화 지연 시간을 숨길 수 있습니다. barrier_arrive 를 반환합니다 arrival_token 해당하는 함수에 전달해야 하는 객체 barrier_wait. 토큰은 이 방식으로 소비되며 다른 용도로는 사용할 수 없습니다 barrier_wait 호출.

클러스터 전반에서 공유 메모리 초기화를 동기화하기 위해 barrier_arrive 및 barrier_wait를 사용하는 예:

#include <cooperative_groups.h>

using namespace cooperative_groups;

void __device__ init_shared_data(const thread_block& block, int *data);
void __device__ local_processing(const thread_block& block);
void __device__ process_shared_data(const thread_block& block, int *data);

__global__ void cluster_kernel() {
    extern __shared__ int array[];
    auto cluster = this_cluster();
    auto block   = this_thread_block();

    // Use this thread block to initialize some shared state
    init_shared_data(block, &array[0]);

    auto token = cluster.barrier_arrive(); // Let other blocks know this block is running and data was initialized

    // Do some local processing to hide the synchronization latency
    local_processing(block);

    // Map data in shared memory from the next block in the cluster
    int *dsmem = cluster.map_shared_rank(&array[0], (cluster.block_rank() + 1) % cluster.num_blocks());

    // Make sure all other blocks in the cluster are running and initialized shared data before accessing dsmem
    cluster.barrier_wait(std::move(token));

    // Consume data in distributed shared memory
    process_shared_data(block, dsmem);
    cluster.sync();
}

5.6.3.6.2.1. 그리드 동기화#

코오퍼러티브 그룹이 도입되기 전에는, CUDA 프로그래밍 모델에서 커널 완료 경계에서만 스레드 블록 간 동기화가 가능했습니다. 커널 경계는 상태의 암시적 무효화를 수반하며, 그에 따른 잠재적인 성능 영향도 있습니다.

예를 들어, 특정 사용 사례에서는 애플리케이션이 많은 수의 작은 커널을 가지며, 각 커널은 처리 파이프라인의 한 단계를 나타냅니다. 이러한 커널의 존재는 현재 CUDA 프로그래밍 모델에서, 한 파이프라인 단계에서 동작하는 스레드 블록이 데이터를 생성한 뒤에 다음 파이프라인 단계에서 동작하는 스레드 블록이 이를 소비할 준비가 되도록 보장하기 위해 필요합니다. 이런 경우, 전역적인 스레드 블록 간 동기화를 제공할 수 있다면 애플리케이션을 재구성하여, 주어진 단계가 완료되면 디바이스에서 동기화할 수 있는 지속 스레드 블록(persistent thread blocks)을 갖도록 할 수 있습니다.

커널 내부에서 그리드 전반에 걸쳐 동기화하려면, 단순히 grid.sync() 함수를 사용하면 됩니다:

grid_group grid = this_grid();
grid.sync();

그리고 커널을 실행할 때는 <<<...>>> 실행 구성 구문 대신, cudaLaunchCooperativeKernel CUDA 런타임 실행 API 또는 CUDA driver equivalent를 사용해야 합니다.

예:

GPU에서 스레드 블록의 동시 상주(co-residency)를 보장하려면, 실행되는 블록 수를 신중하게 고려해야 합니다. 예를 들어, 다음과 같이 SM의 개수만큼 블록을 실행할 수 있습니다:

cudaGetDeviceProperties(&deviceProp, dev);
// initialize, then launch

또는 다음과 같이 점유율(occupancy) 계산기를 사용하여 SM당 동시에 들어갈 수 있는 블록 수를 계산함으로써 노출되는 병렬성을 최대화할 수 있습니다:

/// This will launch a grid that can maximally fill the GPU, on the default stream with kernel arguments

디바이스 속성 cudaDevAttrCooperativeLaunch를 질의하여 디바이스가 협력적 실행(cooperative launches)을 지원하는지 먼저 확인하는 것이 좋은 관행입니다:

  • MPS 없이 Linux 플랫폼

  • 최신 Windows 플랫폼

5.6.4. CUDA 디바이스 런타임#

CUDA 디바이스 런타임은 커널 코드 내에서 사용할 수 있는 API로, 호스트의 CUDA Runtime API와 동일한 많은 기능을 제공합니다. 이러한 API는 주로 CUDA 동적 병렬 처리 또는 디바이스 그래프 실행의 맥락에서 가장 자주 사용됩니다.

5.6.4.1. CUDA 코드에 디바이스 런타임 API 포함#

파일 범위에서 __device__ 또는 __constant__ 메모리 공간 지정자로 선언된 메모리는 디바이스 런타임을 사용할 때 동일하게 동작합니다. 모든 커널은, 해당 커널이 처음에 호스트 또는 디바이스 런타임에 의해 실행되었는지와 관계없이, 디바이스 변수를 읽거나 쓸 수 있습니다. 동등하게, 모든 커널은 모듈 범위에서 선언된 __constant__s에 대해 동일한 뷰를 갖습니다.

5.6.4.2.2.1.2. 텍스처 및 서피스#

디바이스 런타임은 디바이스 코드 내에서 텍스처 또는 서피스 객체를 생성하거나 파괴하는 것을 허용하지 않습니다. 호스트에서 생성된 텍스처 및 서피스 객체는 디바이스에서 자유롭게 사용하고 전달할 수 있습니다. 생성 위치와 관계없이, 동적으로 생성된 텍스처 객체는 항상 유효하며 부모로부터 자식 커널로 전달될 수 있습니다.

참고

디바이스 런타임은 디바이스에서 실행된 커널 내에서 레거시 모듈 범위(즉, compute capability 2.0 또는 Fermi 스타일) 텍스처 및 서피스를 지원하지 않습니다. 모듈 범위(레거시) 텍스처는 호스트에서 생성되어 어떤 커널과 마찬가지로 디바이스 코드에서 사용될 수 있지만, 최상위 커널(즉, 호스트에서 실행되는 커널)에서만 사용할 수 있습니다.

5.6.4.2.2.1.3. 공유 메모리 변수 선언#

CUDA C++에서 공유 메모리는 정적으로 크기가 정해진 파일 범위 또는 함수 범위 변수로 선언하거나, 커널의 호출자가 실행 구성 인자를 통해 런타임에 크기를 결정하는 extern 변수로 선언할 수 있습니다. 두 유형의 선언 모두 디바이스 런타임에서 유효합니다.

__global__ void permute(int n, int *data) {
   extern __shared__ int smem[];
   if (n <= 1)
       return;

   smem[threadIdx.x] = data[threadIdx.x];
   __syncthreads();

   permute_data(smem, n);
   __syncthreads();

   // Write back to GMEM since we can't pass SMEM to children.
   data[threadIdx.x] = smem[threadIdx.x];
   __syncthreads();

   if (threadIdx.x == 0) {
       permute<<< 1, 256, n/2*sizeof(int) >>>(n/2, data);
       permute<<< 1, 256, n/2*sizeof(int) >>>(n/2, data+n/2);
   }
}

void host_launch(int *data) {
    permute<<< 1, 256, 256*sizeof(int) >>>(256, data);
}
5.6.4.2.2.1.4. 상수 메모리#

상수는 디바이스에서 수정할 수 없습니다. 상수는 호스트에서만 수정할 수 있지만, 수명 동안 어느 시점이든 해당 상수에 접근하는 동시 그리드가 존재하는 동안 호스트에서 상수를 수정하는 동작의 동작은 정의되지 않습니다.

5.6.4.2.2.1.5. 심볼 주소#

디바이스 측 심볼(즉, __device__로 표시된 것)은 모든 전역 범위 디바이스 변수가 커널에서 가시적인 주소 공간에 있으므로, 커널 내부에서 단순히 & 연산자를 통해 참조할 수 있습니다. 이는 __constant__ 심볼에도 적용되지만, 이 경우 포인터는 읽기 전용 데이터를 참조합니다.

디바이스 측 심볼을 직접 참조할 수 있으므로, 심볼을 참조하는 CUDA 런타임 API(예: cudaMemcpyToSymbol() 또는 cudaGetSymbolAddress())는 불필요하며 디바이스 런타임에서 지원되지 않습니다. 이는 __constant__ 공간에 대한 참조가 읽기 전용이므로, 자식 커널 실행에 앞서서라도 실행 중인 커널 내부에서 상수 데이터를 변경할 수 없음을 의미합니다.

5.6.4.3. SM Id 및 Warp Id#

PTX에서 %smid 및 %warpid는 volatile 값으로 정의된다는 점에 유의하십시오. 디바이스 런타임은 리소스를 더 효율적으로 관리하기 위해 스레드 블록을 서로 다른 SM으로 재스케줄링할 수 있습니다. 따라서 스레드 또는 스레드 블록의 수명 동안 %smid 또는 %warpid가 변경되지 않은 채로 유지된다고 신뢰하는 것은 안전하지 않습니다.

5.6.4.4. 실행 설정 API#

디바이스 측 커널 실행은 호스트 CUDA Runtime API와 동일한 트리플 셰브론 실행 표기법을 사용하여 디바이스 코드에서 커널을 실행하는 구문을 설명합니다.

커널 실행은 디바이스 런타임 라이브러리를 통해 노출되는 시스템 수준 메커니즘입니다. 또한 PTX에서 cudaGetParameterBuffer() 및 cudaLaunchDevice() API를 통해 직접 사용할 수도 있습니다. CUDA 애플리케이션이 PTX와 동일한 요구 사항으로 이러한 API를 직접 호출하는 것도 허용됩니다. 두 경우 모두 사용자는 명세에 따라 올바른 형식으로 필요한 모든 데이터 구조를 정확히 채울 책임이 있습니다. 이러한 데이터 구조에서는 하위 호환성이 보장됩니다.

5.6.4.5. 디바이스 관리#

5.6.4.7. API 오류 및 실행 실패#

CUDA 런타임에서 일반적으로 그렇듯, 어떤 함수든 오류 코드를 반환할 수 있습니다. 마지막으로 반환된 오류 코드는 기록되며 cudaGetLastError() 호출을 통해 가져올 수 있습니다. 오류는 스레드별로 기록되므로, 각 스레드는 자신이 생성한 가장 최근의 오류를 식별할 수 있습니다. 오류 코드는 cudaError_t 타입입니다.

호스트 측 실행과 유사하게, 디바이스 측 실행은 여러 이유(잘못된 인자 등)로 실패할 수 있습니다. 사용자는 실행이 오류를 생성했는지 확인하기 위해 cudaGetLastError()를 호출해야 하지만, 실행 이후 오류가 없다고 해서 자식 커널이 성공적으로 완료되었음을 의미하지는 않습니다.

디바이스 측 예외(예: 유효하지 않은 주소에 대한 접근)의 경우, 자식 그리드에서의 오류가 호스트로 반환됩니다.

5.6.4.8. 디바이스 런타임 스트림#

CUDA 디바이스 런타임은 디바이스에서 실행되는 커널과 그래프에 대해 특정 동작을 제공하는 특수한 이름 있는 스트림을 제공합니다. 디바이스 그래프 실행과 관련된 이름 있는 스트림은 디바이스 실행에 문서화되어 있습니다. CUDA 디바이스 런타임에서 커널 및 memcpy 작업에 사용할 수 있는 다른 두 이름 있는 스트림은 cudaStreamTailLaunch 및 cudaStreamTailLaunch입니다. 이러한 이름 있는 스트림의 구체적인 동작은 이 섹션에 문서화되어 있습니다.

이름 있는 스트림과 이름 없는(NULL) 스트림 모두 디바이스 런타임에서 사용할 수 있습니다. 스트림 핸들은 부모 또는 자식 그리드에 전달할 수 없습니다. 즉, 스트림은 생성된 그리드에만 사적으로(private) 속하는 것으로 취급해야 합니다.

호스트 측 NULL 스트림의 스트림 간 배리어 의미(semantics)는 디바이스에서 지원되지 않습니다(자세한 내용은 아래 참조). 호스트 런타임과의 의미적 호환성을 유지하기 위해, 모든 디바이스 스트림은 cudaStreamCreateWithFlags() API를 사용해 생성해야 하며, cudaStreamNonBlocking 플래그를 전달해야 합니다. cudaStreamCreate() API는 CUDA 디바이스 런타임에서 사용할 수 없습니다.

cudaStreamSynchronize() 및 cudaStreamQuery()은 디바이스 런타임에서 지원되지 않습니다. 애플리케이션이 스트림으로 실행된 자식 커널이 완료되었는지 알아야 할 때에는, 대신 cudaStreamTailLaunch 스트림에 실행된 커널을 사용해야 합니다.

5.6.4.8.1. 암시적(NULL) 스트림#

호스트 프로그램 내에서 이름 없는(NULL) 스트림은 다른 스트림과 추가적인 배리어 동기화 의미(semantics)를 가집니다(자세한 내용은 차단 및 비차단 스트림과 기본 스트림 참조). 디바이스 런타임은 스레드 블록 내 모든 스레드가 공유하는 단일 암시적 이름 없는 스트림을 제공하지만, 모든 이름 있는 스트림은 cudaStreamNonBlocking 플래그로 생성되어야 하므로, NULL 스트림으로 실행되는 작업은 다른 어떤 스트림(다른 스레드 블록의 NULL 스트림 포함)의 보류 중인 작업에 대해 암시적 의존성을 삽입하지 않습니다.

5.6.4.8.2. Fire-and-Forget 스트림#

Fire-and-forget 이름 있는 스트림(cudaStreamFireAndForget)은 사용자가 더 적은 보일러플레이트로, 그리고 스트림 추적 오버헤드 없이 fire-and-forget 작업을 실행할 수 있게 해줍니다. 기능적으로는 실행마다 새 스트림을 생성해 그 스트림으로 실행하는 것과 동일하지만, 더 빠릅니다.

Fire-and-forget 실행은 이전에 실행된 그리드의 완료에 대한 어떤 의존성도 없이 즉시 실행되도록 스케줄링됩니다. 다른 어떤 그리드 실행도, 부모 그리드 종료 시의 암시적 동기화를 통해서가 아니라면, fire-and-forget 실행의 완료에 의존할 수 없습니다. 따라서 테일 실행(tail launch)이나 부모 그리드 스트림의 다음 그리드는 부모 그리드의 fire-and-forget 작업이 완료되기 전에는 실행되지 않습니다.

// In this example, C2's launch will not wait for C1's completion
__global__ void P( ... ) {
   C1<<< ... , cudaStreamFireAndForget >>>( ... );
   C2<<< ... , cudaStreamFireAndForget >>>( ... );
}

Fire-and-forget 스트림은 이벤트를 기록하거나 이벤트를 대기하는 데 사용할 수 없습니다. 이를 시도하면 cudaErrorInvalidValue가 발생합니다. Fire-and-forget 스트림은 CUDA_FORCE_CDP1_IF_SUPPORTED이 정의된 상태로 컴파일되면 지원되지 않습니다. Fire-and-forget 스트림을 사용하려면 64비트 모드로 컴파일해야 합니다.

5.6.4.8.3. Tail Launch 스트림#

Tail launch 이름 있는 스트림(cudaStreamTailLaunch)은 그리드가 자신의 완료 이후에 새 그리드를 실행하도록 스케줄링할 수 있게 합니다. 대부분의 경우, tail launch를 사용해 cudaDeviceSynchronize()와 동일한 기능을 달성할 수 있어야 합니다.

각 그리드는 자신만의 tail launch 스트림을 가집니다. 그리드가 실행하는 모든 비-tail launch 작업은 tail 스트림이 시작되기 전에 암시적으로 동기화됩니다. 즉, 부모 그리드의 tail launch는 부모 그리드 및 부모 그리드가 일반 스트림 또는 스레드별 스트림 또는 fire-and-forget 스트림에 실행한 모든 작업이 완료될 때까지 실행되지 않습니다. 두 그리드가 동일한 그리드의 tail launch 스트림에 실행되면, 나중 그리드는 이전 그리드와 그 모든 자손 작업이 완료될 때까지 실행되지 않습니다.

// In this example, C2 will only launch after C1 completes.
__global__ void P( ... ) {
   C1<<< ... , cudaStreamTailLaunch >>>( ... );
   C2<<< ... , cudaStreamTailLaunch >>>( ... );
}

Tail launch 스트림으로 실행된 그리드는, tail launch 이후에 실행되거나 실행되도록 스케줄링된 작업을 포함하여, tail launch를 수행한 부모 그리드가 모든 비-tail launch 스트림에서 실행한 모든 작업이 완료될 때까지 실행되지 않습니다. 여기에는 부모가 실행한 다른 모든 그리드(및 그 자손)도 포함됩니다.

// In this example, C will only launch after all X, F and P complete.
__global__ void P( ... ) {
   C<<< ... , cudaStreamTailLaunch >>>( ... );
   X<<< ... , cudaStreamPerThread >>>( ... );
   F<<< ... , cudaStreamFireAndForget >>>( ... )
}

부모 그리드 스트림의 다음 그리드는 부모 그리드의 tail launch 작업이 완료되기 전에는 실행되지 않습니다. 다시 말해, tail launch 스트림은 부모 그리드와 부모 그리드 스트림의 다음 그리드 사이에 삽입된 것처럼 동작합니다.

// In this example, P2 will only launch after C completes.
__global__ void P1( ... ) {
   C<<< ... , cudaStreamTailLaunch >>>( ... );
}

__global__ void P2( ... ) {
}

int main ( ... ) {
   ...
   P1<<< ... >>>( ... );
   P2<<< ... >>>( ... );
   ...
}

각 그리드는 오직 하나의 tail launch 스트림만 가집니다. tail launch로 그리드를 동시에 실행하려면, 아래 예시처럼 하면 됩니다.

// In this example,  C1 and C2 will launch concurrently after P's completion
__global__ void T( ... ) {
   C1<<< ... , cudaStreamFireAndForget >>>( ... );
   C2<<< ... , cudaStreamFireAndForget >>>( ... );
}

__global__ void P( ... ) {
   ...
   T<<< ... , cudaStreamTailLaunch >>>( ... );
}

Tail launch 스트림은 이벤트를 기록하거나 이벤트를 대기하는 데 사용할 수 없습니다. 이를 시도하면 cudaErrorInvalidValue가 발생합니다. Tail launch 스트림은 CUDA_FORCE_CDP1_IF_SUPPORTED이 정의된 상태로 컴파일되면 지원되지 않습니다. Tail launch 스트림을 사용하려면 64비트 모드로 컴파일해야 합니다.

5.6.4.9. ECC 오류#

CUDA 커널 내 코드에서는 ECC 오류에 대한 어떤 알림도 사용할 수 없습니다. ECC 오류는 전체 실행 트리가 완료된 후 호스트 측에서 보고됩니다. 중첩 프로그램의 실행 중 발생하는 ECC 오류는 예외를 발생시키거나(오류 및 구성에 따라) 실행을 계속합니다.
