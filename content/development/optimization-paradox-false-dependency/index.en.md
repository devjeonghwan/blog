```

When there is an expression "float InvDet = 1.0f / Det"
1. divss (The formula as is)
2. rcpss (Using the instruction that takes the reciprocal)
3. rcpss + correction (Adding correction using subtraction and multiplication because rcpss has low precision)

Among these three methods, AI said #2 is the fastest, and recommended #3 for performance and accuracy.
As a result, #1 is the fastest. Even rcpss was almost the same or slower than divss. #3 was much slower.

If you ask AI to write SIMD code, it generates looking good code. But if you run it and measure performance yourself, the code it showed is never the optimized code.
Usually, the basis for the performance it claims is wrong, and consequently, it is not fast either.
```

Actually, intuitively, I thought `DIVSS` should naturally be slower than `RCPSS`. This is because `RCPSS` is a hardware-level instruction implemented to calculate the **Reciprocal** without using expensive division operations.

However, **Yeong-Cheon You** mentioned that it was almost similar or slower. Also, he noted that adding correction operations to compensate for the low precision of `RCPSS` made it much slower. (`RCPSS` generates an approximate value for the reciprocal and has a 12-bit Mantissa precision.)

* ***DIVSS:** Divide Scalar Single Precision Floating-Point Values
* ***RCPSS:** Compute Reciprocal of Scalar Single Precision Floating-Point Values

## Profiling

Since I had free time in the early morning, I decided to verify if **Yeong-Cheon You's** claim was correct (though I expected it was) and analyze the cause. 

### Basic Implementation

I wrote a C++ benchmark code using simple compiler intrinsics and measured the processing time of the two instructions. Here are the results tested on an Intel i9-13900KF environment.

```text
DIVSS : 1.652 cycles (total=6927580)
RCPSS : 2.215 cycles (total=9291130)
RCPSS_NR1 : 0.868 cycles (total=3641804)
RCPSS_NR2 : 1.492 cycles (total=6256057)
```

Shockingly, **Yeong-Cheon You** was right. The hardware instruction (`RCPSS`), which calculates a low-precision approximation, was more than 30% slower than the complex division (`DIVSS`).

Also, if you look at the benchmark results of `RCPSS_NR1` and `RCPSS_NR2` together with `RCPSS`, you can sense something strange. A weird phenomenon is happening where the code becomes faster even though we added extra operations to increase precision, compared to `RCPSS` doing nothing.

A situation where Latency is much shorter, but Throughput drops. Why did this **paradox** happen?

* ***RCPSS_NR1:** `RCPSS` followed by 1 correction (multiplication + subtraction) using the Newton-Raphson method
* ***RCPSS_NR2:** Performing the correction 2 times for higher precision

To understand the cause, I analyzed the generated assembly code. The `RCPSS` loop generated by the MSVC compiler was as follows

```asm
; ... Loop

; RCPSS Operation
rcpss xmm1, dword ptr [rcx+rdx]       ; Store result to XMM1
lea   rdx, [rdx+4]                    ; Move pointer

; Store Result
movss dword ptr [rdx-4], xmm1         ; Store XMM1 to result array

; ... Loop
```

The key point here is how the `XMM1` register is used. The `RCPSS` instruction only updates the **lower 32 bits (one float32)** of the `XMM1` register. It looks efficient at first glance, but it creates a fatal dilemma from the CPU architecture perspective.

> **"I am going to change the lower 32 bits, but I must keep the remaining upper 96 bits as they were."**

Because of this, the CPU falls into the swamp of **False Dependency**. To start the operation for this loop, it has to wait until the `XMM1` result from the *previous* loop is confirmed to preserve the upper bits.

### Improved(?) Implementation

So, to solve this problem, we need to tell the CPU **"I don't need the previous value! You can overwrite it!"** So I modified the code to be **longer**. I added a process to initialize the entire register using instructions like `MOVAPS`.

Similarly, to avoid writing raw assembly, I worked using compiler intrinsics `_mm_setzero_ps()` and `_mm_move_ss()`.

```asm
; XMM3 = 0 (Pre-initialized outside the loop)
; ... Loop

movss  xmm0, dword ptr [rcx+rdx]        ; Load values

; RCPSS Operation
movaps xmm2, xmm3                        ; Overwrite XMM2 with 0 (!! Remove Dependency !!, zero-idiom)
lea    rdx, [rdx+4]                      ; Move pointer
movss  xmm2, xmm0                        ; Load necessary value to XMM2
rcpss  xmm2, xmm2                        ; Store result to XMM2

; Store Result
movss dword ptr [rdx-4], xmm2            ; Store XMM2 to result array

; ... Loop
```

The number of instruction lines definitely increased. But the result was amazing.

```text
RCPSS (Before Optimization): 2.215 cycles
RCPSS (After Optimization) : 0.673 cycles (Approx. 3.3x improvement)
```

The number of instructions increased, but the speed became **3 times faster**.

The moment we overwrite the entire register, the modern CPU uses **Register Renaming** to break the dependency between loops. Thanks to this, powerful **Out-of-Order Execution** actively kicked in and started parallel processing.

## Verification

To check if my thought was correct, I analyzed the pipeline using Intel VTune Profiler.

```text
1. Before Optimization
Microarchitecture Usage       : 6.2% of Pipeline Slots
    Front-End Bound           : 11.3%
    Core Bound                : 69.3%
    Memory Bound              : 1.9%
    Back-End Bound Auxiliary  : 71.2%
    ...
    Serializing Operations    : 23.1%
    ...

2. After Optimization
Microarchitecture Usage       : 25.6% of Pipeline Slots
    Front-End Bound           : 0.0%
    Core Bound                : 26.4%
    Memory Bound              : 5.1%
    Back-End Bound Auxiliary  : 31.5%
    ...
    Serializing Operations    : 6.0%
    ...
```

First, looking at the metrics before optimization, the **Serializing Operations** item occupies **23.1%**. This means 1/4 of the pipeline is Stalled due to dependency. On the other hand, looking at the same item after optimization, it occupies a low figure of **6.0%**, just as expected.

Therefore, as the bottleneck was resolved, the **Microarchitecture Usage (Pipeline Efficiency)** improved more than **4 times, from 6.2% to 25.6%**.

## Today's Conclusion

1. As expected, AI only chatters about "theoretical" optimization.
2. The answer changes depending on the hardware, so don't blindly trust AI, a human must test and tune it personally.
3. Compilers were less smart than I thought.
4. For reference, the reason NR1 and NR2 were faster is that the dependency was accidentally broken due to FMA (Fused Multiply-Add) used for the NR calculation.
5. AVX types (3-Operand) do not have this problem.
